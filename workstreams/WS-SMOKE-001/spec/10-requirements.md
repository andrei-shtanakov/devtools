# Requirements: Наблюдаемость прогонов behaviour-runner

## Область требований

Требования описывают read-only обзор локальных прогонов `behaviour-runner` в
консоли `devtools`. Источник истины — сохранённые `run.json` из канонического
runtime-каталога прогонов. Управление жизненным циклом прогонов, изменение
runtime-артефактов и удалённая агрегация в объём не входят.

#### FR-01: Обнаружение прогонов
**Priority**: Must

Консоль должна обнаруживать каждый каталог прогона в каноническом
runtime-каталоге и представлять его в обзоре не более одного раза. Порядок строк
должен быть детерминированным: лексикографически по `run_id`.

#### FR-02: Минимальная сводка прогона
**Priority**: Must

Для каждого читаемого журнала обзор должен показывать как минимум `run_id`,
`ws_id`, репозиторий, текущий статус и текущий шаг. Если в журнале есть номер PR,
он должен быть доступен в сводке; отсутствие PR не должно считаться ошибкой.

#### FR-03: Текущий статус
**Priority**: Must

Статус читаемого прогона должен браться из поля `status` канонического журнала
без вывода из имени каталога, наличия PR или состояния отдельных операций.
Консоль должна отображать все состояния, записываемые runner'ом, включая
`running`, стоп-состояния, `waiting_human_merge`, `completed` и
`merged_unverified`. Незнакомое, но читаемое строковое значение не должно
скрываться или подменяться известным статусом.

#### FR-04: Текущий шаг
**Priority**: Must

Для нетерминального читаемого прогона текущим шагом должен быть первый ещё не
завершённый обязательный шаг в каноническом порядке pipeline. Для терминальных
`completed` и `merged_unverified` текущий шаг должен отсутствовать независимо от
остаточного состояния необязательных операций. Во всех представлениях
отсутствие текущего шага должно иметь однозначное значение.

#### FR-05: Повреждённый журнал
**Priority**: Must

Если отдельный `run.json` отсутствует, не читается, не является валидным JSON
или не соответствует ожидаемой форме журнала, обзор должен сохранить строку
этого каталога с `run_id` и синтетическим статусом `corrupt`. Ошибка одного
журнала не должна скрывать остальные прогоны или аварийно завершать построение
списка. Для повреждённой строки консоль не должна домысливать предмет, шаг или
другие поля из непроверенных данных.

#### FR-06: Пустой runtime-каталог
**Priority**: Must

Отсутствующий или пустой runtime-каталог должен давать успешный пустой обзор.
Plain-режим должен сообщать `no runs`, JSON-режим должен возвращать пустой
массив, а интерактивный режим должен оставаться работоспособным без строк.

#### FR-07: Выбор режима вывода
**Priority**: Must

При явном запросе JSON консоль должна печатать JSON независимо от наличия TTY.
Без запроса JSON в non-TTY-среде она должна печатать plain-представление без
зависимости от интерактивной TUI-библиотеки. В TTY без явного неинтерактивного
режима консоль должна открывать интерактивный список.

#### FR-08: Машиночитаемый контракт
**Priority**: Must

JSON-обзор должен быть синтаксически валидным массивом объектов. Каждый объект
должен содержать стабильные ключи `run_id`, `ws_id`, `repo`, `status`, `step`,
`pr` и `remediated_by`; отсутствующие значения должны кодироваться JSON `null`
или пустой строкой согласно типу поля, а не удалением ключа.

#### FR-09: Семантическая эквивалентность представлений
**Priority**: Must

TTY, plain и JSON должны строиться из одной read-model. Для одного снимка
runtime-каталога множество прогонов, их идентификаторы, статусы и текущие шаги
должны совпадать во всех трёх представлениях; различаться может только формат.

#### FR-10: Read-only обзор
**Priority**: Must

Открытие списка и построение любого представления не должны изменять
`run.json`, создавать операции pipeline, запускать `resume`/`verify` или
выполнять иные внешние эффекты. Явные пользовательские команды управления из
интерактивной консоли не относятся к построению обзора.

#### NFR-01: Изоляция ошибок
**Priority**: Must

Сбой разбора одного журнала должен быть локализован одной строкой `corrupt`.
Обход остальных каталогов и сериализация результата должны продолжаться.

#### NFR-02: Детерминизм
**Priority**: Must

При неизменных runtime-артефактах повторное построение обзора должно возвращать
одинаковый порядок строк и одинаковую классификацию статуса и текущего шага.

#### NFR-03: Совместимость с автоматизацией
**Priority**: Must

Plain- и JSON-режимы должны завершаться без интерактивного ввода и быть пригодны
для pipe/CI. Диагностический текст не должен смешиваться с JSON-документом в
стандартном выводе успешной команды.

#### NFR-04: Маскирование чувствительных данных
**Priority**: Should

Сводный список не должен выводить полное содержимое `run.json`, findings или
иные произвольные payload-поля. Он должен ограничиваться полями сводки из
FR-02 и FR-08.

## Критерии приёмки WS-SMOKE-001

1. Фикстуры как минимум с `running`, одним стоп-состоянием, `completed` и
   `merged_unverified` появляются ровно по одному разу, в порядке `run_id`, с
   ожидаемыми статусами и шагами.
2. Валидный журнал с незнакомым строковым статусом остаётся видимым с тем же
   значением; повреждённый журнал рядом представлен как `corrupt`, не мешая
   валидным строкам.
3. Для отсутствующего runtime-каталога plain-вывод равен `no runs`, а JSON после
   разбора равен `[]`; обе команды завершаются успешно.
4. JSON непустого обзора разбирается стандартным JSON-парсером, содержит все
   ключи FR-08 и совпадает с plain/TTY по `run_id`, `status` и `step`.
5. Снимки или хэши `run.json` до и после построения plain-, JSON- и TTY-обзора
   совпадают; ни один pipeline-op не запускается.

## Трассируемость к charter

- Обзор доступных прогонов: FR-01, FR-02.
- Однозначный и честный статус: FR-03, FR-04, FR-05.
- Пустые и повреждённые данные без потери всего обзора: FR-05, FR-06, NFR-01.
- TTY, plain и JSON с одной семантикой: FR-07, FR-08, FR-09, NFR-03.
- Read-only граница решения: FR-10.
