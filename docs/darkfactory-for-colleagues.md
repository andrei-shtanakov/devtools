# DarkFactory для коллег

Памятка для разработчика, который ставит DarkFactory на свой Mac или Linux и
гоняет его на своём репо. Экосистему знать не нужно.

## Что получится

Одна команда `dfl run --subject '…'` проводит цепочку:

1. агент-«заказчик» проводит с вами интервью по теме (вопросы — в терминале,
   ответы — `dfl answer`, см. «Интервью: как отвечать»);
2. по интервью готовится бриф, `dfl run` открывает PR с брифом;
3. вы мержите бриф сами;
4. `dfl run` одобряет бриф и запускает инженерный прогон: он сам делится на
   волны и задачи и запускает `spec-runner run`;
5. на выходе проверенный PR с кодом. **Мерж кода — ваш**, агент его не мержит.

Каждый вызов `dfl run` делает ровно один шаг вперёд и печатает, что дальше.

## Что нужно

- macOS или Linux (на другой ОС `install.sh` откажет). На обеих — только режим
  `test`: песочница авторинга (режим strict) есть только на macOS;
- `git`, `gh` (залогинен: `gh auth login`), `uv`, `claude` (залогинен), `make`,
  `jq` (на Linux обычно ставятся пакетами `make` и `jq`);
- одна учётка GitHub: она и автор, и ревьюер, и человек (см. «Что выключено»);
- sudo не нужен.

## Установка

```sh
git clone https://github.com/andrei-shtanakov/devtools ~/darkfactory/devtools \
  && sh ~/darkfactory/devtools/install.sh
```

`install.sh` проверяет ОС (macOS или Linux), наличие `git`, `gh`, `uv`, `claude`,
`make`, `jq` и вход в `gh`,
затем ставит окружение devtools (`uv sync --frozen`) и запускает установщик.
Установщик клонирует рядом с devtools (в `~/darkfactory/`) закреплённые на
конкретный коммит репо из `lite/components.toml`:

- `discovery` — ставится как зависимость каталога (`uv sync`);
- `spec-runner` — ставится как утилита (`uv tool install`), даёт `spec-runner run`.

Дальше он пишет конфиг и обёртку:

- конфиг `~/.config/darkfactory/config.toml` (режим `test`, ваш логин GitHub
  на все роли). Логин берётся из `--login`, иначе из `gh api user`
  (подтверждается вопросом; `--yes` — без вопросов, если логин определился).
  Уже существующий конфиг не перезаписывается; если он не в режиме `test`,
  будет предупреждение;
- обёртка `~/.local/bin/dfl`. Если этого каталога нет в `PATH`, установщик
  напечатает строку `export PATH=…` для вашего шелла.

Опции: `sh install.sh --login <логин> --yes`.

## Подготовка репо: `dfl init-repo`

Из каталога вашего репо (он должен быть на ветке по умолчанию, дерево чистое,
`origin` на GitHub):

```sh
cd ~/code/my-repo
dfl init-repo
```

Команда открывает PR с шаблонами DarkFactory (профили, review-kit, конфиг
spec-runner), ставит на него метку `human-merge-required` и просит вас
**смержить его самому**. Свой уже открытый PR подготовки повторный вызов
находит и не дублирует; чужой PR с этой веткой — отказ.

Отказы (код 2, с причиной):

- ветка по умолчанию **требует ревью**: обязательное approving-ревью или ревью
  владельцев кода (правила ветки и rulesets). Пока агент работает под вашей же
  учёткой, GitHub не даёт одобрить собственный PR, поэтому такое правило
  заблокирует каждый мерж. `dfl` чужую защиту не меняет — снимите требование
  сами. Если правила не удалось прочитать (нет прав, ошибка `gh`), это тоже
  отказ, а не «правил нет»: проверьте `gh auth status`;
- в репо уже есть файлы назначения (конфликт) — ничего не создано, переименуйте
  или удалите их;
- остатки прерванного запуска: ветка `darkfactory/init-repo` локально или на
  origin без PR. Очистка:

  ```sh
  git branch -D darkfactory/init-repo
  git push origin --delete darkfactory/init-repo
  ```

## Запуск

Новый конвейер `dfl run --subject` начинает только в подготовленном репо: PR
`dfl init-repo` смержен и подтянут (`git pull`) — в рабочем дереве есть
`profiles/team-exp.yaml`, `scripts/review/local.sh` и `spec-runner.config.yaml`.
Иначе отказ «репо не подготовлен: нет … — сначала dfl init-repo, смержите его
PR и git pull».

```sh
cd ~/code/my-repo
dfl run --subject 'добавить экспорт отчётов в CSV'   # первый вопрос интервью
dfl answer --file answer.yaml                        # ответ; следующий вопрос
# … dfl answer на каждый вопрос, пока интервью не кончится …
dfl run                                              # открывает PR брифа
# смержите PR брифа в GitHub
dfl run                                              # одобрение + инженерный прогон
# инженерный прогон тоже задаёт вопросы — отвечайте dfl answer
dfl run                                              # (при остановке) продолжить
dfl status                                           # прогоны репо и что дальше
```

## Интервью: как отвечать

Интервью — это несколько кругов. На каждом `dfl run` (или `dfl answer`)
печатает вопрос (`_step_interview: вопрос <id>: <текст>`) и подсказку
«ответьте: dfl answer --file answer.yaml». Ответ — YAML-файл: `text:` — ответ
своими словами, `entries:` — пункты темы вопроса. **Покрытие интервью
засчитывается только по `entries:`**: на одном `text:` интервью не закончится,
сколько ни отвечай. `id` пункта — с префикса темы (цели `G-`, персоны `P-`,
задачи `J-`, функции `FR-`, нефункциональные `NFR-`, ограничения `CON-`,
метрики `M-`, вне рамок `OUT-`); `FR` — с `traces` на `G`/`J`, `Priority` и
`Acceptance`; `NFR` — с `Acceptance` или `Target`; `M` — с `traces` на `G`:

```yaml
text: |
  Отчёт нужен бухгалтерии раз в месяц; колонки — дата, сумма, контрагент.
entries:
  - id: FR-01
    body: выгрузка отчёта за месяц в CSV с колонками дата, сумма, контрагент
    traces: [G-01, J-01]
    Priority: Must
    Acceptance: файл открывается в табличном редакторе, три колонки, строка на операцию
```

Затем:

```sh
dfl answer --file answer.yaml
```

`dfl answer` передаёт файл закреплённому `discovery` (тот, что поставил
`install.sh`) и сразу делает следующий шаг `dfl run`: печатает следующий
вопрос или, когда вопросы кончились, идёт дальше (бриф). Для каждого вопроса
пишите ответ заново (тот же файл можно переписать). Строку `discovery answer …`
из вывода раннера запускать не нужно — `discovery` не в `PATH`, это делает
`dfl answer`; подсказки `make …` из вывода тоже игнорируйте, `dfl` делает эти
шаги сам. Если `discovery` ответ не принял (например, нет ключа `text:`), отказ
называет причину — исправьте файл и повторите `dfl answer`. Поправить уже
данный ответ: `dfl answer --question <id вопроса> --supersede --file answer.yaml`
(id — из строки `вопрос <id>`). `dfl status`
показывает «дальше: ответьте: dfl answer --file answer.yaml», пока прогон ждёт
ответа. Инженерный прогон (после мержа брифа) тоже может задать вопросы —
отвечают на них так же.

## Бросить конвейер: `dfl abandon`

Если конвейер не продолжить (PR брифа закрыт без мержа, интервью зашло не туда,
остановку не разобрать) или он просто не нужен:

```sh
dfl abandon
```

Каталоги его прогонов (заказчик и инженерный) переезжают в
`~/darkfactory/devtools/out/governance-runs-abandoned/<время UTC>/` — это
обратимо: перенесите каталог обратно в `out/governance-runs/`. Открытые PR
конвейера (бриф, задачи) `dfl abandon` не трогает — закройте их сами. После
этого `dfl run --subject` снова начинает новую тему. Если незаконченных
конвейеров несколько — `dfl abandon --subject '<тема>'`. Прогон, который
сейчас исполняется (`dfl run` в другом терминале), бросить нельзя — отказ.

- `dfl run --stakeholder <роль>` меняет роль собеседника (по умолчанию `customer`).
- `dfl status` только читает журнал прогонов: форджу не трогает, эффектов нет.
- После перерыва (закрыли терминал, остановка по причине) просто `dfl run`.
- Когда код проверен, `dfl run` печатает: «PR с кодом проверен: <url>; мерж — за вами».
- Параллельных конвейеров в одном репо нет: пока прогон не закончен, новый
  `--subject` отказывает («конвейер репо не закончен … новая тема не
  начинается»). Продолжите его `dfl run` без `--subject` или бросьте
  `dfl abandon`.
  Если незаконченных несколько, `dfl run` просит выбрать тему.
- Нечитаемый журнал прогона блокирует `dfl run`: отказ называет каталог. Почините
  или уберите его и повторите.
- PR брифа закрыт без мержа — конвейер не продолжить: `dfl run` отказывает и
  называет `dfl abandon`.
- Остановка до конца инженерного прогона — строка с причиной и статус
  `stopped_…` в `dfl status`; разберите причину и снова `dfl run`.
- Остановки после инженерного прогона (мерж задач, `spec-runner run`, проверка
  PR с кодом) статус не меняют: прогон остаётся `completed`, а `dfl status`
  пишет «конвейер после прогона остановился — причина в выводе dfl run;
  повторите dfl run». Конвейер закончен, только когда `dfl run` напечатал
  «PR с кодом проверен: …».

`dfl` работает только в режиме `test`; при другом `mode` откажет. Чтобы
включить test, поставьте `mode = "test"` в `~/.config/darkfactory/config.toml`
сами — `install.sh` существующий конфиг не переписывает, переустановка не
поможет.

## Что выключено в режиме test

Режим test **сознательно ослабляет защиты**: он для одного человека с одной
учёткой, а не для командной эксплуатации. `dfl` при каждом запуске печатает
баннер с этим перечнем. Выключено:

- репо политики утверждения не используется: утверждающий — accounts.human
- песочница авторинга: claude запускается обычным процессом пользователя (нет sandbox-exec, допуска и связки ключей)
- белый список целей: цель — из targets.toml рядом с конфигом, манифест флота необязателен
- одобрение ревью: вердикт публикуется комментарием (GitHub не даёт одобрить свой PR), вердикт обязателен
- корень доверия df (/etc/df/trust.toml) не используется: акт — по мержу (режим до миграции)
- акт человека не требуется (test): candidate-PR мержит раннер после зелёных проверок
- класс актора не применяется (test): finalize не сверяет класс актора; kill switch действует
- утверждение задач человеком не требуется (test): tasks-PR, spec approve и approve-PR проводит раннер
- мерж PR с кодом — за вами (test): приёмка проверяет PR с кодом, но не мержит его
- проверок нет (test): у PR нет .github/workflows и чеков — CI не ждём; чеки CI вне GitHub Actions, пришедшие позже 2 минут, не учитываются
- одна учётка GitHub: accounts.human может совпадать с accounts.agent

Простыми словами: учётка одна на всё; нет песочницы авторинга (она есть только
в режиме strict) — агент-автор работает с вашими правами; утверждение задач и
candidate-PR происходит автоматически; ревью приходит комментариями, а не
approve.

Репо без CI: если у PR нет проверок и в `.github/workflows` на его голове нет
файлов, после нескольких опросов с пустым списком проверок конвейер пропускает
ожидание с пометкой «проверок нет (test)». Есть workflows, но проверок пока нет —
ждёт как обычно.

Ограничение: если CI репо работает вне GitHub Actions (внешний статус или
App) и его чеки приходят позже 2 минут, в test это читается как «проверок нет»,
и spec/candidate-PR вмерживаются без них. Лекарство — workflow в
`.github/workflows` (тогда конвейер ждёт) или режим strict.

## Остановки на смысловой проверке (edge-check)

Каждую волну спецификации проверяет ревьюер-модель (edge-check). Его находки
лежат в `out/governance-runs/<прогон>/edge-findings.txt`; прогон встаёт со
статусом `stopped_review`. Поправьте узел (файл в бандле рабочего дерева) и
повторите `dfl run`. Каждый круг — платный вызов. Известное ограничение
(devtools#728): ревьюер недетерминирован и его правила могут тянуть одно место
в разные стороны — если одна и та же находка возвращается после правок, не
крутите круги дальше, а бросьте прогон или сообщите о нём.

## Не поддерживается в test

`criteria-close` (закрытие критериев) в режиме test не поддерживается.

## Обновление и остановки

- Обновление: `sh ~/darkfactory/devtools/install.sh` повторно (после
  `git pull` в devtools). Он переведёт компоненты на закреплённые коммиты и
  перепишет `dfl`; конфиг не тронет.
- Повторная установка **откажет посреди прогона**: «Есть незавершённые прогоны
  DarkFactory: …» (код 2) — компоненты посреди прогона не обновляются.
  Незавершённый — в том числе `completed` инженерный прогон, у которого цепочка
  после прогона не дошла до проверенного PR с кодом. Закончите их (`dfl run`)
  или бросьте (`dfl abandon`) в каталоге репо и повторите.
- Также отказ (до любых изменений: проверяются все клоны компонентов сразу) при
  локальных изменениях в клоне компонента, при нештатной ветке (ожидается
  detached HEAD на закреплённом коммите) и при несовпадении `origin`.
- Сбой `git` (нет сети, нет доступа) — отказ с текстом ошибки git; проверьте
  сеть и доступ и повторите `install.sh`. Неудавшийся свежий клон удаляется,
  повтор начинает заново.
- `--yes` без входа в `gh` и запуск без терминала (логин не спросить) — отказ
  «укажите --login <логин>».
