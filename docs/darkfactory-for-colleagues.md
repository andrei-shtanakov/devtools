# DarkFactory для коллег

Памятка для разработчика, который ставит DarkFactory на свой Mac или Linux и
гоняет его на своём репо. Экосистему знать не нужно.

## Что получится

Одна команда `dfl run --subject '…'` проводит цепочку:

1. агент-«заказчик» проводит с вами интервью по теме (вопросы — в терминале,
   вы отвечаете текстом, см. «Интервью: как отвечать»);
2. по интервью готовится бриф, `dfl run` открывает PR с брифом;
3. вы мержите бриф сами;
4. `dfl run` одобряет бриф и запускает инженерный прогон: он сам делится на
   волны и задачи и запускает `spec-runner run`;
5. на выходе проверенный PR с кодом. **Мерж кода — ваш**, агент его не мержит.

Каждый вызов `dfl run` делает ровно один шаг вперёд и печатает, что дальше.

## Что нужно

- macOS или Linux (на другой ОС `install.sh` откажет). На обеих — только режим
  `test`: песочница авторинга (режим strict) есть только на macOS;
- `git`, `gh` (залогинен: `gh auth login`), `uv`, `claude` (залогинен), `make`,
  `jq` (на Linux обычно ставятся пакетами `make` и `jq`);
- одна учётка GitHub: она и автор, и ревьюер, и человек (см. «Что выключено»);
- sudo для самой установки DarkFactory не нужен (только для пакетов ниже).

## Перед установкой

Поставьте недостающие программы и войдите в `gh` и `claude`. Что уже есть —
пропускайте; проверка: `git --version`, `gh --version`, `uv --version`,
`claude --version`, `make --version`, `jq --version`.

**macOS** (через [Homebrew](https://brew.sh)):

```sh
xcode-select --install          # git и make, если их ещё нет
brew install gh jq uv
curl -fsSL https://claude.ai/install.sh | bash
```

**Linux** (Ubuntu/Debian; на других дистрибутивах — те же пакеты своим
менеджером):

```sh
sudo apt update && sudo apt install -y git make jq gh
curl -LsSf https://astral.sh/uv/install.sh | sh
curl -fsSL https://claude.ai/install.sh | bash
```

Если `gh` в репозитории дистрибутива нет или он сильно старый — поставьте его
по [официальной инструкции](https://github.com/cli/cli/blob/trunk/docs/install_linux.md).

**Вход** (на обеих ОС):

```sh
gh auth login      # GitHub.com, HTTPS; та учётка, под которой вы будете работать
claude             # при первом запуске предложит войти; затем /exit
```

Проверьте, что всё видно из нового терминала: `uv` и `claude` ставятся в
`~/.local/bin` — если команды не находятся, добавьте этот каталог в `PATH`
(строку в `~/.zshrc` или `~/.bashrc`) и откройте терминал заново.

Две ловушки, встреченные на живой установке:

- **Работа по `ssh` без входа в шелл.** `ssh host 'команда'` не читает
  `~/.bashrc`, и `~/.local/bin` в `PATH` не попадает — `dfl`, `uv`, `claude`
  «не найдены». Запускайте через login-шелл: `ssh host 'bash -lc "dfl status"'`.
- **Несколько копий `gh`.** Старая копия в `~/.local/bin` затеняет системную.
  `which -a gh` покажет все; оставьте одну свежую.

## Установка

```sh
git clone https://github.com/andrei-shtanakov/devtools ~/darkfactory/devtools \
  && sh ~/darkfactory/devtools/install.sh
```

`install.sh` проверяет ОС (macOS или Linux), наличие `git`, `gh`, `uv`, `claude`,
`make`, `jq` и вход в `gh`,
затем ставит окружение devtools (`uv sync --frozen`) и запускает установщик.
Установщик клонирует рядом с devtools (в `~/darkfactory/`) закреплённые на
конкретный коммит репо из `lite/components.toml`:

- `discovery` — ставится как зависимость каталога (`uv sync`);
- `spec-runner` — ставится как утилита (`uv tool install`), даёт `spec-runner run`.

Дальше он пишет конфиг и обёртку:

- конфиг `~/.config/darkfactory/config.toml` (режим `test`, ваш логин GitHub
  на все роли). Логин берётся из `--login`, иначе из `gh api user`
  (подтверждается вопросом; `--yes` — без вопросов, если логин определился).
  Уже существующий конфиг не перезаписывается; если он не в режиме `test`,
  будет предупреждение;
- обёртка `~/.local/bin/dfl`. Если этого каталога нет в `PATH`, установщик
  напечатает строку `export PATH=…` для вашего шелла.

Опции: `sh install.sh --login <логин> --yes`.

## Подготовка репо: `dfl init-repo`

Из каталога вашего репо (он должен быть на ветке по умолчанию, дерево чистое,
`origin` на GitHub):

```sh
cd ~/code/my-repo
dfl init-repo
```

Если `origin/HEAD` нет (репо собран через `git init` и `git remote add`, а не
`git clone`), `dfl` сам выполнит `git remote set-head origin -a` и скажет об
этом. Отказы `dfl` печатает отдельным блоком: команда и код, «причина» и
«что сделать».

Команда открывает PR с шаблонами DarkFactory (профили, review-kit, конфиг
spec-runner), ставит на него метку `human-merge-required` и просит вас
**смержить его самому**. Свой уже открытый PR подготовки повторный вызов
находит и не дублирует; чужой PR с этой веткой — отказ.

В `.gitignore` PR дописывает недостающие строки для кэшей, которые оставляет
исполнение задач (`__pycache__/`, `*.pyc`, `.venv/`, `.pytest_cache/`,
`.ruff_cache/`): без них после прогона дерево грязное и приёмка PR с кодом
останавливается. Ваши строки не трогаются; если всё уже есть, файл не
меняется, а если `.gitignore` нет — он создаётся.

Отказы (код 2, с причиной):

- ветка по умолчанию **требует ревью**: обязательное approving-ревью или ревью
  владельцев кода (правила ветки и rulesets). Пока агент работает под вашей же
  учёткой, GitHub не даёт одобрить собственный PR, поэтому такое правило
  заблокирует каждый мерж. `dfl` чужую защиту не меняет — снимите требование
  сами. Если правила не удалось прочитать (нет прав, ошибка `gh`), это тоже
  отказ, а не «правил нет»: проверьте `gh auth status`;
- в репо уже есть файлы назначения (конфликт) — ничего не создано, переименуйте
  или удалите их; `.gitignore` конфликтом считается, только если это не обычный
  файл (ссылка или каталог);
- остатки прерванного запуска: ветка `darkfactory/init-repo` локально или на
  origin без PR. Очистка:

  ```sh
  git branch -D darkfactory/init-repo
  git push origin --delete darkfactory/init-repo
  ```

## Запуск

Новый конвейер `dfl run --subject` начинает только в подготовленном репо: PR
`dfl init-repo` смержен и подтянут (`git pull`) — в рабочем дереве есть
`profiles/team-exp.yaml`, `scripts/review/local.sh` и `spec-runner.config.yaml`.
Иначе отказ «репо не подготовлен: нет … — сначала dfl init-repo, смержите его
PR и git pull».

```sh
cd ~/code/my-repo
dfl run --subject 'добавить экспорт отчётов в CSV'   # интервью: вопрос, вы отвечаете текстом
# … пустая строка заканчивает ответ; так до конца интервью (/стоп — пауза,
#   dfl run — продолжить; dfl interview — что уже собрано) …
# потом dfl run сам открывает PR брифа
# смержите PR брифа в GitHub
dfl run                                              # одобрение + инженерный прогон
# инженерный прогон тоже задаёт вопросы — отвечайте в том же разговоре
dfl run                                              # (при остановке) продолжить
dfl status                                           # прогоны репо и что дальше
```

## Сколько `dfl` пишет на экран

По умолчанию `dfl` молчаливый: 1–3 строки результата каждого вызова. Если от вас
ждут действия (смержить PR, ответить на вопрос), оно видно всегда. Подробность
выбирается флагом `-v` (до или после подкоманды: `dfl -v run`, `dfl run -vv`);
флаги складываются, выше трёх — то же, что три.

| Уровень | Что видно на экране |
|---|---|
| 0 (без флага) | строка режима test; итог шага; требуемое действие; отказ блоком «причина / что сделать»; вопросы и реплики интервью разговором; при сбое — причина и `подробно: dfl log` (у команд без лога — `отчёт разработчикам: dfl report`) |
| 1 (`-v`) | то же, плюс подсказки по командам: `dfl status`, `dfl interview`, `dfl correct`, `dfl report`, «новая тема: dfl run --subject …», `dfl abandon` |
| 2 (`-vv`) | то же, плюс краткое состояние: id прогона, frame, статус, номер PR и волны, если есть, и какие шаги раннер прошёл в этом вызове (по журналу прогона) |
| 3 (`-vvv`) | всё: полный баннер test, вывод раннера и дочерних процессов вживую, подсказки раннера (`make …`, `discovery answer …`) |

Уровень по умолчанию можно задать переменной `DFL_VERBOSITY=0..3` (флаг
сильнее). Неверное значение считается за 0 и даёт одну строку предупреждения.

Примеры `dfl run` на уровне 0. Бриф ждёт вашего мержа:

```text
режим test: ослаблено 11 проверок — список: dfl status -v

бриф ждёт вашего мержа: https://github.com/<владелец>/<репо>/pull/7 — после мержа снова dfl run
```

Остановка с причиной (код ненулевой):

```text
режим test: ослаблено 11 проверок — список: dfl status -v

прогон <id> остановлен: <причина из stop-reason.txt>
подробно: dfl log
```

Вывод раннера и дочерних программ на экран не идёт, но ничего не теряется: его
пишет лог вызова.

- `dfl log` — лог последнего вызова целиком; `dfl log -n 2` — предпоследнего;
  `dfl log --list` — перечень (время, команда, код). Нет логов — «логов нет».
  Если показанный вызов кончился ненулевым кодом, в конце напоминание
  `отчёт разработчикам: dfl report`. `dfl log -n N` при N больше числа
  логов отказывает (код 2); `dfl log --list` покажет все.
- Лог пишут `dfl run`, `dfl answer`, `dfl correct` и `dfl init-repo`;
  `dfl status`, `dfl interview`, `dfl abandon`, `dfl log` и `dfl report` — нет,
  поэтому `dfl status` после сбоя не заменяет «последний лог».
- Хранятся последние 20 логов на репо (лог, на который ссылается запись
  последнего сбоя, не удаляется).
- `dfl status -v` добавляет полный список ослаблений test и путь к конфигу,
  `dfl status -vv` — статусы операций каждого прогона.

## Интервью: как отвечать

Интервью — разговор в терминале. `dfl run --subject '…'` печатает вопрос, вы
отвечаете обычным текстом, `dfl` задаёт следующий — и так до конца интервью,
потом сам идёт дальше (бриф). Ни YAML, ни id пунктов вам видеть не нужно.

```text
Вопрос 1 (цели): Зачем нужен экспорт отчётов и кому?
> Бухгалтерии, раз в месяц.
> Колонки — дата, сумма, контрагент.
>
Вопрос 2 (задачи пользователей): …
```

- **Ответ** — любой текст в несколько строк; **пустая строка** заканчивает
  ответ и отправляет его. Пустой ответ вопрос не пропускает — вопрос
  повторится.
- **Уточнение.** Если агенту не хватает деталей, он спросит
  `Уточнение: …` — отвечайте так же. На один вопрос не больше двух уточнений.
- **Пропустить.** Ответ «пропустить» или «не знаю» (на вопрос или на
  уточнение) — идём дальше с тем, что есть. «Пропустить» сразу на вопрос
  уходит как есть, без вызова агента.
- **Пауза.** `/стоп` отдельной строкой, Ctrl-D или Ctrl-C прерывают интервью
  (`интервью прервано — продолжить: dfl run`); ничего не теряется, `dfl run`
  продолжит с того же вопроса. Ctrl-C, пока агент работает над ответом или
  ждёт `discovery`, — то же самое: неотправленный ответ не записан, вопрос
  придёт снова. Ctrl-C в остальное время (например, на шаге конвейера) —
  строка «прервано», без трассировки.
- Агент раскладывает ответ по пунктам (цели, функции, критерии…) молча, сам.
  Если разобрать не удалось, напечатает «не удалось разобрать ответ —
  переформулируйте» или «ответ не принят — ответьте на вопрос ещё раз», и тот
  же вопрос придёт снова.
- Если ответ дополняет уже записанный пункт (например, вопрос «что
  подождёт?» о важности функции), агент дополняет этот пункт, а не заводит
  второй такой же.
- **Добор тем.** Если вопросы кончились, а обязательные темы не раскрыты
  (например, их пропустили), `dfl` спросит по каждой: `Не хватает: <тема> —
  расскажите об этом своими словами («пропустить» — оставить так)`. Ответ
  дописывается к уже данному ответу этой темы. Добор — один раз за разговор;
  если что-то осталось пропущенным, следующий `dfl run` предложит его снова.
- **Критерии проверки.** Все темы раскрыты, но у функции или
  нефункционального требования нет способа проверить, что оно выполнено, —
  бриф не пройдёт проверку. Тогда после вопросов `dfl` спросит по каждому
  такому пункту: `Как проверить «<пункт>»? …`. Ответ записывается в пункт
  дословно, агент не вызывается; годится и грубый критерий («из 10 запусков 8
  доходят до конца»). Пропущенный пункт `dfl run` спросит снова.
- **Интервью инженера: связи и вердикты.** Проверка брифа инженера требует,
  чтобы каждый интерфейс был связан с системой, а архитектурное
  предпочтение — с системой или ограничением; и чтобы по каждой обязательной
  функции брифа заказчика был вердикт реализуемости. Если этого нет, после
  вопросов `dfl` покажет предложенные связи (`«интерфейс» → «система»`) и
  спросит «Записать так?», а затем по каждой функции: `FR-NN «…» —
  реализуемо как есть?`. «да» — реализуемо; любой другой ответ записывается
  как расхождение между заказчиком и инженером (открытый конфликт брифа, он
  проверку не валит).
- Каждый ответ, уточнение и поправка — как минимум один платный вызов
  `claude` (бывает больше: повтор, если агент ответил не по форме или
  `discovery` не принял собранное).
- Разговор работает только в терминале и при `harness.author = claude` в
  конфиге. В терминале без `claude` `dfl run` печатает подсказку и завершается
  отказом: «интервью разговором требует harness.author = claude —
  используйте dfl answer --file answer.yaml».

Инженерный прогон (после мержа брифа) тоже может задать вопросы — они идут тем
же разговором. Вернуться к интервью можно и командой `dfl answer` (без
`--file`): она ведёт разговор и сразу делает шаг `dfl run`.

### Что уже собрано: `dfl interview`

```sh
dfl interview
```

Печатает тему, текущий вопрос (или «вопросов больше нет») и темы интервью с
отметкой `[x]` у раскрытых и `[ ]` у ещё нет; под каждой — действующие пункты
вида `FR-01 тело — Must; критерий: …; → G-01`. Внизу, если что-то мешает
готовности, блок «Мешает готовности» простыми словами. Агент не нужен, команда
ничего не меняет и работает в любом статусе прогона, у которого есть интервью.
Несколько конвейеров — `--subject '<тема>'`.

### Поправить собранное: `dfl correct`

```sh
dfl correct 'не раз в неделю, а раз в месяц'
```

Одна поправка текстом, без разговора: агент находит затронутые пункты и
исправляет их. Печатает, что изменилось, строками
`FR-01: «было» → «стало»` (для полей — `FR-01 Priority: «…» → «…»`). Если
поправка неясна, агент не угадывает: печатает
`Уточните: … — повторите dfl correct '<текст с уточнением>'`, ничего не меняя;
повторите команду уже с уточнением. Если не понял вовсе — «не понял, что
исправить — переформулируйте поправку». Требует `harness.author = claude`;
как минимум один платный вызов `claude`. Несколько конвейеров —
`--subject '<тема>'`. Когда интервью уже закончено и бриф собран, поправка
отказывает: «интервью завершено, бриф уже собран — поправка в бриф не
попадёт» (`dfl interview` при этом работает).

### Писать YAML самому: `dfl answer --file`

Для скриптов и тех, кто хочет контролировать пункты вручную. Без терминала
(скрипт, CI, ввод не из терминала) разговора нет — `dfl run` печатает вопрос
и подсказку «ответьте: dfl answer --file answer.yaml», а `dfl answer` без
`--file` отказывает («без терминала: dfl answer --file answer.yaml»). В
терминале без `harness.author = claude` `dfl run` печатает ту же подсказку и
завершается отказом (см. выше). Строки раннера
`discovery answer …` и подсказки `make …` на экран не выходят (они в логе
вызова — `dfl log`; на экране — только с `-vvv`) — запускать их не нужно:
`discovery` не в `PATH`, нужный вызов делает `dfl answer`.

Ответ — YAML-файл: `text:` — ответ своими словами, `entries:` — пункты темы
вопроса. **Покрытие интервью засчитывается только по `entries:`**: на одном
`text:` интервью не закончится, сколько ни отвечай. `id` пункта — с префикса
темы (цели `G-`, персоны `P-`, задачи `J-`, функции `FR-`, нефункциональные
`NFR-`, ограничения `CON-`, метрики `M-`, вне рамок `OUT-`); `FR` — с `traces`
на `G`/`J`, `Priority` и `Acceptance`; `NFR` — с `Acceptance` или `Target`;
`M` — с `traces` на `G`:

```yaml
text: |
  Отчёт нужен бухгалтерии раз в месяц; колонки — дата, сумма, контрагент.
entries:
  - id: FR-01
    body: выгрузка отчёта за месяц в CSV с колонками дата, сумма, контрагент
    traces: [G-01, J-01]
    Priority: Must
    Acceptance: файл открывается в табличном редакторе, три колонки, строка на операцию
```

Затем:

```sh
dfl answer --file answer.yaml
```

`dfl answer --file` передаёт файл закреплённому `discovery` (тот, что поставил
`install.sh`) и сразу делает следующий шаг `dfl run`: печатает следующий
вопрос или, когда вопросы кончились, идёт дальше (бриф). Для каждого вопроса
пишите ответ заново (тот же файл можно переписать). Если `discovery` ответ не
принял (например, нет ключа `text:`), отказ называет причину — исправьте файл и
повторите `dfl answer --file answer.yaml`. Поправить уже данный ответ:
`dfl answer --question <id вопроса> --supersede --file answer.yaml` (id — из
строки `вопрос <id>` вывода раннера); `--question` и `--supersede` работают
только вместе с `--file`. `dfl status` показывает «дальше: ответьте: dfl answer
--file answer.yaml», пока прогон ждёт ответа.

## Бросить конвейер: `dfl abandon`

Если конвейер не продолжить (PR брифа закрыт без мержа, интервью зашло не туда,
остановку не разобрать) или он просто не нужен:

```sh
dfl abandon
```

Каталоги его прогонов (заказчик и инженерный) переезжают в
`~/darkfactory/devtools/out/governance-runs-abandoned/<время UTC>/` — это
обратимо: перенесите каталог обратно в `out/governance-runs/`. Открытые PR
конвейера (бриф, задачи) `dfl abandon` не трогает — закройте их сами. После
этого `dfl run --subject` снова начинает новую тему. Если незаконченных
конвейеров несколько — `dfl abandon --subject '<тема>'`. Прогон, который
сейчас исполняется (`dfl run` в другом терминале), бросить нельзя — отказ.

- `dfl run --stakeholder <роль>` меняет роль собеседника (по умолчанию `customer`).
- `dfl status` только читает журнал прогонов: форджу не трогает, эффектов нет.
- После перерыва (закрыли терминал, остановка по причине) просто `dfl run`.
- Когда код проверен, `dfl run` печатает: «PR с кодом проверен: <url>; мерж — за вами».
  Если PR с кодом вмержили раньше, чем приёмка проверила его голову (например
  приёмка отказала, а вы вмержили сами), `dfl run` печатает «PR с кодом вмержен
  без автоматической приёмки: <url>; конвейер закончен». Если ревью головы
  одобрило, но приёмка не завершилась (например красные проверки), а вы
  вмержили PR сами — «PR с кодом вмержен человеком после одобряющего ревью,
  приёмка не завершена: <url>; конвейер закончен».
- `dfl status` для законченного конвейера пишет «смержите <url> — конвейер
  закончен; новая тема: dfl run --subject '<тема>'», а если мерж уже записан —
  «конвейер закончен (<url> вмержен); новая тема: …». Хвост про новую тему
  есть, только если в репо нет другого незаконченного конвейера. Мерж, сделанный после
  «проверен», `dfl` не отслеживает: конвейер закончен и так.
- Параллельных конвейеров в одном репо нет: пока прогон не закончен, новый
  `--subject` отказывает («конвейер репо не закончен … новая тема не
  начинается»). Продолжите его `dfl run` без `--subject` или бросьте
  `dfl abandon`.
  Если незаконченных несколько, `dfl run` просит выбрать тему.
- Нечитаемый журнал прогона блокирует `dfl run`: отказ называет каталог. Почините
  или уберите его и повторите.
- PR брифа закрыт без мержа — конвейер не продолжить: `dfl run` отказывает и
  называет `dfl abandon`.
- Остановка до конца инженерного прогона — строка с причиной и статус
  `stopped_…` в `dfl status`; разберите причину и снова `dfl run`.
- Остановки после инженерного прогона (мерж задач, `spec-runner run`, проверка
  PR с кодом) статус не меняют: прогон остаётся `completed`, а `dfl status`
  и итог `dfl run` пишут «конвейер после прогона остановился — причина в логе
  вызова (dfl log); повторите dfl run». Конвейер закончен, только когда
  `dfl run` напечатал «дальше: смержите … — конвейер закончен», «PR с кодом
  проверен: …» или одно из сообщений «PR с кодом вмержен …; конвейер
  закончен».

`dfl` работает только в режиме `test`; при другом `mode` откажет. Чтобы
включить test, поставьте `mode = "test"` в `~/.config/darkfactory/config.toml`
сами — `install.sh` существующий конфиг не переписывает, переустановка не
поможет.

## Что выключено в режиме test

Режим test **сознательно ослабляет защиты**: он для одного человека с одной
учёткой, а не для командной эксплуатации. `dfl` при каждом запуске печатает
одну строку `режим test: ослаблено 11 проверок — список: dfl status -v`;
полный перечень — в `dfl status -v` и на уровне `-vvv`. Выключено:

- репо политики утверждения не используется: утверждающий — accounts.human
- песочница авторинга: claude запускается обычным процессом пользователя (нет sandbox-exec, допуска и связки ключей)
- белый список целей: цель — из targets.toml рядом с конфигом, манифест флота необязателен
- одобрение ревью: вердикт публикуется комментарием (GitHub не даёт одобрить свой PR), вердикт обязателен
- корень доверия df (/etc/df/trust.toml) не используется: акт — по мержу (режим до миграции)
- акт человека не требуется (test): candidate-PR мержит раннер после зелёных проверок
- класс актора не применяется (test): finalize не сверяет класс актора; kill switch действует
- утверждение задач человеком не требуется (test): tasks-PR, spec approve и approve-PR проводит раннер
- мерж PR с кодом — за вами (test): приёмка проверяет PR с кодом, но не мержит его
- проверок нет (test): у PR нет .github/workflows и чеков — CI не ждём; чеки CI вне GitHub Actions, пришедшие позже 2 минут, не учитываются
- одна учётка GitHub: accounts.human может совпадать с accounts.agent

Простыми словами: учётка одна на всё; нет песочницы авторинга (она есть только
в режиме strict) — агент-автор работает с вашими правами; утверждение задач и
candidate-PR происходит автоматически; ревью приходит комментариями, а не
approve.

Репо без CI: если у PR нет проверок и в `.github/workflows` на его голове нет
файлов, после нескольких опросов с пустым списком проверок конвейер пропускает
ожидание с пометкой «проверок нет (test)». Есть workflows, но проверок пока нет —
ждёт как обычно.

Ограничение: если CI репо работает вне GitHub Actions (внешний статус или
App) и его чеки приходят позже 2 минут, в test это читается как «проверок нет»,
и spec/candidate-PR вмерживаются без них. Лекарство — workflow в
`.github/workflows` (тогда конвейер ждёт) или режим strict.

## Остановки на смысловой проверке (edge-check)

Каждую волну спецификации проверяет ревьюер-модель (edge-check). Прогон
встаёт со статусом `stopped_review`, и `dfl` печатает сводку («смысловая
проверка узлов: блокирующих замечаний 1, рекомендаций 6»), сами замечания и что
править: файл узла в бандле, чекаут цели и ветку волны. Валят проверку только
блокирующие (`blocker`, `major`) и неоценённый пункт правил; `minor` —
рекомендации, их можно оставить. Стоп без блокирующих замечаний `dfl`
называет так («не прошла без блокирующих замечаний») и править файл не
предлагает: повторите `dfl run`, повторится — `dfl report`.
Поправьте файл (агент сам по замечаниям пока не переписывает — можно
попросить `claude` в чекауте цели), не коммитьте — раннер закоммитит сам, — и
повторите `dfl run`. Если проверка не состоялась
(сбой ревьюера: упал, ответил не по форме; нет набора правил), `dfl` пишет
«смысловая проверка узлов не состоялась — сбой ревьюера, ваш файл ни при
чём» и предлагает повторить `dfl run`; подробности — с `-v`. При стопе гейта бандла
(`stopped_gate`) причина называет файл с выводом гейта, сам вывод — с `-v`.
Каждый круг — платный вызов. Известное ограничение
(devtools#728): ревьюер недетерминирован и его правила могут тянуть одно место
в разные стороны — если одна и та же находка возвращается после правок, не
крутите круги дальше, а бросьте прогон или сообщите о нём.

## Не поддерживается в test

`criteria-close` (закрытие критериев) в режиме test не поддерживается.

## Обновление и остановки

- Обновление: `sh ~/darkfactory/devtools/install.sh` повторно (после
  `git pull` в devtools). Он переведёт компоненты на закреплённые коммиты и
  перепишет `dfl`; конфиг не тронет.
- Повторная установка **откажет посреди прогона**: «Есть незавершённые прогоны
  DarkFactory: …» (код 2) — компоненты посреди прогона не обновляются.
  Незавершённый — в том числе `completed` инженерный прогон, у которого цепочка
  после прогона не дошла до проверенного PR с кодом. Закончите их (`dfl run`)
  или бросьте (`dfl abandon`) в каталоге репо и повторите.
- Также отказ (до любых изменений: проверяются все клоны компонентов сразу) при
  локальных изменениях в клоне компонента, при нештатной ветке (ожидается
  detached HEAD на закреплённом коммите) и при несовпадении `origin`.
- Сбой `git` (нет сети, нет доступа) — отказ с текстом ошибки git; проверьте
  сеть и доступ и повторите `install.sh`. Неудавшийся свежий клон удаляется,
  повтор начинает заново.
- `--yes` без входа в `gh` и запуск без терминала (логин не спросить) — отказ
  «укажите --login <логин>».

## Если что-то сломалось: `dfl report`

Каждый неудачный вызов `dfl` запоминает, что случилось (последний сбой в этом
репо). Если вызов писал лог, последняя строка на уровне 0 —
`подробно: dfl log`; подсказка `отчёт разработчикам: dfl report` идёт с `-v`,
у вызовов без лога и при аварии `dfl`.

```sh
dfl report             # показать отчёт и спросить, отправить ли
dfl report --print     # только показать (например, чтобы прислать в чат)
dfl report --with-log  # то же, но хвост — из лога вызова, с выводом git, gh, ревью
```

`dfl report` печатает отчёт целиком и спрашивает
`Отправить в <репо> как публичное issue? [y/N]`, где `<репо>` — devtools, из
которого вы ставили DarkFactory (по этой памятке — `andrei-shtanakov/devtools`).
Только `y` отправляет: issue открывается **публично** от вашей учётки GitHub (профиль `gh`
из `accounts.human_gh_config_dir`). Если такой же сбой уже заведён и не закрыт,
вопрос будет «Добавить комментарий к …?» — повтор уходит туда, а не новым issue.
Без терминала отчёт не отправляется.

В отчёте: команда и код, причина, где остановился прогон (статус, последняя
операция, `stop-reason.txt`), хвост вывода сбойного вызова, версии devtools,
компонентов, `claude`, `gh`, `uv`, `git`, ОС и режим с логинами из конфига.
Домашний каталог заменён на `~`; скрыты только известные формы секретов
(токены GitHub, GitLab, AWS, Anthropic, Slack, JWT, пароли в `ключ=…`,
блоки приватных ключей) — код и имена файлов целевого репо из вывода
ревью и `git` остаются как есть. **Не
входят:** транскрипты агентов, файлы бандла, бриф, ответы интервью, переменные
окружения. Перед `y` прочитайте отчёт: скрытие — страховка, а не гарантия.

Хвост вывода по умолчанию — строки `dfl` и раннера (уровня Python), **без
вывода дочерних программ** (`spec-runner`, `git`, `gh`, ревью): в нём могут
быть код и имена файлов целевого репо, а отчёт публичный. Если для разбора
нужен и он, добавьте `--with-log`: тогда в отчёт идут последние 200 строк
лога сбойного вызова (`dfl log`; у вызова с `-vvv` лога раннера нет — хвост
прежний). Когда лог есть, а флага нет, `dfl report` напоминает об этом строкой
`полный вывод дочерних процессов (git, gh, ревью) из лога в отчёт не включён;
добавить: dfl report --with-log`. Строки раннера по умолчанию тоже могут
называть файлы и PR целевого репо и пересказывать ошибки `git`/`gh`.

`dfl report` работает и при сломанном конфиге — это тоже сбой, о котором стоит
сообщить.
