# Пин базы вердикта: живая верхушка и отпечаток вместо `baseRefOid`

**Дата:** 2026-09-15 (ревизия 2 — по терминальному ревью #234: вход ревьюера якорен на merge-base, D2 переформулирован, добавлена D4). **Статус:** proposed (дизайн к devtools#223, решение —
владелец). **Область:** `merge-pr.sh` (гвард базы), `governance/accept_pr.py`
(реконсиляция после отказа), без изменений в review-kit.

## 1. Дефект

`merge-pr.sh --expect-base <sha>` сравнивает sha, который передал вызывающий,
с полем `pulls/{n}.baseRefOid` GitHub (`merge-pr.sh:460`). Вызывающий
(`accept_pr.py:~205`) передаёт `base0` — верхушку `origin/<base>` на момент
гарда путей, то есть ту базу, от которой посчитан диф ревью. А `baseRefOid` —
снимок базы **на момент создания PR или последнего update-branch**; при
мержах в `master` GitHub его не пересчитывает.

Сравниваются две разные величины. Гвард проходит только пока `master` не
двигался с момента открытия PR — совпадение, не проверка. Живая приёмка E1
(spec-runner#512): три отказа подряд «база уехала — вердикт вынесен от
f770cac, сейчас 95a77a5» при `origin/master == f770cac` везде. Обход
`update-branch` меняет голову и стоит платного круга ревью; каждый
параллельный мерж в `master` наказывает соседний PR.

Класс по [[operator-error-classes]]: предикат, верный по формулировке
(«база уехала») и ложный по аргументу (не та величина).

## 2. Что видит ревьюер на самом деле

Инвариант мержа: **смерженный результат равен проверенному**. Для squash в
`master` результат = `base_now` + патч `merge-base(base_now, head)..head`.

Что видит ревьюер (по коду кита, не по названию флага `--base`):

- диапазон — `mb..head`, где `mb = git merge-base <base> <head>`
  (`local.sh:426`, `:440`); диф считается от merge-base;
- контекст — `collect-context.sh --base "$mb"` (`local.sh:494`): callers,
  callees, тесты читаются **из merge-base**, не с верхушки базы;
- с верхушки базы читается ровно одно: декларации `linguist-generated`
  (`check-attr --source="$base"`, `local.sh:578`), как `BASE_SHA` в CI.

Следствие, которое меняет постановку задачи: **вход ревьюера якорен на
merge-base**. Движение верхушки `origin/<base>` без движения merge-base (то
есть без рибейза или update-branch головы) не меняет ни диф, ни контекст —
меняет только список generated-деклараций, и только если новые коммиты
базы правили `.gitattributes`. Всё это входит в отпечаток `fp`
(`local.sh:645+`: `prompt.txt` = канонизированный диф + контекст +
инструкции; схема, порог, `review_cmd`; framed-поток v1).

Отсюда два честных вывода о нынешнем гварде «база уехала ⇒ перегоните
вердикт»:

1. Повторное ревью после движения верхушки при неподвижном merge-base
   строит **тот же `prompt.txt`** — платный вызов проверяет байт-в-байт тот
   же вход. Гвард не покупает ничего, кроме счёта.
2. Взаимодействие патча с новыми коммитами базы (семантический конфликт при
   `mergeStateStatus: CLEAN`) нынешний контур **не видит ни до, ни после**
   движения базы: ревьюер его не читает по построению, CI GitHub тоже не
   перезапускает merge-ref при движении базы. Претендовать на эту гарантию
   гвардом сравнения sha — изображать проверку.

Идентичность входа ревью в экосистеме уже определена как `head + fp`
(`--use-verdict` переносит вердикт ровно при их совпадении). Дизайн ниже
опирается на неё и не расширяет обещаний.

## 3. Дизайн

### D1. Гвард базы сравнивает с живой верхушкой, не с `baseRefOid`

`merge-pr.sh` в фазе фактов читает верхушку базы отдельным запросом
`GET repos/{slug}/git/ref/heads/{baseRefName}` (fail-closed на пустом
ответе, как остальные факты) и сверяет `--expect-base` с ней. `baseRefOid`
остаётся фактом только для того, что он означает: снимок базы PR у форджи;
ретаргет ловится по `baseRefName` как сейчас (`accept_pr.py:~285`).

Окно TOCTOU «сверка → PUT» остаётся и называется вслух, как сейчас; оно не
расширяется — удаляется лишь ложный отказ. Текст отказа сохраняет смысл, но
называет обе величины честно: «верхушка base сейчас X, вердикт вынесен от Y».

Симметрия с ADR-ECO-011: обвязка по-прежнему не знает, от какой базы
вынесен вердикт, и пинует то, что ей передали. Без `--expect-base` база не
проверяется, и это говорится вслух — без изменений.

### D2. При движении базы — наследование вердикта по отпечатку, не ревью

Когда верхушка базы действительно двинулась (код 5 от D1), `accept_pr`
проверяет не «двинулась ли база», а «изменился ли вход ревьюера»:

1. `git fetch origin +refs/heads/<base>:refs/remotes/origin/<base>` — тот же
   refspec с явным destination, что в `review-pr.sh:510`.
2. `review-pr.sh <repo> <pr> --fingerprint-only` — новый режим драйвера:
   ровно ветка `--fingerprint-only` кита, без ревьюера и без публикации;
   выход — `fp=<sha256>` и `base=<sha верхушки, по которой считан>`.
   Локальный git, ноль платных вызовов.
3. `fp_new == fp_verdict` ⇒ `prompt.txt` побайтово тот же (по §2 это
   ожидаемый исход при неподвижном merge-base). Повторить
   `Ops.merge(repo, pr, head, base_new)` с пином **новой** базы. Запись в
   журнал прогона: «база двинулась base0→base_new, merge-base неподвижен,
   fp совпал, вердикт унаследован».
4. `fp_new != fp_verdict` ⇒ вход изменился (merge-base двинулся —
   рибейз/update-branch, либо база сменила generated-декларации): повторная
   приёмка с новым ревью, как сегодня.

Честная формулировка того, что D2 делает: **снимает платное ревью,
которое по построению проверяло тот же вход**. Честная формулировка того,
чего D2 не делает: не добавляет проверки взаимодействия патча с новыми
коммитами базы — её нет и сегодня (§2, вывод 2). Кто хочет эту гарантию,
выбирает D4.

Цикл 1–3 ограничен: не более трёх кругов на одну приёмку; четвёртый —
отказ с перечнем виденных верхушек. `fp_verdict` берётся из маркера
`<!-- codex-terminal-review head=… fp=… -->` опубликованного PR review (тот
же, по которому работает `--use-verdict`). Вердикт без маркера (старый кит,
`review-pr.sh:496`) ⇒ D2 не применяется, поведение как сегодня.

### D3. `update-branch` обвязка не делает

Авто-`update-branch` меняет голову (новый merge-коммит) ⇒ инвалидирует пин
головы и чеки CI, и по определению стоит платного ревью. Это ручной
инструмент оператора для конфликтов (`mergeStateStatus: DIRTY`), обвязка
его не вызывает. Предложение из #223 «update-branch и ревью только при
изменённом дифе» D2 покрывает без движения головы.

### D4 (альтернатива, отдельное решение). Ревью результата мержа, а не патча

Единственный способ дать гарантию «смерженный результат проверен» —
ревьюить **merge-результат**: локальный test-merge `base_now` + `head`
(или `refs/pull/N/merge` форджи) и диапазон `base_now..merge`. Тогда
движение базы, трогающее контекст патча, меняет `prompt.txt`, и D2
различает «база двинулась мимо» от «база двинулась в тот же код». Цена —
изменение кита (`local.sh` считает диапазон от merge-base намеренно:
декларации, потолки, generated) и ревью каждого PR после каждого мержа
соседа, который трогает его контекст. Не входит в объём #223; выносится
владельцу как отдельный вопрос.

## 4. Инварианты после изменения

- Мерж выполняется только при `head == head_verdict` **и** (`base_now ==
  base_verdict` **или** `fp(base_now, head) == fp_verdict`). Второе условие
  утверждает ровно то, что доказуемо: вход ревьюера не изменился.
  Нынешнее условие «`baseRefOid` совпал» не утверждает о базе мержа ничего.
- Ноль дополнительных платных вызовов на путях D1/D2; платное ревью —
  только при фактически изменившемся `prompt.txt`.
- Гарантия, которой контур **не даёт** ни сегодня, ни после D1/D2, названа
  в спеке вслух (§2, вывод 2; D4) — а не подразумевается гвардом.
- Все отказы называют обе сравниваемые величины и процедуру повтора
  (правило #183, круг 5).

## 5. Границы и приёмка

- `merge-pr.sh` — харнесс-путь и authority-root: PR с D1 ревьюится
  терминально из доверенного дерева и **мержится человеком**. D2 —
  `accept_pr.py`/`ops.py` — обычный путь.
- Тесты. D1: подсадка — факты с `baseRefOid ≠ live tip` при `expect-base ==
  live tip` ⇒ мерж проходит; `expect-base ≠ live tip` ⇒ код 5 с обеими
  величинами в тексте. D2: стаб `fingerprint-only` с совпадающим fp ⇒ один
  повторный `merge` с `base_new`, ноль вызовов ревью; с несовпадающим ⇒
  ревью вызвано, `merge` не повторён; четвёртый круг ⇒ отказ. Negative
  control обязателен ([[guards-need-a-negative-self-check]]): с вырезанным
  сравнением fp тест D2 обязан краснеть.
- Живая приёмка: воспроизвести сценарий #223 — открыть два PR, влить
  первый, принять второй одной командой `make accept-pr` без
  `update-branch` и без второго ревью; в леджере — запись «fp совпал».

## 6. Открытые решения владельца

1. **D1 + D2 или только D1.** Рекомендация — D1 + D2: по §2 повторное
   ревью при неподвижном merge-base проверяет тот же `prompt.txt`; платить
   за него — платить за подтверждение того, что fp уже доказал локально.
   Только D1 сохраняет сегодняшнюю цену (лишний круг на каждый параллельный
   мерж соседа) без добавления гарантий.
2. **D4** — нужна ли гарантия проверки merge-результата. Если да — это
   отдельный дизайн кита, и тогда D2 получает настоящий различитель
   (контекст от `base_now`). Если нет — зафиксировать в CLAUDE.md, что
   терминальное ревью проверяет патч от merge-base, а семантика слияния —
   зона CI и тестов.
3. Потолок кругов реконсиляции (предложено 3).
