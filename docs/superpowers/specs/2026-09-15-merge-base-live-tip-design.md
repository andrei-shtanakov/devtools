# Пин базы вердикта: живая верхушка и отпечаток вместо `baseRefOid`

**Дата:** 2026-09-15. **Статус:** proposed (дизайн к devtools#223, решение —
владелец). **Область:** `merge-pr.sh` (гвард базы), `governance/accept_pr.py`
(реконсиляция после отказа), без изменений в review-kit.

## 1. Дефект

`merge-pr.sh --expect-base <sha>` сравнивает sha, который передал вызывающий,
с полем `pulls/{n}.baseRefOid` GitHub (`merge-pr.sh:460`). Вызывающий
(`accept_pr.py:~205`) передаёт `base0` — верхушку `origin/<base>` на момент
гарда путей, то есть ту базу, от которой посчитан диф ревью. А `baseRefOid` —
снимок базы **на момент создания PR или последнего update-branch**; при
мержах в `master` GitHub его не пересчитывает.

Сравниваются две разные величины. Гвард проходит только пока `master` не
двигался с момента открытия PR — совпадение, не проверка. Живая приёмка E1
(spec-runner#512): три отказа подряд «база уехала — вердикт вынесен от
f770cac, сейчас 95a77a5» при `origin/master == f770cac` везде. Обход
`update-branch` меняет голову и стоит платного круга ревью; каждый
параллельный мерж в `master` наказывает соседний PR.

Класс по [[operator-error-classes]]: предикат, верный по формулировке
(«база уехала») и ложный по аргументу (не та величина).

## 2. Что гвард обязан утверждать

Инвариант мержа: **смерженный результат равен проверенному**. Для squash в
`master` результат = `base_now` + патч `merge-base(base_now, head)..head`.
Ревьюер видел: диф `origin/<base>@base0...head` и base-контекст с верхушки
`base0` (`local.sh:582`: декларации и контекст читаются с верхушки base, как
`BASE_SHA` в CI). Всё это входит в отпечаток `fp` (`local.sh:645+`:
`prompt.txt` несёт канонизированный диф и base-контекст, плюс схема, порог,
`review_cmd`; framed-поток, протокол v1).

Значит у вердикта уже есть точная идентичность входа — `head + fp`, и
экосистема ей уже доверяет: `--use-verdict` переносит вердикт ровно при
совпадении `head + fp`. Движение базы, не меняющее `fp`, по построению не
меняет ничего из того, что видел ревьюер.

## 3. Дизайн

### D1. Гвард базы сравнивает с живой верхушкой, не с `baseRefOid`

`merge-pr.sh` в фазе фактов читает верхушку базы отдельным запросом
`GET repos/{slug}/git/ref/heads/{baseRefName}` (fail-closed на пустом
ответе, как остальные факты) и сверяет `--expect-base` с ней. `baseRefOid`
остаётся фактом только для того, что он означает: снимок базы PR у форджи;
ретаргет ловится по `baseRefName` как сейчас (`accept_pr.py:~285`).

Окно TOCTOU «сверка → PUT» остаётся и называется вслух, как сейчас; оно не
расширяется — удаляется лишь ложный отказ. Текст отказа сохраняет смысл, но
называет обе величины честно: «верхушка base сейчас X, вердикт вынесен от Y».

Симметрия с ADR-ECO-011: обвязка по-прежнему не знает, от какой базы
вынесен вердикт, и пинует то, что ей передали. Без `--expect-base` база не
проверяется, и это говорится вслух — без изменений.

### D2. Реконсиляция по отпечатку вместо повторного платного ревью

Когда база действительно двинулась (код 5 от D1), `accept_pr` не идёт сразу
на новое ревью, а проверяет, изменился ли **вход ревьюера**:

1. `git fetch origin +refs/heads/<base>:refs/remotes/origin/<base>` —
   освежить базу локально (тот же refspec с явным destination, что в
   `review-pr.sh:510`).
2. `review-pr.sh <repo> <pr> --fingerprint-only` — новый режим драйвера:
   ровно ветка `--fingerprint-only` кита без вызова ревьюера и без
   публикации; выход — строка `fp=<sha256>` и `base=<sha верхушки, по
   которой считан>`. Локальный git, ноль платных вызовов.
3. `fp_new == fp_verdict` ⇒ вход ревьюера побайтово тот же: диф от нового
   merge-base не изменился и base-контекст тех же файлов не изменился.
   Повторить `Ops.merge(repo, pr, head, base_new)` — с пином **новой** базы,
   которую только что видел отпечаток. Запись в журнал прогона: «база
   двинулась base0→base_new, fp совпал, вердикт унаследован».
4. `fp_new != fp_verdict` ⇒ как сегодня: повторная приёмка с новым ревью по
   новой базе (диапазон или контекст изменились — вердикт обязан
   относиться к ним).

Цикл 1–3 ограничен: не более трёх кругов реконсиляции на одну приёмку
(база может двигаться быстрее, чем обвязка мержит); четвёртый круг —
отказ с полным перечнем виденных верхушек. Каждый круг — только локальный
git и один запрос фактов.

`fp_verdict` берётся оттуда, где он уже есть: маркер
`<!-- codex-terminal-review head=… fp=… -->` опубликованного PR review
(тот же, по которому работает `--use-verdict`). Вердикт без маркера
(старый кит без `--fingerprint-only`, `review-pr.sh:496` feature-detect)
⇒ D2 не применяется, поведение как сегодня — повторное ревью.

### D3. `update-branch` обвязка не делает

Авто-`update-branch` меняет голову (новый merge-коммит) ⇒ инвалидирует пин
головы и чеки CI, и по определению стоит платного ревью. Это ручной
инструмент оператора для конфликтов (`mergeStateStatus: DIRTY`), обвязка
его не вызывает. Предложение из #223 «update-branch и ревью только при
изменённом дифе» D2 покрывает без движения головы.

## 4. Инварианты после изменения

- Мерж выполняется только при `head == head_verdict` **и** (`base_now ==
  base_verdict` **или** `fp(base_now, head) == fp_verdict`). Второе условие
  сильнее нынешнего: «отпечаток совпал» утверждает равенство входа
  ревьюера, «baseRefOid совпал» не утверждает ничего о базе мержа.
- Ноль дополнительных платных вызовов на путях D1/D2; платное ревью —
  только при фактически изменившемся входе.
- Все отказы называют обе сравниваемые величины и процедуру повтора
  (правило #183, круг 5).

## 5. Границы и приёмка

- `merge-pr.sh` — харнесс-путь и authority-root: PR с D1 ревьюится
  терминально из доверенного дерева и **мержится человеком**. D2 —
  `accept_pr.py`/`ops.py` — обычный путь.
- Тесты. D1: подсадка — факты с `baseRefOid ≠ live tip` при `expect-base ==
  live tip` ⇒ мерж проходит; `expect-base ≠ live tip` ⇒ код 5 с обеими
  величинами в тексте. D2: стаб `fingerprint-only` с совпадающим fp ⇒ один
  повторный `merge` с `base_new`, ноль вызовов ревью; с несовпадающим ⇒
  ревью вызвано, `merge` не повторён; четвёртый круг ⇒ отказ. Negative
  control обязателен ([[guards-need-a-negative-self-check]]): с вырезанным
  сравнением fp тест D2 обязан краснеть.
- Живая приёмка: воспроизвести сценарий #223 — открыть два PR, влить
  первый, принять второй одной командой `make accept-pr` без
  `update-branch` и без второго ревью; в леджере — запись «fp совпал».

## 6. Открытые решения владельца

1. Принять D2 (наследование вердикта по fp при движении базы) или
   остановиться на D1 (честный предикат, повторное ревью при любом
   движении базы). Рекомендация — D1 + D2: `fp` уже признан идентичностью
   входа ревью в `--use-verdict`; отказываться от него здесь значит платить
   за круг, который ничего нового не проверяет.
2. Потолок кругов реконсиляции (предложено 3).
