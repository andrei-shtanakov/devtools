# DarkFactory на Linux: режим test — дизайн

Дата: 2026-11-11. Статус: черновик на одобрение владельца.
Предыстория: devtools#726 закрыт — `install.sh` пускал Linux, но конвейер там
отказывал на первом же авторинге. Замер в Linux-контейнере (10.11, master
40ae440) показал, что блокер ровно один — `governance/safe_io.py`.

## Зачем

Лёгкая установка DarkFactory (режим `test`, `install.sh` + `dfl`) сейчас
работает только на macOS. Не у всех коллег macOS. Владелец: «только macOS —
работа наполовину»; Linux **обязателен**.

Поддержка Linux означает: коллега на Linux без sudo ставит DarkFactory по
`docs/darkfactory-for-colleagues.md` и проходит тот же путь, что и на Mac —
`dfl init-repo` → `dfl run` → интервью → бриф → инженерный прогон →
проверенный PR с кодом.

## Цели

1. **Переносимый `safe_io`** с той же гарантией, что `O_NOFOLLOW_ANY` на
   Darwin: ни одной символической ссылки ни в одном компоненте пути, включая
   предков корня, без гонки «проверил → подменили».
2. **Путь режима `test` одинаков на macOS и Linux.** Различия ОС живут только
   внутри файлового слоя (`safe_io`); в путь `test` не добавляется ни одной
   новой развилки по ОС.
3. **Режим `strict` на Linux явно отказывает** до запуска агента, с понятной
   причиной, и никогда сам не переключается в `test`.
4. **Проверено на Linux:** тесты, которые сегодня на Linux пропускаются,
   выполняются в Linux CI; плюс сквозной тест пути пользователя и один
   настоящий прогон до объявления поддержки.
5. **Установка и инструкция:** `install.sh` пускает macOS и Linux;
   инструкция и README говорят «macOS или Linux»; `make` — в требованиях и в
   проверке программ установщика.

## Не цели

- Песочница авторинга на Linux (настоящий `strict`). Это **следующая работа**;
  этот дизайн только называет её стыки (раздел «Место под strict на Linux»).
- `df` (root-установщик) на Linux aarch64; к лёгкой установке не относится.
- `openat2` / `RESOLVE_NO_SYMLINKS`: короче, но требует ядро 5.6+ и вызова
  через `ctypes`; покомпонентный обход даёт ту же гарантию на macOS и Linux.
- Другие ОС (BSD, Windows/WSL как отдельная цель).

## Анти-цели (провал, даже если «работает»)

- Ослабление гарантии `safe_io` на Linux (обычный `open`, «в test можно»).
  Вариант владельцу озвучен и не выбран.
- Обход, который открывает корень обычным `open`, а безопасно идёт только
  по относительной части: ссылка в предке корня (`/home → /var/home`)
  осталась бы лазейкой, которую `O_NOFOLLOW_ANY` закрывает.
- Изменение поведения на macOS без необходимости: проверенная ветка
  `O_NOFOLLOW_ANY` остаётся.
- Объявление поддержки Linux в инструкции до настоящего прогона.

## Ограничения

- `governance/safe_io.py`, `governance/sandbox.py`, `governance/author_launch.py`,
  `install.sh` — под authority-root / пути обвязки: PR мержит **владелец**
  (D10), агент не мержит. Ревью — `review-pr.sh` (2 платных прогона на PR).
- Каждый `subprocess.run` в `governance/` — с литеральной первой программой
  из git/gh/tmux/spec-runner/security (инвариант песочницы).
- Нынешний CI (`.github/workflows/ci.yml`, ubuntu-latest) уже гоняет весь
  набор тестов на Linux — новых job не нужно, нужно, чтобы пропуски
  `@darwin_only` перестали быть пропусками там, где это про `test`.

## Как устроено сейчас (замер, а не предположение)

- Вся зависимость от Darwin в пути `test` — одна функция `safe_io._open`
  (`safe_io.py:100`): при `any_component=True` добавляет `O_NOFOLLOW_ANY`,
  на Linux `_flag()` поднимает `SafeIOError("… только macOS …")`.
- Через `_open` идут: `read_regular` (абсолютный путь `root/rel`), `list_tree`
  (абсолютный старт, затем имена от `dir_fd`), `_dir_chain` (абсолютный
  корень, затем имена от `dir_fd`) → `ensure_dirs`, `create_dir`, `publish`.
  `publish` создаёт временный файл с `any_component=False` + `O_NOFOLLOW` в
  закреплённом каталоге — уже переносимо.
- `sandbox.create_call_dir` строит каталог вызова только через `safe_io`;
  `author_launch.launch_author` зовёт его и `safe_io.ensure_dirs` до развилки
  test/strict (`author_launch.py:700`) — отсюда отказ на Linux.
- Linux-замер (podman, debian bookworm aarch64, без `tests/df`): 8918 passed,
  187 skipped, 5 failed (все 5 — артефакты контейнера: root, нет `ps`, нет
  `make`). Пропуски из-за Darwin — 111: `test_governance_sandbox.py` 51
  (каталог вызова), `test_governance_safe_io.py` 26 (`O_NOFOLLOW_ANY`),
  `test_governance_sandbox_live.py` 32 (проба `sandbox-exec` — только strict),
  `test_governance_runner.py` 2 (настоящий допуск и каталог вызова).
- Остальное Darwin-специфичное — только strict: `sandbox-exec`/SBPL-профиль,
  `security find-generic-password`, проба `sandbox-admit`; плюс безвредное
  `PRAGMA fullfsync` только на darwin в `act_journal_wire`.

## Решения

### 1. Файловый слой: две реализации одной гарантии

`safe_io._open` при `any_component=True`:

- **Darwin** (есть `os.O_NOFOLLOW_ANY`) — как сейчас, без изменений.
- **Иначе** — покомпонентный обход:
  - абсолютный путь — обход **от `/`**: `open("/", O_RDONLY|O_DIRECTORY)`,
    затем каждый компонент `openat(dir_fd, name, O_RDONLY|O_DIRECTORY|O_NOFOLLOW)`,
    последний — с запрошенными флагами вызывающего `| O_NOFOLLOW`;
  - путь от `dir_fd` — тот же обход от `dir_fd`;
  - компонент-ссылка → отказ. **Замер ядра Linux (6.16, 11.11):**
    `openat(…, O_DIRECTORY|O_NOFOLLOW)` на ссылке (в т.ч. висячей) даёт
    `ENOTDIR`, а не `ELOOP`; без `O_DIRECTORY` — `ELOOP`. Поэтому отказ —
    на любом из двух кодов (безопасность от кода не зависит: открытия не
    было). Чтобы текст был тот же, что на Darwin («ссылка в пути»), после
    отказа `ENOTDIR` делается `fstatat(dir_fd, name, follow_symlinks=False)`
    **только для выбора текста** (ссылка → «ссылка в пути», иначе «не
    каталог»). Гонка этого `fstatat` влияет лишь на формулировку, не на
    решение: отказ уже состоялся. *(Решение исполнителя.)*
  - компоненты `""`, `.`, `..` в любой части пути, включая корень, — отказ
    (на Darwin неканонический корень и так отказ);
  - промежуточные дескрипторы закрываются на любом исходе (успех, отказ,
    исключение).
- Гонки нет: каждый шаг разрешает одно имя относительно уже удерживаемого
  дескриптора без следования ссылкам, поэтому подмена компонента после
  открытия предыдущего ничего не перенаправляет.
- Выбор реализации — по наличию флага, а не по `sys.platform`.

Весь остальной контракт `safe_io` сохраняется побайтово по смыслу: только
обычный файл, `st_nlink == 1`, `O_NONBLOCK` (FIFO не вешает открытие), потолок
и таймаут чтения, публикация через `O_EXCL`-временный файл и `rename` (новый
inode, висячая ссылка заменяется, а не следуется), режим файла 0644 мимо
umask, `SafeIOError` — единственный тип отказа. Одинаковыми между ОС
обещаются **прикладные** тексты отказов модуля; системный `strerror` внутри
них может отличаться.

**Регистр имён** (`_fold`, `paths_overlap`, `validate_bundle_dir`, сверка
`.git`): проверки, рассчитанные на регистронезависимый APFS, остаются как
есть. На регистрозависимой ФС Linux они изредка отказывают лишнее — это
безопасная сторона и не развилка по ОС. *(Решение исполнителя.)*

**Следствие для коллеги:** если путь к домашнему каталогу или к целевому репо
содержит ссылку (Fedora Silverblue/ostree: `/home → /var/home`), вызывающий
обязан передать канонический корень (`realpath`) — как сейчас с `/var →
/private/var` на macOS. Иначе — честный отказ, не дыра. Пути, которые сегодня
канонизируются (`calls_root`, корни цели и бандла), проверить на Linux тем же
тестом. **В объёме работы — аудит всех мест вызова `safe_io`** (импортёры
сегодня — только `author_launch` и `sandbox`): каждый корень, переданный в
`safe_io`, должен быть канонизирован `realpath` один раз у вызывающего;
где этого нет (например, `run_dir`) — добавить. На macOS такие пути случайно
каноничны, на Linux с ссылкой в `$HOME` они дали бы отказ на рабочем пути.
*(Решение исполнителя; файлы под authority-root — мерж владельцем.)*

### 2. Тесты обеих веток на любой машине

Покомпонентный обход тестируется **и на macOS** (принудительно, подменой
флага в тестах), чтобы владелец на своей машине проверял обе ветки. Тесты
`safe_io` и каталога вызова, помеченные `darwin_only` только из-за
`O_NOFOLLOW_ANY`, становятся общими (параметризованными по реализации, где
нужно); `darwin_only` остаётся лишь у того, что действительно про
`sandbox-exec`/strict. Ожидание по замеру: на Linux начинают выполняться ~77
тестов (51 + 26) и 2 теста раннера, если они про каталог вызова, а не про
допуск strict. Пути вида `/private/var/folders` в тестах — заменить на
вычисляемые (`realpath(tmp_path)`).

### 3. Путь пользователя на Linux — сквозной тест

В Linux CI — тест пути `test`: конфиг `mode = "test"` → `launch_author` с
**поддельным** `claude` в `PATH` (скрипт, пишущий узел) → каталог вызова
создан через `safe_io` → результат перенесён в бандл через `publish`.
Отдельный тест: `strict` на ОС без песочницы отказывает **до** создания
каталога вызова и запуска агента, текст отказа называет ОС, перехода в `test`
нет (сегодня это делает `author_launch._sandbox_binary`; закрепить тестом).

### 4. Установщик и инструкция (последними коммитами)

- `install.sh`: `uname -s` ∈ {Darwin, Linux}, иначе отказ с названием ОС.
  `make` — в списке обязательных программ.
- Тест `install.sh` с подменённым `uname`: `PATH` — **только** каталог
  стабов (на usrmerge-Linux `/bin` = `/usr/bin` с настоящими `git`/`gh`).
- Инструкция и README: «macOS или Linux»; «на Linux — только режим `test`,
  `strict` требует песочницы, которой на Linux пока нет»; `make` в «Что
  нужно».
- Строка про Linux в инструкции появляется только вместе с подтверждением
  настоящим прогоном (п. 5).

### Порядок поставки *(решение исполнителя)*

- **PR1** — файловый слой, аудит вызывающих, тесты, сквозной тест `test`,
  тест отказа `strict`. Не трогает `install.sh` и инструкцию: Linux по-прежнему
  отказывается установщиком, никакого объявления. Мержит владелец.
- **PR2** — `install.sh` (Linux + `make`), тест `install.sh`, инструкция и
  README. Открывается после мержа PR1; **настоящий прогон (п. 5) идёт с
  ветки PR2** (`git clone -b <ветка PR2>`), мерж PR2 — только после
  успешного прогона. Так объявление поддержки и разрешение в установщике
  вливаются одним PR и только после доказательства.
- План заканчивается PR1 как завершённой частью; PR2 и прогон — отдельный
  этап, заблокированный на машине владельца.

### 5. Настоящий прогон до объявления поддержки

Один прогон на реальной Linux-машине по SSH (машину даёт владелец позже):
обычный пользователь без sudo, **отдельная учётка GitHub** (не
`andrei-shtanakov`) с собственным тестовым репо; входы `gh auth login` и
`claude` на машине делает владелец, агент учётных данных не вводит и не
переносит. Агент: `git clone` → `install.sh` → `dfl init-repo` (мерж — по
правилам режима test) → `dfl run` с интервью → PR с кодом. Перед стартом —
подтверждение владельца (расход токенов, PR в тестовом репо). Итог прогона —
в PR с правкой инструкции.

**Прогон пройден, если** на чистой машине без sudo:
`install.sh` завершился успешно; `dfl init-repo` открыл PR подготовки и после
его мержа `dfl run` прошёл интервью, открыл и (после мержа владельцем-учёткой)
принял бриф, инженерный прогон дошёл до **открытого PR с кодом** в тестовом
репо и ревью-шаг режима test отработал (комментарии на PR). Мерж PR с кодом не
требуется — он за человеком и в test. **Прервать и чинить**, если любой шаг
отказывает с ошибкой файлового слоя/ОС или требует sudo; ошибки, не связанные с
Linux (сеть, лимиты токенов), — повторить шаг, в итог прогона записать.

## Место под strict на Linux (только стыки, без кода)

Следующая работа добавит песочницу авторинга на Linux. Сейчас ничего не
абстрагируется; стыки, которые она затронет:

1. **Профиль и обёртка запуска** — `sandbox._wrap` и генерация SBPL. Выбор
   механизма Linux (bubblewrap, Landlock, их сочетание, иное) — **следствие
   требуемых гарантий** (запись только в каталог вызова, чтение цели, сеть,
   процессы), а не заранее заданный вариант: гарантии bubblewrap зависят от
   его настройки, возможности Landlock — от ABI ядра.
2. **Проба допуска** — `sandbox-admit` (`sandbox.py:1288`, сейчас «только
   macOS с sandbox-exec») и наблюдаемые каталоги (`/private/tmp`).
3. **Формат записи допуска** — `contracts/author-sandbox/v1/admitted.toml`:
   поля `macos_major`, `profile_sha256`. Linux потребует указать бэкенд,
   политику и проверенные возможности среды (версия ядра / ABI Landlock и т.п.)
   — вероятно, новая версия схемы.
4. **Проверка ОС** — `author_launch._sandbox_binary` (сегодня отказ «только на
   macOS»).
5. **Секрет агента** — сегодня токен из связки ключей macOS (`security`).
   Хранение и передачу секрета на Linux определить отдельно: файл 0600 **не**
   решение — агент с тем же UID его прочтёт.

Переносимый `safe_io` из этой работы нужен и будущему strict.

## Что остаётся исполнителю

- Структура кода внутри `safe_io` (отдельная функция обхода, имена), если
  гарантия и тексты отказов соблюдены.
- Как именно параметризовать тесты по реализации и подменять флаг.
- Какие из 32 тестов `test_governance_sandbox_live.py` и 2 раннера про `test`,
  а какие про strict (по смыслу каждого).
- Нарезка на PR (ожидаемо: файловый слой + тесты; затем установщик и
  инструкция после настоящего прогона).

## Приёмка

- Linux CI (ubuntu-latest) зелёный; тесты `safe_io` и каталога вызова там
  **выполняются**, а не пропускаются (число пропусков `darwin_only` падает с
  111 до ≈32+, остаток — только strict).
- На macOS полный набор зелёный, обе реализации обхода проверены.
- Тесты: ссылка в предке корня, в середине, в последнем компоненте;
  висячая ссылка; `..`; hardlink; FIFO; потолок чтения; публикация поверх
  ссылки и hardlink — для покомпонентной реализации.
- Сквозной тест `test` с поддельным `claude` на Linux; тест отказа `strict`.
- Один настоящий прогон на Linux-машине до PR с объявлением поддержки.
