# Переиздание tasks-спеки (supersede) — контракт

**Статус:** draft (спека контракта; код — отдельным заходом после утверждения)
**Предмет:** `governance/task_bridge.py` — санкционированная повторная доставка
tasks-спеки после correction'а вышестоящего бандла.
**Основание:** решение владельца 2026-09-09 — «отдельный заход по supersede
нужен: это повторяемая штатная операция после correction, а не одноразовый
обход. Но сначала короткая спека контракта, затем код».

## 1. Зачем

После correction'а бандла (правка `30-decomposition.md` вышестоящей стадии)
доставленная ранее tasks-спека протухает: она выведена из байтов, которых
больше нет. Штатного пути переиздать её нет — мост видит завершённый op
`tasks-deliver`, находит прежний PR и принимает доставку как состоявшуюся.
Ручная чистка леджера недопустима (решение владельца): леджер — журнал фактов,
а не рабочая поверхность оператора.

Боевой случай: воркстрим `verify-first-file-scope-group-targets-20260908`
(spec-runner#403) — семь verify-задач переразмечены correction'ом, tasks-спека
помечена `stale`, переиздать её нечем.

## 2. Границы

- Переиздание — **операторская команда с явным флагом**, не автоматика.
- Мержи PR-ов переизданием **не выполняются** (ни бандла, ни tasks) — решение
  владельца: «никаких автоматических мержей».
- Смена состава DAG (`--legacy-bundle`) supersede не касается: переиздание
  идёт тем же активным DAG, что и исходная доставка.

## 3. Инварианты (перечень владельца, дословно расшифрован)

### I1. Новая ветка от свежего base

Переиздание создаёт **новую** ветку доставки от только что подтянутого
`base_ref` и не переиспользует ветку прежней доставки. Причина (боевые круги
3–5 PR devtools#161): `ensure_branch` на существующую ветку откатывает дерево к
её содержимому, и спека рендерится из устаревшего бандла.

Имя: `spec/<ws-id>-tasks-v<N>`, где `N` — порядковый номер переиздания
(первое → `v2`). `N` выводится из истории доставок в леджере (см. I4), а не из
существующих веток: ветка могла быть удалена после мержа.

### I2. Идентичность доставки — пост-штамповый anchor, вычисленный ДО эффектов

Доставка идентифицируется blob-хешем **терминального узла активного DAG после
штампа** (`stamp_bundle_approved`) — именно эти байты уходят в PR и после его
мержа лежат в base. Пред-штамповый anchor непригоден: сравнение с base после
мержа никогда не совпало бы, и гейт стал бы fail-open.

Но в base лежат **до**штамповые байты, а штамп — эффект. Поэтому anchor
вычисляется **проспективно и чисто**, до единого эффекта, в такой
последовательности:

1. `checkout_and_pull(base_ref)` — единственная операция чтения, дерево не
   меняется;
2. разрешается provenance correction-PR (§3.I7 / §5) — его `mergedBy`/
   `mergedAt` входят в штамп, поэтому без него проспективный штамп не
   вычислим;
3. в памяти строится **prospective stamp**: те же преобразования, что делает
   `stamp_bundle_approved`, но результат никуда не пишется;
4. `prospective_anchor = blob_sha1(<проштампованный в памяти терминальный
   узел>)`.

Сравнение (I5) и запись намерения (I4) идут именно по `prospective_anchor`.
Реальный штамп на диск ложится позже, уже внутри доставки, и обязан
совпасть с проспективным — расхождение фатально (значит вход изменился между
проверкой и эффектом).

### I3. Реконсиляция ревизии: явные переходы, идентичность важнее имени ветки

Совпадения имени ветки недостаточно — ветка могла остаться от другого захода.
Ревизия реконсилируется по паре «состояние op × состояние PR», и в каждом
случае сверяется **идентичность**: `head` PR-а и артефакт (пути + пин анкера в
доставленной спеке) обязаны отвечать записанному намерению (§I4).

| Состояние ревизии | PR по её ветке | Действие |
|---|---|---|
| `completed` | OPEN | вернуть существующий PR; `v<N+1>` НЕ создаётся |
| `completed` | MERGED | доставка состоялась; переиздание решается только по I5 |
| `started` | OPEN | сверить идентичность → продолжить (докоммитить/допушить) |
| `started` | MERGED | сверить идентичность → завершить op этим PR |
| `started` | нет PR | продолжить с шага создания PR |
| любое | CLOSED-unmerged | **fail-closed**: ветка отклонена человеком |
| любое | идентичность не сошлась | **fail-closed**: `head`/артефакт чужие |

«Идентичность не сошлась» — это `head` PR-а не тот, что записан в намерении,
либо доставленный в PR файл спеки пинует не тот anchor. Молча продолжать в
такой ветке нельзя: под тем же именем может лежать чужая работа.

### I4. Завершённый op не перезаписывается

`op_complete("tasks-deliver", …)` прежней доставки **остаётся неизменным**.
Переиздание добавляет отдельную запись истории — ревизию:

```
ops["tasks-deliver"]      = {status: completed, pr: 392, anchor: <blob>}      # v1, неприкосновенна
ops["tasks-deliver-v2"]   = {status: completed, pr: 4xx, anchor: <blob'>}     # переиздание
```

Форма ключа ревизии — `tasks-deliver-v<N>`, тот же `N`, что в имени ветки (I1).
Отсюда же выводится `N` для следующего переиздания: максимальный существующий
плюс один. Провалившееся переиздание оставляет свою ревизию в `started` и не
трогает предыдущие — повторный заход возобновляет её (write-ahead, как везде в
леджере).

**`op_start` фиксирует намерение целиком.** Без этого после падения или сдвига
base нельзя отличить «возобновляется тот же supersede» от «начинается другой».
Записываются:

```
ops["tasks-deliver-v2"] = {
  status:             "started",
  revision:           2,
  branch:             "spec/<ws-id>-tasks-v2",
  base_sha:           "<sha base_ref на момент старта>",
  prospective_anchor: "<blob, §I2>",
  approval_pr:        <номер correction-PR, §I7>,
  tasks_version:      <версия, которую получит спека, §I6>,
  dag:                ["00-charter.md", …]        # активный DAG
}
```

Возобновление сверяет намерение с фактом: `base_sha` сдвинулся или
`prospective_anchor` пересчитался иначе — это уже **другое** переиздание;
старая ревизия остаётся в истории как незавершённая, новая получает
следующий `N`. Молчаливое продолжение под тем же ключом запрещено.

### I5. Равный anchor → успешный бесследный no-op

Если проспективный anchor (§I2) **равен** anchor'у последней завершённой
доставки, переиздание не выполняется: апстрим не менялся, переиздавать нечего.
Это **успех, а не отказ**: RC 0, сообщение «апстрим не менялся — переиздание не
требуется». Не создаются ни ветка, ни PR; леджер не пишется вовсе — ни
`started`, ни новая ревизия.

Свойство «бесследности» проверяемо: снимок `run.json` до и после вызова
побайтово совпадает.

### I6. Монотонная версия tasks-спеки

`version:` в frontmatter переизданной спеки строго больше версии предыдущей
доставленной (читается из `spec/<ws-id>-tasks.md` в свежем base). Сброс в `1`
недопустим: версия — счётчик поколений документа, а не счётчик вызовов
рендера.

### I7. Штамп correction'а — по correction-PR

`approved_by`/`approved_at` штампа бандла берутся из фактов **того PR, который
доставил correction** (mergedBy/mergedAt correction-PR), а не исходного
бандл-PR. Иначе штамп утверждает, что текущие байты одобрил человек, который
одобрял другую версию.

**Алгоритм provenance (исполним, без догадок):**

1. Найти последний коммит, изменивший файл терминального узла активного DAG в
   base: `git log -1 --format=%H -- <bundle_dir>/<anchor_file>` на свежем
   `base_ref`. Нет такого коммита — отказ («анкер не менялся в истории base»).
2. Связать коммит ровно с одним merged PR: запросить PR-ы, содержащие этот
   коммит (`gh api .../commits/<sha>/pulls`), оставить только `MERGED` и
   нацеленные в `base_ref`.
3. Кандидатов ровно один → это correction-PR. **Ноль** (правка вне PR, прямой
   коммит, squash без связи) или **больше одного** → отказ: подписи взять
   неоткуда, гадать нельзя.
4. Проверить кандидата: его `mergeCommit` содержит изменение того же файла
   анкера, `mergedBy`/`mergedAt` непусты. Иначе — отказ.
5. `approved_by = mergedBy.login`, `approved_at = mergedAt`.

**Fallback `--approval-pr <n>`** — для случаев, когда автоматика даёт ноль или
несколько кандидатов, оператор называет PR явно. Верификация та же (шаг 4):
явно названный PR обязан быть merged, нацелен в `base_ref` и содержать
изменение файла анкера — иначе отказ. Флаг не отключает проверку, он заменяет
только шаги 1–3.

### I8. Никаких автоматических мержей

Переиздание открывает PR и останавливается. Мерж — человеческий (tasks-спека
исполнима: её approve и есть санкция на исполнение).

## 4. Наблюдаемое поведение (для приёмки)

| Вход | Наблюдаемое | RC |
|---|---|---|
| `--supersede`, anchor изменился, прежняя доставка вмержена | новая ветка `-v<N>`, новый PR, ревизия `tasks-deliver-v<N>`, версия спеки +1 | 0 |
| `--supersede`, проспективный anchor равен последнему | «апстрим не менялся — переиздание не требуется»; `run.json` побайтово прежний; ветки и PR нет | **0** |
| `--supersede`, ревизия `completed`, её PR OPEN | возвращается существующий PR; `v<N+1>` не создаётся | 0 |
| `--supersede`, ревизия `started`, PR OPEN, идентичность сошлась | доставка продолжается в той же ветке | 0 |
| `--supersede`, ревизия `started`, PR MERGED, идентичность сошлась | op завершается этим PR | 0 |
| `--supersede`, PR CLOSED-unmerged | fail-closed: ветка отклонена человеком | ≠0 |
| `--supersede`, идентичность не сошлась (`head`/артефакт чужие) | fail-closed с указанием расхождения | ≠0 |
| `--supersede`, `base_sha`/проспективный anchor сдвинулись у `started`-ревизии | это другое переиздание: старая ревизия остаётся незавершённой, заводится следующий `N` | 0 |
| `--supersede`, correction-PR: 0 или >1 кандидатов, без `--approval-pr` | отказ: «подписи взять неоткуда» | ≠0 |
| `--supersede --approval-pr <n>`, PR не merged / не в `base_ref` / не менял анкер | отказ той же проверки | ≠0 |
| `--supersede`, у последней доставки anchor не записан (легаси) | одноразовый compatibility-случай: ревизия несёт `comparison: unavailable`, переиздание выполняется | 0 |
| без флага, op завершён | сегодняшнее поведение: адоптирует прежний PR | 0 |
| без флага, op отсутствует | сегодняшнее поведение: обычная доставка | 0 |

## 5. Вне объёма

- Автоматическое обнаружение необходимости переиздания (кто-то должен решить,
  что correction состоялся).
- Ретроспективная починка леджеров, где anchor не записывался (см. вместо неё
  compatibility-случай §7).
- Каскад на downstream-артефакты spec-runner (`status: stale` ставится
  correction'ом бандла, не мостом).

## 7. Compatibility-случай: доставка без записанного anchor

Доставки, выполненные до введения anchor'а, не несут его в леджере. Сравнение
(§I5) для них невозможно **по построению**, и одного warning'а недостаточно:
неизвестное должно остаться неизвестным в самом журнале, а не раствориться в
логе.

Правило — одноразовый compatibility-случай:

- переиздание выполняется (иначе такие воркстримы неремонтируемы);
- ревизия несёт явное поле `comparison: "unavailable"` рядом с
  `prospective_anchor` — запись фиксирует, что решение принято без сверки;
- в выводе оператору сказано то же самое: сверка не производилась, потому что
  предыдущая доставка anchor не записала;
- случай одноразовый: новая ревизия anchor записывает, поэтому следующее
  переиздание того же воркстрима уже сверяется нормально.

`comparison: "unavailable"` — это не «сверка прошла», а «сверки не было»:
любой последующий аудит отличает одно от другого по самому леджеру.

## 6. Уроки, которые контракт закрывает

Пять кругов ревью devtools#161 показали: локального фикса порядка операций
недостаточно, потому что переиздание конфликтовало с моделью «одна ветка / один
PR / штамп внутри PR». Контракт разводит их явно: переиздание — новое
поколение доставки со своей веткой, своим PR и своей записью в леджере, а не
повторный проход по существующей.
