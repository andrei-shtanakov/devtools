## 0. Зачем

Владелец тратит день на выяснение, почему не закрыт issue A в проекте B:
B завёл issue в A с вопросом и не закрывает своё, пока A не ответит; A тем
временем ждёт C. Замер 2026-09-29 показывает, что дело не в объёме
(22 открытых issue, 12 PR на 16 репо; 915 `@id`-пунктов, 130 рёбер
`@blocked_by`), а в трёх дырах:

1. **Рёбра issue↔issue не видит никто.** Граф ожиданий dispatcher
   (`/api/waits`) строится только по `@blocked_by:todo://`; связи между
   issues живут в телах (`from:`, `repo#N`, `slug:`) — около половины открытых
   issues их несут. Живой пример пинг-понга: приёмка оракула devtools ждёт
   `spec-runner#603`, а `spec-runner#603` завёл обратно `devtools#491`
   (sign-off формы) — из обоих мест видно «ждём соседа».
2. **Ожидание пассивно.** 74 условия `@trigger:"…"` во флоте написаны прозой
   и не вычисляются никем; ожидание срабатывает, только когда человек
   «пнёт».
3. **У приоритета нет носителя.** 0 тегов приоритета в TODO. `status` эпика в
   `epics.toml` (`active | paused | standing | done`) говорит, жив ли поток, но
   не упорядочивает живые: активных — больше десятка, без ранга.
   `prograph-vault/authored/roadmaps/` держит два yaml про контракты.
   Приоритет живёт в голове владельца и в заметках памяти сессий.

Роль «управляет» заведена ADR «Fleet agent» (2026-07-10, `proposed`), но
выродилась в набор инструментов: датчики (`inbox.py`, `issue_console.py`,
`check-plan-fields.py`), исполнители одного пункта (`todo_worker.py`,
`issue_worker.py`), контур ревью/мержа (`review-pr.sh`, `merge-pr.sh`).
Отчёт в `derived/fleet/` за всё время один (2026-07-10). Не хватает цикла,
который их связывает и решает «что сейчас главное».

**conductor** — этот цикл: детерминированное ядро собирает единый граф
зависимостей флота, активно проверяет ожидания, раскладывает работу по
роадмапу владельца и действует через существующие каналы в пределах
разрешённого уровня автономии. Модель — только на краях.

## 1. Границы и инварианты

- **I1. Только существующие каналы.** PR, issue, `todo://`. Новых сущностей
  (очередей, БД, трекеров) нет; снимок прогона — артефакт, не источник истины.
- **I2. Дом — devtools**, не новый репо. Конституция роли — `devtools/CLAUDE.md`
  (дополняется §1 этой спеки).
- **I3. Границы запрета применяются к исполнителю, а не к выбору места.**
  Правило полирепо «работай только в своём репо» относится к сессии внутри
  репо. conductor ни в каком репо не сидит. Его исполнители (worker, intake)
  запускаются **внутри целевого репо** (изолированная рабочая копия, его
  `CLAUDE.md`), правят только его файлы, результат доставляется PR-ом в него
  (§5.6). Выбор «попросить соседа» вместо запуска при исполнимом кандидате в
  контуре — **дефект** (тест §10).
- **I4. Межрепные запросы идут через conductor** (§6). Репо не адресуют
  друг другу inbox-issues напрямую. Заменяет ряд положений ADR-ECO-006
  (новый ADR-ECO-012, §9).
- **I5. Решение политики — в коде.** Уровни, выбор действия, признаки
  «решение владельца» вычисляет код до вызова модели (§5.2–5.3). Модель может
  поднять `needs_human`, не может опустить. Неоднозначность → владелец.
- **I6. Честность и свежесть источников.** Каждый источник — `read | absent |
  not_queried | error`. Прочитанное читается **с опубликованной
  default-ветки** (`origin/<default>` после `git fetch`, SHA пишется в снимок),
  не из рабочей копии. Граф с хотя бы одним непрочитанным источником,
  упавшим `fetch`, усечённым поиском или недогруженной ссылкой — `partial`;
  на `partial` — только уровень 0.
- **I7. Действие = сверка желаемого состояния.** Каждое действие —
  «обеспечить X», вычисляемое заново каждым прогоном из удалённого состояния
  GitHub и git, а не «сделать X однажды». Маркеры предотвращают дубли
  записей и не запрещают довести недоделанное (§5.4).
- **I8. Один управляющий писатель.** Управляющие записи во флот (§5.5) делает
  только хост, назначенный роадмапом и держащий действующий ключ App.
  Публикация снимка в vault — отдельная операция со своей матрицей (§5.5).
- **I9. `_cowork_output/` не читается** (CLAUDE.md флота).

Границы ролей (не дублировать): dispatcher *смотрит и даёт guarded-действия
человеку*, Robin *объясняет*, steward *гейтит*, conductor *планирует и
управляет*. Цикл планирования один — conductor; действия из UI dispatcher по
очереди conductor вызывают conductor, а не второй управляющий цикл.

## 2. Роадмап

### 2.1 Файл

`ai-orchestrators-workspace/roadmap.toml` — рядом с `epics.toml`, читается с
`origin/<default>` зонтика, правится PR-ом (история смены приоритетов в git).
Для разового прогона — `--roadmap <path>` (локальный файл; такой прогон
всегда уровня 0).

```toml
# roadmap.toml — порядок работ. Владелец: Andrei. Порядок [[focus]] = приоритет.
schema_version = 1
updated      = "2026-09-29"
autonomy     = 0                          # потолок, 0..3
writer_host  = "vps-conductor"            # управляющий писатель (I8)
writer_since = "2026-09-29T12:00:00Z"     # момент назначения (§5.5)

[[focus]]
epic = "eco.dark-factory"
goal = "todo://devtools/bundle-docs-as-oracle"   # необязательно: веха

[[focus]]
epic     = "eco.governance-plane"
autonomy = 1                      # необязательно; по умолчанию = autonomy файла
pull_prerequisites = false        # необязательно; true — фоновые предпосылки
                                  # этого фокуса запускаются без допуска (§2.4)

[parked]
epics = ["eco.research-bench"]

[limits]                          # необязательно
max_writes_per_run   = 20         # 1..200
max_launches_per_run = 2          # 0..10
max_open_prs_per_repo = 2         # 0..10 — открытая работа conductor на репо
worker_timeout_min   = 45         # 5..180 — дедлайн одного worker'а
run_timeout_min      = 55         # 10..240 — дедлайн прогона
max_model_calls_per_run = 20      # 0..200
max_prerequisite_launches_per_run = 1  # 0..10 — бюджет pull_prerequisites
stale_after_days     = 3          # 1..60
renudge_after_days   = 7          # 1..60
```

### 2.2 Валидация

Ошибки (`RM-INVALID`): неизвестный `schema_version`; `epic`, которого нет в
`epics.toml`; эпик дважды в `focus` ∪ `parked`; эпик со статусом `done` в
`focus`; `goal` не вида `todo://<repo>/<id>`; `autonomy` вне 0..3; лимит не
целое или вне диапазона; `writer_host` пуст; `writer_since` не RFC 3339 UTC.
При `RM-INVALID` прогон продолжается на уровне 0 **без ранжирования**, снимок
пишется, код выхода 4 (§7.2).

Предупреждения: `goal`, которого нет ни в одном TODO (`RM-GOAL-MISSING`);
эпик `paused` в `focus` (`RM-FOCUS-PAUSED`).

### 2.3 Классы эпиков

Собственный класс узла — по его эпику: **фокус** (в `[[focus]]`, ранг =
позиция), **отложен** (в `[parked]`), **фоновый** (прочие). Узел без `@epic`
— фоновый. Класс не меняется от протекания приоритета (§4.2): ранг
наследуется, класс — нет.

### 2.4 Уровень на действие

- Потолок прогона `run_level`: `min(--level, roadmap.autonomy)`, если хост —
  действующий управляющий писатель (§5.5); иначе 0. Также 0 при `--roadmap`,
  `partial`, `RM-INVALID`, `ID-MISMATCH`. Ручной вызов без `--level` — 0;
  таймер передаёт `--level 3`, т.е. ограничивает только роадмап.
- Уровень позиции:
  - собственный класс **фокус**: `min(run_level, focus.autonomy)`;
  - **фоновый** с унаследованным рангом фокуса F (предпосылка фокуса):
    `min(run_level, F.autonomy)`, если у F `pull_prerequisites = true` —
    запуск без допуска в пределах `max_prerequisite_launches_per_run`;
    иначе `min(run_level, F.autonomy, 2)`, `launch` — по допуску (§5.8).
    Строгий вариант — значение по умолчанию первой версии; включение
    `pull_prerequisites` — правка роадмапа владельцем;
  - **отложенный** с унаследованным рангом: `min(run_level, F.autonomy, 2)`;
    `launch` — **только** по допуску владельца (отложенность — сознательное
    решение не заниматься работой сейчас; `pull_prerequisites` на него не
    действует);
  - **фоновый без ранга**: `min(run_level, 1)` — работу не запускает;
  - **отложенный без ранга**: 0;
  - **запрос `kind: report`** (§6.1): `min(run_level, 2)` — сообщение о
    неисправности идёт в intake адресата без ранга.

## 3. Единый граф

### 3.1 Узлы и источники

| Узел | Идентификатор | Источник |
|---|---|---|
| пункт плана | `todo://<repo>/<id>` | `TODO.md` с `origin/<default>` каждого репо-цели (§8.2), пакет `plan-fields` (пин в `pyproject.toml`) |
| issue | `<repo>#<N>` | `gh` |
| PR | `<repo>!<N>` | `gh` |

Набор репо-целей — репо `workspace-manifest.toml` зонтика **плюс сам
зонтик** (его в манифесте нет). На пишущем хосте клоны ведёт conductor:
`clone_fleet.py` для отсутствующих, затем `git fetch` каждого (ошибка fetch →
`error` → `partial`).

**Загрузка GitHub в два шага.** (1) Обнаружение: поиск по владельцу флота —
все открытые issues/PR, с пагинацией до конца (окно закрытых не используется:
замер 2026-09-29 — 1310 закрытых за 30 дней, больше потолка поиска в 1000, и
граф был бы `partial` всегда; закрытые узлы, на которые кто-то ссылается,
приходят шагом 2 независимо от возраста — rev 10); ответ с
`incomplete_results` или упёршийся в потолок поиска → `partial`.
(2) Дочитывание: каждый узел, на который ссылается любое ребро §3.2 (включая
`@blocked_by:<repo>#<N>` в TODO), загружается адресно **независимо от
возраста и состояния**; тела и комментарии — полностью, с пагинацией.
Недогруженный узел → `partial`. Отсутствие в окне поиска не означает
отсутствия объекта.

### 3.2 Рёбра

Ориентация единая: **от зависящего к предпосылке** (`A → B` = «A ждёт B»).

| Тип | Из чего | Участвует в |
|---|---|---|
| `depends_on` | `@blocked_by:todo://…`; `@blocked_by:<repo>#<N>`; ждущий пункт отправителя → запрос (`from:`, §6) | готовность, циклы, протекание ранга |
| `accepted_as` | запрос/inbox-issue → пункт TODO адресата при действующей связи принятия (§6.3) | склейка: запрос и пункт — один узел работы |
| `implements` | PR → issue (`closingIssuesReferences`); PR → пункт (`@id:<id>` в теле PR; ветка поколения `conductor/work/<repo>/<id>/g<n>`, §5.9) | состояние работы узла (§3.5); не ожидание |
| `mentions` | свободные `repo#N`, `todo://` в прозе тел и комментариев | только объяснения; предложение оформить — вопрос владельцу (§5.1) |

Эпик — атрибут узла (`@epic` пункта; для issue/PR — эпик склеенного пункта,
иначе нет), не ребро. Граф dispatcher (`/api/waits`) как источник не
используется.

### 3.3 Вычисления над графом

1. **Готовность.** Узел готов, если все его исходящие `depends_on` ведут в
   узлы в состоянии «выполнено» (§3.4). `A → B → C` при открытом C: готов
   только C.
2. **Циклы** — компоненты сильной связности **только по `depends_on`**
   (`GR-CYCLE`, error). Пинг-понг обнаружим, когда обе стороны оформлены
   структурно; неоформленная сторона видна как `GR-WEAK-EDGE` — честная
   граница обнаружения, названная явно.
3. **Листья.** Для каждой вехи и каждого фокуса — спуск по `depends_on` до
   готовых узлов; `actor` и `need` — по таблице §5.2.
4. **Отгружено, но не закрыто** (`GR-SHIPPED-OPEN`) — только при действующей
   связи: склеенный пункт `[x]` на `origin/<default>`, а запрос открыт; PR
   влит, закрываемый им issue открыт. Совпадение имени без связи — сверка
   (`GR-SLUG-MATCH`, вопрос владельцу).
5. **Висячее:** запрос `kind: need` без ждущего пункта (`GR-ORPHAN-REQUEST`);
   `depends_on` на пункт, которого нет, без открытого запроса на него
   (`GR-DANGLING-WAIT`).

### 3.4 Состояние предпосылки и активная проверка

Состояние вычисляется каждым прогоном для **всех** открытых ожиданий:

| Узел | Выполнено | Отменено |
|---|---|---|
| пункт | `[x]` на `origin/<default>` | удалён из TODO после того, как существовал (по истории файла) |
| issue | закрыт `state_reason = completed` | закрыт `not_planned` |
| PR | влит | закрыт без мержа |

«Отменено» не разблокирует зависящего: вопрос владельцу («предпосылка
отменена: снять ожидание или найти замену»).

**Ожидание, принадлежащее запросу** — `@blocked_by:todo://<to>/<slug>`
ждущего пункта, названного в `from:` запроса (принадлежность определяется
телом запроса, а **не** действительностью `accepted_as`): выполнено — только
если состояние запроса `done` (связь по **текущей** ревизии, §6.2). В любом
другом состоянии — `changed`, повторный intake, `accept-pending`,
`accepting` — `pending` с `reason: request_not_done`, даже если пункт
`[x]`. Это же вычисление выполненности используют `notify_satisfied` и
`todo_hygiene_pr` — отдельной проверки у них нет, поэтому старый `[x]` не
снимает ожидание изменённого запроса ни одной записью.

**Условия `@trigger:"…"`** — дополнительная предпосылка пункта:
структурное — код; формы (значение `@trigger` целиком): `date>=YYYY-MM-DD`
(дата наступила по UTC) и `exists:<repo>:<path>` (путь есть на
`origin/<default>` репо; путь с сегментом `v<N>` при наличии соседнего
`v<M>`, `M > N`, и отсутствии `v<N>` — `unknown / version_mismatch`);
любой другой текст — проза. Проза — `unknown` до среза 2, в срезе 2 — край модели: перевод в структурное
условие (предложение владельцу) или оценка по коду и коммитам продюсера с
цитатой. Модельный `satisfied` — совет; записи по нему — только уровень 2.

Вердикт ожидания: `satisfied | pending | unknown` с `reason` и `evidence`
(SHA / URL / путь). Ждали `…/v1`, есть `…/v2` без `v1` — `unknown`,
`reason: version_mismatch`.

**Застой.** `pending` дольше `stale_after_days` и у предпосылки нет движения
(коммит с её `@id` в сообщении, PR с `implements` на неё, новый комментарий
в её треде) — событие `stale`, действие `nudge`. Пинок ранг не повышает.

Предыдущий снимок используется только для отчёта «что изменилось»; ни одно
действие от него не зависит (I7).

### 3.5 Состояние работы узла

Для открытого пункта — по рёбрам `implements` и истории поколений субъекта
`work/<repo>/<id>` (§5.9); первое совпадение сверху:

| Состояние | Признак | Следствие |
|---|---|---|
| `in_review` | открытый PR с `implements` на узел (любого автора) | новый запуск запрещён; `need` — по PR (§5.2) |
| `in_flight` | последнее поколение — `claimed`, либо `abandoned` с записанным преемником, которого ещё нет | новый запуск запрещён; §5.6 восстановление / §5.9 доведение перехода |
| `delivered` | последнее поколение — `merged`, пункт открыт | сверка результата: вопрос владельцу с вариантами `close-item` (работа завершена, забыли закрыть — бухгалтерская правка `[x]` через `todo_hygiene_pr`, без worker), `more-work` (допуск на конкретное следующее поколение `g<n+1>`), `unknown` (показать неопределённость, ничего не делать) |
| `rejected` | последнее поколение — `rejected` | `decide`: «повторить / оставить» (повтор — только по допуску) |
| `idle` | поколений нет, открытого PR нет | кандидат по §4.1 |

## 4. Порядок работ

### 4.1 Кандидаты

Готовые (§3.3.1) открытые узлы вне циклов в состоянии работы `idle`; PR —
кандидаты по своему `need`.

### 4.2 Протекание приоритета

Ранг узла = минимальный ранг фокуса среди собственного эпика и эпиков всех
узлов, которые **транзитивно зависят** от него (обратный обход `depends_on`).
Лист отложенного эпика, от которого зависит веха фокуса 1, получает ранг 1;
класс остаётся «отложен».

### 4.3 Ключ сортировки

1. ранг (меньше — выше; без ранга — в конце);
2. на пути к `goal` своего фокуса ранга;
3. число узлов, транзитивно зависящих от него (больше — выше);
4. возраст самого старого ожидания на нём (старше — выше);
5. идентификатор узла.

У каждой позиции `why`: откуда ранг и через какую цепочку, сколько
разблокирует, веха. Пример:
`rank 1 via devtools/bundle-docs-as-oracle → spec-runner#603; unblocks 3`.

## 5. Политика и действия

### 5.0 Единый протокол действия

Каждое действие — запись плана:
`{subject, revision, evidence, permission, preconditions, expected}` —
субъект (узел/запрос/поколение), его ревизия, доказательства, на которых
основано решение, разрешение (уровень позиции + допуск, если нужен),
предусловия и ожидаемое удалённое состояние. Планировщик выдаёт такие
записи; **один исполнитель** проводит каждую через одни и те же шаги, и
восстановление (§5.6, §5.9, §6.2) идёт тем же путём:

1. **authorize/revalidate** — непосредственно перед **каждым** побочным
   эффектом: перечитать роадмап с `origin` (писатель §5.5, `autonomy`,
   фокусы, `F.autonomy`, лимиты) и пересчитать уровень; перечитать субъект
   на GitHub/`origin` и сверить ревизию и доказательства; проверить, что
   допуск всё ещё действителен (§5.10). Изменился любой значимый вход →
   действие снимается (перепланируется следующим прогоном), остальные
   продолжаются; снят писатель или `autonomy` стал ниже уровня действия →
   записи прогона прекращаются.
2. **write** — одна запись с маркером (§5.4).
3. **verify** — перечитать цель и сверить с `expected`; расхождение —
   исход «неопределённо» (§5.4).

Остаточная гонка между последним чтением и записью там, где API не даёт
условной мутации, признаётся и не маскируется: атомарного снимка всего флота
conductor не обещает.

менять

**Делегируемость `implement`** (все условия, иначе `decide` владельцу):

1. `owner_ref` пункта (`plan-fields`): `repository:<repo>` или
   `github_user` = владелец флота. `github_user` другого человека,
   `github_team`, `TBD`, отсутствие — не делегируемо.
2. Класс работы (машинно, до модели):
   - **запрещено этому контуру** — контекст-пак `todo_context` называет путь
     authority-root целевого репо: не делегируется ни при каком допуске;
   - **решение человека** — принятие или изменение политики, подпись,
     одобрение, новое ADR, новая версия контракта: слова `sign-off, подпис,
     approve, одобр, approval-policy, утверд, новая версия контракта, new
     contract version` в заголовке/теле узла или склеенного запроса, либо
     путь под `prograph-vault/authored/decisions/` или `.github/`;
   - **исполнение принятого решения** — всё прочее, включая упоминания `ADR`
     и `контракт`/`contract` без признаков выше («исправить тест реализации
     утверждённого контракта» — обычная работа);
   - эпик узла не `active` → решение человека.
   Слова — **сигнал**: в первой версии сигнал блокирует консервативно, и
   каждый блок пишется в показатели (§10) с причиной, чтобы по ложным
   отказам уточнять список; модельная доклассификация сигнала — кандидат
   следующего среза, не этой спеки.
3. Репо в контуре: не `sdd-framework`, есть `.git`.

Проверка диффа после worker (§5.6) — **дополнительная**, не заменяет п. 2.

### 5.4 Протокол действий

Для каждой записи — удалённый объект с устойчивой идентичностью, маркер,
проверка результата. Маркер — скрытый `<!-- conductor:<kind>:<key> -->`.

| Действие | Удалённый объект | Ключ / идентичность | Где маркер | Завершено, когда |
|---|---|---|---|---|
| `close_shipped` | комментарий + состояние issue | `close:<node>:<evidence-sha>` | комментарий | issue закрыт `completed` и маркер есть |
| `notify_satisfied` | комментарий в адресе | `sat:<wait-id>:<evidence-sha>` | комментарий | маркер в каждом адресе |
| `nudge` | комментарий | `nudge:<wait-id>:<окно>`, окно = `floor(days_stale / renudge_after_days)` | комментарий | маркер есть |
| `pr_nudge` | комментарий в PR | `prnudge:<pr>:<head-sha>:<окно>` | комментарий | маркер есть |
| `todo_hygiene_pr` | поколение субъекта `hygiene/<repo>/<change-sha8>`, `change-sha` — хэш набора нужных преобразований (§5.9) | ветка поколения | тело PR | все преобразования набора есть на `origin/<default>`; PR открыт → ждать; `rejected` → вопрос владельцу; новый набор преобразований → новый субъект (старый открытый PR conductor закрывает как заменённый — это его собственный PR) |
| `owner_queue` | тело закреплённого issue; комментарий на новый вопрос | тело — полная перезапись; комментарий — `q:<question-id>` | тело; комментарий | тело равно вычисленному; маркер каждого нового вопроса есть |
| `request_triage` | метки + комментарий | `triage:<request>:<check-rev>:<переход>` | комментарий | метка = вычисленному состоянию, маркер есть |
| `answer_fact` | комментарий-ответ | `ans:<question-key>` (§5.7) | комментарий | маркер есть |
| `request_intake` | комментарий `intake-start`, комментарий `intake-verdict` (несёт вердикт, `todo_line` целиком и номер поколения `g`), для `accept` — PR поколения субъекта `accept/<request>/<body-rev>` | `intake:<request>:<body-rev>:<n>`, `n` — порядковый номер intake по этой ревизии | комментарии; тело PR | состояние §6.2 вышло из семейства `intake`/`accept-pending` |
| `request_rename` | `slug:` в теле запроса | желаемое значение — `slug` последнего вердикта `accept` | — (сверка значения) | `slug:` тела равен `slug` вердикта |
| `launch` | поколение субъекта `work/<repo>/<id>` (§5.9) | ветка поколения | коммит-заявка, тело PR | PR поколения существует |

- **Поиск маркеров** — во всех комментариях цели и в теле PR (с
  пагинацией); PR ищется по `head=<ветка>`.
- **Довести недоделанное.** Маркер шага есть, следующий шаг не выполнен →
  следующий прогон выполняет его, если предусловие ещё истинно.
- **Неопределённый результат** (таймаут/обрыв записи): в этом прогоне шаг не
  повторяется. Следующий прогон (≥ 1 ч, таймер) ищет маркер или объект по
  идентичности; нашёл — выполнено; нет — повторяет. Для объектов с
  идентичностью по содержимому (ветка поколения/попытки, PR по `head` этой
  ветки, состояние issue, тело очереди) повтор не создаёт второго объекта;
  для комментариев остаточный риск —
  задержанная запись, пришедшая позже часа, — принимается и называется явно.
- **Сбой** шага два прогона подряд → вопрос владельцу.

### 5.5 Писатели и лимиты

Все управляющие записи conductor выполняются **только токеном App** (иных
учётных данных для записи во флот conductor не использует, §5.1) — поэтому
отзыв ключа App отзывает всю его пишущую способность.

**Управляющий писатель** (все записи §5.1, кроме `publish_snapshot`) — хост,
на котором одновременно: (1) имя хоста = `writer_host` роадмапа с
`origin/<default>` зонтика; (2) `now ≥ writer_since + 65 мин`; (3) ключ App
действует (проверка §8.2). Перед **каждым** шагом записи условия
перепроверяются вместе со всем разрешением (§5.0, шаг 1); нарушено → прогон
прекращает записи.

**Передача писателя** (с гарантированным отзывом):

1. Владелец создаёт новый ключ для нового хоста (GitHub не даёт удалить
   последний ключ App, поэтому новый — первым), затем **удаляет приватный
   ключ** старого хоста. С момента удаления старый хост не может выпустить
   новый токен — независимо от его доступности.
2. Владелец правит `writer_host` и `writer_since = <момент удаления ключа>`
   PR-ом в зонтик и кладёт новый ключ на новый хост.
3. Новый хост начинает писать не раньше `writer_since + 65 мин` — после
   истечения любого токена, выпущенного старым хостом (срок жизни токена
   установки — 1 ч, плюс 5 мин запаса на расхождение часов).
   `writer_since` — момент **подтверждённого** удаления ключа в настройках
   App (не удаления PEM-файла на сервере).

У каждого хоста — свой ключ App (App допускает несколько ключей), поэтому
отзыв одного не трогает другие. `flock` на хосте исключает пересечение его
собственных прогонов (занят → выход `skipped`, код 0).

**Матрица записей:**

| Команда | Управляющие записи во флот | `publish_snapshot` |
|---|---|---|
| `status`, `why`, `plan` | никогда | никогда |
| `run` на управляющем писателе | по уровням | да, если `publish = true` в конфиге хоста |
| `run` на любом другом хосте | никогда (уровень 0) | да, если `publish = true` |

`publish_snapshot` не зависит от уровня, `partial`, `ID-MISMATCH` (снимок
несёт `graph_state` и находки) и выполняется **учётными данными git самого
хоста** в vault — как `dispatcher publish-snapshot` сегодня, не токеном App.

**Лимиты:** запись = каждый мутирующий вызов GitHub/`git push` во флот
(`max_writes_per_run`); запуск = каждый прогон worker, включая intake
(`max_launches_per_run`), и не более одного запуска на репо за прогон.
Остаток — в следующий прогон, находка `RUN-BUDGET`. `publish_snapshot` в
лимиты не входит.

### 5.6 Стадия доставки `launch`

`launch` применяется **только к пунктам TODO** и использует только
`todo_worker.py`; работа по issue попадает сюда через пункт (intake или
владелец). Worker намеренно не публикует и не коммитит («publish phases
absent by construction») и остаётся таким. Коммитит и публикует conductor.

1. **Заявка.** Новое поколение `g<n>` субъекта `work/<repo>/<id>` разрешено
   правилами §5.9. Свежий `git worktree` целевого репо от `origin/<default>` в
   `out/conductor/attempts/<repo>/<id>/g<n>/`; пустой коммит
   `conductor: claim <id> g<n>` на ветку `conductor/work/<repo>/<id>/g<n>`
   пушится **до** запуска worker'а.
2. **Worker** `todo_worker.py --mode execute` в этой рабочей копии,
   окружение без токенов (§8.3). Ворота — `execute_allowed` из
   `todo_context` (достаточность требования; не разрешение на публикацию).
   Результат worker'а (его JSON) сохраняется в каталоге попытки.
3. **Допустимый исход.** Публикуется только при: код выхода 0,
   `outcome = done` (схема `todo_worker.py`), непустом диффе. `blocked`,
   `needs_human`, ошибка или пустой дифф → ветка и рабочая копия остаются,
   вопрос владельцу с результатом worker'а.
4. **Проверка диффа** (код): только внутри рабочей копии; ни одного пути
   authority-root целевого репо, `contracts/`, `.github/`. Провал → как п. 3.
5. **Рабочий коммит (conductor) → push → PR** от App; сообщение рабочего
   коммита `conductor: work <id>` (отличимо от заявки); тело PR с `@id:<id>`
   и маркером. Дальше обычный контур ревью/мержа.

**Восстановление** (`in_flight`, уровень 3). Сверяются: голова удалённой
ветки (заявка или рабочий коммит), локальная ветка попытки, результат
worker'а. Первое совпадение сверху:

| Состояние попытки | Действие |
|---|---|
| PR поколения есть | ничего: открытый — `in_review`, закрытый — поколение терминально (§5.9) |
| удалённая голова — рабочий коммит, PR нет | п. 5, только PR |
| локальный рабочий коммит есть, удалённая голова — заявка | push рабочего коммита, затем PR |
| рабочая копия с диффом и результат worker'а есть, рабочего коммита нет | продолжить с п. 3 |
| результат worker'а есть с исходом, отличным от допустимого | вопрос владельцу (как п. 3), если его ещё нет |
| каталога попытки на хосте нет или результата worker'а нет | вопрос владельцу «попытка потеряна: перезапустить?»; автоматического повтора нет |

Повторный запуск worker'а по узлу — только по допуску владельца на этот
вопрос (§5.8), по таблице переходов §5.9 (строка «`claimed`, попытка
потеряна»).

### 5.7 Адреса, вопросы соседей, вопросы владельцу

**Адрес доставки** зависящего узла: для issue — его тред; для пункта —
треды всех запросов, склеенных с ним или исходящих от него; для TODO-only
пункта без запросов — `todo_hygiene_pr` в его репо (PR — и уведомление, и
правка плана).

**Вопрос соседу** (вход `answer`) — комментарий или тело issue со строкой
`ask: <repo>`: адресат указывается структурно, по автору не угадывается
(один аккаунт может говорить за несколько репо); `<repo>` обязан быть
среди репо-целей (иначе — вопрос владельцу). Вопрос без `ask:` — не вход
`answer_fact`: conductor может **предложить** адресата в очереди владельца,
но от имени угаданного репо не отвечает. Ответ ссылается на исходный
комментарий (`question-key`). Строку `ask:` вводит волна `CLAUDE.md` (§9).
Идентичность вопроса `question-key = (issue, comment-id | body,
sha256(текста))`. Ответ — в том же треде, ссылкой на комментарий, с
контекстом **репо-адресата** (рабочая копия с `origin/<default>`).
Отредактированный вопрос — новый ключ: старый ответ остаётся, новый
публикуется. Несколько вопросов в одном комментарии — один ключ, один ответ
на все.

**Вопрос владельцу** задаётся только по позиции **с рангом** (связанной с
фокусом, §4.2); `decide` без ранга виден в выдаче, но в очередь владельца не
попадает — очередь не должна переписывать в вопросы весь бэклог (§10,
показатели). `question-id = sha256(kind, subject, evidence,
варианты по порядку)[:8]` (изменение вариантов или их порядка — новый вопрос,
старое «2» не получает нового смысла);
закреплённое issue очереди в зонтике (метка `owner-queue`, автор —
conductor) перечисляет вопросы: ссылка, вопрос в одну строку, варианты со
**стабильными именами** (`retry`, `delegate`, `close-item`, `more-work`,
`keep`, …) и вариантом по умолчанию, что разблокирует ответ. Упоминание
владельца в комментарии — механизм уведомления GitHub; доставка зависит от
его настроек.

### 5.8 Ответ владельца и допуск

Владелец отвечает **комментарием в очереди**: `Q-<id>: <имя варианта>`
(например `Q-a81c2f: retry`); номер варианта тоже допустим — набор и порядок
вариантов входят в `question-id`. Проверка автора и версии — §5.10. Ответ
действителен, пока `question-id` тот же (изменились доказательства →
новый вопрос, старый ответ не применяется). Свободный текст **не является
разрешением**: conductor может его понять и ответить предложением
(«Понял как разрешение повторить запуск; для исполнения подтвердите
`Q-a81c2f: retry`»), вопрос остаётся открытым до структурного ответа.

Допуск относится к **конкретному** следующему поколению (`g<n+1>`, §5.9).
Техническое доведение уже разрешённой попытки после обрыва (§5.6, строка
«`abandoned` с записанным преемником») нового допуска не требует.

Ответ, выбирающий действие, — **допуск**: разрешение ровно на это действие
над этим узлом этой версии. Допуск снимает только ограничение, названное в
вопросе:

- запрет `launch` для фонового/отложенного класса (§2.4);
- отсутствие автоматического повтора потерянной попытки (§5.6) и нового
  поколения после `rejected` / `delivered` (§5.9);
- смысловое оформление `mentions` (§5.1);
- делегируемость по `owner_ref`/признакам решения (§5.2) — вариант «делегировать».

Допуск **не** поднимает `run_level` выше роадмапа и не снимает абсолютные
запреты §5.1. Действие, требующее уровня выше текущего, остаётся в очереди
с пометкой «разрешено, ждёт уровня».

### 5.9 Поколения доставки

Каждый PR conductor доставляет **субъект**: `work/<repo>/<id>` (`launch`),
`accept/<request>/<body-rev>` (принятие запроса), `hygiene/<repo>/<change-sha8>`.
Попытка доставки субъекта — **поколение** `g<n>` на ветке
`conductor/<субъект>/g<n>`.

- **История** субъекта — все PR автора `conductor[bot]` в целевом репо в
  любом состоянии (`state=all`, с пагинацией) с головой под
  `conductor/<субъект>/`, плюс удалённые ветки под этим префиксом без PR.
  Закрытые PR GitHub хранит и после удаления ветки, поэтому история не
  теряется от чистки веток.
- **Состояние поколения:** `claimed` (ветка есть, PR нет), `open`, `merged`,
  `rejected` (закрыт без мержа). Последние два — терминальные.
- **Терминальное `abandoned`**: ветка поколения без PR, голова которой —
  коммит `conductor: abandon g<n>`. conductor ветки поколений **не удаляет**:
  без PR ветка — единственная запись поколения в истории, и номер не должен
  сбрасываться.
- **Переходы.** У субъекта не больше одного нетерминального поколения;
  question-id допуска включает номер последнего поколения (§5.8):

| Последнее поколение | Что разрешено | Условие |
|---|---|---|
| нет | создать `g1` | действие разрешено уровнем и политикой |
| `claimed`, попытка жива (§5.6) | продолжить **то же** поколение | — |
| `claimed`, попытка потеряна | запушить `conductor: abandon g<n> -> g<n+1> permit Q-<id>` → `abandoned` с записанным преемником, затем создать `g<n+1>` | допуск «перезапустить» |
| `abandoned` с записанным преемником, преемника нет (переход прерван) | создать записанный `g<n+1>` по допуску из коммита | тот же допуск (доказательства не изменились: преемник записан до изменения) |
| `open` | ничего (ждать) | — |
| `rejected` / `abandoned` | создать `g<n+1>` | допуск «повторить» |
| `merged`, субъект `work/…`, пункт открыт (`delivered`) | создать `g<n+1>` | допуск «нужна ещё работа» |
| `merged`, иначе | ничего: `work/…` при закрытом пункте — готово; `accept/…` — связь принятия (§6.3); `hygiene/…` — набор доставлен | — |

### 5.10 Управляющие сообщения и их доверие

Состояние протокола живёт в GitHub (комментарии, ветки, PR) — это его
хранилище, поэтому у него есть контракт, а не только строковые маркеры.
Один декодер управляющих событий; событие действительно только при всех
условиях:

| Событие | Формат | Допустимый автор | Дополнительно |
|---|---|---|---|
| маркер conductor (`intake-start`, `intake-verdict`, `triage`, `sat`, `close`, …) | `<!-- conductor:v1 <kind> <key=value …> -->` | только `conductor[bot]` | комментарий не редактировался после создания (`updated_at = created_at`); иначе событие недействительно, вопрос владельцу |
| ответ владельца | `Q-<id>: <номер>` в очереди | только логин владельца флота | учитывается текст на момент чтения; уже исполненный ответ повторно не читается |
| два ответа на один `Q-<id>` с разными номерами | — | — | не исполняется ни один; conductor просит подтвердить |
| ответ на `Q-<id>`, которого нет в текущей очереди | — | — | игнорируется (вопрос устарел) |
| коммит поколения (`claim`, `work`, `abandon`) | сообщение `conductor: <kind> …` | коммиттер — App | иначе поколение не признаётся (`GR-FOREIGN-GENERATION`, вопрос владельцу) |

Маркер правильного вида от другого автора, скопированный маркер, удалённый
комментарий — не события. Полномочия даёт только автор + формат + версия
схемы, текст сам по себе — нет.

## 6. Запросы между репо (узел запросов)

### 6.1 Канал и полномочия

Репо (его сессия/агент), которому нужно что-то от соседа, заводит **issue в
зонтике** с меткой `request`:

```
kind: need | report
slug: <предлагаемый @id у адресата>
from: <repo>#<@id ждущего пункта>      # для kind: need обязательно
to: <repo>
<проза: что нужно и зачем>
```

`kind: report` — сообщение о неисправности без ждущего пункта (сохраняется
возможность ADR-ECO-006); `GR-ORPHAN-REQUEST` и шаг ранга к нему не
применяются.

**Доверенные авторы:** владелец, `ai-prosto`, `conductor[bot]`,
коллаборатор с `write` на репо `from` (API коллабораторов). Иной автор →
`triage` владельцу.

Ждущий пункт отправителя несёт `@blocked_by:todo://<to>/<slug>`; пока запрос
открыт, это ребро не `GR-DANGLING-WAIT` (правка `check-plan-fields.py`, §9).

**Ревизия требования** `body-rev = sha256(kind, from, to, проза)` —
байты содержания сохраняются, нормализуются только концы строк (LF) и
хвостовые пробелы строк (кодовые блоки и литералы не схлопываются); в
маркерах хранится полный digest, короткие 8 символов — только для показа. `slug:` в
ревизию **не входит**: это имя, а не содержание, и переименование по
протоколу D4 не меняет ревизию. Меняется только при правке содержания, не от
меток/комментариев. **Ревизия механической проверки** `check-rev` — тот же
хэш по всем полям, включая `slug`: исправление одного имени заново открывает
механическую проверку, не трогая принятие.

### 6.2 Функция состояния

Состояние вычисляется каждым прогоном **по первому совпадению сверху**.
**Последний вердикт** — самый поздний маркер `intake-verdict` любой ревизии;
он заменяет все предыдущие. Маркеры `intake-start` учитываются только для
текущей `body-rev`, маркеры механического отказа — только для текущей
`check-rev`. Метка — кэш результата.

| # | Состояние | Условие |
|---|---|---|
| 1 | `intake` | есть `intake-start` текущей ревизии позже последнего вердикта |
| 2 | `changed` | действующая связь принятия, её ревизия ≠ текущей (выполненный старый пункт **не** закрывает изменённый запрос) |
| 3 | `done` | действующая связь принятия **по текущей ревизии**, склеенный пункт `[x]` |
| 4 | `accepted` | действующая связь принятия по текущей ревизии, пункт открыт |
| 5 | `accepting` | последний вердикт — `accept` текущей ревизии с поколением `g`, PR поколения `g` открыт |
| 6 | `accept-rejected` | то же, поколение `g` — `rejected` |
| 7 | `accept-pending` | последний вердикт — `accept` текущей ревизии с поколением `g`, поколения `g` нет или оно `claimed` |
| 8 | `needs-human` | последний вердикт — `needs_human` текущей ревизии |
| 9 | `declined` / `countered` | последний вердикт текущей ревизии — `decline` / `counter` соответственно |
| 10 | `needs-revision` | маркер механического отказа текущей `check-rev` |
| 11 | `deferred` | `kind: need`, у ждущего пункта нет ранга, или его эпик отложен |
| 12 | `new` | иначе (в т.ч. последний вердикт — по старой ревизии без действующей связи) |

Действия по состоянию:

| Состояние | Действие |
|---|---|
| `new` | механическая проверка (поля, `to` среди репо-целей, ждущий пункт для `need`, нет открытого дубля `(to, slug)`); провал → маркер отказа (`needs-revision`); успех → `request_intake` (уровень 2) или `owner_queue` (< 2). Пункт `todo://<to>/<slug>` уже существует без связи — `GR-SLUG-MATCH`, intake решает, та ли это работа |
| `needs-revision` | ждать правки любого поля (новая `check-rev` → `new`) |
| `countered` | ждать правки содержания (новая `body-rev` → `new`) |
| `deferred` | ждать ранга; эпик отложен — вопрос владельцу |
| `intake` | маркер `intake-start` старше 2 ч без вердикта → повтор intake (intake только читает, повтор безопасен) |
| `accept-pending` | `request_rename` при несовпадении slug; затем довести **то же** поколение `g` из `todo_line`, сохранённой в комментарии-вердикте: ветка есть — проверить её, при необходимости коммит/push; затем PR — **без** нового intake и вызова модели |
| `accepting` | ждать мержа |
| `accept-rejected` | вопрос владельцу: «принять иначе (новый intake) / оставить»; ответ «новый intake» — допуск: новый intake, его вердикт `accept` получает поколение `g+1` (§5.9) |
| `accepted` | отслеживание §3.4 |
| `changed` | вопрос владельцу: принятая работа была по старой ревизии — «переоценить (новый intake) / оставить»; новый intake заменит вердикт, связь по новой ревизии вытеснит старую |
| `needs-human` | вопрос владельцу с `reason` intake; ответ «принять / отказать» исполняется как вердикт |
| `declined` | вопрос владельцу «закрыть?»; закрытие `not_planned` делает владелец руками (§5.1) |
| `done` | `close_shipped`; `todo_hygiene_pr` у отправителя снимает выполненный `@blocked_by` |

### 6.3 Intake и связь принятия

Intake — worker в режиме `plan` (без записи) в свежей рабочей копии адресата;
контекст: его `CLAUDE.md`, `TODO.md`, `epics.toml`, `roadmap.toml`, тело
запроса. Вывод по схеме:

```json
{"verdict": "accept | decline | counter | needs_human",
 "slug": "…", "epic": "…", "reason": "…", "todo_line": "…"}
```

- `accept` → код проверяет `todo_line` парсером `plan-fields`: `@id` = `slug`
  вывода, `@epic` в реестре, `@source-ref:ai-orchestrators-workspace#<N>`
  (существующий тег провенанса), **чекбокс открыт** `- [ ]`. Не прошла →
  `needs_human`. Принятие новой ревизии запроса, чей пункт уже `[x]`,
  **переоткрывает** пункт той же PR-правкой (тот же `@id`, строка
  обновлена). Если intake считает, что v2 уже покрыта сделанным, — вердикт
  `needs_human` с доказательством покрытия, решает владелец.
- **Выполнено по ревизии** — пункт `[x]` на `origin/<default>` **и**
  коммит, поставивший `[x]`, — потомок мерж-коммита PR принятия этой
  ревизии. `[x]`, поставленный до принятия, выполнения текущей ревизии не
  доказывает; строки `done` (§6.2) и выполненность ожидания (§3.4) читают
  именно это условие. Прошла → PR
  conductor в TODO адресата; в теле PR и в комментарии-вердикте — принятая
  `body-rev`.
- **Связь принятия действует**, когда одновременно: пункт с
  `@source-ref:ai-orchestrators-workspace#<N>` есть на `origin/<default>`
  адресата, и **последний** вердикт `accept` в треде запроса — той
  `body-rev` и того поколения, PR которого влит (субъект
  `accept/<request>/<body-rev>`).
  Совпадение slug без `@source-ref` связью не является. Правка тела после
  принятия → состояние `changed`.
- Принят под другим slug → `request_rename` сверяет `slug:` тела со
  `slug` последнего вердикта `accept` (протокол переименования ADR-ECO-006
  D4; ревизия от этого не меняется, так что прерванное переименование
  доводится следующим прогоном той же сверкой), и `todo_hygiene_pr` у
  отправителя переводит `@blocked_by` на новое имя.
- `decline` → `declined`, `counter` → `countered`: вердикт комментарием;
  `needs_human` и признаки
  решения → очередь владельца.

### 6.4 Наследие

Открытые inbox-issues в репо (ADR-ECO-006, 9 на 2026-09-29) ведутся тем же
циклом со сдвигом: связь принятия — по правилу ADR-ECO-006 D2 (пункт со
`slug:` запроса), но `close_shipped` по ней **не выполняется** без
`@source-ref` — вместо закрытия вопрос владельцу «похоже отгружено,
закрыть?». Новые запросы — только через зонтик после ADR-ECO-012 и волны
`CLAUDE.md`.

## 7. Выдача и интерфейсы

### 7.1 Снимок

Каждый прогон пишет `out/conductor/<run_id>/snapshot.json` (контракт
`conductor-snapshot/v1`, JSON-схема `devtools/contracts/conductor-snapshot/v1/`):
`host`, `run_id`, `started_at`, `writer` (bool и причина), `roadmap`
(источник, SHA, находки), `run_level`, `sources` (состояние и SHA каждого),
`graph_state`, `nodes` (с состоянием работы §3.5), `edges` (с типом), `waits`
(вердикт, `reason`, `evidence`), `queue` (позиции с `why`, `actor`, `need`,
уровнем и действием), `cycles`, `findings`, `actions` (план; журнал шагов с
маркерами и исходами), `owner_questions` (с `question-id`, вариантами,
допусками), `changes_since_previous` (только для отчёта).

### 7.2 Команды (`conductor.py`, алиасы в `Makefile`)

- `status` — фокусы, верх очереди, циклы, сработавшие/застоявшиеся ожидания,
  вопросы владельцу;
- `why <node>` — цепочка `depends_on` от узла до листьев с `actor`/`need`;
- `plan [--level N] [--roadmap P]` — действия, которые были бы выполнены;
- `run [--level N] [--roadmap P]` — прогон;
- `--selftest` — встроенные проверки без сети (конвенция devtools).

Коды выхода: 0 — прогон выполнен (`complete`, `partial`, `skipped`); 2 —
аргументы CLI не разобраны (снимок не пишется); 3 — не собран ни один
источник; 4 — прогон выполнен деградированно из-за конфигурации
(`RM-INVALID`, `ID-MISMATCH`) — для любой команды; `run` при этом пишет
снимок, `status`/`why`/`plan` снимков не пишут никогда.

Скилл `skills/conductor/` — разговорный режим поверх тех же команд.

### 7.3 Фон и расписание

- **Управляющий писатель (VPS):** systemd-таймер по образцу R16
  (`deploy/conductor/`, пользователь `conductor`), раз в час,
  `run --level 3` (потолок даёт роадмап).
- **Прочие хосты:** launchd/ручной запуск; управляющих записей нет (§5.5).

### 7.4 Публикация снимка и dispatcher

`publish_snapshot` (матрица §5.5) пишет `derived/conductor/<host>.json` в
ветку `derived-snapshots` vault механикой эфемерного `git worktree`, как
`dispatcher publish-snapshot`. Регистрация `derived/conductor/` как пути
нового писателя — изменение authority vault (§9).

dispatcher вендорит `conductor-snapshot/v1` и читает
`origin/derived-snapshots`; одна интеграция даёт:

- веб-панель «Оркестратор»: очередь с `why`, цепочки, циклы, ожидания,
  вопросы владельцу;
- вид в существующем VSCode-расширении dispatcher (`vscode-ext`), `why` из
  контекстного меню;
- read-only MCP-инструменты `conductor_queue`, `conductor_why`.

Кнопки действий — второй срез интеграции; мутации — клик человека.

## 8. Учётные записи и токены

### 8.1 Роли

| Роль | Кто |
|---|---|
| управляющие записи: PR, комментарии, закрытие issues, метки, очередь | GitHub App `conductor` (`conductor[bot]`) |
| ревьюит | `ai-prosto` через `review-pr.sh` (без изменений; conductor не вызывает) |
| мержит | `ai-prosto`, `merge-pr.sh`, контур DarkFactory (без изменений; conductor не вызывает) |
| authority-root, «Мерж: человек» | владелец, `human-merge.sh` (без изменений) |
| публикация снимка в vault | git-учётные данные хоста |

Почему App (решение владельца 2026-09-29): отдельный актор — вопросы агента
приходят владельцу как чужие упоминания, а не как его собственные действия
(о своих GitHub по умолчанию не уведомляет; доставка в любом случае — по его
настройкам); действия агента отличимы в истории; права узкие; токен живёт
час, вечного PAT на VPS нет; отзыв — удалением ключа; ToS «один бесплатный
машинный аккаунт» занят ai-prosto. Лимиты не решают: REST ≥ 5 000
запросов/ч, как у PAT; вторичные лимиты общие; объём прогона — десятки
чтений, единицы записей.

### 8.2 Права и проверка установки

Права App: `contents`, `issues`, `pull_requests` — write; `checks`,
`statuses`, `metadata` — read. Без admin. Установка — на **все репо-цели**:
репо манифеста + зонтик `ai-orchestrators-workspace`.

Перед первой записью прогона (JWT из ключа этого хоста):
`GET /app/installations/{installation_id}` (id — из конфига хоста) —
установка существует, `account.login` = владелец флота; токен выпускается
для этой установки; `GET /installation/repositories` **этим токеном** (с
пагинацией) — покрыты все репо-цели. Ошибка или несовпадение → `ID-MISMATCH`,
уровень 0. Непокрытый репо → записи в него запрещены (`ID-REPO-UNCOVERED`);
непокрытый зонтик → `ID-MISMATCH` (без него нет очереди и запросов).

### 8.3 Разделение окружений

- Токен App передаётся **только** дочерним процессам conductor для его
  записей: `gh` — `GH_TOKEN` в явно собранном окружении; `git push` —
  HTTPS-remote и credential helper с `x-access-token:<token>` (SSH-remote'ы
  для записи не используются). Токен старше 50 мин обновляется перед шагом.
- conductor не вызывает инструменты с учётками ai-prosto и владельца
  (§5.1); права `checks`/`statuses` нужны только для вычисления `need` PR
  по head SHA (§5.2).
- **Изоляция worker и intake — критерий, а не очистка переменных.**
  Удаление `GH_TOKEN`/`GITHUB_TOKEN`/`GH_ENTERPRISE_TOKEN` недостаточно:
  `gh` читает сохранённую авторизацию из `GH_CONFIG_DIR`, git — credential
  helper'ы, ssh — agent. Критерий: процесс worker/intake **не может
  получить** ключ App, токен установки, git- и `gh`-учётные данные хоста,
  ssh-agent и учётные данные публикации снимка, даже если инструкция в
  репо велит опубликовать результат. Реализация (отдельный системный
  пользователь без доступа к этим путям и сокетам либо контейнер с явно
  переданной рабочей копией) — выбор среза 2; проверка — интеграционный
  тест среды: из-под worker'а `gh auth status`, `git push`, чтение ключа и
  ssh-agent — отказ.

Создание App, ключи хостов и установка — **за владельцем**; до неё conductor
работает на уровне 0.

## 10. Тестирование

Ядро детерминировано → фикстуры флота: bare-репо с `origin/<default>` и
отличающейся рабочей копией, JSON ответов `gh`, `roadmap.toml`, `epics.toml`.
GitHub — через интерфейс `Ops` с фейком (паттерн `governance/ops.py`);
модель — фейковый харнесс со схемным выводом; время — инъекцией.

Граф и порядок:

1. `A → B → C`, C открыт → готов только C; C `[x]` → готов B.
2. Пинг-понг, оформленный с обеих сторон → `GR-CYCLE`; одна сторона
   упоминанием → цикла нет, `GR-WEAK-EDGE`.
3. Лист отложенного эпика, от которого зависит веха фокуса 1 → ранг 1;
   на уровне 3 — вопрос владельцу; после допуска при `F.autonomy = 3` —
   `launch`; при `F.autonomy = 2` — «разрешено, ждёт уровня».
4. Делегируемый исполнимый кандидат фокуса на уровне 3 → `launch`, не
   `nudge` (I3).
5. `owner_ref` = `TBD` / другой человек / команда → `decide`, не `launch`;
   заголовок с «sign-off» → `decide` без вызова модели.
6. Открытый PR человека с `implements` на узел → `in_review`, нет `launch`.
7. `[x]` только в рабочей копии → не выполнено.
8. Ссылка на issue 40-дневной давности → дочитан, `complete`; поиск с
   `incomplete_results` → `partial`, уровень 0.
9. Предпосылка закрыта `not_planned` → «отменено», вопрос владельцу.
10. `v1` ждали, есть `v2` → `unknown / version_mismatch`.

Действия и идемпотентность:

11. Условие выполнено, прогон уровня 0, затем уровня 1 → `notify_satisfied`
    во втором.
12. `close_shipped`: комментарий есть, закрытие упало → следующий прогон
    закрывает, второго комментария нет.
13. Пинок: окно 0 → пинок; тот же прогон повторно → нет; окно 1 → второй.
14. Повторный прогон без изменений → ноль записей.
15. `todo_hygiene_pr`: открытый PR поколения → ждать; закрыт без мержа →
    вопрос, поколение не пересоздаётся; изменился набор → новое поколение,
    старый PR закрыт как заменённый; правки на `origin` → завершено.
16. Неопределённый результат записи → повтор только в следующем прогоне.

Запросы:

17. Функция состояния: для каждой из 12 строк §6.2 — фикстура, дающая
    ровно это состояние, и отрицательный двойник, дающий соседнее;
    повторное принятие новой ревизии при открытом пункте → `accepted`, не
    `changed`; вердикт `accept` без PR → `accept-pending` → PR из
    сохранённой `todo_line` без вызова модели; PR принятия закрыт без
    мержа → `accept-rejected`; `needs_human` → `needs-human`.
18. Правка тела после принятия → `changed`, вопрос владельцу.
19. Intake: `todo_line` не проходит парсер → `needs_human`; `accept` → PR
    `accepting`; slug совпал без `@source-ref` → `GR-SLUG-MATCH`; принят под
    другим slug → правка `slug:` + PR у отправителя, `changed` не возникает.
20. `intake-start` старше 2 ч без вердикта → повтор intake.
21. `kind: report` без ждущего пункта → нет `GR-ORPHAN-REQUEST`, не
    `deferred`, intake на уровне `min(run_level, 2)`.

Доставка:

22. Каждая строка таблицы восстановления §5.6 → своё действие (включая
    «локальный рабочий коммит, удалённая голова — заявка» → push, затем PR);
    потерянная попытка → вопрос, без автоповтора.
23. Worker вернул `outcome = blocked` / `needs_human` с непустым диффом →
    нет PR, вопрос; `outcome = done` с пустым диффом → нет PR, вопрос.
24. Дифф трогает authority-root → нет PR, вопрос.

Писатели, токены, владелец:

25. Хост ≠ `writer_host` с `--level 3` → ноль управляющих записей;
    `publish_snapshot` при `publish = true` выполняется.
26. `now < writer_since + 60 мин` → уровень 0.
27. `writer_host` сменился посреди прогона → записи прекращаются со
    следующего шага.
28. Ни на каком уровне conductor не вызывает `merge-pr.sh`, `review-pr.sh`,
    `attest-vendor.sh`, `human-merge.sh` (проверка по журналу `Ops`); готовый

29. Токен не покрывает зонтик → `ID-MISMATCH`.
30. Ответ `Q-<id>: 2` при прежних доказательствах → допуск; при изменившихся
    → не применяется; свободный текст → не исполняется.
31. Допуск на действие уровня выше `run_level` → «разрешено, ждёт уровня».
32. `RM-INVALID` → нерангованная очередь, снимок записан, код 4.
33. Вопрос соседу без `ask:` → не `answer_fact`; с `ask: <repo>` → ответ из
    рабочей копии этого репо.
34. Поколения: PR запуска закрыт без мержа, ветка удалена → узел `rejected`
    (история по закрытому PR), не `idle`; повтор только по допуску → `g2`.
35. PR запуска влит, пункт открыт → `delivered`, вопрос, нет `launch`.
36. Принят v1, пункт `[x]`, тело правлено до v2 → `changed`, не `done`;
    закрытия и снятия ожидания нет.
37. `accept-rejected` → допуск → новый intake `accept` → поколение `g2` →
    `accepting`.
38. Переименование slug прервано после вердикта → следующий прогон
    доводит `request_rename`; `body-rev` не меняется, повторного intake нет.
39. Принят v1, пункт `[x]`, тело правлено до v2 → ожидание отправителя
    `pending / request_changed`; нет `notify_satisfied`, нет hygiene-снятия.
40. Вердикт `accept` с `g1`, ветка запушена, PR не создан → `accept-pending`,
    доводится `g1`, intake не вызывается.
41. Таблица переходов §5.9: каждая строка — фикстура; `delivered` + допуск
    → `g2`; потерянный `claimed` + допуск → `abandon`-коммит, затем `g2`;
    номер поколения не сбрасывается после удаления веток контуром мержа.
42. Механический отказ за дубль `(to, slug)`, исправлен только slug →
    новая `check-rev` → `new`, `body-rev` прежняя.

    публикации нет (§5.0).
44. Запрос изменён между сборкой графа и `close_shipped` → действие снято.
45. Управляющие сообщения: чужой автор с верным `Q-<id>`; скопированный
    маркер conductor от другого автора; отредактированный маркер; два
    противоречащих ответа; изменённый порядок вариантов → ни одно не даёт
    полномочий.
46. v1 `[x]` → v2 принята → PR принятия переоткрывает пункт; `[x]` до
    мержа принятия не даёт `done`; `[x]` после — даёт.
47. `body-rev` различает запросы, отличающиеся пробелами внутри кодового
    блока.

**Показатели полезности** (в снимке каждого прогона, §7.1):
ожиданий снято (и медианное время от `satisfied` до снятия); выполнено
доступных действий / всего доступных; доля прогонов `partial`; вопросов
владельцу — всего и по причинам (признак решения, допуск, `unknown`,
делегируемость); запусков и их исходов.

**Живая приёмка по срезам:** уровень включается, когда за неделю по
расписанию: (1) нет ложных действий (разбор журнала владельцем); (2) доля
`partial` ниже порога, названного в спеке среза; (3) вопросов владельцу
меньше, чем снятых ожиданий, — система снимает ручную работу, а не
переписывает её в очередь; (4) для среза 0 — **replay** на сохранённых
входах: верх очереди совпадает с приоритетами владельца и показывает ранее
невидимые цепочки.

общий дизайн, на который они ссылаются.

изменение ревизии субъекта, роадмапа/допуска и удалённого состояния между

общего дизайна, тренд находок 17 → 12 → 7 → 4 → 3 → 2, все поздние — края
автомата доставки/запроса): автоматы §5.9 и §6.2 спека среза задаёт
**полной таблицей переходов** «состояние × исход каждого шага (успех, сбой,
неопределённость, исчерпание лимита)» с отрицательным двойником на каждую
строку в тестах; ни одна запись, зависящая от выполненности, не вычисляет её
сама — только через §3.4.
