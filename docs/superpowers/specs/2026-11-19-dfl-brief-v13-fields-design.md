# dfl: поля контракта брифа v1.3 в раскладке и починке (devtools#813)

Статус: утверждён владельцем 19.11 (схема — в разговоре; решения А и Б — ниже).

## 1. Зачем

С 16.11 (ре-вендор контракта брифа v1.3, #773/#780) customer-бриф проходит
проверку только с полями, которых `dfl` не заполняет:

- **GC-18/19** — секция `## Translation table`: строка на каждое высказывание
  заказчика, из которого выведено ограничение (слова, категория, id записей,
  допущение, подтверждающий, срок `YYYY-MM-DD`); есть строки всех четырёх
  обязательных категорий `делать`, `не делать`, `стоить`, `доказывать`.
- **GC-20** — у каждой `NFR` есть `Category`; есть ≥1 `NFR` категории `perf` и
  ≥1 `cost`, их цель — число с единицей или ссылка на `Q-NN`.
- **GC-21** — домены `process`, `data`, `quality`, `operations` закрыты `owns:`
  у `P` (владелец назван) или у открытого `Q` (не назван).

discovery эти поля принимает (`entries[].category`, `entries[].owns`,
верхнеуровневый `translations`), но раскладка `lite/structure.py` их не
просит, а `lite/gate_repair.py` и `lite/interview_remote.py` их не чинят.
Итог: любое enterprise customer-интервью через `dfl` — и в терминале, и без
него — кончается стопом `stopped_interview` (код 10). Найдено живым прогоном
19.11 (eng-helper).

**Цель:** customer-интервью через `dfl` доходит до брифа, проходящего
GC-18…GC-21, без ручной правки брифа — в терминале и без терминала (скил).

## 2. Не цели

- Фрейм engineer — без изменений (промпт раскладки engineer побайтово прежний).
- Репо `discovery` не трогаем (поля он уже принимает); короткий набор вопросов
  фрейма — discovery#86.
- Правила GC не меняем, проверку не ослабляем.
- Английский путь: enterprise остаётся русским (#769).

## 3. Подходы (выбран 1)

1. **Раскладка заполняет поля по ходу + починка недостающего в конце** —
   выбран владельцем. Поля появляются из ответов человека там, где он их
   назвал; что не выводится — вопрос в конце, как GC-08.
2. Только починка в конце (раскладку не трогать) — меньше правок, но таблица
   и категории собирались бы задним числом без слов человека в момент ответа:
   таблица требует дословных слов заказчика, их потом не восстановить.
3. Умолчания без вопросов (категория по эвристике, подтверждающий — роль
   собеседника, срок +14 дней) — отвергнут владельцем: решение А.

## 4. Решения владельца

- **А.** Подтверждающий и срок допущений таблицы — **один вопрос в конце
  интервью** на всю таблицу («Кто подтвердит наши допущения и к какой дате?»),
  не умолчания и не гипотеза агента.
- **Б.** Полноценная задача: дизайн → план → исполнение субагентами.
- devtools#816 (длина интервью): скил может пропускать блок одной темы
  целиком — это срез 5; здесь не делается.

## 5. Раскладка ответа (терминал и без терминала — один источник, R2 среза 3)

Только для фрейма **customer** (`view.frame`); для engineer промпт и проверки
прежние.

- Пункт `NFR` получает `category` — список из словаря
  `perf, cost, safety, security, compliance, availability, quality, …`
  (открытый: GC-20 проверяет только наличие и `perf`/`cost`); пишет агент
  по смыслу пункта. У `perf`/`cost` цель — число с единицей или ссылка на `Q`
  (как правило числа v1.2).
- Пункт `P` и `Q` получает `owns` — подмножество
  `process, data, quality, operations`, только если человек назвал владельца
  (у `P`) или прямо сказал, что владельца нет/не знает (у `Q`).
- Ответ агента получает необязательный `translations` — строки
  `{words, category, constraint, assumption}`:
  - `words` — дословная цитата из ответа (как `preference`);
  - `category` — из словаря таблицы (`делать`, `не делать`, `стоить`,
    `доказывать`, `данные`, `приёмка`, `эксплуатация`, `передача`);
  - `constraint` — id записанных `FR/NFR/CON/OUT` или `ref` новых пунктов
    этого ответа (скрипт подставит id, как в `traces`);
  - `assumption` — если ограничение не следует из слов напрямую (наш перевод:
    порог, правило), иначе null.
  Подтверждающего и срок агент **не пишет** (решение А).
- Скрипт проверяет форму: словари, ссылки, нет `|` и перевода строки в
  ячейках (discovery откажет), пустые `words` — ошибка формы (повтор агента).
- `dfl answer --items` (скил) принимает тот же `translations` в JSON; промпт
  в `dfl pending --json` — тот же `build_prompt`.
- Обновление пункта (`id`) может менять `category`/`owns`.

## 6. Починка в конце интервью

После нынешних GC-08, GC-13, GC-05 — в этом порядке (новые записи нужны
таблице раньше вопроса о допущениях):

1. **GC-20, нет `Category` у `NFR-NN`** — агент предлагает категорию по
   пункту, человек подтверждает (`да`) или называет своё словами; без
   терминала — `interview-repair` `category:<NFR-NN>`, ответ — `dfl reply`
   (слово/слова словаря или «да» на гипотезу из `data`).
2. **GC-20, нет `NFR` категории `perf`** (затем `cost`) — вопрос «Есть ли
   ожидания по скорости ответа и объёму?» / «…по стоимости и бюджету?».
   Ответ раскладывается (агент / скил: `answer --items`) в `NFR` с этой
   категорией; «не знаю» — `NFR` с целью-ссылкой на новый `Q` исследования
   (`owner_role: analyst`) — гейт закрыт честно: значение ищет аналитик.
3. **GC-21, домен без владельца** — «Кто отвечает за <процесс/данные/
   качество/эксплуатацию>?» Имя/роль — `P` с `owns: <домен>`; «не знаю» —
   открытый `Q` с `owns: <домен>`, `owner_role: analyst`. Без терминала —
   `dfl reply` (текст), раскладка не нужна.
4. **GC-18/GC-19, таблица пуста или нет обязательной категории** — сначала
   без вопроса: строки из уже записанных пунктов с `Preference` (слова —
   `Preference`; категория по пункту: `FR` → `делать`, `OUT` → `не делать`,
   `NFR perf/cost` → `стоить`, `NFR/CON compliance` → `доказывать`; допущение —
   критерий/цель пункта, это наш перевод). Если обязательной категории всё
   ещё нет — вопрос по ней («Что заказчик говорил о том, чего система делать
   не должна?»), ответ раскладывается в пункт и строку.
5. **GC-18, у допущений нет подтверждающего/срока** — **один** вопрос на всю
   таблицу (решение А): «Кто подтвердит наши допущения и к какой дате?
   (например: «владелец продукта, 2026-12-01»)». Дата — `YYYY-MM-DD` или
   `ДД.ММ.ГГГГ`; без даты или с прошедшей датой — переспросить; остальное —
   подтверждающий. Записывается во все строки с допущением без них.

Пропуск любого пункта — как сейчас: не исправлено, `GATE_LEFT`, следующий
`dfl run` спросит снова (без терминала — отметка прохода, как в срезе 3).

Каждая правка — пересылка ответа держателя (`--supersede`), как сейчас:
`NFR` — держателю темы `nfr`, `P`/`Q` с `owns` — держателю `personas`, строки
таблицы — держателю ответа, где записан первый пункт строки. `appended`
сливает и `translations` (строки ответа держателя + новые; строка с теми же
`words` и `constraint` заменяется — так дописываются подтверждающий и срок).

## 7. Без терминала (`interview_remote`)

Новые ключи `interview-repair`: `category:<NFR-NN>`, `nfr:perf`, `nfr:cost`,
`owner:<домен>`, `table:<категория>`, `assumptions`. Вид ответа:

- `category:*`, `owner:*`, `assumptions` — `dfl reply` с текстом (как вердикт
  GC-05): `pending.check` пускает непустой текст; разбор — скриптом;
- `nfr:*`, `table:*` — `dfl answer --items` (раскладка скила по `prompt`
  записи), «пропустить» — `dfl reply`.

`data` записи несёт гипотезу категории (для `category:*`) и список допущений
(для `assumptions`) — скил показывает их человеку.

## 9. Проверка

- Юнит: форма `category`/`owns`/`translations` (словари, ссылки, `ref` →
  id, ячейки без `|`), engineer-промпт побайтово прежний.
- Починка: каждый из пяти шагов §6 в терминале (фейк агента/ask) и без
  терминала (pending → reply/answer --items → run) на фейках discovery;
  `appended` с `translations`.
- Сквозной: customer-интервью на фейках до брифа, в котором vendored
  `gate_check` не даёт GC-18…GC-21 (бриф для проверки собирается в тесте из
  отправленных payload в формате секций контракта §2 — тот же, что рендерит
  discovery).
- Живой прогон (владелец): eng-helper без терминала, бриф проходит проверку.
