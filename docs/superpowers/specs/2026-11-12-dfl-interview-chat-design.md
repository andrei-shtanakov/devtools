# Интервью `dfl` разговором в терминале — дизайн

Дата: 2026-11-12. Статус: черновик, ждёт одобрения владельца. Проверен
свежим агентом-исполнителем; его вопросы закрыты решениями автора дизайна
(§4, §5, §7, §8).

## 1. Зачем

Сейчас коллега отвечает на каждый вопрос интервью YAML-файлом
(`dfl answer --file answer.yaml`): открыть редактор, вспомнить формат, разложить
ответ по пунктам `G-`/`J-`/`FR-` с `traces`, `Priority`, `Acceptance`,
сохранить, запустить. Ошибка структуры — отказ `discovery` и новый круг. Вопросов
десятки; по оценке владельца, интервью, которое должно занимать час, растягивается
на дни. Раскладка ответа по пунктам — работа аналитика, которую агент делает лучше
человека. Плюс вывод раннера подсказывает коллеге неверную команду
(`discovery answer --session … --role …` — её у коллеги нет в `PATH`).

Цель — **интервью как один разговор в терминале**: вопрос на экране, ответ
текстом, следующий вопрос.

## 2. Решения владельца (2026-11-12)

1. Вопрос показывается на экране, человек **отвечает текстом**; файлов и YAML нет.
2. **Агент раскладывает** ответ на пункты сам; раскладку после каждого ответа
   **не показывает**.
3. Нужна **команда просмотра текущего состояния интервью**: что покрыто, какие
   пункты собраны.
4. Исправление — **поправкой текстом** («не раз в неделю, а раз в месяц»).
5. **Гибрид:** агент извлекает смысл в заданную форму, всё остальное (id,
   ссылки, обязательные поля, YAML, отправка, проверка) делает скрипт. Платный
   вызов `claude` на каждый ответ, уточнение и поправку — принят.
6. Отдельно (вне этого дизайна, §9): баннер режима test — одна строка;
   служебная информация и состояние — отдельной командой.

## 3. Как устроен `discovery` (факты, пин `c7961b9`)

Это определяет, что должен делать наш агент.

- **Вопросы не адаптивные.** Следующий вопрос — первый неотвеченный из банка
  `contract/frames/<frame>.md` по порядку; LLM в `discovery` нет
  (`lifecycle.py:38-58`, `bank.py:149-170`). `next_action` несёт `session_id`,
  `question_id` (`<frame>.<coverage_key>.NN`), `coverage_key`, `question_text`.
- **Тема покрыта**, если среди действующих пунктов есть хотя бы один с префиксом
  темы (`render.py:154-173`); карта тема → префикс — `FRAMES` в
  `contract/gate_check.py:18-45` (customer: goals `G`, personas `P`, jobs `J`,
  functions `FR`, nfr `NFR`, constraints `CON`, success_metrics `M`,
  out_of_scope `OUT`, risks `RK` — опц.; engineer: systems `S`, interfaces `IF`,
  constraints `CON`, arch_preferences `AP`, risks `RK`, feasibility_review —
  покрыт фактом ответа).
- **Ответ без пункта нужного префикса тему не покрывает**, и `discovery` об этом
  не переспросит: вопрос считается отвеченным, интервью уходит дальше и в конце
  останавливается неготовым (живой Linux-прогон: 19 ответов текстом, 8 тем не
  покрыты). Значит, **уточнять по недостающему обязан наш агент**, до отправки.
- **Приём ответа** (`payload.py`): обязателен `text`; `entries` — список, `id`
  по `^[A-Z]+-\d+$`, `traces` — YAML-список; дубль id в одном ответе — отказ;
  невалидный файл отклоняется целиком (exit 1, `operation.status=unknown`).
- **Обязательные поля пунктов** проверяются не при приёме, а линтером брифа
  (`gate_check.py:286-330`): `FR` — `traces` на существующий `G`/`J`, `Priority`
  (Must|Should|Could|Won't) и `Acceptance`; `NFR` — `Acceptance` или `Target`;
  `M` — `traces` на `G`; `Q` — `owner_role`, `blocking`; `X` — `status`. Ошибка
  всплывает только в конце, на брифе.
- **Действующие пункты**: последний ответ на каждый вопрос; последняя декларация
  каждого id побеждает целиком (`render.py:88-105`). Поправить пункт можно
  повторной декларацией его id; если он объявлен в ответе на тот же вопрос — ответ
  переотправляется целиком с `--question <id> --supersede` (иначе
  `answer_conflict`).
- **Состояние сессии** — `$DISCOVERY_HOME/sessions/<id>/journal.jsonl`
  (по умолчанию `~/.discovery/…`). Публичной команды «покажи собранное» нет;
  есть функции `discovery.render.effective_entries(events)` и
  `readiness(events, frame)`.

## 4. Поток для коллеги

```
$ dfl run --subject 'экспорт отчётов в CSV'
Вопрос 1 из ~N (цели): Зачем это нужно? Какой результат считаем успехом?
> Бухгалтерии раз в месяц нужна выгрузка операций, чтобы сверять платежи
> без ручного копирования.
>                                   ← пустая строка — ответ закончен
Уточнение: как поймём, что цель достигнута — что изменится для бухгалтерии?
> Сверка за месяц занимает полчаса вместо дня.
>
Вопрос 2 из ~N (пользователи): …
```

- `dfl run` (и `dfl answer` без `--file`), когда прогон ждёт ответа и **stdin —
  терминал**, входит в цикл интервью: вопрос → ответ → (уточнения) → отправка →
  следующий вопрос — до конца интервью; затем обычный следующий шаг конвейера.
- Ввод ответа — несколько строк, конец — пустая строка. `Ctrl-D` или `/стоп` —
  выйти из цикла; состояние сохранено, `dfl run` продолжает с текущего вопроса.
- Уточнения агента — не больше **2 на вопрос**. Человек может ответить «не знаю»
  / «пропустить» — тогда отправляется то, что есть (тема может остаться
  непокрытой; это видно в команде просмотра, §6).
- Цикл ведёт **оба интервью**: customer (до брифа) и engineer (после мержа брифа
  — отдельный прогон со своей сессией; цикл стартует при следующем `dfl run`).
  Роль отвечающего — та, с которой идёт прогон (`--stakeholder`, по умолчанию
  `customer`). Тема без префикса (engineer `feasibility_review`) покрывается
  самим ответом: пунктов не требуется, отправляется `text`.
- После последнего ответа цикл делает тот же следующий шаг, что сейчас делает
  `dfl answer` после ответа (`run` — например, публикация PR брифа); отдельный
  `dfl run` не нужен.
- Текущий вопрос цикл берёт у `discovery` (`discovery status` сессии — без
  изменений журнала), а не из вывода раннера.
- Без терминала (stdin не tty) поведение прежнее: печать вопроса и подсказки
  `dfl answer --file answer.yaml`. **`dfl answer --file` сохраняется** — для
  скриптов и тех, кто хочет писать YAML сам. `--file` у `dfl answer`
  становится необязательным: без него — цикл интервью (только в терминале);
  `--question`/`--supersede` по-прежнему только вместе с `--file`.
- На экране — только вопрос, уточнения и следующий шаг. Подсказки раннера
  `discovery answer …`/`make …` в пути `dfl` не печатаются (§8).

## 5. Раскладка ответа (гибрид)

На каждый ответ:

1. **Агент** (один вызов `claude -p`) получает: текст вопроса, `coverage_key` и
   требуемый префикс (из `FRAMES`), ответ человека (с уточнениями), действующие
   пункты сессии (id, тема, текст — чтобы ссылаться на `G`/`J` и не дублировать)
   и правила полей (§3). Пункты могут быть **любых префиксов темы фрейма**
   (ответ про цели нередко называет и задачи, и функции — тема засчитывается по
   любому пункту её префикса); служебные `Q`/`X` агент не создаёт. Возвращает
   **строгий JSON** по схеме, например:
   `{"items": [{"prefix": "FR", "body": "...", "traces": ["G-01"],
   "priority": "Must", "acceptance": "..."}], "ask": "уточняющий вопрос или null"}`.
   Агент пишет пункты **только из сказанного**; чего нет в ответе — не выдумывает,
   а просит через `ask`.
2. **Скрипт** проверяет и собирает:
   - JSON по схеме (иначе — одна повторная попытка агента с текстом ошибки;
     вторая неудача — сообщение человеку «не удалось разобрать ответ,
     переформулируйте», без YAML и трассировки);
   - есть хотя бы один пункт требуемого префикса (иначе — уточнение);
   - обязательные поля по префиксу (§3) и что `traces` ведут на существующие
     id (иначе — уточнение у человека, если не хватает смысла, или повтор агента,
     если нарушена форма);
   - назначает id: следующий номер префикса после **всех когда-либо объявленных**
     в журнале сессии (не только действующих) — заменённые id не переиспользуются;
   - собирает YAML (`text` — ответ человека дословно, с уточнениями;
     `entries` — пункты) и отправляет `discovery answer` (как сейчас
     `_discovery_answer`). Отказ `discovery` — повтор агента с причиной; человеку
     — только если причина в смысле.
**Отправка и повторы.** Ответ всегда уходит с `--question <id текущего
вопроса>`. Если цикл прервался после отправки (обрыв, `Ctrl-D`), при
продолжении `discovery status` покажет уже следующий вопрос — повтор не
нужен. `--supersede` — только для поправок (§7).

3. Если агент вернул `ask` — показать вопрос человеку, добавить ответ к тексту,
   повторить шаг 1 (лимит уточнений — §4).

**Вызов агента** — тот же `claude`, что у коллеги, неинтерактивно:
`--safe-mode`, без инструментов (только ответ текстом), модель из `[harness]`
конфига (`model`); `harness.author` не `claude` — отказ с подсказкой
`dfl answer --file`. Вход — промпт в stdin, выход — JSON в stdout. Этот вызов —
не авторинг узла бандла: он не пишет файлов, не идёт через `author_launch` и
живёт в `lite/` (вне `governance/`, вне перечня мест порождения процессов
песочницы). `dfl` работает только в режиме test, где автор и так — обычный
процесс пользователя; strict этот путь не затрагивает.

## 6. Просмотр состояния интервью

Команда `dfl interview` (имя — §10) печатает для текущего прогона:

- тему и номер текущего вопроса;
- темы: покрыта / не покрыта (обязательные и необязательные);
- собранные пункты человеческим текстом по темам:
  `FR-01 выгрузка операций за месяц в CSV — Must; критерий: файл открывается в
  Excel, строка на операцию; → G-01`;
- что мешает готовности (`readiness_findings` по-человечески).

Источник — сам `discovery` на закреплённой версии: небольшой скрипт devtools
исполняется интерпретатором окружения `discovery` (`uv run --frozen --project
<discovery> python -I <скрипт devtools>`; код соседа только читается, не
правится) и возвращает JSON из `effective_entries`/`readiness` и
`FRAMES`. Это внутренний API `discovery` (публичной команды нет) — связь держит
пин и тест на нём; в `discovery` заводится inbox-просьба о публичной команде
(§9).

## 7. Поправки

`dfl correct '<текст>'` (имя — §10), например
`dfl correct 'не раз в неделю, а раз в месяц'`:

1. Агент получает действующие пункты и поправку, возвращает изменённые пункты
   (с их id) в той же JSON-схеме.
2. Скрипт находит **держателя** каждого пункта — ответ, чья декларация id
   сейчас действует (`entry_holders`, `render.py:127-138`), пересобирает этот
   ответ **целиком** (неизменённые пункты — как были, изменённые — новые) и
   отправляет `discovery answer --question <id> --supersede`.
3. Печатает одну строку: что изменено (`FR-01: «раз в неделю» → «раз в
   месяц»`). Не понял, что менять, — переспрашивает.

## 8. Вывод раннера в пути `dfl`

Минимум, без которого разговор не сложится: в пути `dfl` раннер не печатает
`ответьте вне spec-loop … discovery answer --session …` и подсказки `make …`;
вопрос интервью показывает `dfl`. Подсказка `discovery answer` печатается в
`governance/runner.py` из `_print_answer_hint` и ещё трёх мест (около строк
2126, 2419, 2453) — глушить нужно все. Способ (флаг/режим вызова раннера из
`dfl`) — решение исполнителя; `governance/runner.py` вне authority-root. Остальная чистка вывода — §9.

## 9. Не цели и смежное

- **Чистый вывод `dfl`** — отдельный дизайн по решению владельца: баннер test —
  одна строка; служебное и состояние — отдельной командой. Здесь только §8.
- Правка `discovery` — нет. Просьба о публичной команде просмотра сессии — inbox
  issue в `discovery` (кросс-репный канал, ADR-ECO-006), не блокирует.
- Адаптивный выбор вопросов (`discovery` задаёт их по порядку банка) — не меняем.
- Показ раскладки после каждого ответа — нет (решение владельца 2).

**Анти-цели:** агент приписывает человеку то, чего тот не говорил; ошибка формата
доходит до человека; человек видит YAML или трассировку; ломается
`dfl answer --file`.

## 10. Оставлено исполнителю

- Имена команд просмотра и поправки (`dfl interview`, `dfl correct` — рабочие).
- Точная JSON-схема ответа агента и текст промпта (с тестами на правила §3).
- Номер вопроса «N из ~M» — из банка, если доступен, иначе без «из».
- Как раннер в пути `dfl` молчит про `discovery answer`/`make` (§8).

## 11. Проверка

- Тесты с поддельным агентом: ответ → YAML с правильными префиксом, id,
  `traces`, полями; ответ без пункта нужного префикса → уточнение; лимит
  уточнений; «пропустить»; битый JSON → одна повторная попытка → сообщение;
  отказ `discovery` → повтор агента; поправка → `--supersede` с целым ответом
  и сохранёнными чужими пунктами; без tty — прежний путь; `dfl answer --file` —
  как было.
- Тест связи с `discovery` на пине: скрипт просмотра читает настоящий журнал
  сессии (локальный `discovery`, без сети).
- Живая проверка на сервере: интервью темы от начала до брифа разговором;
  поправка; `dfl interview` на середине и в конце. Мерило — бриф готов без
  единого YAML-файла, руками.
