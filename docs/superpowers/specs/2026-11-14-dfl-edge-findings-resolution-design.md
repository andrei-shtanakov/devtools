# dfl: разбор замечаний смысловой проверки — дизайн

Дата: 2026-11-14. Статус: черновик на одобрение владельца.
Связано: devtools#757 (находки на экране, PR #758), #759 (блокирующие отдельно
от рекомендаций), #728 (сходимость edge-check).

## 1. Зачем

Человек в `dfl` — заказчик, а не редактор спецификаций. Сейчас, когда
смысловая проверка (edge-check) возвращает узел, написанный агентом, `dfl`
останавливается и говорит: «поправьте файл сами». Живой прогон
`sdd-runer` 13–14.11 встал так дважды подряд (W2 requirements, W3
behaviour-spec), каждый раз из-за одной major-находки к тексту агента.
Владелец: «ощущение, что я сдаю экзамен в ГАИ на примитивной программе».

Цель: замечания к тексту агента исправляет агент; человека спрашивают только
о том, что требует решения по существу, — вопросом с вариантами; несогласие
человека с замечанием — тоже ответ.

## 2. Как сейчас (факты кода)

- Волна: авторинг узла → коммит → гейт → `_step_edge` → candidate-PR
  (`governance/runner.py`). Edge-check `FAIL` → `stopped_review`, строки
  находок — `out/governance-runs/<run>/edge-findings.txt`, полные записи
  рёбер — `edge-check/w<N>/*.json` (`rule_id`, `class`, `statement`,
  `location`).
- `FAIL` дают только блокирующие классы (`blocker`, `major`) и пункт без
  находок / `insufficient`; `minor` — рекомендации (`edge_check.check.decide`,
  с #730).
- `resume` из `stopped_review` сбрасывает `commit/gate-candidate/edge`
  текущей волны; автор повторно не зовётся — ждут ручной правки файла в
  чекауте цели.
- Автор узла (`ops.author` → `author_launch.launch_author`) получает в
  промпте только формат узла (`_AUTHOR_DSL`), но не правила рёбер, по
  которым его потом проверяют (`contracts/edge-check/v1/rules/*.yaml`,
  `subject_role` = вид узла). Отсюда основной класс находок: автор не знал
  про R1 «каждая цель G покрыта или явно отклонена» и ссылался на id брифов,
  которых нет в основании.

## 3. Цели

**Ц1. Профилактика.** Автор узла получает в промпте правила всех рёбер, где
его узел — `subject_role`: текст пунктов `items` и требование ссылаться только
на id узлов-оснований (`basis_roles`). Источник — те же файлы правил, без
пересказа. Применяется и к первому авторингу, и к переписыванию (Ц2).

**Ц2. Разбор при стопе.** `dfl run` на прогоне в `stopped_review` с находками
(не отказ прибора) не печатает «поправьте файл», а ведёт разбор:

1. **Сортировка.** Вызов агента без инструментов (как разбор ответов
   интервью в `lite/structure.py`): вход — находки, текст узла, тексты
   оснований; выход — JSON по каждой блокирующей находке:
   - `fix` — правка без решения по существу (не хватает трассировки,
     формулировка непроверяема, ссылка на чужой id, лишнее поле);
   - `decision` — нужен выбор заказчика: вопрос простыми словами, 2–3
     варианта с последствием каждого, один помечен рекомендуемым.
   Рекомендации (`minor`) в сортировку не идут: их агент правит заодно,
   если правка не меняет смысла, иначе оставляет (см. §6, вопрос 2).
2. **Вопросы человеку** — только по `decision`, по одному, в стиле интервью
   разговором: номер варианта, «своё: …», «не согласен: <почему>»,
   «пропустить» (= остановиться, прогон стоит как сейчас). Перед вопросами
   одна строка: «исправлю сам: N замечаний; вопросов к вам: M». Нет
   `decision` — вопросов нет, сразу шаг 3.
3. **Переписывание.** Авторский вызов через ту же границу `launch_author`
   (в `test` — обычный процесс claude, каталог вызова, транскрипт, перенос
   одного файла): промпт = промпт автора узла (Ц1) + текущий текст узла +
   находки + решения человека дословно. Пишется только файл остановленного
   узла; утверждённые узлы выше не трогаются.
4. **Повтор проверки** — тем же вызовом `dfl run`: обычный `resume`
   (коммит, гейт, edge-check текущей волны).

**Ц3. Несогласие.** «Не согласен: <причина>» по находке переписывание вносит
в узел явной записью «Решение заказчика: … Причина: …» в месте, к которому
относится находка. Правила рёбер такое принимают (R1 «явно отклоняет с
названной причиной»), и ревьюер видит решение в тексте узла. Кроме того,
решения пишутся в журнал прогона `edge-decisions.jsonl` (находка, вопрос,
ответ, круг) — для аудита и чтобы не спрашивать одно и то же на следующем
круге.

**Ц4. Предел.** Не больше 2 кругов «переписать → проверить» на волну за один
`dfl run`. Не сошлось — стоп с честной сводкой: что осталось, какие находки
повторяются (признак #728), и выбор: `dfl run` (ещё круг), правка руками,
`dfl abandon`. Каждый круг — платные вызовы (сортировка, переписывание,
проверка); их число печатается.

## 4. Не делаем (non-goals)

- Не меняем правила рёбер, `decide()` и политику серьёзности.
- Человек не может «пропустить» блокирующую находку в обход проверки: гейт
  остаётся гейтом; несогласие проходит только через текст узла (Ц3) и снова
  проверяется (см. §6, вопрос 1).
- Не трогаем discovery (вопросы интервью — отдельный issue в discovery).
- Стоп гейта бандла (`stopped_gate`) и отказ прибора edge-check — как сейчас
  (#758): там решать человеку нечего.

## 5. Чего нельзя допустить (anti-goals)

- Агент «чинит», ослабляя содержание, чтобы прошёл ревьюер: удаляет
  требование, понижает Must, снимает сценарий. Любая такая правка — только
  как `decision` с вопросом человеку; промпт переписывания это запрещает, а
  `dfl` сверяет до/после: исчезнувший id `FR/NFR/BEH/…` или понижение
  `Priority` без решения человека — переписывание отклоняется, стоп.
- Тихие изменения: человек видит, что исправлено (одна строка на находку на
  уровне 1, сводка на уровне 0, дифф — `dfl log`).
- Бесконечные платные круги (Ц4).

## 6. Решения владельца (до плана)

1. **Несогласие с блокирующей находкой**, которое ревьюер на следующем
   круге всё равно не принимает: только стоп (как в §4) — или в `test`
   разрешить человеку принять узел вопреки находке с записью в журнал
   (ослабление гейта, видимое в отчёте)?
2. **Рекомендации (`minor`)**: агент правит их заодно (дешевле круг, но
   риск лишних изменений и новых находок) — или не трогает вовсе?
3. **Предел кругов**: 2 на волну за вызов — годится?

## 7. Ограничения

- Пакет `lite/` и `governance/ops.py` — вне authority-root;
  `governance/author_launch.py` — authority-root: используем как есть, не
  меняем (переписывание — новый `make_prompt`, граница прежняя).
- Соседние репо не трогаем.
- Вывод — по правилам чистого вывода `dfl` (уровни 0–3,
  `docs/darkfactory-for-colleagues.md` «Сколько dfl пишет на экран»).
- Режим `test` (lite). Strict — вне объёма.
- Каждый вызов агента — через существующие точки (`lite.structure` агент без
  инструментов; `launch_author` для записи файла).

## 8. На усмотрение исполнителя

Схема JSON сортировки, имена модулей (`lite/edge_resolve.py` — предложение),
формулировки строк вывода, где в `dfl run` встраивается разбор (до
`spec_loop.main` на `stopped_review`), набор тестов (подменённые агент,
человек и раннер, как в `tests/test_lite_gate_repair.py`).

## 9. Решения автора дизайна (проверка «можно ли строить», 14.11)

Вопросы свежего читателя, решённые без владельца; владелец может оспорить.

1. **Причина находки — в утверждённом узле выше** (ссылка на id, которого
   нет в основании; цель, которой нет в основании). Это `decision` с
   вариантами внутри остановленного узла: убрать ссылку, отклонить с
   причиной, сослаться на id основания. Переоткрытие узла выше (`--reopen`)
   в v1 не предлагается: если ни один вариант не годится, «пропустить» —
   стоп, как сейчас.
2. **Сверка до/после.** Id узла — заголовки `#### <ID>` (тот же разбор, что
   `ops.bundle_node_index`), приоритет — строка `**Priority**:` под ним.
   Каждый вариант `decision` в ответе сортировки объявляет свои эффекты
   (`removes: [ids]`, `downgrades: [ids]`); выбранный человеком вариант их
   разрешает. Всё прочее исчезновение id или понижение `Must` → отклонение
   переписывания. Узлы без `Priority` сверяются только по id.
3. **«Та же» находка между кругами** — ключ `(узел, ребро, rule_id)`.
   Решения прошлых кругов уходят в сортировку следующего: по ключу с
   записанным решением вопрос не повторяется, а повтор блокирующей находки
   с тем же ключом два круга подряд — признак несходимости в сводке Ц4.
4. **Несколько узлов в волне (W4: design + acceptance)** — находки
   группируются по файлу из `location`; переписывание — по вызову на файл;
   круг и проверка — по волне. Находка без разрешимого файла — разбор не
   начинается, стоп как сейчас. Узлы, написанные человеком, разбираются так
   же.
5. **Ручные правки.** Основа переписывания — текущий файл в чекауте (с
   правками человека, если были). Перед переписыванием копия файла
   сохраняется в каталог прогона; отклонённое сверкой переписывание
   возвращает копию.
6. **Без терминала** (`stdin` не tty) — разбора нет, прежний стоп с
   находками (как отказ интервью разговором без tty).
7. **Прерванный разбор.** Ответы человека пишутся в `edge-decisions.jsonl`
   сразу; сортировка кэшируется по хэшу (файл находок + текст узла). Круг
   считается только при состоявшемся переписывании.
8. **`FAIL` без находок / `insufficient`** — как отказ прибора (§4): разбора
   нет, сообщение из #758.
