## 0. Зачем и что считается успехом

Срез 0 показывает, кто кого ждёт. Срез 1 делает так, чтобы **участники
узнавали об этом без владельца**: владелец видит свои вопросы в одном месте,
потребитель — что его предпосылка выполнена, продюсер и автор PR — что их
ждут, отгруженная работа закрыта с объяснением. Всё — комментарии и
состояния issues от отдельного актора `conductor[bot]`; ни веток, ни PR.

Успех среза:

1. Приёмка в песочнице пройдена по всем сценариям §9 с квитанцией §9.4.
2. Во флоте пройдены тень и все четыре ступени §10 по правилу перехода §10.2.
3. Ни одной записи, которая не проходит повторную проверку §5 (журнал и учёт
   вызовов адаптера это показывают).
4. Отзыв (`enabled_actions` без действия; `autonomy = 0`; удаление ключа)
   останавливает записи со следующего шага, что показано и в песочнице, и
   тестами последовательностей.

## 1. Границы

**Действия среза:** `owner_queue`, `notify_satisfied`, `nudge`, `pr_nudge`,
`close_shipped` (все — уровень 1, §5.1). Граница: **комментарии и состояния
issues**, без веток и PR.

**Вне среза:**

- `todo_hygiene_pr` → срез 1b (ветки и PR, автомат поколений §5.9).
- `request_triage` и механическая часть §6.2 → срез 2 (зависят от протокола
  заявок ADR-ECO-012).
- Исполнение ответов владельца, кроме `close` на `GR-SHIPPED-OPEN` (§6.2).
- Допуски на `launch`, поколения доставки — срез 3.
- Чтение логов CI (у App нет прав `actions`).

**TODO-only потребитель** (пункт без запросов, §5.7 «адрес — todo_hygiene_pr»)
в срезе 1 адреса доставки не имеет: `notify_satisfied` пишет в журнал и
выдачу причину `канал доставки — срез 1b`; доставленным это не считается;
новый канал (например, комментарий в произвольный issue репо) не выдумывается.
Адрес доставки — только **открытый** тред (решение владельца 2026-10-01):
треды у потребителя или продюсера есть, но все закрыты → причина `нет открытого
адреса доставки` — это не доставка и не случай 1b; заявка не переоткрывается,
произвольный тред не ищется.

**Чтения** графа остаются как в срезе 0 (учётные данные чтения хоста). Токен
App и JWT используются только для записей среза и для служебных проверок
шага перед ними (ключ, установка, покрытие, свежее чтение цели — §5.1)
через HTTP-адаптер §4.5.

## 2. Включение: `enabled_actions` и тень

### 2.1 Поле роадмапа

```toml
autonomy        = 1
enabled_actions = ["owner_queue", "notify_satisfied"]
```

Разрешение записи = **все** условия: `autonomy` достаточен для уровня позиции
(§2.4) **и** действие есть в `enabled_actions` **и** прочие проверки шага (§5).

- Поля нет или список пуст → записей нет (любых действий среза).
- Неизвестное имя → `RM-INVALID` (ошибка конфигурации): записей нет, прогон
  продолжается как при `RM-INVALID` (§2.2).
- `nudge` и `pr_nudge` — **разные** имена; включаются раздельно.
- Поле перечитывается с `origin/<default>` зонтика **перед каждым шагом**
  (§5). Действие, убранное из списка, не доводится даже частично: уже
  сделанный первый шаг `close_shipped` остаётся, выдача показывает
  «частично: шаг 2 отозван» (§7.6).

### 2.2 Тень

Режим хоста `shadow = true` (конфиг хоста §4.2, не роадмап). В тени
планировщик и проверки шага (§5) выполняются полностью, **кроме отправки
мутации**; интерфейс мутаций не вызывается, учёт мутаций (§4.7) это подтверждает.

Журнал каждой предложенной записи несёт два признака:

- `admissible_when_enabled` — запись прошла бы все проверки, если бы действие
  было включено и уровень достаточен; при отрицательном значении — блокирующее
  условие по имени (`writer`, `key`, `coverage`, `fence`,
  `evidence_changed`, …);
- `allowed_by_roadmap` — текущий роадмап разрешает запись (уровень и
  `enabled_actions`). При `autonomy = 0` всегда `false`, а блокирующее
  условие — `autonomy`.

Предложения тени **не выполнены** и никогда не проигрываются как очередь:
после выхода из тени каждый прогон вычисляет действия заново (I7).

## 3. Операционное состояние — определение

**I7 (уточнение, дословно в общую спеку):** «Операционное состояние не
предоставляет полномочий и не доказывает выполнение действия. Оно
используется только для защитных запретов и задержек, а также для
формирования вопросов об операционных сбоях; такие вопросы проходят обычный
протокол разрешений.»

Операционное состояние хранит ровно четыре вида записей: попытки мутаций,
серии сбоев, карантин (§4.6, по профилю) и запрет по лимиту (§5.5, общий
для хоста по установке). Журнал (§4.7) — диагностика и **не** операционное
состояние: из него ничего не читается при принятии решений.

## 4. Устройство

### 4.1 Модули

```
conductor/
  host_config.py   # §4.2 — чтение конфига хоста
  gh_app.py        # §4.3 — JWT, токен установки, проверка ключа
  markers.py       # §4.4 — кодер/декодер управляющих сообщений §5.10
  opstate.py       # §4.6 — попытки, серии сбоев, карантин
  journal.py       # §4.7 — журнал и учёт мутаций
  gh_write.py      # §4.5 — HTTP-адаптер App (urllib, без перенаправлений)
  writer.py        # §5 — единственный исполнитель шагов
  actions/
    owner_queue.py
    answers.py     # ответы владельца, производный вопрос (§6.2)
    notify.py      # notify_satisfied
    nudge.py       # nudge, pr_nudge (возраст, тишина, §7.3–7.4)
    close.py       # close_shipped
```

Планировщики `actions/*` — чистые функции: (результат ядра среза 0 + свежие
чтения) → список записей плана `{action, subject, revision, evidence,
target, steps[], expected}` (§5.0). Писать умеет только `writer.py` через
`gh_write.py`. Существующие модули ядра записей не получают.

### 4.2 Конфиг хоста

`/srv/conductor/conductor.toml` (вне git, владелец — пользователь службы):

```toml
[app]
app_id          = 123456
installation_id = 7890123
private_key     = "/srv/conductor/keys/conductor.pem"

[run]
profile   = "fleet"               # fleet | acceptance
shadow    = true
state_dir = "/srv/conductor/opstate"  # не state/: там runs/ и lock среза 0
# lock    = "/srv/conductor/state/conductor.lock"  # по умолчанию; один на хост

[acceptance]                      # только при profile = "acceptance"
sandbox     = "<owner>/conductor-sandbox"
outside     = ["<owner>/conductor-sandbox-outside"]  # фикстура забора, §9.3 A10
stop_points = []                  # имена из §9.2
```

Ошибка конфига (нет файла, неизвестный ключ, `stop_points` или `[acceptance]`
в профиле `fleet`) → `CFG-INVALID`, записей нет, чтение и выдача — как в
срезе 0. Профиль `acceptance` — отдельный файл `/srv/conductor/acceptance.toml`
со своим `state_dir`; совпадение `state_dir` с боевым — `CFG-INVALID`. Lock хоста
(`[run] lock`, по умолчанию `/srv/conductor/state/conductor.lock`) — один на все
профили (они делят журнал установки §5.5) и вне любого `state_dir`: восстановление
и `init-state --recover` его не переносят; lock внутри `state_dir` — `CFG-INVALID`.

### 4.3 `gh_app.py`

- JWT RS256 (PyJWT[crypto]) из ключа хоста; `iat = now − 60 с`, `exp = now +
  9 мин`.
- **Проверка ключа** перед каждым шагом: свежий JWT и `GET /app` этим JWT.
  Действующий токен установки ключ не доказывает (ключ могли удалить после
  выпуска токена).
- Токен установки: `POST /app/installations/{id}/access_tokens`, хранится
  только в памяти процесса; обновляется, если до истечения < 10 мин.
- Токен и JWT живут только в памяти процесса и передаются только в
  заголовке `Authorization` собственного HTTP-адаптера (§4.5); в окружение
  дочерних процессов, файлы и `gh` они не попадают. Нет токена → записи
  нет; отката на сохранённую учётку `gh` нет.
- Обновление токена не повторяет мутацию с неопределённым исходом (§5.3).
- Секреты (ключ, JWT, токен, заголовок `Authorization`) не попадают в
  журнал, снимок, текст ошибок и учёт мутаций и журнал установки; текст ошибок адаптера проходит
  фильтр, вырезающий `ghs_…`/`ghp_…`/`github_pat_…`/`eyJ…`/PEM-блоки до
  записи.

Все вызовы токеном App или JWT (выпуск токена, `GET /app`, проверка
установки, мутации) проходят проверку запрета по лимиту (§5.5) **до**
отправки. Проверка установки §8.2 — на старте прогона; покрытие конкретного репо —
свежим запросом перед каждой записью в него (§5.1, шаг 7).

### 4.4 `markers.py`

Единый формат (правка §5.4 под §5.10): `<!-- conductor:v1 <kind> k=v … -->`,
ключи в каноническом порядке (по алфавиту). **Значения полей** (rev 15 —
механизм вместо расширения алфавита): каждый идентификатор (`id`, `wait`,
`evidence`, `node`, `pr`, `p`, `period`, `projection`) записывается как
`h1-<hex>` = первые 16 hex `sha256` канонической сериализации — JSON-массив
`[тип, поля кортежа…]` в UTF-8 без пробелов, ключи и строки как есть
(репо — каноническое имя, путь нормализован); `n` — десятичное целое.
Алфавит значения — `[a-z0-9-]+`; любой иной символ — маркер
недействителен. Кодер и поиск (§5.4 `effect_key`, поиск маркеров)
используют одну функцию; префикс `h1` — версия сериализации. Исходный
читаемый текст (условие, путь, id PR) идёт в тело комментария, не в
маркер.
Виды среза и их поля (иные поля или вид — маркер недействителен):

| Вид | Поля |
|---|---|
| `q` | `id` |
| `sat` | `wait`, `evidence` |
| `nudge` | `wait`, `p`, `n` |
| `prnudge` | `pr`, `n` |
| `close` | `node`, `period`, `evidence` |
| `queue` | `projection` |

**Размещение.** Управляющий блок — ровно один, **последней непустой строкой**
тела комментария (или тела очереди); тело, где подстрока `conductor:v1`
встречается больше одного раза или не в последней строке, маркера не несёт
(`MK-MALFORMED` в журнал). Любой вставляемый в запись исходный текст
(заголовки, доказательства, цитаты) экранируется: `<!--` → `&lt;!--`,
`conductor:` → `conductor&#58;`. Так цитата не может стать маркером даже в
собственном комментарии App.

Действителен только маркер **события** (все виды, кроме `queue`), у
которого автор `conductor[bot]` (бот App из конфига) **и** `updated_at =
created_at`. Маркер `queue` — маркер изменяемой **проекции**: тело очереди
штатно перезаписывается, запрет редактирования к нему не применяется и
`MK-EDITED` не порождает; он ничего не доказывает, а только несёт хэш
проекции для сверки «тело равно вычисленному» (правка тела человеком —
расхождение, которое следующий шаг 1 очереди перезаписывает). Отредактированный маркер —
недействителен, находка `MK-EDITED` в снимке и выдаче (решение владельца
2026-10-01: без вопроса — у вопроса нет исполнимого выбора); доставкой не
считается, новая запись проходит всю авторизацию §5. Если правка ведёт к
повторной ошибке протокола, действует обычная эскалация. Маркер правильного
вида от другого автора — не событие (`MK-FOREIGN` в журнал, без вопроса).

### 4.5 `gh_write.py`: HTTP-адаптер App

**Транспорт** (rev 11, R4; решение владельца 2026-10-01 — заменяет `gh api`
для вызовов App/JWT): все вызовы токеном App или JWT — проверки шага
(§5.1: ключ, покрытие, свежее чтение цели) и мутации — идут через
собственный HTTP-адаптер на стандартной библиотеке (`urllib.request`) с
обработчиком перенаправлений, который **отказывает** на любой 3xx (301,
302, 303, 307, 308) вместо следования. `gh api` не даёт запретить
следование перенаправлениям, поэтому для этих вызовов не используется;
чтения учётными данными чтения хоста остаются как в срезе 0. 3xx на
проверке цели → `TARGET-MOVED` (снято); 3xx на мутации → `failed`
(перенаправление — не применение) с причиной `TARGET-MOVED`, новый адрес
не запрашивается; следующий прогон планирует и авторизует его заново.

Единственный адаптер мутаций — `gh_write.py` поверх этого транспорта, с
явным методом, endpoint и репо; issue или PR определяется по данным API
(`pull_request` в ответе `GET /issues/N`), а не по номеру. Набор мутаций
среза закрыт: `POST /repos/{r}/issues/{n}/comments`,
`PATCH /repos/{r}/issues/{n}` (`body`; `state=closed,
state_reason=completed`), `POST /repos/{r}/issues` (создание очереди),
закрепление — GraphQL `pinIssue`. Любой другой вызов — ошибка программы
(тест перечисляет белый список). Контрактный тест настоящего адаптера
против локального HTTP-сервера: 301/302/307/308 на GET и на POST/PATCH —
ни одного повторного запроса по `Location`.

Исходы вызова:

- `ok` — 2xx и тело разобрано; для GraphQL — ещё и нет `errors`, поле
  результата не `null`;
- `failed` — **доказанный** отказ до применения: HTTP 400, 401, 403, 404,
  410, 422; GraphQL `errors` с типом `NOT_FOUND`, `FORBIDDEN`,
  `UNPROCESSABLE`;
- `rate_limited` — отказ по лимиту: 403/429 с `x-ratelimit-remaining: 0`
  или `retry-after`, вторичный лимит; GraphQL — HTTP 200 с `errors` типа
  `RATE_LIMITED` (приоритет над веткой `uncertain`): доказанный отказ **и** запрет
  немедленного повтора — отдельные признаки (§5.5);
- `uncertain` — всё прочее: 5xx, 408, иные коды, серверный таймаут, обрыв,
  таймаут клиента, процесс прерван, ответ не разобран, иные GraphQL
  `errors`.

Отказ до отправки (проверки §5.1) исходом вызова не является. Для шагов,
идемпотентных по содержимому (тело, закрытие, закрепление), `uncertain`
проходит тем же путём §5.3 — повтор не создаёт второго объекта, но и
правило задержки для них не ослабляется (один механизм).

### 4.6 `opstate.py`

Файлы в `state_dir`: `attempts.jsonl`, `failures.json`, `quarantine.json`,
`INIT` (метка инициализации).

**Устойчивость:** замена файла — во временный файл в том же каталоге,
`fsync(file)`, `rename`, `fsync(dir)`; строка `attempts.jsonl` дописывается с
`fsync` файла.

Все операции над состоянием — под тем же `flock`, что и прогон: lock хоста
(§4.2) берёт **сам процесс** каждой команды записи — `run --config`,
`init-state`, `init-state --recover`; занят — команда не выполняется (`run` —
пропуск прогона, как `flock -n -E 0`). Внешняя обёртка не нужна и не
используется: два ручных процесса, ручной и таймер, `run` и `--recover` не
пересекаются по построению.

**Попытка:** до отправки мутации пишется `{attempt_id, action, subject,
mutation_id, effect_key, target, marker_key, started_at, status: "in_flight"}`. Не удалось
записать → мутация не отправляется, **общий отзыв** записей прогона,
находка `OPSTATE-WRITE` (уровень `error`) в снимке и код выхода 4:
локальный отказ виден в выдаче и dispatcher, а не в очереди владельца
(записать в неё тоже нельзя). После проверки результата (§5.0 шаг 3) дописывается исход
`ok | failed | rate_limited | uncertain` (для `rate_limited` — после
строки `end` журнала вызовов установки §5.5). Попытка, оставшаяся `in_flight` после прерывания,
считается **неопределённой**, даже если процесс упал до отправки.

**Серия сбоев** — §5.4.

**Карантин.** Состояние утрачено или повреждено (файла нет при наличии
`INIT`, ошибка разбора, несогласованность файлов) → находка `OPSTATE-LOST`
и **восстановление** в одном переходе, по шагам:

1. повреждённые файлы переносятся в `corrupt/<ts>/` (не удаляются);
2. устойчиво пишется `quarantine.json` с `started_at` и новым номером
   поколения состояния `generation = прежний + 1` (прежний неизвестен →
   `1` и признак `unknown_previous`);
3. создаются пустые `attempts.jsonl` и `failures.json` с этим поколением.

Сбой любого шага → записей нет; следующий прогон начинает восстановление
заново с шага 1 (шаги повторяемы). Состояние исправно, когда все файлы
разбираются и несут одно поколение; тогда действует только срок
карантина: 65 минут от `started_at`, перезапуск процесса его не сокращает.
Повторная порча после восстановления — новый переход с новым
карантином. 65 минут — **защитная задержка**, а не
гарантия, что все отправленные ранее мутации проявились; для комментариев
остаётся названный риск позднего дубля (§5.4 общей спеки). После карантина
разрешение не возникает автоматически: прогон заново читает удалённые
объекты и маркеры, пересчитывает действия и проходит все проверки §5.

**Инициализация.** `conductor init-state --config <path>` — явная команда
первого запуска: под `flock` создаёт `INIT`, пустое состояние поколения 1
**и карантин** с `started_at = now` (первый запуск неотличим от полной
потери каталога — задержка выдерживается в обоих случаях). Каталог не пуст
(любой файл, включая `corrupt/`) → отказ, ничего не меняется: повторная
инициализация задержку не сбрасывает. `INIT` пишется
**последним**; прерванная инициализация оставляет каталог без `INIT`.
Обычный `run` при отсутствии `INIT` не угадывает «новая установка или
потеря»: записей нет, находка `OPSTATE-UNINITIALIZED`. Непустой каталог
без `INIT` (потерян только `INIT`, прерванная инициализация) —
`init-state --recover`: под `flock` переносит всё содержимое в
`corrupt/<ts>/`, затем выполняет шаги 2–3 восстановления и пишет `INIT`
последним; сбой любого шага → повторить команду (шаги повторяемы).
`INIT` есть, прочих файлов нет → восстановление с карантином (выше).

### 4.7 `journal.py`: журнал и учёт мутаций

Журнал прогона (`runs/<ts>/journal.jsonl` рядом со снимком) — по строке на
предложенную запись и шаг: действие, субъект, ревизия, доказательство,
признаки тени (§2.2), исход, причина, ключ маркера.

**Учёт мутаций** (`runs/<ts>/calls.jsonl`) — только интерфейс **мутаций**
`gh_write.py` (служебные вызовы App/JWT — ключ, установка, покрытие, свежее
чтение цели — сюда не входят, их учитывает журнал вызовов установки §5.5).
По каждой мутации, включая отказ до отправки, две строки с
`fsync` каждая: `intent` (`{seq, attempt_id, method, endpoint, repo,
marker_key, body_sha256}`) — **до** отправки и после записи попытки
(§4.6); `result` (`{seq, sent: bool, outcome, status_code}`) — после.
Без тела запроса, токенов, JWT и заголовков. `intent` без `result` —
«мог быть отправлен». Учёт прогона **завершён**, когда последняя строка —
`run-end` и у каждого `intent` есть `result`.

Отрицательный результат («вызов не отправлялся») доказывается только
завершённым учётом, согласованным с `attempts.jsonl` того же прогона: нет
`intent` для цели либо `result.sent=false`. Незавершённый учёт
отрицательного результата не доказывает.

## 5. Шаг записи

### 5.1 Проверки перед каждым шагом

Непосредственно перед **каждой** мутацией, в этом порядке; первое
нарушенное условие — причина отказа в журнале:

1. **Забор профиля:** цель ∈ допустимых репо профиля. `fleet` — репо
   манифеста ∪ зонтик; `acceptance` — только `sandbox`. Цель вне забора →
   `FENCE`, мутации нет. Проверка статическая и идёт **раньше** покрытия
   установки, чтобы отказ по забору не маскировался отказом по покрытию.
2. **Состояние:** инициализировано, карантин не действует.
3. **Роадмап** перечитан с `origin/<default>` зонтика (`git fetch` +
   `show`), валиден.
4. **Писатель:** `hostname = writer_host`, `now ≥ writer_since + 65 мин`.
5. **Ключ:** свежий JWT, `GET /app` = 200, `id` = `app_id` конфига.
6. **Разрешение:** уровень позиции ≥ 1 (§2.4), действие ∈ `enabled_actions`;
   в тени — вычисляется, но мутация не отправляется (§2.2). Уровень считается по
   роадмапу шага 3: потолок прогона `run_level = min(--level, autonomy)` (О §2.4;
   `--level` по умолчанию 0, при `--replay` и роадмапе не с origin — 0: офлайн-
   входы не источник живых мутаций; таймер передаёт `--level 3`), уровень
   позиции — по свежему классу, фокусу и `focus.autonomy` её узла. Потолок
   прогона ниже уровня — общий отзыв; уровень позиции ниже — снимается только
   эта запись.
7. **Покрытие:** свежий авторитетный запрос перед **каждым** шагом —
   `GET /repos/{owner}/{repo}/installation` свежим JWT (без следования
   перенаправлениям): 200 и `id` = `installation_id` конфига. 404 →
   `ID-REPO-UNCOVERED`, мутации нет; любая другая ошибка → мутации нет
   (отказ до отправки). Список установки со старта (§8.2) — только для
   планирования, не для разрешения.
8. **Субъект:** свежее чтение цели и субъекта; ревизия и доказательство
   совпадают с записью плана; ответ владельца (если есть) ещё действителен.
   **Цель — существующий объект** (комментарий, правка, закрытие,
   закрепление): свежее чтение без следования
   перенаправлениям возвращает объект, чьи репо (`repository_url`, по
   каноническому имени) и номер равны запланированным; перенаправление
   (перенесённый issue) или расхождение → **снято** (`TARGET-MOVED`), мутация
   не отправляется; следующий прогон планирует заново по новому адресу, и
   забор (шаг 1) и покрытие (шаг 7) проверяются для него. Endpoint мутации
   строится только из запланированных и сверенных репо и номера.
   **Цель — создание в репо** (только создание очереди): `GET /repos/{r}`
   без следования перенаправлениям возвращает запланированное
   каноническое имя (переименование/перенос репо → `TARGET-MOVED`), и
   повторный поиск очереди (§6.1, открытые и закрытые) пуст; номер
   берётся из ответа создания, сверяется на шаге verify и используется
   последующими шагами как цель — существующий объект.
8a. **Запрет по лимиту:** действующий запрет журнала вызовов установки
   (§5.5) в прошлом; иначе — общий отзыв записей прогона (лимит — у
   установки, не у шага).
9. **Задержка повтора:** для того же ключа эффекта `effect_key` (§5.4) нет
   попытки
   `in_flight` или `uncertain` моложе 60 минут (§5.3).
10. **Бюджет:** счётчик попыток прогона < `max_writes_per_run`.

Нарушены 3–5, снят писатель или `autonomy` стал ниже уровня → **общий
отзыв**: записи прогона прекращаются. Нарушено 6 только по `enabled_actions`
→ **отзыв действия**: его шаги не выполняются, остальные продолжаются.
Нарушено 8 → **снято**: запись плана перепланируется следующим прогоном.
Нарушено 2 → записи прогона прекращаются.

### 5.2 Матрица исходов шага

| Исход | Что значит | Этот прогон | Следующий прогон |
|---|---|---|---|
| успех | мутация `ok`, проверка сошлась (verify — **независимое** чтение цели после мутации: комментарий по id, issue, `isPinned`; ответ мутации эффекта не доказывает; не прочитано или не совпало — неопределённо) | следующий шаг действия | — |
| снято | доказательство/ревизия изменились (шаг 8) | не выполнять | пересчёт с нуля |
| отзыв действия | шаг 6 для этого действия | шаги действия не выполняются | по роадмапу |
| общий отзыв | шаги 3–5, писатель, `autonomy` | записи прекращены | по роадмапу |
| забор | шаг 1 | мутации нет, `FENCE` | то же — ошибка данных/конфигурации |
| задержка | шаг 9 | шаг не выполняется | после задержки |
| сбой | `failed` | зависимые шаги не выполняются | повтор; серия §5.4 |
| неопределённо | `uncertain` или `in_flight` | шаг не повторяется, зависимые не выполняются | поиск по идентичности; повтор не раньше §5.3 |
| лимит | `rate_limited` или шаг 8a | записи прекращены | после действующего запрета (§5.5) |
| бюджет | шаг 10 | записи прекращены, `RUN-BUDGET` | остаток |

Неопределённость и сбой блокируют **зависимые** шаги того же действия над тем
же субъектом в этом прогоне; независимые записи продолжаются.

`max_writes_per_run` считает **попытки** мутаций — каждую отправку, включая
неопределённые и `failed`; отказ до отправки попыткой не считается.

### 5.3 Неопределённый исход

- Следующий прогон **до планирования** ищет результат каждой незавершённой
  попытки по идентичности, сохранённой в ней (`op` и ожидаемое: маркер в треде,
  sha256 тела очереди, `closed`/`completed`, закрепление, найденная очередь).
  Нашёл → шаг выполнен, попытке дописывается исход `ok` и задержка её эффекта
  снимается; найденный эффект разрешения не даёт (I7). Не нашёл или чтение не
  удалось — попытка не меняется.
- Не нашёл → повтор разрешён не раньше `started_at + 60 мин` сохранённой
  попытки. Ручной запуск эту задержку **не обходит**: она считается от
  момента попытки в операционном состоянии, а не от таймера.
- Остаточный риск: комментарий, пришедший позже часа, даст дубль — признаётся
  и не маскируется (§5.4 общей спеки). Шаги, идемпотентные по содержимому
  (тело очереди, состояние issue), дубля не дают.

### 5.4 Серия сбоев и вопрос владельцу

**Идентичность мутации** `mutation_id = (action, subject, значимая ревизия,
операция, каноническая цель, ключ события)`: операция — `comment`,
`create`, `body`, `pin`, `close`; цель — `repo#N` или репо для `create`;
ключ события — ключ маркера для комментариев (`q:<id>`,
`sat:<wait>:<evidence>`, …), имя операции для остальных. Два новых вопроса
или два адреса одного ожидания — разные мутации. Значимая ревизия — хэш
доказательства записи плана. `mutation_id` — ключ попытки (§4.6), учёта
вызовов и серии сбоев.

**Ключ эффекта** `effect_key = (операция, каноническая цель, ключ
события)` — **без** действия, субъекта и ревизии: то, что останется в
GitHub после отправки. Для `create` очереди — `(create, <репо>,
owner-queue)` независимо от состава проекции; для комментария —
`(comment, repo#N, ключ маркера)`. Задержка повтора (шаг 9 §5.1, §5.3)
ищет неопределённые попытки по `effect_key`: изменение ревизии плана
(новый вопрос в проекции, новое доказательство) задержку не обходит.
Ревизия остаётся для повторной проверки разрешения (шаг 8 §5.1).

Ключ серии = `mutation_id`. Мутация отправляется не больше одного раза за
прогон, поэтому у ключа в прогоне ровно одно событие; переход — по
таблице (первая подходящая строка):

| Событие ключа в прогоне | Серия |
|---|---|
| отправлен, `ok` | 0 |
| отправлен, `failed` | +1 |
| отправлен, `uncertain` | без изменений |
| отправлен, `rate_limited` | без изменений |
| не отправлен: задержка после неопределённой попытки этого ключа (§5.3) | без изменений |
| не отправлен по любой иной причине (снято, отзыв, бюджет, забор, карантин, записи плана нет) | 0 |

Снятие, отзыв, бюджет, забор и неопределённость — не сбой; «подряд»
значит «без прогона, где шаг не отправлялся по причине, отличной от
задержки своей неопределённой попытки». Локальный отказ до отправки
(`OPSTATE-WRITE`) в серию не входит — он общий и виден находкой (§4.6).

- серия **≥ 2** → **эпизод сбоя** (решение владельца 2026-10-01). Эпизод
  начинается первым сбоем серии и завершается успехом шага (или сбросом
  серии по таблице выше). Локальная запись эпизода в `failures.json`:
  `mutation_id`, класс ошибки (`failed`-код или тип
  GraphQL), последовательные `run_id`, времена, обезличенная диагностика
  (без тел запросов, токенов и заголовков).
- На эпизод — **один** вопрос через обычный `owner_queue` (вид
  `op-failure`, варианты `retry` / `keep`):
  `question-id = sha256("op-failure", ключ серии, run_id первого сбоя
  эпизода, варианты)[:8]`. Очередная неудача того же эпизода не меняет id
  и не вызывает нового упоминания; недоставленный вопрос (очередь
  выключена, бюджет) доставляется следующими прогонами, пока эпизод
  открыт; доставка дедуплицируется маркером `q:<id>`. Завершённый эпизод
  убирает вопрос из проекции очереди; новый эпизод — новый id.
- Ответ на `op-failure` в срезе 1 не исполняется (§6.2): «ответ принят;
  исполнение недоступно». Вопрос — исключение из положительного критерия
  §5.7, принятое владельцем: он сообщает о повторяющемся сбое, который
  иначе не виден вне хоста.
- Сломана сама очередь (сбой `owner_queue`, `GR-QUEUE-*`) или действует
  общий запрет (карантин, лимит, отзыв) → вопрос остаётся только в
  локальной выдаче и снимке; обходного канала записи нет.

Утрата `failures.json` → карантин (§4.6) и отсчёт с нуля.

### 5.5 Запрет по лимиту

Механизм один: **журнал вызовов установки**; действующий запрет из него
**выводится** и устойчиво сохраняется как `blocked_until`. Политика ниже —
выбор conductor (решение владельца 2026-10-01), а не обещание GitHub.

- Файл на хосте, общий для всех профилей:
  `/srv/conductor/shared/app-calls-<app_id>-<installation_id>.jsonl`;
  строки дописываются с `fsync`; путь профилем не настраивается.
- **Каждый** вызов токеном App или JWT (выпуск токена, `GET /app`,
  проверка установки и покрытия, свежее чтение цели, мутации) — две
  строки: `begin` `{seq, at, class}` **до**
  отправки; `end` `{seq, at, outcome, status_code, retry_after_s,
  ratelimit_reset, ratelimit_remaining, blocked_until}` после. Только
  числовые параметры лимита — без тел и заголовков авторизации. Не удалось
  записать `begin` → вызова нет.
- **Признаки лимита:** 403/429 с `x-ratelimit-remaining: 0` или
  `retry-after`, сообщение о вторичном лимите; GraphQL — `errors` типа
  `RATE_LIMITED`. Обычный 403 без этих признаков — `failed`, не лимит.
  Успешный ответ (`ok`) с `x-ratelimit-remaining: 0` остаётся `ok`, но
  устанавливает запрет до `x-ratelimit-reset` для последующих вызовов.
- **Срок известен:** есть `Retry-After` → `at + retry-after` (полностью,
  без верхней границы); исчерпан основной лимит → `x-ratelimit-reset`.
- **Срок неизвестен** — лимит без обоих заголовков, `begin` без `end`
  (прерванный вызов), утраченный или неразбираемый журнал (кроме
  обрезанной последней строки — она считается `begin` без `end` с `at` =
  время изменения файла): запрет `1 ч · 2^k`, `k` = 0, 1, 2, 3 — 1, 2, 4,
  максимум 8 часов. `k` ведётся **по классу операций** — `create` (`POST
  …/comments`, `POST …/issues`), `update` (`PATCH …/issues/{n}`,
  `pinIssue`), `service` (выпуск токена, `GET /app`, проверки установки,
  покрытия и цели); событие относится к классу своего `begin`. `k` класса
  сбрасывает только успешный вызов **того же класса**: обязательный
  успешный `GET /app` перед шагом не сбрасывает серию `create`. Утраченный
  журнал — одно событие неизвестного срока для всех классов с `k = 0`.
  Запрет `blocked_until` — общий для установки, независимо от класса.
- Утраченный/неразбираемый журнал переносится в `corrupt/`, новый
  начинается записью события неизвестного срока, находка
  `RATE-STATE-LOST`. Первый `init-state` на хосте создаёт пустой журнал.
- `blocked_until` = максимум по всем действующим срокам; хранится
  устойчиво и действует между ручными запусками и профилями (шаг 8a §5.1).
  До срока — **никаких** вызовов установки, включая попытку опубликовать
  вопрос о самом лимите (он остаётся в локальной выдаче).
- После срока запрет не даёт разрешения сам: следующий шаг проходит все
  проверки §5.1 заново (ключ, установка, роадмап, субъект). Неопределённая
  мутация восстановлением после лимита **не** переотправляется — её путь
  только §5.3 (поиск по идентичности, задержка).

Чтения учётными данными чтения хоста запрет не касается.

## 6. Очередь владельца и ответы

### 6.1 `owner_queue`

Объект: issue в зонтике (в профиле `acceptance` — в `sandbox`), метка
`owner-queue`, автор `conductor[bot]`. Поиск — среди **открытых и
закрытых** issues с этой меткой и этим автором.

| Найдено | Вопросы есть | Действие |
|---|---|---|
| ничего | нет | ничего |
| ничего | да | создать issue (тело — проекция), затем шаги 2–3 |
| одно открытое | любое | шаги 1–3 |
| одно закрытое | любое | не переоткрывать; `GR-QUEUE-CLOSED`, записей очереди нет |
| больше одного | любое | `GR-QUEUE-AMBIGUOUS`, записей очереди нет |

Шаги:

1. **Тело** — полная перезапись проекцией: все текущие вопросы (с рангом,
   §5.7) по строке `Q-<id>`, варианты со стабильными именами и вариантом по
   умолчанию, «что разблокирует ответ»; при отсутствии вопросов — «вопросов
   нет». В конце — маркер `queue` с хэшем проекции. Сверка: тело равно
   вычисленному.
2. **Закрепить** (`pinIssue`), если не закреплено. Сбой закрепления не
   блокирует шаг 3; сбой или неопределённость шага 1 (тела или создания)
   блокирует шаг 3 этого прогона — вопросы не публикуются поверх
   неподтверждённой проекции. Шаги 1–3 — одна запись плана с этими
   зависимостями. Все три места закрепления заняты (предел GitHub) →
   находка `GR-QUEUE-UNPINNED`, выдача «частично: очередь не закреплена»,
   попыток нет, пока место не освободится. Завершённость очереди — тело
   равно проекции, `pinned = true`, маркер каждого нового вопроса есть.
3. **Комментарий на каждый новый вопрос** — `@<owner> Q-<id>: …` с маркером
   `q:<id>`. Вопрос новый, если действительного маркера `q:<id>` в треде нет.

Тело — проекция и ничего не доказывает; события (вопросы, ответы)
восстанавливаются из треда.

### 6.2 Ответы владельца

Ответ — комментарий в треде очереди от логина владельца флота:
`Q-<id>: <имя варианта | номер>` (§5.8, §5.10). Учитывается текст на момент
чтения; ответ на `Q-<id>`, которого нет среди текущих вопросов, игнорируется.

**Исполнение в срезе 1** — только `close` на `GR-SHIPPED-OPEN` (§7.5).
Действительный ответ с другим вариантом: выдача «ответ принят; исполнение
недоступно в текущем срезе» — только для того же `question-id`,
пересчитывается при изменениях; когда исполнитель появится, ответ
проверяется заново по правилам того среза. Срок исполнения для
`drop-wait`/`treat-done`/… не обещается.

**Идентичность ответа** — `(comment-id, выбранное значение)`; значение —
имя варианта (номер переводится в имя). Редактирование комментария меняет
значение (учитывается текст на момент чтения), удаление убирает ответ.
**Канонический набор ответов** на `Q-<id>` — список действительных
ответов `comment-id:значение`, отсортированный по `comment-id` (числу).

**Конфликт ответов.** В наборе больше одного различного значения → ни
один ответ не исполняется; появляется **производный вопрос
подтверждения** `Q-<id'>`:

- `id' = sha256("confirm", id, канонический набор, версия протокола,
  варианты по порядку)[:8]` — функция **текущего** набора: новый ответ
  (даже повторяющий выбранное значение) или изменение значения меняет
  `id'`, и подтверждение прежнего `id'` перестаёт действовать;
- подтверждение связано с **содержимым** набора, а не с его историей:
  если набор вернулся к подтверждённому (добавленный ответ удалён, значение
  отредактировано обратно), подтверждение снова действует — владелец
  выбирал ровно между этими ответами. Удаления комментариев GitHub в
  timeline не показывает, и более сильного обещания срез не даёт;
- варианты — различные выбранные значения в порядке вариантов исходного
  вопроса; `keep` («не исполнять») добавляется последним, только если его
  среди них нет;
- подтверждение **выбирает** ответ, но не снимает ни одной проверки §5:
  исполнение идёт как по обычному ответу;
- новый ответ на исходный `Q-<id>` меняет набор → `id'` меняется, старое
  подтверждение недействительно (инвалидация);
- конфликт на самом подтверждении → новых вопросов нет, исполнение
  заблокировано, выдача «оставьте один ответ на `Q-<id'>`».

## 7. Действия

### 7.1 Общее

Каждое действие — только по позициям, которые выдаёт ядро среза 0; ни одно
не вычисляет выполненность само — только через §3.4 (требование §11).
Собственные записи conductor (автор `conductor[bot]`) **никогда** не
считаются движением.

**Идентичность факта выполнения** `fact_id` — то, что входит в ключи
маркеров (`sat:…:<evidence>`, `close:…:<evidence>`), `mutation_id` и
`effect_key` вместо SHA снимка. SHA головы репо, на которой факт прочитан,
доказывает свежесть чтения и в ключи не входит:

- пункт TODO выполнен → SHA первого коммита first-parent истории
  `origin/<default>`, в котором пункт стал `[x]` в разобранной версии (как
  период `P` §7.3; снятие и повторная отметка — новый факт); история
  неполна → факт неизвестен, записи нет;
- issue закрыт `completed` → id события `closed` из timeline (`ClosedEvent.id`;
  `closedAt` — только для отображения: время не обещает уникальности
  последовательных закрытий, решение владельца 2026-10-01);
- PR влит → merge commit SHA;
- запрос `done` (§3.4) → `fact_id` пункта, принятого по текущей ревизии;
- структурный `@trigger` (§3.4 общей спеки; ожидание без узла-предпосылки):
  `wait-id` = `(репо потребителя, @id потребителя, каноническое условие)`;
  изменение текста условия — новое ожидание;
  - `date>=YYYY-MM-DD` → `fact_id = date:<YYYY-MM-DD>` (дата наступает
    один раз);
  - `exists:<repo>:<path>` (репо — каноническое имя, путь нормализован) →
    SHA первого коммита first-parent истории `origin/<default>` этого репо,
    в котором путь есть, а в первом родителе — нет (последнее появление);
    удаление и повторное появление пути — новый факт; неполная история →
    факт неизвестен, записи нет.

`evidence-sha = sha256(fact_id)[:12]`. Посторонний коммит в репо не меняет
ключ; действительно новое выполнение — меняет.

### 7.2 `notify_satisfied`

Идентичность — тройка `(ожидание, доказательство, адрес)`; ключ маркера
`sat:<wait-id>:<evidence-sha>`; маркер ищется в треде **этого** адреса.
Условие: вердикт ожидания `satisfied` (§3.4), потребитель открыт и всё ещё
держит тег ожидания, открытый адрес есть (§5.7). Запись — комментарий
«предпосылка выполнена: чем» со ссылкой на доказательство. Несколько открытых
адресов — по записи на каждый; повторный прогон не дублирует ни одной. Нет
адреса (TODO-only) или все закрыты — §1. Перед отправкой (шаг 8 §5.1) свежим
чтением сверяются: адрес открыт и маркера нет, потребитель держит тег на
`origin`, факт выполнения тот же.

### 7.3 `nudge`: возраст и тишина

**Идентичность ожидания** — ребро `(репо потребителя, @id потребителя,
ссылка предпосылки)`. Правка заголовка или владельца строки её не меняет.

**Период ожидания `P`** — SHA первого коммита в first-parent истории
`origin/<default>` репо потребителя, в котором ребро есть в **разобранной**
версии TODO.md, а в его первом родителе — нет (сравниваются множества рёбер,
а не строки). Удаление ребра и повторное добавление — новый период (берётся
последнее появление). Неполная история (мелкий клон, недочитанная история)
или неоднозначность → возраст неизвестен, **пинка нет**, строка выдачи
«возраст неизвестен».

**Возраст** = `now − дата коммита P` (committer date). **Тишина** = `now −
max(дата P, последнее движение)`; движения не было — тишина равна
возрасту. «Не было» доказывается только полным чтением всех источников
движения (история коммитов, PR, тред предпосылки); любой недочитанный
источник → тишина неизвестна, пинка нет. Движение — коммит с `@id` предпосылки в сообщении,
PR с `implements` на неё, комментарий в её треде — всё **не** от
`conductor[bot]`. `updated_at` issue движением не считается (его меняют и
наши комментарии). Движение сбрасывает тишину, но не возраст.

Ключ маркера `nudge:<wait-id>:<P>:<n>`; `n` — следующий номер после
наибольшего `n` действительных маркеров этого `wait-id` и `P`.

- **Первый пинок** (`n = 1`): возраст ≥ `stale_after_days` **и** тишина ≥
  `stale_after_days`.
- **Повтор** (`n > 1`), две ветки:
  - движения с последнего пинка не было → достаточно `now − последний пинок
    ≥ renudge_after_days`;
  - движение было → `now − последний пинок ≥ renudge_after_days` **и**
    тишина (от последнего движения) ≥ `stale_after_days`.

Пинок — только по позициям **с рангом** (§4.2), вердикт ожидания `pending`,
открытый адрес продюсера есть; пинок идёт в первый открытый адрес (по
каноническому порядку). Нумерация `n` и интервал повтора — по ожиданию и
периоду: маркеры `nudge` ищутся во **всех** тредах продюсера, включая закрытые
(решение владельца 2026-10-01): смена или закрытие первого адреса не разрешает
немедленного повтора. Иначе — строка выдачи с причиной: `нет ранга` /
`нет адреса` / `нет открытого адреса доставки` / `маркер есть` / `ожидание не
pending` / `возраст неизвестен`.
Текст пинка: что ждёт, с какой даты (дата `P`), следующий шаг.

### 7.4 `pr_nudge`

Ключ `prnudge:<pr>:<n>`; пороги и две ветки повтора — как у `nudge`, где
возраст — от **последнего** события `ready_for_review` (у PR, который не был
драфтом, — от `created_at`); PR сейчас драфт → пинка нет; тишина — от
max(начало возраста, последнее движение); движение — коммиты, ревью,
комментарии **не** от App. Событие `ready_for_review` — движение
(сбрасывает тишину) и начало нового возраста, но не новая нумерация `n`:
повтор после него идёт по ветке «движение было» и требует полного
периода тишины `stale_after_days`. Новая голова PR — движение, но сама по себе
пинка не разрешает. Красный CI пинка не разрешает: нужен тот же порог
застоя. Для красного PR текст несёт имена упавших проверок на head SHA,
ссылки на них и пометку «лог не прочитан»; исправление не предлагается.
Перед отправкой (шаг 8 §5.1) основания потребности перечитываются: проверки
и одобрение текущего head, драфт, head; пересчитанная потребность и (для
красного) набор упавших проверок должны совпасть с текстом плана, иначе пинок
снят; не прочитано — не писать. Изменение `updated_at` — дополнительный
консервативный запрет, а не замена этого чтения.

### 7.5 `close_shipped`

Основание (единый вердикт ядра `GR-SHIPPED-OPEN`, §3.4) — одно из:

- (а) у issue есть ребро `implements` от PR, влитого в **ветку по умолчанию**
  репо, через `closingIssuesReferences` (строгая ссылка) — вопрос владельцу
  не нужен и не задаётся. **Обнаружение:** для каждого открытого issue с
  рангом срез 1 дочитывает `closedByPullRequestsReferences(includeClosedPrs: true)` (GraphQL,
  с пагинацией) и проверяет мерж, базу = ветку по умолчанию и
  `closingIssuesReferences` самого PR; так влитый PR находится, даже если на
  него нет ссылок в TODO и других загруженных объектах. Недочитано — граф
  `partial`;
- (б) действительный ответ владельца `close` на вопрос `GR-SHIPPED-OPEN`
  текущего периода (§6.2) — для **любого** происхождения: legacy inbox по
  `accepted_as`, а также issue, переоткрытый после влитого PR (основание (а)
  прежнего периода; вопрос текущего периода задаёт строка `GR-REOPENED`
  таблицы ниже).

Slug-наследие само основания не даёт.

Шаги:

1. Комментарий «выполнение подтверждено: чем» (артефакт, SHA, ссылка) с
   маркером `close:<node>:<period>:<evidence-sha>`.
2. Закрыть `state=closed, state_reason=completed`.

**Период открытия** — от последнего события `reopened` (любого автора,
после любого закрытия: App, человека, GitHub при мерже, иной автоматизации)
или от создания issue. Основание действует только в **своём** периоде:

- (а) — PR влит **после** начала текущего периода (влитый до переоткрытия
  основанием не служит: владелец переоткрыл issue вопреки ему);
- (б) — действительный ответ `close` на вопрос текущего периода:
  доказательство `GR-SHIPPED-OPEN` включает id последнего `reopened`, так
  что каждый период даёт новый `question-id` и `evidence-sha`.

Ключ маркера включает период: `close:<node>:<period>:<evidence-sha>`
(`period` — id последнего `reopened` или `0`); маркеры прежних периодов не
учитываются.

Строки проверяются сверху вниз, действует первая подходящая.

| Состояние перед прогоном | Основание текущего периода | Действие |
|---|---|---|
| открыт, переоткрыт (есть `reopened`), основание есть только в прежних периодах | нет | записей нет; находка `GR-REOPENED`; вопрос текущего периода (`close` / `keep`) |
| открыт, маркер с **полным** текущим ключом `(node, period, evidence-sha)` есть | есть | шаг 2 (маркер перечитывается непосредственно перед ним) |
| открыт, маркера с полным текущим ключом нет (маркер другого доказательства или периода не считается) | есть | шаги 1–2 |
| открыт, маркер текущего периода есть | нет | ничего; выдача «частично: основание снято» |
| закрыт `completed`, маркер текущего периода есть | — | готово |
| закрыт `completed`, маркера текущего периода нет | — | цель достигнута извне; записей нет |
| закрыт `not_planned` или причина пуста | — | автозакрытие прекращено; выполненным не считается |

Перед **каждым** шагом (шаг 8 §5.1) основание перечитывается: (а) — PR
влит тем же merge SHA и всё ещё закрывает issue; (б) — ответ действителен
по свежим комментариям очереди **и** основание самого вопроса пересчитано по
свежим данным (пункт на `origin` — тем же каноническим разбором TODO, что
у ядра: есть и выполнен; затем склейка заявки с ним — теми же правилами
`accepted_as`; снимок графа прогона существования пункта не доказывает;
влитый PR, переоткрытие) с той же идентичностью вопроса: ответ разрешает
закрытие, но не заменяет доказательство. Перед шагом 2 в треде должен быть
действительный маркер подтверждения с полным текущим ключом (событие App,
без правки) — удалённое или отредактированное подтверждение снимает шаг;
новый прогон пересчитает план, новый комментарий в рамках прежнего
разрешения не дописывается.

События `closed`/`reopened` читаются из timeline issue
(`GET /repos/{r}/issues/{n}/timeline`, право `issues: read`).

Никогда: переоткрывать, закрывать `not_planned`, закрывать PR.

### 7.6 Частичное выполнение

Действие, прерванное между шагами (отзыв, снятие, сбой, неопределённость),
не откатывается. Выдача показывает «частично: <какой шаг> — <причина>».
Следующий прогон доводит, если основание в силе и действие разрешено
(I7: маркеры не запрещают довести недоделанное).

## 8. Расписание и запуск

- Таймер (`conductor.service`) — боевой конфиг хоста: срез 0 — под внешним
  `flock -n -E 0`; с фазой записи (drop-in) — `run --level 3 --config …`, lock
  хоста берёт сам процесс (§4.6).
- Ручной `conductor run` на хосте — тот же путь; lock хоста исключает
  пересечение с таймером.
- Профиль `acceptance` — отдельный конфиг `/srv/conductor/acceptance.toml`
  с отдельным `state_dir` (`/srv/conductor/acceptance/`), запускается только
  вручную (`--config`).
- `conductor init-state --config <path>` — один раз на конфиг (§4.6).

## 9. Приёмка в песочнице

### 9.1 Стенд

- Репо `<owner>/conductor-sandbox` — мини-флот, одновременно зонтик и
  единственный репо-цель: `roadmap.toml`, манифест, `epics.toml`, `TODO.md`,
  issues, заранее созданный PR с нарочно красной проверкой.
- Репо `<owner>/conductor-sandbox-outside` — фикстура забора: в манифесте
  песочницы (его узлы попадают в граф и дают адреса), App на него **не**
  ставится, в заборе профиля его нет. **Обязательное покрытие** на старте
  (§8.2 общей спеки) — только репо записи профиля: в `acceptance` —
  `sandbox`, в `fleet` — зонтик; репо чтения вне забора покрытия не
  требуют и `ID-MISMATCH` не дают.
- Репо, App и установку создаёт владелец; App ставится только на песочницу.
- Правку приёмочного `roadmap.toml` (только `autonomy` и `enabled_actions`)
  публикует `deploy/conductor/acceptance.sh` полномочиями владельца — не
  conductor и не App.
- Учётные данные чтения хоста имеют доступ к обоим репо.
- Зонтик профиля `acceptance` — сама песочница: манифест, роадмап, эпики,
  очередь и состав мини-флота читаются только из неё; настоящий зонтик
  владельца в граф приёмки не добавляется и не читается (внешние чтения —
  `sandbox` и объявленный `outside`).

### 9.2 Точки остановки

Фиксированные именованные точки из `stop_points`, только в профиле
`acceptance`: `after_comment` (после успешного комментария, до следующего
шага), `before_close` (перед шагом 2 `close_shipped`), `after_intent` (попытка и
`intent` записаны, вызов **не** отправлен — неопределённость без
видимого результата), `after_send` (HTTP-ответ адаптера получен, строка `end` журнала вызовов
установки §5.5 записана устойчиво, затем результат отброшен **до** исхода
попытки §4.6 и строки `result` учёта §4.7 — «GitHub принял, ответа нет»
для шага; попытка остаётся `in_flight`, запрета установки нет). Обрыв
**до** `end` (запрет неизвестного срока) — только тестами с фейком. В точке процесс пишет журнал и выходит с кодом 5.
Команд и произвольных хуков нет. Отзыв **внутри** прогона доказывается
тестами последовательностей (§11); живьём — через остановку, правку
роадмапа и следующий прогон.

## 10. Ступени во флоте

### 10.1 Порядок

0. **Тень**: `shadow=true`, `autonomy=0`; App ставится на флот. Не меньше
   недели ежечасных прогонов.
1. `autonomy=1`, `enabled_actions=["owner_queue"]`, тень снята.
2. `+ "notify_satisfied"`.
3. `+ "nudge", "pr_nudge"`.
4. `+ "close_shipped"`.

### 10.2 Правило перехода

Три дня — **минимальный срок наблюдения**, не доказательство. Переход к
следующей ступени требует:

- реальных успешных действий включённого на ступени типа (для тени —
  предложений каждого типа);
- разбора каждого частичного и неопределённого исхода;
- отсутствия нерешённых дефектов.

Если подходящих действий не было — ступень **не проверена**, переход не
делается. Включение следующей ступени подтверждается самой правкой роадмапа
владельцем (authority-root). Выход из тени — дополнительно ноль `sent=true`
за неделю и разбор каждого неверного предложения.

**Соответствие общим критериям живой приёмки (§10 общей спеки).** Для
среза 1 они применяются так:

1. «нет ложных действий» — на каждой ступени, разбором журнала владельцем
   (неверное предложение тени или запись = дефект, ступень не пройдена);
2. два показателя раздельно, оба за период ступени:
   - **полнота собранных графов** = `partial / (complete + partial)` по
     прогонам **таймера** за период — не больше **5 %**; ручные прогоны не
     входят ни в числитель, ни в знаменатель;
   - **доступность расписания** = число часовых слотов периода, в которых
     есть хотя бы один прогон **таймера** с `complete` или `partial`
     (не больше одного засчитанного на слот), / число часовых слотов
     периода — не меньше **90 %**; `skipped` по `flock`, аварии и
     отсутствующие запуски — неизмеренные слоты. Ручные прогоны в
     доступность не входят.
   Нулевой знаменатель — «не проверено». Любой показатель вне порога —
   ступень не пройдена, разбор причин. (Пример: 68 skipped, 3 partial,
   1 complete из 72 — полнота 75 %, доступность 6 % — не пройдена.)
3. «вопросов меньше, чем снятых ожиданий» — к ступеням 0–3 не
   применяется (очередь и уведомления ожиданий не снимают); измеряется за
   неделю после включения ступени 4 и является условием приёмки среза
   целиком (ожидание снято = вердикт перешёл в `satisfied` или узел
   закрыт `close_shipped`);
4. replay — только для среза 0.

**Откат** — правка роадмапа (убрать действие или `autonomy=0`) или удаление
ключа. Код не меняется; сделанные записи не отменяются.

## 11. Тестирование

- **Тесты последовательностей с фейковым GitHub** (CI): для каждого действия
  полная таблица «состояние × исход каждого шага (успех, сбой,
  неопределённость, задержка, бюджет, отзыв действия, общий отзыв, снято,
  забор)» с отрицательным двойником на каждую строку (требование §11 общей
  спеки). Изменение ревизии субъекта, роадмапа, ответа и удалённого
  состояния между **любыми** двумя шагами.
- **Управляемые часы**: возраст, тишина и обе ветки повтора §7.3–7.4;
  задержка повтора §5.3; карантин §4.6 и его несокращаемость перезапуском.
- **Операционное состояние**: сбой записи до мутации → нет мутации;
  `in_flight` после «падения» → неопределённо; порча каждого файла →
  карантин; нет `INIT` → нет записей; все правила серии §5.4.
- **Маркеры**: чужой автор, отредактированный, неизвестная версия,
  неканонический порядок ключей.
- **Секреты**: фильтр ошибок; в журнале, учёте и снимке нет секретов.
- **Белый список мутаций** адаптера (§4.5).
- **Производный вопрос**: детерминизм `id'`, инвалидация (в том числе
  ответом, повторяющим выбранное значение; редактированием; удалением),
  конфликт на подтверждении.
- **Ревизия против задержки**: неопределённое создание очереди → в
  проекции появился новый вопрос → ручной прогон до часа → повторного
  `create` нет.
- **Несколько мутаций одного шага**: два новых вопроса и два адреса со
  смешанными исходами (`ok` / `failed` / `uncertain`) — свои серии и
  задержки у каждой; обе доставляются.
- **Успех с нулевым остатком** (`pinIssue`, `x-ratelimit-remaining: 0`) →
  `ok` и запрет до reset.
- **Маркер и экранирование**: цитата с `conductor:v1` в исходном тексте не
  становится маркером собственного комментария; два блока — не маркер.
- **Исходы вызова**: каждый код/тип GraphQL ошибки из §4.5 → свой исход;
  5xx на комментарии → задержка, не немедленный повтор.
- **Переоткрытие**: `closed` от App → `reopened` → записей нет, в том числе
  после удаления или правки нашего комментария `close`; `merged PR →
  closed не от App (человек, мерж) → reopened` — записей закрытия нет, со
  старым маркером и без; ответ `close` текущего периода разрешает только
  его; PR, влитый после `reopened`, — основание (а) текущего периода.
- **Покрытие**: цель покрыта на старте, после первого шага доступ отозван
  → второй шаг без мутирующих вызовов; проверяется фактический свежий
  запрос `GET /repos/{r}/installation`, а не подмена стартового списка.
- **Серия по классу через полный исполнитель**: `POST limited → пауза →
  GET /app ok → POST limited` — 1, 2, 4, 8 ч; успешный `POST` сбрасывает.
- **Показатели ступени**: 68 skipped / 3 partial / 1 complete из 72 — не
  пройдена; 1 таймерный complete + 71 ручной при 71 пропущенном слоте —
  доступность 1/72, не пройдена; полностью пропущенное расписание —
  «не проверено».
- **Полнота при ручных прогонах**: 68 таймерных `partial` + 4 `complete` и
  1292 ручных `complete` — полнота 94 % неполных, не пройдена.
- **Кодирование маркера**: полный цикл для `date>=…`, `exists` с не-ASCII
  и спецсимволами пути, `repo!N` — `h1-…` → отправка → чтение → повторной
  отправки нет; значение вне `[a-z0-9-]+` — недействительно.
- **Смена доказательства закрытия**: маркер с фактом A, затем основание B
  в том же периоде — шаги 1–2 с B, закрытие не опирается на маркер A.
- **`@trigger`**: `exists` — первая доставка, посторонний коммит без
  дубля, удаление и повторное появление пути — новое уведомление; `date>=` —
  одно уведомление; правка условия — новое ожидание.
- **Стабильность `fact_id`**: посторонний коммит после выполнения пункта —
  ключ `sat` тот же, повторного уведомления нет; снятие и повторная
  отметка `[x]` — новый ключ.
- **Тень и служебные вызовы**: тень с реальными `GET /app` и проверкой
  покрытия — ноль `sent=true` в учёте мутаций.
- **Старт приёмки**: манифест с `outside`, установка только на `sandbox` —
  нет `ID-MISMATCH`, A2 пишет, A10 даёт `FENCE` через полный путь проверки
  установки.
- **Ответ `close` для не-legacy issue**, переоткрытого после влитого PR,
  исполняется (шаги 1–2 текущего периода).
- **Лимит**: `Retry-After` больше 8 ч выдерживается полностью;
  `x-ratelimit-reset` при исчерпании; без заголовков — 1, 2, 4, 8, 8 ч и
  сброс после успеха; падение между ответом и `end` → неизвестный срок;
  обычный 403 без признаков → `failed`; `pinIssue` с GraphQL
  `RATE_LIMITED` → `rate_limited`; вопрос о лимите до срока не
  публикуется; после срока неопределённая мутация не переотправляется.
- **Обнаружение влитого PR** от открытого issue через загрузчик (без
  заранее подложенного PR в графе) → основание (а).
- **Первое создание очереди** через полный исполнитель §5: проверка «создание
  в репо», номер из ответа, шаги 2–3 по нему.
- **Лимит (прочее)**: ручной запуск запрет не обходит; запрет из `fleet`
  виден `acceptance` той же установки; порча журнала → `corrupt/` и
  запрет неизвестного срока; выпуск токена и проверка установки при запрете не
  выполняются.
- **Два переоткрытия** с закрытием по ответу между ними — второй период
  требует нового ответа.
- **Перенос issue** в репо вне забора, но покрытое установкой →
  `TARGET-MOVED`, мутации нет; следующий прогон — `FENCE`.
- **Обрыв до `end`** журнала установки после принятого комментария: маркер
  сверяется сразу (`ok`), но шаг 2 ждёт запрета неизвестного срока —
  находка маркера запрет установки не снимает.
- **Полный цикл маркера** для каждого вида, включая `prnudge` с
  `pr` = `h1-…` от `repo!N`: кодирование → отправка → чтение → повторной отправки нет.
- **Невидимая принятая запись** (`after_send`, комментарий не виден в
  чтении) — фейком: задержка, затем поиск и повтор через час.
- **Повтор `pr_nudge` после `ready_for_review`** при существующем пинке —
  нужен полный `stale`.
- **Учёт мутаций**: падение между `intent` и `result` → «мог быть
  отправлен».
- **Мутационная проверка**: каждое условие §5.1 удаляется по одному — хотя бы
  один тест краснеет.
