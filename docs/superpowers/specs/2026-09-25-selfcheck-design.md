## 0. Цель и границы

`selfcheck` — детерминированный конвейер проб над репо, выдающий **отчёт**
(JSON + Markdown) с находками категорий: bug, quality, dead, duplicate, deps,
llm-replaceable, selfcheck (о самом приборе). Главная ценность — dead и
duplicate для скриптов devtools, целей `Makefile`, skills и slash-команд.

Критерии успеха:
1. каждая проба видна в сводной таблице прогона (версия, argv, код выхода,
   статус, канарейка, покрытие, число находок); проба, чей анализ не
   подтверждён, — находка, а не тишина (§4);
2. каждый исполняемый узел devtools получает класс использования с рёбрами-
   доказательствами (§3.2); на трудных вызывающих (§6.1) dead-находок нет;
3. находки имеют стабильную идентичность (§2.1) и `owner_repo` — формат готов
   к автозаведению issues без переделки;
4. каждое правило на фикстуре срабатывает на своём случае и не срабатывает на
   отрицательном двойнике (§6); ожидания dead выводятся из матрицы §2.3;
5. пробы S1–S3 не исполняют код цели и не пишут в сканируемые checkout'ы
   штатно (§1.3: read-only копия, вынесенные кэши — защита от случайной
   записи, не изоляция); LLM без `--judge` не вызывается, с `--judge` — без
   инструментов и доступа к файлам (§5).

Вне объёма (S1–S5): автофиксы и автоудаление; автозаведение issues; CI-гейт
(решается после нескольких прогонов по доле ложных срабатываний); правка
соседних репо; runtime-телеметрия фактических запусков (§3.2.2);
LLM-вызовы в Elixir; **пробы, исполняющие код цели** (clippy, credo,
`mix xref`, knip) — отдельная спека S4 со своими песочницей, материализацией
зависимостей и проектной канарейкой; установка зависимостей цели.

## 1. Архитектура

Пакет `devtools/selfcheck/`, точка входа `python -m selfcheck`.

```
load (manifest, config) ─► materialize (копии корпусов) ─► collect (пробы)
    ─► normalize ─► group ─► judge (opt) ─► delta ─► report
```

- **Проба** — один внешний инструмент или один собственный анализатор. Вход —
  `RepoTarget` (`owner_repo`, языки, путь к **копии** корпуса §1.3,
  путь к исходному checkout — только для чтения git-истории) и каталог пробы;
  выход — `ProbeResult` (§4.1). Пробы не знают друг о друге.
- **Нормализация** приводит вывод к атомарным `Finding` (§2).
- **Группировка** связывает находки на одном якоре для показа, не сливая их
  (§2.1), и применяет allowlist (§2.4).
- **Дельта** сравнивает с базовым прогоном (§4.3).
- **Отчёт** — `out/selfcheck/<run_id>/report.{json,md}` в devtools.

`run_id` = UTC-метка `YYYYMMDDTHHMMSSZ` + `-` + 6 случайных hex; каталог
прогона создаётся атомарно (`mkdir` без `exist_ok`), существующий каталог
никогда не переиспользуется. Отчёт, который владелец хочет сохранить в
истории, копируется в `reports/selfcheck/` вручную; этот путь имеет роль
`diagnostic-output` (§1.4) и не влияет на следующие прогоны.

### 1.1 Цели Makefile

| Цель | Что делает |
|---|---|
| `make selfcheck` | прогон на devtools (`ARGS`: `--fleet`, `--repo X`, `--judge`, `--sched-dir D`) |
| `make selfcheck-dogfood` | прогон на собственном пакете `selfcheck/` + фикстурные тесты |

Имя `selfcheck` принадлежит инструменту; прогон на себе — только
`selfcheck-dogfood`.

### 1.2 Набор репо и языки

Репо выводятся из `$(MANIFEST)`: записи секций `cores`, `apps`, `tools`
дедуплицируются по `git_dir` (записи с `member = true` делят каталог с
родителем). Число репо в спеке не фиксируется: отчёт печатает, сколько записей
прочитано, сколько уникальных `git_dir` просканировано; отсутствующий на диске
или нечитаемый каталог — находка `selfcheck/repo-missing` и `fleet = partial`
(§3.2.4).

Языки — по файлам-маркерам в `git_dir`:

| Маркер | Язык | Пробы S1–S3 |
|---|---|---|
| `pyproject.toml` | Python | ruff, pyrefly, vulture, deptry, radon, ast-dup |
| `Cargo.toml` | Rust | cargo-machete |
| `mix.exs` | Elixir | — |
| `package.json` | TS/JS | — (llm-sites через semgrep — в строке «любой») |
| любой | — | usage-graph, cli-overlap, llm-sites, shellcheck, actionlint, zizmor, jscpd |

Репо с несколькими маркерами получает объединение проб.

**Граница S1–S3 / S4 — по признаку «проба исполняет код цели»**, не по языку.
Каждая проба реестра объявляет `executes_target_code`; для S1–S3 допустимо
только `false`:

| Проба | Исполняет код цели | Этап |
|---|---|---|
| ruff, vulture, radon, deptry, pyrefly | нет (AST / статический разбор / чтение метаданных) | S1–S3 |
| shellcheck, actionlint, zizmor `--offline` | нет | S1–S3 |
| jscpd, semgrep (в т.ч. TS для `llm-sites`) | нет | S1–S3 |
| cargo-machete (разбор `Cargo.toml` + поиск по исходникам, `build.rs` не запускает) | нет | S3 |
| usage-graph, ast-dup, cli-overlap, llm-sites | нет | S1–S3 |
| clippy (`build.rs`, proc-macro), credo и `mix xref` (компиляция), knip (загружает JS/TS-конфиги) | **да** | S4, отдельная спека |

### 1.3 Read-only копия корпуса: защита от случайной записи

**Что гарантируется и что нет.** Пробы S1–S3 не исполняют код цели (§1.2),
поэтому единственный источник записи — сам инструмент (кэш, отчёт). Механизм
ниже защищает от **случайной** записи инструмента в сканируемый код и делает
её видимой; это **не изоляция**: процесс с правами пользователя может вернуть
себе права (`chmod`) или писать по абсолютному пути в исходный checkout, и
selfcheck этого не предотвращает. Изоляция нужна пробам, исполняющим код
цели, — она в объёме спеки S4.

- **Материализация.** Для каждого репо корпус (§1.4) копируется в
  `out/selfcheck/<run_id>/src/<repo>/` (обычные файлы; symlink'и не
  копируются), затем копия делается read-only (`chmod -R a-w`). Все пробы
  получают **только путь к копии**. Одна неизменяемая копия на репо — одна и
  та же поверхность для всех проб (рабочая копия, включая незакоммиченное);
  порядок проб на неё не влияет.
- **Кэши и вывод — вне копии**, для каждой пробы явно (фиксируется в
  реестре): `cwd` = `out/selfcheck/<run_id>/work/<probe>/<repo>/`; ruff —
  `--no-cache`; jscpd — `--output <work>` и `--store-path <work>`; semgrep —
  `--metrics off`, выход в `<work>`; zizmor — `--offline`. Инструмент,
  попытавшийся писать в копию, получает `EACCES` и становится `failed` с
  причиной `write-to-corpus` — это видимый сбой, а не порча.
  **Исключение `cwd`:** проба, чьи правила исключений инструмент применяет
  к путям относительно `cwd` (deptry: регулярные выражения исключений
  якорятся к началу относительного пути), объявляет в реестре `cwd = копия`
  и передаёт корень как `.`; её единственный вывод — явный файл в каталоге
  пробы (`--json-output <work>/…`). Запись в копию по-прежнему ловит
  read-only. Чужие канарейки в копии исключаются из обхода такой пробы явно
  (`.selfcheck-canary`).
- **Уборка** — `chmod -R u+w` перед `rm -rf` каталога `src/`; сбой уборки —
  предупреждение в отчёте, не код выхода.
- **Git-история и корпус** читаются ядром selfcheck из исходного checkout
  только командами `git ls-files` и `git log` с `GIT_OPTIONAL_LOCKS=0`
  (`git status` не используется — он обновляет индекс). Пробы к исходнику
  не обращаются.
- **Окружение инструментов.** Python-инструменты — `uv run --project
  <devtools> --frozen --group selfcheck <tool>` (группа добавляется в
  `devtools/pyproject.toml` рядом с `dev`/`governance`); node-инструменты —
  `npx --yes <pkg>@<точная версия>`; системные бинари (`shellcheck`,
  `actionlint`, `zizmor`, `semgrep`, `cargo-machete`) — из `PATH` с проверкой
  версии по диапазону реестра (§4.1). Окружение инструментов —
  `devtools/.venv`; при dogfood (цель = devtools) это игнорируемый каталог
  вне корпуса, и `uv run` может его синхронизировать — это окружение
  инструмента, не сканируемый код.

### 1.4 Корпус и роли источников

Корпус репо — `git -C <target> ls-files --cached --others --exclude-standard`
минус пути из `[corpus] exclude` в `selfcheck.toml` (glob'ы; исключённый
путь не видит ни одна проба); игнорируемые git'ом файлы (`.venv`,
`out/`, установленные копии skills в `devtools/.claude/skills/*`) в корпус не
входят. `_cowork_output/` в корпус не входит никогда (не репо манифеста;
правило корневого `CLAUDE.md`).

Каждому файлу корпуса назначается **роль** по реестру путей (дефолты — в коде,
дополнения — `[roles]` в `selfcheck.toml`). Роль определяет, что файл может
давать графу; включение в корпус само по себе ничего не даёт:

| Роль | Пути по умолчанию | Узлы | Рёбра | Упоминания |
|---|---|---|---|---|
| `source` | всё, что не подпало под другие роли | да | исполняемые | да |
| `skill-root` | `skills/*/SKILL.md`, `.claude/skills/*/SKILL.md`, `authored/skills/*/SKILL.md`, `.claude/commands/*.md` | корень | `skill` | да |
| `test` | `tests/**`, `test_*.py`, `*_test.py` | нет | `test` | нет |
| `documentation` | `*.md` вне ролей выше, `docs/**` | нет | `runbook`, `doc` | нет |
| `diagnostic-output` | `reports/**`, `out/**` | нет | нет | нет |
| `canary` | `.selfcheck-canary/**` (§4.1) | только для своей пробы | только внутри канарейки | нет |
| `vendored-in` | не по путям: член вендор-декларации (§9.7), поверх роли выше | как у базовой роли, но без dead | как у базовой роли | как у базовой роли |

Один и тот же реестр путей применяется при выделении узлов, корней и рёбер.
Различие двух механизмов: `[corpus] exclude` убирает путь из корпуса — его
не видит **ни одна** проба (ни линтеры, ни граф); роль `diagnostic-output`
оставляет файл в корпусе (линтеры его видят, если он в их входах), но
запрещает ему быть доказательством для графа.
Установленные skills учитываются через их трекаемый исходник
(`prograph-vault/authored/skills/*/SKILL.md`) при `--fleet`.

### 1.5 Окружение статических проб

pyrefly и deptry без окружения цели дают шум: неразрешённые сторонние
импорты у pyrefly, угаданное соответствие модулей и дистрибутивов у deptry.
Замер 2026-09-26 на devtools: `deptry .` без окружения — 21 находка, в том
числе ложная `DEP001 'yaml'`. Ставить зависимости самим нельзя без исполнения
кода: `uv sync --frozen --no-install-project --no-install-workspace
--no-build` на devtools отказывает — `plan-fields` подключён git-источником
без wheel и требует сборки (класс S4).

**Правило: окружение цели — только данные.** Каталог `site-packages` цели
никогда не попадает в путь импорта процесса инструмента (`PYTHONPATH`,
`.pth`), и интерпретатор цели не запускается: иначе `sitecustomize.py` или
исполняемые строки `.pth` из окружения цели исполнились бы при старте
инструмента, и проба перестала бы быть статической.

| Режим | Когда | Как запускаются пробы | Находки import-класса |
|---|---|---|---|
| `checkout-venv` | в исходном checkout есть `.venv/pyvenv.cfg` | **deptry**: selfcheck сам читает `<site-packages>/*.dist-info` как файлы (`METADATA` → `Name`; `top_level.txt`, иначе верхние элементы `RECORD`), сопоставляет дистрибутивы с объявленными зависимостями цели по нормализованному имени (PEP 503) и передаёт `--package-module-name-map` с ключами **в написании деклараций цели** (deptry ищет ключ точным совпадением с именем требования: `pyyaml>=6.0.3` ↔ `Name: PyYAML` → ключ `pyyaml`); `--ignore DEP003` (§ниже). **pyrefly**: `--skip-interpreter-query --site-package-path <site-packages> --python-version <из pyvenv.cfg> --python-platform <платформа хоста>` | как есть |
| `checkout-venv` + флаг `env-stale` | то же, но `uv.lock` новее `pyvenv.cfg` | то же | не выше `candidate` |
| `no-env` | `.venv/pyvenv.cfg` нет | без окружения | pyrefly — неразрешённые импорты, deptry — `DEP001` переносятся в раздел `suppressed-no-env` со счётчиком по правилу; остальные — как есть |

Замер механизма `checkout-venv` на devtools (2026-09-26): соответствие,
переданное через `--package-module-name-map`, даёт те же 11 находок, что и
`PYTHONPATH=<site-packages>`, без добавления каталога цели в путь импорта.

**`DEP003` отключается во всех режимах**: deptry решает, «установлен» ли
пакет, по окружению **своего** процесса, то есть по окружению инструмента, а
не цели (в замере ложный `DEP003 'tomli'` пришёл из окружения deptry).
Цена названа явно: импорт необъявленного пакета, который **есть в окружении
инструмента**, deptry относит к `DEP003`, а не к `DEP001`, поэтому после
отключения `DEP003` такой импорт не виден ни одним правилом. Импорт
необъявленного пакета, которого в окружении инструмента нет, остаётся
видимым как `DEP001`. Потеря покрытия фиксируется в сводной таблице проб
(`deptry: DEP003 off — tool-env packages not covered`).

Selfcheck зависимостей цели не ставит (§0, вне объёма).

## 2. Находка

```json
{
  "id": "sc-3f9a1c2e",
  "rule": "usage-graph/dead.file",
  "probe": "usage-graph",
  "category": "dead",
  "severity": "medium",
  "confidence": "likely",
  "owner_repo": "fixture",
  "anchor": "file:scripts/unused_fixture.py",
  "text_key": null,
  "group": "file:scripts/unused_fixture.py",
  "occurrences": 1,
  "locations": [{"path": "scripts/unused_fixture.py", "line": 1}],
  "related": [],
  "evidence": [{"kind": "cap", "detail": "P1"}],
  "suggestion": "удалить или перенести в docs/archive",
  "judge": null
}
```

### 2.1 Идентичность: атомарные находки, агрегаты повторов, группы без слияния

- **Находки разных проб и правил не сливаются.** `rule` всегда префиксован
  пробой (`ruff/B006`, `vulture/unused-function`, `usage-graph/dead.file`);
  bug от линтера и dead от vulture на одной функции — две находки со своими
  `id`, severity и confidence.
- `anchor` без номеров строк: `file:<path>`, `func:<path>::<qualname>`,
  `make:<path>#<target>`, `skill:<path>`, `workflow:<path>#<job>`,
  `probe:<repo>#<probe>` (находки прибора §4.2),
  `dup:<exact|structural|text>:<hash>` (`text` — клоны jscpd, хэш
  нормализованного фрагмента), `dup:cli:<hash>` (хэш отсортированного
  пересечения флагов `argparse`), `dup:make:<hash>` (хэш нормализованного
  рецепта), `llm:<path>::<qualname>`. У каждого вида
  якоря есть **определяющий файл** (`<path>`; для `dup` — файлы участников).
- **Ключ находки** = (`rule`, `owner_repo`, `anchor`, `text_key`).
  `text_key` — sha1 текста строки нарушения после `strip` и схлопывания
  любых пробельных последовательностей в один пробел; для правил уровня
  якоря (`usage-graph/dead.*`, `usage-graph/root-stale`, `dup:*`,
  `llm-sites/*`) `text_key = null`. Правила, у которых строка нарушения не
  различает находки, берут **ключевой токен** вместо текста строки:
  `deptry/*` — `<код>:<модуль>` (DEP002 указывает на строку 1
  `pyproject.toml` для всех пакетов), `usage-graph/broken-root` —
  отсутствующий токен команды. `usage-graph/unresolved-exec` — строковое
  правило: ключ — текст строки вызова. Сравнение — по хэшу.
- **Агрегат:** все вхождения с одинаковым ключом — **одна** находка с
  `occurrences` и `locations[]`. Стабильность отдельных неразличимых
  экземпляров не обещается: их идентичность — это их общий ключ.
- `id = "sc-" + sha1(ключ)[:8]`; исключение — дубли: `id = "sc-" +
  sha1(rule | anchor)[:8]` без `owner_repo` (владелец — вычисляемый атрибут
  и может смениться вместе с составом участников).
- **Что значит «та же находка»:** тот же `id`. Статус дельты `changed` —
  при том же `id` изменились `occurrences`, **множество путей** в
  `locations` или состав участников дубля. Чистое смещение номеров строк
  при тех же путях и том же числе вхождений — не изменение: `persisting`.

Поведение на формах (нормативно; каждая строка — тест §6.3):

| # | Изменение кода | Итог |
|---|---|---|
| C1 | вставка строк выше | тот же `id`, `persisting` |
| C2 | добавлена вторая одинаковая по тексту строка нарушения | тот же `id`, `occurrences 2`, `changed` |
| C3 | удалена одна из двух одинаковых | тот же `id`, `occurrences 1`, `changed` |
| C4 | изменён текст строки нарушения | новый `id` (`new`) + прежний `resolved` — идентичность следует тексту |
| C5 | строка перенесена в другую функцию | новый якорь → новый `id` |
| C6 | функция переименована | новый якорь → новый `id` |
| C7 | два правила на одной строке | две находки |
| C8 | перестановка порядка проб | тот же набор `id` |
| C9 | переформатированы пробелы внутри строки | тот же `id` |
| C10 | у дубля сменился состав участников (≥ 2 осталось) | тот же `id`, `changed` |

- **Группа** (`group`) — якорь уровня файла/функции для совместного показа;
  в `id` не входит.
- **Идентичность участника дубля** — (`owner_repo`, `path`, `member`), где
  `member` — qualname функции (`ast-dup`, `cli-overlap/argparse`), имя цели
  (`cli-overlap/make-recipe`) или начальная строка фрагмента (`jscpd`, у
  которого другой идентичности нет); номер строки в идентичность не входит,
  кроме jscpd. «Состав участников» в C10 и §4.3 — множество этих троек.
- **Дубли:** все участники — в `related[]` (`owner_repo`, `path`, `line`, `member`);
  `owner_repo` — владелец лексикографически первого участника. Группа дублей
  существует, пока хэш разделяют ≥ 2 участника.
- Ключ `(id, owner_repo)` — будущий ключ идемпотентного заведения issue
  (для дублей — по `id` с текущим владельцем).

### 2.2 Severity

bug от линтеров — по уровню инструмента; dead/duplicate — medium;
llm-replaceable — low; `usage-graph/unresolved-exec` — low; `selfcheck/*` — §4.2.

### 2.3 dead: три отдельных решения

**Шаг 1 — класс использования** (§3.2.1): `live` / `test-only` / `doc-only`
/ `orphan`; корень (§3.2.2) и зона неразрешённого запуска (§3.2.3) —
отдельные признаки узла.

**Шаг 2 — допустимость.** dead-находка (`usage-graph/dead.file`,
`usage-graph/dead.module`) **выпускается**, только если одновременно:
класс ∈ {`orphan`, `test-only`, `doc-only`}; узел не корень; узел не в зоне
неразрешённого запуска; узел не `vendored-in` и не назван в строке
неразобранной вендор-декларации (§9.7). Во всех остальных случаях dead-находки **нет**
(не «низкая уверенность», а отсутствие). Узлы зоны перечисляются в evidence
находки `usage-graph/unresolved-exec` на вызывающем (low, «сделайте вызов
разрешимым»), а не как dead.

**Шаг 3 — уверенность** = min(база, все сработавшие потолки), порядок
`candidate < likely < confirmed`.

База: `orphan` → `confirmed`; `test-only`, `doc-only` → `candidate`.

Потолки (каждый сработавший — отдельная запись `cap` в evidence):

| Потолок | Условие | Предел |
|---|---|---|
| P1 fleet | `surface.fleet ≠ complete` | `likely` |

| P3 history | у файла нет git-истории | `likely` |

### 3.2 Граф использования (dead)

#### 3.2.1 Узлы и рёбра

**Узлы** (только из файлов роли `source`): исполняемые файлы (`*.py` с
`__main__`, `*.sh`, любой файл с shebang, включая безрасширенные вроде
`scripts/review/harness-claude`), Python-модули, цели `Makefile`, jobs
workflows, CLI-имена из `[project.scripts]`; плюс файлы роли `skill-root`.

**Рёбра:**

| Тип | Источник | Исп. |
|---|---|---|
| `make` | цель запуска в рецепте `Makefile`; `$(MAKE) x` / `make x` — ребро к цели `x` | да |
| `ci` | `.github/workflows/*.yml`: `run:`, локальные `uses:` | да |
| `import` | Python-импорты (AST), `python -m pkg.mod` | да |
| `exec` | запуск с **разрешённой** целью (§3.2.3) из Python, shell, рецептов | да |
| `entry` | `uv run [--project D] <cli>` / вызов CLI-имени → функция из `[project.scripts]` проекта D | да |
| `skill` | путь/команда в файле роли `skill-root` | да |
| `sched` | systemd-юниты в корпусе (`**/*.service`, `**/*.timer`); launchd-плисты из `--sched-dir` | да |
| `runbook` | команда в fenced-блоке `sh`/`bash`/`console` в файле роли `documentation` | да |
| `fleet` | исполняемое ребро из **другого** репо манифеста — правила сопоставления в §9.3 | да |
| `test` | файлы роли `test` | нет |
| `doc` | путь к узлу в файле роли `documentation` вне fenced-команд | нет |

**Цель запуска и файл-аргумент.** В командах (рецепты, `run:`, `ExecStart=`,
fenced-команды, команды skills) ребро даёт только **цель запуска**: токен в
командной позиции или скрипт-аргумент интерпретатора/обёртки (`python X`,
`sh X`, `bash X`, `uv run X`, `exec X`, `sudo X`, `python -m M`). Прочие
файловые токены команды (`cat a.py`, `shellcheck x.sh`, `--config y`) —
**упоминание** (evidence `mentioned-in`, потолок P5), не ребро.
`.timer`-юнит — корень с ребром к своему `.service` (`Unit=` или одноимённый).

**Классы:** `live` — есть исполняемое ребро; `test-only` — только `test`;
`doc-only` — только `doc` (и, возможно, `test`); `orphan` — рёбер нет.
**Упоминание** — вхождение голого имени файла в файлах ролей `source` и
`skill-root` вне определяющего файла; это не ребро и не меняет класс, только
включает потолок P5.

#### 3.2.2 Корни

Корни — публичные точки входа, для которых отсутствие входящего вызова
нормально: цели `Makefile`, упомянутые в `help`; файлы роли `skill-root`;
jobs workflows; юниты расписаний в корпусе; CLI-имена `[project.scripts]`.
Корень никогда не получает dead (матрица D9). Для корня статически
проверяется только:
- `usage-graph/broken-root` (bug, high): корень запускает несуществующий
  файл/цель/CLI;
- `usage-graph/root-stale` (`candidate`): определяющий файл не менялся
  > 180 дней **и** имя корня не упоминается в корпусе флота вне
  определяющего файла.

Фактическое использование корней статически недоказуемо; телеметрия
запусков — вне объёма.

#### 3.2.3 Разрешение вычисляемых запусков

Резолвер понимает конечный набор форм и превращает их в `exec`-ребро:
- Python: `Path(__file__).with_name("x")`, `Path(__file__).parent / "x"`
  (любая цепочка `.parent` и `/` с литералами),
  `os.path.join(os.path.dirname(__file__), "x")`; argv, собранный списком и
  переданный в `subprocess.*` напрямую **или** через склейку в строку для
  `tmux new-session`/`sh -c` (пример — `issue_console.py`:
  `Path(__file__).with_name("issue_worker.py")` → `shlex.quote`-склейка →
  `tmux`);
- shell: `"$SCRIPT_DIR/x"`, `"$(dirname "$0")/x"`, `$(cd … && pwd)/x`, где
  переменная присвоена в том же файле литеральным выражением этих форм;
- обёртки: `uv run [--project D] X`, `python3 X`, `sh X`, `bash X`,
  `exec X`;
- функция-обёртка того же модуля, передающая свой параметр первым
  аргументом в запуск (`def _run(cmd): subprocess.run(cmd)`): сам этот
  запуск зоны не порождает, цель разрешается по вызовам обёртки в модуле
  (`_run(["./x.sh"])`); неразрешимый аргумент вызова обёртки — обычная зона.

Запуск, цель которого не разрешилась (переменная из аргумента, чтение из
конфига, выбор по имени репо — напр., `review-pr.sh` →
`"$trusted_kit_dir/local.sh"`), порождает **зону неразрешённого запуска**:
все узлы, чьё имя совпадает с остаточным литеральным суффиксом (`*/local.sh`),
а при его отсутствии — все узлы каталога вызывающего файла. То же — для
`getattr`/`importlib.import_module` с неконстантным аргументом и glob по
каталогу с последующим запуском (зона — каталог вызывающего). Регистрация
entry-points с явным модулем (`[project.entry-points.*] x = "pkg.mod:obj"`)
— не зона, а ребро `entry` к модулю. Узлы зоны dead не получают (шаг 2 §2.3).

#### 3.2.4 Поверхность

Каждый прогон фиксирует `run.surface`:
- `fleet`: `complete` (строгое определение — §9.6: канарейка флота
  сработала, все репо флота на диске, прочитаны без ошибок, на ветке по
  умолчанию без отставания), `partial` (есть `fleet-partial` или канарейка
  флота не сработала), `absent` (прогон без `--fleet`);
- `sched`: `repo-units` всегда плюс `launchd:<host>:<N плистов>` при
  `--sched-dir`; полноту launchd доказать нельзя, поэтому отчёт перечисляет
  учтённые плисты, а без `--sched-dir` действует потолок P2;
- `history`: по файлу — есть/нет (потолок P3).

Следствие: в S1 (без `--fleet`) dead выше `likely` не бывает (P1).

### 3.3 Дубли по смыслу (duplicate)

- `ast-dup`: два хэша на функцию ≥ 8 строк — **exact** (стёрты только имена
  локальных переменных и докстринги) и **structural** (дополнительно стёрты
  строковые и числовые литералы). Совпадение exact → находка
  `dup:exact:<hash>` `confirmed`; только structural → `dup:structural:<hash>`
  `candidate`, различия литералов — в evidence. Включая межрепные клоны
  (S3: «один хелпер в N репо → кандидат в общий пакет»).
- `cli-overlap`: парсеры `argparse` (флаги — длинные опции `--x`,
  добавленные в одной функции) с перекрытием по Жаккару
  |A∩B| / |A∪B| ≥ 0,8 при |A∩B| ≥ 2, и цели `Makefile` с идентичным
  рецептом после нормализации переменных `$(X)`. Severity — как у всех
  duplicate (§2.2).

### 3.4 LLM-вызовы (llm-replaceable)

**Точка вызова** — место в коде, которое непосредственно запускает модель:
вызов процесса с бинарём харнесса, вызов метода SDK-клиента, HTTP-запрос к
эндпоинту модели. Обёртка, передающая аргументы дальше, — не точка вызова, а
ребро к ней.

`llm-sites` ищет:
- A — бинарь харнесса (`claude`, `codex`, `opencode`, `aider`, `pi`, `qwen`,
  `ollama`, `llama-cli`, `copilot`) в Python-`subprocess` (AST) **и** в
  командных позициях shell-файлов, включая безрасширенные по shebang
  (пример — `scripts/review/harness-claude`);
- B — импорт/вызов SDK (`anthropic`, `openai`, LangChain) — Python и TS;
- C — HTTP на `/v1/messages`, `/v1/chat/completions`, `/api/generate`,
  `/completion` — Python и TS;
- D — описания без вызова (каталоги, конфиги) — в инвентарь, не в кандидаты.

Поиск — semgrep-правила `selfcheck/rules/llm.yml` (Python, bash, TS —
semgrep статичен, поэтому TS не требует S4) плюс AST-досборка аргументов для
Python. Elixir — вне объёма.

Эвристики кандидата (каждая — отдельный признак в evidence): ответ
разбирается в enum/bool/фиксированную JSON-схему; промпт — шаблон с
подстановкой коротких полей; вызов в цикле по однородным элементам; нет
свободного текста, уходящего человеку. Точка — кандидат, если нет признака-
исключения и есть хотя бы один из двух сильных признаков (фиксированная
схема ответа или цикл по однородным элементам); шаблон промпта и отсутствие
текста человеку только дополняют evidence. Исключение: промпт содержит дифф,
код или документ целиком, либо результат — генерация текста/кода → точка
только в инвентаре. Промпт, **не видимый статически** в точке (приходит
аргументом `"$1"`/`"$@"`, из stdin `-` или из переменной без значения в
файле), не позволяет исключить дифф — такая точка только в инвентаре
(типичный случай — shell-обёртки харнессов вроде `harness-claude`).

## 4. Статусы проб и fail-closed на сам прибор

### 4.1 Контракт адаптера и канарейка

Каждая проба декларирует в реестре `selfcheck/probes.py`: диапазон версий;
**форму входа** (`files` | `roots`, ниже); argv и формат вывода; множество нормальных кодов выхода (для закреплённой
версии, подтверждается тестом); путь файла вывода в каталоге пробы;
**канарейку**; режим покрытия.

**Канарейка** — файл из `selfcheck/canaries/<probe>/` с заранее известной
находкой (правило + якорь), который материализуется в копию корпуса (до
перевода её в read-only) по **пути канарейки пробы** и передаётся пробе
**в том же вызове**, что и файлы репо. Путь канарейки объявляется в реестре
для каждой пробы (по умолчанию `.selfcheck-canary/`; проба, которая не
сканирует скрытые каталоги, объявляет другой путь), и тест §6.2 доказывает
`hit` на фикстуре для каждой пробы. Если ожидаемая находка канарейки не пришла, проба — `failed`
(`canary-missed`): это доказывает, что argv, формат вывода и разбор работают
сквозным образом на этом прогоне, в том числе когда на самом репо находок нет
(«чистый непустой корпус»). Находки канарейки вычитаются из результатов и в
отчёт не попадают. Собственные анализаторы и semgrep имеют канарейки на тех
же условиях. Сверка канарейки выполняется по сырым находкам **до** подавлений
(`suppressed-no-env`, allowlist).

Если канарейку подавила конфигурация репо (правило канарейки выключено в
его конфиге, путь исключён): правило канарейки передаётся инструменту явно
в CLI, файлы — явным списком (ruff не применяет `exclude` к явно переданным
файлам без `--force-exclude`); если находка всё равно не пришла и в
конфиге репо есть подавление этого правила/пути — причина `failed:
canary-suppressed-by-config`, отдельная от `canary-missed` и допускающая
запись allowlist по репо (§2.4).

Канарейка не влияет на анализ репо: роль `canary` (§1.4) — её узлы, рёбра и
упоминания существуют только внутри неё; канарейка ast-dup/jscpd —
клон только самой себе, не участнику репо.

**Форма входа.** `files` — инструмент получает явный список файлов корпуса
(ruff, vulture, radon, shellcheck, pyrefly, собственные анализаторы).
`roots` — инструмент принимает только каталоги и сам обходит их (deptry:
`ROOT...` — каталоги исходников; файл в аргументе даёт
`NotADirectoryError`). Для `roots` адаптер фиксирует переданные каталоги,
явный путь конфигурации (deptry — `cwd` = копия по исключению §1.3,
`--config pyproject.toml`, исключения конфига репо передаются в CLI явно,
так как `--extend-exclude` из CLI заменяет их) и **ожидаемый набор файлов**,
вычисленный selfcheck по
корпусу с правилами обхода инструмента (его исключения по умолчанию плюс
исключения из конфигурации репо); канарейка кладётся по пути, который обход
инструмента заведомо включает (для deptry — `selfcheck_canary/` в корне
проекта, не скрытый каталог).

**Покрытие** (`coverage`) — одно из:
- `reported` — инструмент сам сообщает обработанные/пропущенные входы (напр.,
  статистика jscpd, ошибки разбора у ruff); сравнивается с переданными;
- `declared` — инструмент не сообщает обработанного; selfcheck фиксирует
  переданные входы (для `files` — список файлов, для `roots` — каталоги и
  вычисленный ожидаемый набор файлов) и опирается на канарейку и на
  пофайловые диагностики ошибок. Это **слабее** `reported` и так и
  показывается в сводной таблице — поуровневое «файл реально разобран»
  для таких инструментов не доказывается (остаточный риск, §8).

Ожидаемые входы строятся по той же неизменяемой копии корпуса, что видит
проба, поэтому поверхность у всех проб одна. Если инструмент по построению
не сообщает часть входов, реестр пробы сужает ожидаемые входы явным
правилом: jscpd сообщает только файлы известного ему формата длиной не
меньше `min-lines` (5) — остальные не считаются необработанными.

`ProbeResult`: `status`, `tool_version`, `argv`, `exit_code`, `canary`
(`hit`/`missed`), `coverage` (режим, переданные, обработанные при
`reported`, пропущенные), `diagnostics[]`, `findings[]`, `duration`.

### 4.2 Статусы

| Статус | Условие |
|---|---|
| `ok` | версия в диапазоне; код в нормальном множестве; вывод — файл этого прогона в каталоге пробы (каталог уникален для `run_id`, §1) и разобрался; канарейка `hit`; нет пропущенных входов и диагностик об ошибках разбора файлов |
| `partial` | всё как `ok`, но есть пропущенные входы или диагностики об ошибках разбора отдельных файлов |
| `failed` | код вне множества; вывод отсутствует или не разобрался; канарейка `missed`; при `reported` обработано 0 из > 0; таймаут; исключение анализатора вне файла |
| `unavailable` | бинаря/пакета нет или версия вне диапазона (с причиной) |
| `skipped` | язык не совпал или в корпусе нет входов пробы (напр., нет workflows) — с причиной; канарейка в этом случае не запускается |

Находки прибора: `failed` → `selfcheck/probe-failed` (high); `partial` →
`selfcheck/probe-partial` (medium) с перечнем входов; `unavailable` →
`selfcheck/probe-unavailable` (medium).

Ожидаемые нормальные коды (источник истины — реестр + тест на закреплённой
версии, не эта таблица): ruff 0/1; pyrefly 0/1; vulture 0/3; deptry 0/1;
shellcheck 0/1; actionlint 0/1; zizmor — по документации закреплённой
версии (1.29: находки 11–14; «нет входов» 3 у нас не возникает из-за
`skipped`); jscpd 0/1 при разобранном JSON-отчёте; cargo-machete 0/1.
Поскольку канарейка гарантирует хотя бы одну
находку, у инструментов с кодом «есть находки» нормальный код на каждом
прогоне — ненулевой; код 0 при `hit` канарейки невозможен и сам — признак
сбоя разбора.

### 4.3 Прогон, дельта и коды выхода

`run` в JSON: `run_id`, `scope` (репо, флаги), по репо — `HEAD` и признак
dirty, `surface` (§3.2.4), по пробам — версия, конфиг-хэш, набор включённых
правил, sha1 `selfcheck.toml`.

**Ключ сопоставимости** пробы на репо = (`probe`, версия пробы, конфиг-хэш
пробы для репо, набор включённых правил, режим окружения §1.5) плюс, для
`usage-graph`, `surface.fleet`, наличие `--sched-dir` и набор канонических
имён репо флота (§9.6). Для собственных
анализаторов «версия пробы» — версия пакета selfcheck плюс явная версия
логики анализатора (константа в реестре, повышается при изменении
логики), «конфиг-хэш» — sha1 секций `[roles]` и `[corpus]` `selfcheck.toml`.

**Базовый прогон** — последний предыдущий в `out/selfcheck/` (любого
`scope`: различие областей учитывают судьбы ниже).

**Судьба** прежнего определяющего файла / участника в текущем прогоне:

| Судьба | Определение |
|---|---|
| `checked` | репо в `scope`, файл в корпусе, проба `ok`, ключ сопоставимости равен базовому |
| `deleted` | репо в `scope` и материализован, пути нет на диске исходного checkout |
| `excluded` | путь есть на диске, но не в корпусе (gitignore, `[corpus] exclude`) |
| `out-of-scope` | репо не входит в текущий `scope` |
| `unverified` | репо в `scope`, но `repo-missing`, или проба не `ok`, или ключ сопоставимости не равен |

**Одиночный якорь** (`file`, `func`, `llm`, `make`, `skill`, `workflow`),
находки с этим `id` сейчас нет: `checked` → `resolved`; `deleted` →
`resolved: file-removed`; `excluded`, `out-of-scope`, `unverified` →
`not-rechecked`.

**Дубль** (участники P в базе), находки с этим `id` сейчас нет:

| # | Судьбы участников P | Итог |
|---|---|---|
| Δ1 | все `checked` | `resolved` |
| Δ2 | все `deleted` | `resolved: file-removed` |
| Δ3 | только `checked` и `deleted`, смешанно | `resolved` |
| Δ4 | хотя бы один `excluded` / `out-of-scope` / `unverified`, прочие любые | `not-rechecked` |

Находка с этим `id` есть: `persisting`, либо `changed`, если изменились
`occurrences`/`locations`/состав участников (§2.1); участники базы с судьбой
вне {`checked`, `deleted`} помечаются в `related[]` как `unverified`.

**Находка прибора** (`probe:<repo>#<probe>`, `selfcheck/probe-*`), которой
сейчас нет: `resolved`, если репо в `scope` и проба сейчас `ok`/`skipped`;
иначе `not-rechecked`.

Статусы дельты: `new`, `persisting`, `changed`, `resolved`,
`resolved: file-removed`, `not-rechecked`. Критерий `changed` — §2.1
(смещение номеров строк не считается изменением).

Код выхода `selfcheck`: 0 — все пробы `ok`/`skipped`; 2 — есть `failed` или
`partial` или `selfcheck/repo-missing` по репо из `scope`; 3 — нет
`failed`/`partial`, но есть `unavailable`; 4 — ошибка
манифеста, конфига, материализации или записи отчёта (отчёт не выпущен).
Находки по коду сами по себе код выхода не меняют.

## 5. Судья (`--judge`)

Выключен по умолчанию и в CI. Вход — находки `llm-replaceable` и
`duplicate` уровня `candidate`/`likely`.

**Граница полномочий.** Судья — вызов без инструментов и без доступа к
checkout'ам: единственный вход — сериализованный срез в stdin (функция
вызова ± 40 строк, промпт-шаблон, место разбора ответа; для дубля — оба
участника). Адаптер S5 — только `claude`: `claude -p --output-format json
--json-schema <verdict> --restricted --strict-mcp-config
--no-session-persistence --permission-prompts none --tools ""`, `cwd` —
пустой временный каталог, `env` урезан до `PATH`/`HOME` (линза
`scripts/review/harness-claude`, но с пустым набором tools). Другие харнессы
— `unavailable` до своего адаптера. Таймаут 120 с на кандидата, лимит вывода
64 КиБ.

**Выход** валидируется схемой: `{verdict: replace|keep|unsure,
replacement: regex|rules|decision-tree|embedding-classifier|small-model|merge|none,
rationale}`. Вердикт меняет только поле `judge` и уверенность в пределах
§2.3 (`replace` → `likely`; `keep` → раздел `info`); не создаёт находок, не
меняет `id`, `owner_repo`, scope. Невалидный ответ, таймаут, ошибка —
`judge: {verdict: "error", detail}`, находка остаётся как была.

## 6. Тестирование

### 6.1 Фикстура

`tests/fixtures/selfcheck/` — шаблоны, из которых тест собирает мини-флот:
два git-репо с датированными коммитами (`GIT_COMMITTER_DATE`, чтобы
управлять возрастом), мини-манифест и каталог плистов для `--sched-dir`.

- **Матрица dead:** по узлу на каждую строку D1–D12 §2.3; ожидание каждого
  узла выводится из матрицы, а не пишется вручную.
- **Трудные вызывающие** (D10/D11, отрицательные двойники dead): worker через
  `Path(__file__).with_name()` + `tmux`-склейку (`live`); скрипт через
  `"$SCRIPT_DIR/x"` (`live`); `local.sh`, выбираемый вычисляемым каталогом
  (зона → нет dead, есть `usage-graph/unresolved-exec`); установочный скрипт из
  fenced-блока README (`runbook` → `live`); CLI через `uv run --project` и
  `[project.scripts]` (`entry` → `live`); безрасширенный shebang-скрипт с
  вызовом; модуль через `importlib.import_module(name)` (зона).
- **Корни:** skill и цель `Makefile` без входящих вызовов (нет dead); цель,
  вызывающая несуществующий скрипт (`broken-root`).
- **Роли:** скрипт, упомянутый только в `reports/old.md`
  (`diagnostic-output` → остаётся `orphan`, P5 не срабатывает); skill в
  `authored/skills/x/SKILL.md` соседнего репо, вызывающий скрипт (`live`
  при `--fleet`); игнорируемый каталог со скриптом, вызывающим узел (ребро
  не учитывается).
- **Дубли:** exact-клоны; structural с разными порогами (`candidate`); похожие,
  но различающиеся функции (не дубль); одна группа из трёх участников, один
  удалён (группа сохраняется).
- **LLM:** вызов с разбором в enum (кандидат), со свободной генерацией по
  диффу (не кандидат), `claude` из безрасширенного shell-файла (в инвентаре).
- **cli-overlap:** две цели `Makefile` с одинаковым рецептом и две — с разным.
- **Окружение — только данные (§1.5):** `.venv` фикстуры содержит
  `sitecustomize.py` и `.pth` с исполняемой строкой, оба пишут файл-маркер;
  после прогона pyrefly и deptry маркера нет, а соответствие `yaml`/`PyYAML`
  определено верно при декларации `pyyaml>=…` (ключ mapping — в написании
  декларации, не `METADATA`).
- **Форма `roots` (§4.1):** реальный deptry на минимальном проекте с
  канарейкой в `selfcheck_canary/` → `ok`; тот же проект без нарушений в
  собственных исходниках → `ok`; ожидаемый набор файлов записан в
  `coverage`.
- **Окружение (§1.5):** репо с `.venv` (`checkout-venv`): настоящий
  отсутствующий импорт репортится, импорт с несовпадающими именами модуля и
  дистрибутива (`yaml`/`pyyaml`) — нет; тот же репо без `.venv` (`no-env`):
  import-находок нет, счётчик `suppressed-no-env` > 0; `uv.lock` новее
  `pyvenv.cfg` → `env-stale`, import-находки не выше `candidate`.

### 6.2 Прибор

На каждую пробу: находки есть, код из нормального множества → `ok`; чистый
непустой корпус (находки только у канарейки) → `ok`; канарейка сломана
(ожидаемое правило отключено в реестре) → `failed: canary-missed`; правило
канарейки выключено конфигом репо, но явное включение в CLI его
восстанавливает → `hit`, `ok`; подавление конфигом остаётся действующим
несмотря на CLI (напр., путь канарейки исключён так, что инструмент его не
обходит) → `failed: canary-suppressed-by-config`;
вывод не разобрался → `failed`; ошибка разбора одного файла → `partial`;
бинаря нет / версия вне диапазона → `unavailable`; нет входов → `skipped`.

Read-only копия (§1.3):
- каждая проба S1–S3 с вынесенными кэшем и выводом → `ok` на read-only копии
  (отрицательный двойник к `write-to-corpus`);
- фикстурная проба, пишущая в копию, → `failed: write-to-corpus`;
- исходный фикстурный checkout побайтно неизменен после прогона всех проб
  S1–S3 (хэши содержимого всех файлов, включая ignored и untracked), mtime
  `.git/index` не изменился;
- после прогона каталог `src/` удалён (уборка с `chmod -R u+w`);
- реестр: у всех проб S1–S3 `executes_target_code = false`.

### 6.3 Идентичность, дельта, конфиг, судья

- **идентичность:** по тесту на каждую строку C1–C10 §2.1, включая удаление и
  вставку **одинаковых** по тексту строк; bug-находка ruff и dead-находка
  vulture на одной функции — две находки с разными `id` в одной группе;
- `run_id`: два прогона с замороженным временем получают разные каталоги;
- **дельта:** по тесту на каждую судьбу одиночного якоря и на каждую
  строку Δ1…Δ4; плюс именованные контрпримеры: файл исключён
  `.gitignore`, но не удалён → `not-rechecked` (не `file-removed`);
  межрепный дубль, devtools-only прогон после `--fleet` → Δ4
  `not-rechecked`; правило выключено конфигом → `not-rechecked`; пропавший
  бинарь → `not-rechecked`; смена режима окружения → `not-rechecked`;
- allowlist: истёкшая запись → `allow-expired`; запись без `reason` → код 4;
- судья мокается; без `--judge` харнесс не вызывается ни разу; argv адаптера
  содержит `--tools ""` и `--restricted`; ответ, меняющий `id` или
  поднимающий до `confirmed`, отвергается;

## 8. Риски

- **Ложный «мёртвый»** — главный вред. Меры: корни и зоны неразрешённого
  запуска dead не получают вовсе; резолвер вычисляемых запусков;
  `runbook`-рёбра; `confirmed` только при полном флоте и `--sched-dir`;
  матрица D1–D12 закреплена фикстурой.
- **Read-only копия — не изоляция.** Инструмент может вернуть себе права
  или писать по абсолютному пути в исходный checkout; S1–S3 это допускают,
  потому что их пробы не исполняют код цели, а сами инструменты закреплены
  по версии. Исполнение кода цели — только в S4 с песочницей.
- **Режим `no-env`** снижает полноту pyrefly/deptry (подавленный
  import-класс) — видно в сводной таблице и счётчике `suppressed-no-env`.
- **Покрытие `declared`** не доказывает, что каждый переданный файл реально
  разобран инструментом, не сообщающим об этом; канарейка доказывает только
  сквозную работоспособность вызова. Риск принят и виден в сводной таблице.
- **Шум линтеров на старом коде** — отчёт группирует по правилу, показывает
  топ; дельта между прогонами важнее абсолютного числа.
- **Дрейф кодов выхода и форматов** при обновлении инструментов — версии в
  реестре, коды и канарейки закреплены тестами; выход за диапазон версий —
  `unavailable`, а не молчаливый неверный разбор.
- **Ложные рёбра `fleet`** на чужие каталоги с именем репо (`chrome/devtools/…`)
  — принятый компромисс S2 (§9.3): ложный `live`, не ложный dead.
- **`confirmed` относительно манифеста.** Потребители вне флота (корневой
  зонтик, `~/.claude`) полнотой не покрываются (§9.6); отчёт это называет.
- **Текстовый канал флота (§9.4)** понижает до `likely` dead узлов с общими
  именами — осознанная плата за то, что `confirmed` не зависит от полноты
  разбора соседей.
- **Стоимость материализации флота** — копируется только корпус
  (`ls-files`), без `.venv`/`target`/`node_modules`.

### 9.2 Режим `--fleet`

**Флот репо R** из `scope` — все репо множества U, кроме самого R. U — это:
- все уникальные `git_dir` манифеста (§1.2);
- git-репо, содержащее файл `--manifest` (командный зонтик), если такое
  есть.

Другие репо `scope` входят во флот R: вызов из одного репо `scope` в другое —
такое же ребро `fleet`. Иначе прогон `--repo a --repo b` терял бы рёбра
b → a и давал ложный `confirmed`. Полнота (§9.6) считается для каждого R
отдельно. `surface.fleet` — худшее значение по репо `scope`.
`surface.fleet_repos` перечисляет репо U вне `scope`.

Корневой зонтик во флот не входит: он трекает `_cowork_output/`, а
shipped-код его не читает (корневой `CLAUDE.md`). Механизм: git-репо,
содержащее `--manifest`, во флот не включается, если в его корне есть
`_cowork_output/`. Отчёт называет корневой зонтик и
`~/.claude` непокрытой поверхностью (§9.6).

Пробы идут только по `scope`. Репо флота читает одна `usage-graph`, в два
канала:
- точный — §9.3;
- текстовый — §9.4.

Классы и находки самих репо флота — это S3.

Как читается корпус флота:
- Репо флота не материализуются. Корпус — это `git ls-files` без каких-либо
  исключений: `[corpus] exclude` и `[roles]` из `selfcheck.toml` относятся к
  `scope` и к флоту не применяются.
- Роли флота — по умолчанию (§1.4). Корпус читает из checkout собственный
  парсер selfcheck, а он ничего не пишет. Read-only копия (§1.3) защищает от
  записи внешними инструментами, а по флоту они не запускаются.
- Файл читается байтами. Файл с BOM UTF-16 или UTF-32 декодируется по
  BOM. Иначе, если в первых 8 КиБ есть NUL, файл двоичный и пропускается;
  это не ошибка, счётчик пишется в поверхность.
- Остальной текст декодируется как UTF-8 с заменой; поиск ASCII-имён от этого
  не страдает.
- Запись gitlink (submodule, режим `160000`) — ошибка `submodule` (§9.6):
  содержимое подмодуля не прочитано.
- `OSError` — ошибка (§9.6).
- Symlink не читается: его цель внутри репо — отдельный файл корпуса. Цель
  вне репо — ошибка (§9.6).

### 9.3 Точный канал: рёбра `fleet`

Репо флота разбирается построителем графа S1 без `--sched-dir`. **Внешняя
цель** — это цель запуска (§3.2.1), которая:
- записана литеральным путём, после учёта каталога запуска так же, как в S1;
- и не разрешилась ни в один узел своего репо.

Если в нормализованном пути есть сегмент, равный **каноническому имени**
репо `scope`, и остаток после него — путь узла этого репо, ставится
исполняемое ребро `fleet`. Детали сопоставления:
- каноническое имя — basename `git_dir` из манифеста; сравнение без учёта
  регистра;
- пробуется **каждое** вхождение сегмента, а не только последнее, потому
  что у репо бывают одноимённые пакеты (`maestro/maestro/…`).

Формы точного канала — ровно формы S1. `$`-токены рецептов и `run:`, а также
неизвестные `cd` остаются неразрешёнными, как и в S1. Их безопасность
обеспечивает §9.4, а не этот канал. Расширение форм — общее для S1 и флота и
в S2 не входит.

**Известный компромисс.** Каталог с тем же именем, не являющийся репо
(`chrome/devtools/…`), даёт ложное ребро. Это ложный `live`, а не ложный
dead. Дефектом не считается и закреплён тестом (§9.8).

**Класс `fleet-only`** — узел `live`, у которого все исполняемые входящие
рёбра `fleet`. Это не находка, а свидетельство: удаление такого узла сломает
соседа.
- `report.md` — таблица: узел, репо-источник, место;
- `report.json` — `graph.<repo>.fleet_only`;
- пустой класс печатается явно: «fleet-only: 0». Без `--fleet` класс не
  вычислялся, и печатается «fleet-only: — (без --fleet)»: ноль, который
  ничего не доказывает, не печатается.

### 9.4 Текстовый канал: упоминания флота (P5)

Для каждого файлового узла `scope` ищутся его **ключи**:
- голое имя файла (`attest-vendor.sh`);
- путь от корня репо (`governance/console.py`);
- для `.py` — точечное имя модуля (`governance.console`).

Ключ ищется как отдельное слово, без учёта регистра:
- слева от ключа не должно быть `[A-Za-z0-9_-]`;
- справа — не должно быть `[A-Za-z0-9_]`.

`-` слева не даёт считать `attest-vendor.sh` упоминанием `vendor.sh`. Точка
и `/` с обеих сторон границей считаются: `…/attest-vendor.sh.` в конце фразы,
`governance.console.main` и `x.governance.console` — упоминания. Лишнее
совпадение безопасно: это только лишний P5. Точечное имя модуля строится как
в S1 (`commands.module_name`: без `src/`, `__init__` сворачивается в
пакет).
Поиск идёт во **всех** прочитанных текстовых файлах всех репо флота: любая
роль (включая `documentation`, `test`, `diagnostic-output`), любое
расширение (Elixir, TS, md, `justfile`, плисты, `.pre-commit-config.yaml`).
Любое вхождение включает потолок P5. В evidence пишется
`mentioned-in: <репо>:<файл>`, не больше 5 мест плюс счётчик.

Последствие: `confirmed` достижим, только если **ни в одном** трекаемом
текстовом файле флота нет ни одного ключа узла.
- Общие имена (`setup.sh`, `cli.py`) почти всегда упомянуты где-то во флоте,
  и их dead не поднимется выше `likely`. Это принятое безопасное
  направление.
- Не видны только полностью вычисляемые ссылки (`$CMD`, склейка имени из
  частей) — принятый риск, как в S1 (§8).
- Импорт модулей devtools из соседей в полирепо запрещён правилом
  вендоринга, а замер §9.1 дал 0. Форма `from pkg import stem` без точечного
  имени — названный риск.

Зон флота нет: неразрешённый запуск соседа с литеральным суффиксом
(`"$X/foo.sh"`) содержит ключ `foo.sh` и так ловится этим каналом.

### 9.5 Канарейка флота

Каждый прогон с `--fleet` включает синтетического соседа — **git-репо** в
`out/selfcheck/<run_id>/fleet-canary/<R>/` (своё для каждого репо R из
`scope`) с одним коммитом, собранное selfcheck.
Он проходит **тот же код**, что настоящие репо флота: перечисление
`ls-files`, чтение байтами, проверку двоичности, проверку `stale` (у
канарейки нет `origin`: она проверяется тем же кодом, и ожидаемый результат
— ровно причина «нет `origin/HEAD`». Иное означает, что сломана проверка
`stale`, и канарейка не сработала), точный и текстовый каналы. Git-личность
и окружение коммита канарейки задаются явно: переменные `GIT_AUTHOR_*` и
`GIT_COMMITTER_*` = selfcheck, `commit.gpgsign=false`, хуки отключены. Всё это
не зависит от конфигурации исполнителя. Он ссылается на канареечный узел `scope`
`.selfcheck-canary/usage-graph/fleet_canary.py` двумя формами:
- литеральный путь `<каноническое имя>/.selfcheck-canary/usage-graph/fleet_canary.py`
  в `run:` workflow — ожидается ребро `fleet`;
- голое имя в fenced-блоке `zsh` markdown-файла — ожидается упоминание.

Канареечный узел материализуется в копии R и входит в граф R. Канареечный
сосед подаётся **в тот же вызов**, который добавляет к графу R рёбра и
упоминания настоящих соседей. Так канарейка проверяет и функции каналов, и их
проводку в пробе.

Попадание засчитывается, только если источник — ожидаемый файл канарейки:
- для точной формы — её workflow;
- для текстовой — её markdown-файл.

Упоминание `fleet_canary.py` в настоящем репо (например, в заметке о S2) или
голое имя внутри workflow канарейки текстовую форму не удовлетворяет.

Если хотя бы одна форма не сработала:
- `usage-graph` получает статус `failed` и находку `selfcheck/probe-failed`
  (§4.1–4.2);
- `fleet = partial`.

Так положительная точка проверяется на каждом прогоне, а не один раз при
приёмке.

**Изоляция.** Канареечный сосед и канареечный узел — канарейка в смысле §4.1.
Разрешённое ребро `fleet` к канареечному узлу — единственное исключение из
правила роли `canary` «рёбра только внутри канарейки» (§1.4). Рёбра и
упоминания канарейки учитываются только для сверки самой канарейки. Они не
входят в:
- `fleet-only`;
- `surface.fleet_repos` и «N репо» формулировки полноты;
- ключ сопоставимости;
- evidence `mentioned-in` настоящих узлов.

### 9.6 Полнота: `fleet = complete` относительно манифеста

`complete` выставляется, только если выполнено всё сразу:
1. прогон идёт с `--fleet`, и канарейка флота сработала (§9.5);
2. каждое репо флота R найдено на диске (есть `.git`), а число репо флота
   R равно |U − {R}|;
3. у каждого репо флота `ls-files` вернул код 0 и прочитан хотя бы один
   текстовый файл (пустой корпус или корпус из одних двоичных файлов —
   `empty`);
4. ни одного `OSError` при чтении, ни одного symlink'а с целью вне репо и ни
   одного gitlink'а (submodule);
5. каждое репо флота стоит на своей ветке по умолчанию, совпадает с ней и
   чисто:
   - ветка по умолчанию — `refs/remotes/origin/HEAD`; нет `origin/HEAD` —
     `stale`;
   - HEAD не отстаёт от неё, не опережает её и не расходится с ней —
     сравнение по локальным refs, без `fetch`;
   - рабочее дерево чистое (`git status --porcelain` пуст); незакоммиченная
     правка могла убрать упоминание.

   `git status --porcelain` учитывает и неотслеживаемые файлы: они тоже
   могут нести упоминание.

   Давность локальных refs (mtime `FETCH_HEAD`, или `null`, если его нет)
   пишется в `fetched_at` каждого репо. Фраза полноты называет **самую
   старую** дату: «относительно локальных refs не старше <дата>»; при любом
   `null` — «… давность refs неизвестна для: <репо>». Свежесть fetch —
   ответственность исполнителя: selfcheck сеть не трогает.

Иначе — `partial`, P1 остаётся в силе. На каждую пару (репо флота, причина)
выпускается одна находка `selfcheck/fleet-partial` (medium, category
`selfcheck`):
- `owner_repo` — репо `scope`;
- `anchor` — `probe:<scope-repo>#fleet`;
- `text_key` — `<репо флота>:<причина>`, причина из множества `missing`,
  `ls-files`, `empty`, `unreadable`, `symlink-out`, `submodule`, `stale`.
  Расхождение числа репо (условие 2) — `text_key` `fleet:count`, в evidence
  ожидаемый и фактический состав;
- пути файлов — в `locations`, поэтому их изменение даёт `changed` (§2.1).

Судьба находки в дельте (§4.3):
- `checked`, если `scope`-репо в `scope`, прогон с `--fleet` и `usage-graph`
  `ok`;
- иначе `unverified`.

`fleet-partial` не меняет код выхода и статус `usage-graph`: неполный флот
лишь оставляет P1 и ложного dead не создаёт. В режиме `--fleet` отсутствие
репо флота даёт `fleet-partial … :missing`, а не `repo-missing`;
`repo-missing` остаётся за репо `scope` (§1.2, §4.3).

Отчёт говорит о полноте словами: «complete относительно манифеста `<путь>`
(sha1 `<…>`): N репо; не покрыто: корневой зонтик, `~/.claude`».

В JSON:
- `run.surface.fleet_repos` — список
  `{name, head, branch, default, behind, ahead, files, binary, dirty, fetched_at}`;
- `run.surface.manifest_sha1`.

Ключ сопоставимости `usage-graph` (§4.3) дополняется набором канонических
имён репо флота. HEAD соседей в ключ не входит: изменение соседа — это
изменение фактов, а не несопоставимость прогонов.

Нормативные отрицательные двойники — каждый даёт `partial` и
`fleet-partial` с указанной причиной, а dead не поднимается выше `likely`:

| Условие | Причина |
|---|---|
| одного репо флота нет на диске | `missing` |
| файл соседа нечитаем | `unreadable` |
| symlink соседа наружу | `symlink-out` |
| сосед отстаёт от `origin/HEAD`, опережает его или разошёлся с ним | `stale` |
| сосед не на ветке по умолчанию или без `origin/HEAD` | `stale` |
| у соседа грязное рабочее дерево | `stale` |
| submodule у соседа | `submodule` |
| у соседа пустой корпус | `empty` |

### 9.7 Роль `vendored-in` из деклараций

**Кандидаты в декларации** — файлы роли `source` репо `scope`, которые
выполняют одно из двух условий:
- basename без учёта регистра — `PIN`, `PINNED*` или `VENDOR*`, **и** файл
  не узел графа (не код, §3.2.1). Поэтому `vendor_manifest.py` кандидатом
  не является;
- **или** в одной из первых 5 строк есть шапка:
  - `# VENDORED:` с любым хвостом;
  - `# SOURCE:`, если в строке есть `@`;
  - `upstream:` при наличии в файле ключа `commit:` с любым значением.

  Hex-ref проверяет уже грамматика: шапка с тегом вместо sha или без ref даёт
  неразобранную декларацию, а не некандидата. Комментарий
  `# SOURCE: https://…` без `@` и YAML с `upstream:`, но без `commit:`,
  кандидатами не являются.

Файлы ролей `test`, `documentation`, `diagnostic-output` и `canary`
кандидатами не бывают. Так фикстуры и скопированные отчёты не дают ложных
находок.

**Форматы** — все четыре встречены в devtools 2026-09-26:

| Формат | Пример | Шапка | Строка члена | Путь члена |
|---|---|---|---|---|
| A | `scripts/review/PIN` | ровно одна `# SOURCE: <владелец> @ <ref>…` | `<sha256>  <путь>` | от корня репо |
| B | `contracts/steward-actor-policy/v1/PIN` | нет | `<sha256>  <путь>  <владелец>@<ref>` | от каталога декларации |
| C | `governance/discovery_contract/PINNED.txt` | `upstream: <url>` и `commit: <ref>` | `<путь> <sha256>` | от каталога декларации |
| D | `scripts/review/prose-paths.env` | в самом файле: `# VENDORED: <владелец> @ <ref> — <путь апстрима>` | — | членом считается сам файл |

Грамматика:
- `<ref>` — первый токен `[0-9a-f]{7,40}` после `@` или `commit:`; хвост
  строки допускается (реальная шапка A продолжается в скобках на следующую
  строку).
- Владелец C — basename пути `upstream`-URL без `.git`.
- `<sha256>` — 64 hex-символа.
- Разделитель — один или больше пробелов.
- Строки на `#` (кроме шапок) и пустые строки — комментарии.
- Путь члена с `..` или абсолютный делает декларацию неразобранной.

Декларация **не разобрана**, если:
- кандидат не подходит ни под один формат;
- форматы в одном файле смешаны;
- в A, B или C нет ни одного члена;
- строка члена иной формы.

**Что даёт роль.** Член декларации получает роль `vendored-in` (владелец,
ref, путь декларации) поверх роли по реестру путей:
- узлом он остаётся, если это код; его исходящие рёбра и упоминания
  учитываются;
- dead по нему не выпускается (шаг 2 §2.3);
- в `report.md` — таблица «вендор-копии»: путь, владелец, ref, декларация.

Владелец может совпадать с самим `scope` (самовендоринг D) — это не ошибка.
Файл, названный несколькими декларациями (например, `prose-paths.env`: член
A и шапка D), — не ошибка. Роль несёт список деклараций, в таблице
вендор-копий на каждую декларацию своя строка.
sha256 не сверяется: расхождение копии с апстримом — забота `attest-vendor.sh`,
`check_caller_pins` и `check_discovery_vendor.py`. Второй прибор на ту же
величину не заводится.

**Fail-closed.** Битая декларация сняла бы роль с копий, и они стали бы
кандидатами в dead. Поэтому находка `vendor-pin-*` запускает три механизма,
которые не зависят от того, что именно сломано (четвёртый действует
всегда):
1. **Названные пути.** Каждый токен любой строки кандидата, совпавший с путём
   корпуса (от корня или от каталога декларации), защищает этот узел от dead
   — даже если строка не разобрана.
2. **Потолок P6 «декларации».** Пока в репо есть хоть одна находка
   `vendor-pin-*`, dead по всему репо не выше `likely`. Так защищены
   переименованные при ре-вендоре копии, которых декларация уже не называет.
3. **Статус пробы.** `usage-graph` получает статус `partial`: код выхода 2 и
   судьба `unverified` → `not-rechecked` (§4.2–4.3). Иначе dead, подавленный
   этим механизмом, выглядел бы в дельте как `resolved`.

4. **Сам кандидат.** Кандидат-декларация всегда защищён от dead — важно для
   формата D, где член и есть кандидат.

Находки:
- неразобранный кандидат → `selfcheck/vendor-pin-unparsed` (high); `anchor` —
  `file:<декларация>`, `text_key` пустой;
- строка члена, указывающая на путь вне корпуса →
  `selfcheck/vendor-pin-dangling` (medium); `anchor` — `file:<декларация>`,
  `text_key` — путь члена. Одна находка на путь.

Нормативные отрицательные двойники:
- файл в каталоге декларации, не перечисленный в ней, анализируется как
  обычно; без `vendor-pin-*` в репо он может стать dead `confirmed`;
- битая декларация даёт находку, P6 и `partial`, а не молчание;
- тестовый файл, похожий на декларацию, кандидатом не является.

**Ограничения S2:**
- декларации соседей (у них формы вроде `source: devtools@<sha> <каталог>`)
  относятся к S3;
- находки прочих проб по вендор-копиям в S2 не меняются; владелец копии виден
  в таблице вендор-копий.

### 9.8 Приёмка S2

Фикстура — мини-флот из трёх репо (`scope` и два соседа) и мини-манифест в
отдельном git-репо. Она покрывает:
- **точный канал:**
  - ребро из `run:`;
  - ребро из рецепта;
  - ребро из `working-directory` с относительным путём;
  - вхождение сегмента дважды (`<repo>/<repo>/x.py`);
  - регистр (`../<REPO>/x.sh`);
  - класс `fleet-only`;
  - двойник `chrome/<repo>/x.sh` — ложное ребро закреплено;
- **текстовый канал** — каждая форма даёт P5 и dead не выше `likely`:
  - inline-код в `TODO.md` соседа;
  - fenced-блок `zsh`;
  - `"$WS/<repo>/x.sh"` в `run:`;
  - тест соседа;
  - `python -m <pkg>.<mod>`;
  - `.ex`-файл;
- **ключ как слово:**
  - `x.sh` в `xx.sh` и в `attest-x.sh` упоминанием не считается;
  - считаются упоминаниями: `…/x.sh.` в конце фразы, `pkg.mod.attr`,
    `a.pkg.mod`, `../<repo>/X.SH`;
  - файл в UTF-16 с BOM читается;
- **матрица dead через реальный `--fleet`:**
  - D1 → `confirmed`;
  - каждый двойник §9.6 → `partial` и `likely`;
  - репо манифеста (командный зонтик) входит во флот;
- **канарейка флота:**
  - сработала;
  - упоминание `fleet_canary.py` в настоящем репо не засчитывается;
  - канареечный узел не в `fleet-only` и не в поверхности;
  - флот урезан на одно репо → условие 2 §9.6 → `partial`;
  - перечисление настоящего репо вернуло 0 файлов → `empty`;
  - сломанный точный канал → `usage-graph failed`, `fleet = partial`;
  - сломанный текстовый канал → то же самое;
- **декларации:**
  - A с хвостом шапки;
  - B, C, D;
  - файл вне декларации;
  - неразобранный кандидат → P6 + `partial`, названные пути без dead;
  - висячая строка;
  - `..` в пути;
  - кандидат в подкаталоге, не известном заранее;
  - кандидат в `tests/` игнорируется;
  - `vendor_manifest.py` и YAML с `upstream:` без `commit:` — не кандидаты;
  - битая шапка D в коде: файл защищён сам;
  - шапка D с тегом вместо sha → `vendor-pin-unparsed`;
  - `commit: main` в формате C → `vendor-pin-unparsed`;
  - файл в двух декларациях → две строки в таблице.

Реальные данные — `make selfcheck ARGS=--fleet` на devtools после
синхронизации флота `./repos.sh pull`. Не `install`: он ставит репо на
sha или тег, это detached HEAD и, значит, `stale`. Требуются:
1. `surface.fleet = complete`, канарейка флота сработала;
2. ребро `fleet` steward `.github/workflows/arch-evidence-freshness.yml` →
   `file:check-arch-evidence-freshness.py` есть в `report.json` — это
   положительная точка на живых данных;
3. `fleet-only` = 0, и это напечатано явно;
4. дополнительно:
   - члены всех четырёх деклараций §9.1, являющиеся узлами, имеют роль
     `vendored-in` и не дают dead;
   - находок `vendor-pin-*` — 0;
   - код выхода 0.

Ноль в классе сам по себе ничего не доказывает. Сканер на каждом прогоне
доказывает канарейка, а на живых данных — ребро из условия 2.
