# dfl run: видимый прогресс фазы реализации (#765)

Статус: дизайн, решения владельца из обсуждения 17.11.
Issue: devtools#765. Связано: #766 (контроль процесса из Claude Code /
Desktop — следующий шаг, этот дизайн его основа).

## 1. Зачем

В живом прогоне sdd-runer (14.11) после гейтов `dfl run` запустил
`spec-runner run --all --strict --spec-prefix=… --integration-pr`, и терминал
молчал часами. Под `dfl` вывод раннера уходит в лог вызова, на экране — одна
подсказка `TUI_HINT` («прогресс в другом терминале: spec-runner tui …»).
Владельцу в этот момент нужно знать (его слова): **какая задача идёт, сколько
осталось и не завис ли процесс**.

## 2. Цели, не-цели, анти-цели

**Цели**
- Пока идёт реализация, окно `dfl` показывает историю событий раннера —
  **новой строкой на событие** (решение владельца: «чтобы видеть историю»).
- Последняя строка — **живой отсчёт от старта текущей задачи**, обновляется
  каждую секунду, без дополнительных слов (решение владельца: «не 5 минут и
  тем более не 10»). В ней же «N из M», чтобы «сколько осталось» было всегда
  на виду.
- Оба пути: enterprise и личный (оба запускают раннер через `Ops.spec_runner`).

**Не-цели**
- Стоимость — не выводим (решение владельца 17.11: «пока не надо»).
- Управление раннером из окна (пауза, стоп) — нет.
- Правка spec-runner — нет (соседний репо); всё читается из его стабильных
  контрактов.
- Замена `spec-runner tui` — нет, он остаётся для подробностей.

**Анти-цели**
- Прогресс замедляет или ломает раннер (блокировки БД, падение наблюдателя
  валит прогон).
- Отсчёт тикает, когда раннер уже умер, — ложный сигнал «жив».
- Строки событий теряются или дублируются при повторном `dfl run`.

## 3. Поведение

### 3.1 Строки событий (история)

Новой строкой, в момент события:

```
▶ TASK-004 «Команда find» — начата
✓ TASK-004 готова · 18:42
↻ TASK-005 «Порог надёжности» — попытка 2
✗ TASK-005 не прошла: <первая строка ошибки>
```

- «начата» — задача перешла в `running`;
- «готова · ММ:СС» (или «Ч:ММ:СС») — `success`, время от старта задачи;
- «попытка N» — новая попытка той же задачи после неудачной;
- «не прошла» — задача `failed`; текст — первая строка `attempts.error`.

### 3.2 Живая строка (отсчёт)

Последняя строка окна, перерисовывается на месте раз в секунду:

```
  TASK-005 · 5 из 16 · 03:17
```

- отсчёт — от `started_at` текущей задачи; «N из M» — номер текущей и всего
  задач прогона;
- между задачами (ни одна не `running`) — отсчёт от конца предыдущей, без
  номера задачи (мой выбор; строитель может уточнить форму);
- **отсчёт идёт, только пока жив процесс раннера**. Раннер завершился —
  живая строка стирается, дальше обычный вывод `dfl` (итог/стоп как сейчас).
  Растущий отсчёт без новых событий и есть сигнал «долго» — без слов
  (решение владельца).

### 3.3 Итог

После завершения раннера одна строка: `реализация: сделано N из M · Ч:ММ:СС`
(общее время), затем — как сейчас (PR, стоп, ручные проверки #771).
Стоимость не выводится.

### 3.4 Без терминала

Нет TTY (вывод в файл, CI) — только строки событий и итог; живой строки нет
(`\r`-перерисовка в файле — мусор).

## 4. Откуда данные (мои решения)

- **Файл состояния spec-runner** `.executor-state.db` (SQLite) — объявленный
  стабильный контракт экосистемы (`spec-runner/docs/state-schema.md`):
  `tasks(task_id, status, started_at, completed_at)` и
  `attempts(task_id, success, error, timestamp)` — все `stable`. Путь — как
  у spec-runner для `--spec-prefix` (строитель сверяет с его `config.py`).
- **Названия и число задач** — из `tasks.md` прогона (dfl его и так знает и
  рендерит), не из БД.
- Чтение **только на чтение** (`file:…?mode=ro`, URI), короткие запросы,
  опрос раз в ~1–2 с; БД нет или занята — пропуск такта, не ошибка.
- Наблюдатель — фоновый поток рядом с блокирующим `ops.spec_runner(...)`:
  читает БД, сравнивает со снимком прошлого такта, печатает события;
  отдельный такт раз в секунду перерисовывает живую строку. Любая ошибка
  наблюдателя гасится (одна строка в лог), прогон не трогает.
- Вывод на экран — через `notice` / `DFL_SCREEN_FD` (под `dfl` stdout
  раннера перехвачен в лог); живая строка — только когда экран — терминал.
- Повторный `dfl run` (продолжение прогона, #767): события, бывшие до старта
  этого запуска, не печатаются заново — снимок берётся при старте раннера.

## 4a. Решения по вопросам проверки дизайна (мои)

- **Счётчики.** M — все задачи `tasks.md` прогона. «Сделано N» в итоге
  включает задачи, сделанные до остановки (как плашка #767: «сделано 14 из
  16»). «N из M» живой строки — порядковый номер текущей задачи по ходу:
  сделано + 1. `skipped` считается сделанной (раннер её не будет делать).
- **Путь БД** — правило spec-runner по умолчанию
  (`spec/.executor-{prefix}state.db`) плюс ключ `state_file` из его конфига
  (корень, legacy `spec/executor.config.yaml`, обёртка `executor:`);
  `change_id` dfl не использует. БД не появилась за 30 с после старта —
  одна строка `прогресс недоступен: нет <путь>` (неверный путь не должен
  выглядеть как молчаливо здоровый прогон); раннер идёт дальше.
- **Повтор задачи.** Живой отсчёт — от старта текущей попытки (строка
  «↻ попытка N» и есть сброс); «готова · ММ:СС» — полное время задачи с
  первого старта в этом запуске.
- **Задел под #766.** Наблюдатель отдаёт события приёмнику (callable);
  печать на экран — один из приёмников. #766 подключит свой.
- **`-vvv` (PASSTHROUGH).** Вывод раннера идёт прямо на экран — только
  строки событий, без живой строки (иначе перерисовка мешается с выводом).

## 5. Связь с прочим

- `TUI_HINT` остаётся строкой при старте (для подробностей), но больше не
  единственная.
- #766 (доступ из Claude Code / Desktop) переиспользует тот же наблюдатель
  событий как источник уведомлений.

## 6. Оставлено строителю

- Модуль и имена (общий для обоих путей, как `governance/run_resume.py`).
- Точная форма времени (ММ:СС / Ч:ММ:СС), символы ▶ ✓ ↻ ✗.
- Период опроса БД в пределах 1–2 с.
