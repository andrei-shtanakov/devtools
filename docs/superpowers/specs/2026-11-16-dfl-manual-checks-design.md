# dfl run: ручные проверки — вопрос владельцу в конце прогона (#771)

Статус: дизайн, решения владельца из обсуждения 16.11.
Issue: devtools#771. Связано: #765, #768 (пауза на ревью — образец вопроса), #792 (журнал
требований проекта — отделён).

## 1. Зачем

Живой прогон `sprc-runner-claude-agent-sdk-20261112-eng-d52f5f`
(ai-prosto/ssd-runner, режим test) дошёл до «конвейер закончен», PR #19
одобрен ревью. При этом TASK-018 (BEH-39: порог надёжности NFR-01 ≥ 9/10)
закрыт только формально: фактическая серия — 4/10 → 6/10 → 6/10 → 5/10.

Проверки `kind: manual` конвейер не исполняет и свидетельства их
прохождения не требует:

- `governance/task_bridge.py` намеренно выкидывает manual-цели из
  `**Verifies:**` — spec-runner их не прогоняет и закрывает задачу DONE;
- подсчёт «человеческих» критериев есть только в `criteria_close`
  (`make criteria-close`, ручной вызов), `dfl run` его не вызывает;
- личный путь (`lite/personal/`) тоже объявляет `kind: manual` в
  декомпозиции (`lite/personal/prompts/decomposition.md`) и тоже молчит.

Итог «конвейер закончен» читается как «требования выполнены». Для
поведения, которое проверяет только человек, это неправда.

## 2. Цели, не-цели, анти-цели

**Цели**
- Перед словами «конвейер закончен» `dfl` останавливается и спрашивает
  владельца по **каждой** ручной проверке прогона. Оба пути: enterprise и
  личный. Решение владельца.
- Ответ записывается и виден потом в двух местах: `dfl status` и
  комментарий в PR с кодом. Решение владельца.
- «Не выполнено» не теряется: в репо проекта заводится issue. Решение
  владельца.

**Не-цели**
- Исполнять ручные проверки автоматически или проверять ответ человека.
  Ответ владельца и есть свидетельство.
- Блокировать мерж PR с кодом. Прогон завершается при любом ответе.
  Решение владельца: «завершается с честной пометкой».
- Запускать доработку по невыполненным требованиям. Владелец выбрал issue,
  а не новый прогон.
- Менять `criteria_close` и enterprise-закрытие воркстрима по оракулу.

**Анти-цели** (провал, даже если «работает»)
- Прогон с невыполненной ручной проверкой заканчивается строкой, по
  которой этого не видно.
- Повторный `dfl run` после ответов заводит второй issue или второй
  комментарий на ту же проверку.
- Прогон без ручных проверок получает лишний шаг или вопрос.

## 3. Поведение

### 3.1 Когда

После того как PR с кодом проверен (enterprise: `code-accept` завершён с
URL; личный путь: шаг перед `done`) и до финальной строки «конвейер
закончен» / «смержите … — конвейер закончен». Решение владельца: «в конце
прогона, перед словами „конвейер закончен“».

В test-режиме PR к этому моменту обычно не влит — `dfl` пишет «смержите
…». Вопрос задаётся до мержа; ответ мерж не блокирует.

Нет ручных проверок — шага нет, всё как сейчас.

### 3.2 Что считается ручной проверкой

Сценарий (BEH) прогона, чей `checked_by` имеет `kind: manual`, и задача
(TASK/DT), которая его закрывает. Одна проверка = один BEH. Источник —
бандл прогона по пину, тот же, из которого `task_bridge` строил задачи
(enterprise), и бандл личного прогона (личный путь).

Waived-сценарии — не вопрос (их уже сняли осознанно).

### 3.3 Вопрос

По одному на проверку, в стиле паузы на ревью (#768, `lite/review_pause`,
`lite.interview_chat.read_answer`):

```
Ручная проверка BEH-39 (TASK-018): «порог надёжности NFR-01 ≥ 9/10»
шаги: docs/reliability-baseline-2026-11-15.md
1. выполнено · 2. не выполнено · 3. принять с оговоркой
```

- «принять с оговоркой» — следом запрос короткого текста оговорки
  (пустой — повтор вопроса).
- «не выполнено» — следом необязательный комментарий (что видно на деле,
  например «5/10»); он уходит в issue.
- Стоп-слово (`STOP_WORD` интервью) — выход без ответа: прогон стоит на
  этом шаге, повторный `dfl run` спрашивает **только неотвеченные**.
- Неинтерактивный запуск (нет TTY / `read` недоступен) — стоп с причиной
  «ждут ответа N ручных проверок — запустите dfl run в терминале», без
  ответа по умолчанию.

### 3.4 Что дальше по ответу

| Ответ | Запись | Действие |
|---|---|---|
| выполнено | status + PR | — (ответ = свидетельство; ссылка на документ шагов) |
| с оговоркой | status + PR, текст оговорки | — (требование принято с ограничением) |
| не выполнено | status + PR, комментарий | issue в репо проекта |

Issue «не выполнено» (одна на проверку):
- заголовок: `Ручная проверка не выполнена: BEH-39 — <название>`;
- тело: требование (текст сценария), задача, документ шагов, комментарий
  владельца, ссылка на PR с кодом, id прогона; первая строка — маркер
  для `Ops.find_issue` (идемпотентность), например
  `<!-- dfl-manual-check run=<run_id> beh=BEH-39 -->`;
- учётка — та же, что у прочих записей `dfl` в репо проекта (`Ops`).

Комментарий в PR с кодом — один на прогон, со всеми ответами (таблица
BEH · задача · ответ · оговорка/комментарий · issue). Свой маркер для
дедупа. Опубликован — повторный `dfl run` его не дублирует.

Подтверждено владельцем 16.11: issue только для «не выполнено», не для
«с оговоркой»; один общий комментарий в PR, а не по одному на проверку.

### 3.5 Ответ окончателен, журнал только на добавление

Решение владельца 16.11. Запись ответа никогда не меняется: комментарий в
PR — снимок на момент приёмки. Достижение цели позже — **новая** запись
поверх старой, не правка:

```
BEH-39  16.11  не выполнено (5/10) — ответ при приёмке PR #19 → issue #24
BEH-39  20.12  выполнено — issue #24 закрыт
```

Текущее состояние проверки — последняя запись. Вторую запись никто не
обязан помнить: `dfl status` читает состояние issue вживую, и закрытый
issue = «выполнено» со ссылкой. `dfl` ничего не правит задним числом.

Общий журнал требований проекта (отложенное, баги эксплуатации, новые
issues) — отдельная задача devtools#792; этот дизайн её не делает, но и не
мешает ей.

### 3.6 Финальная строка и `dfl status`

- Все «выполнено» — строка прежняя.
- Есть «не выполнено» / «с оговоркой» — строка честная, например:
  `смержите <url> — конвейер закончен; ручные проверки: 1 не выполнена
  (BEH-39 → issue #24), 1 с оговоркой`.
- `dfl status` прогона показывает ту же сводку; `-v` — по проверке на
  строку с оговоркой/комментарием и ссылкой на issue; для «не выполнено»
  — живое состояние issue (открыт / закрыт → «выполнено позже»).

### 3.7 Состояние

Ответы хранятся в состоянии прогона (enterprise: `state.ops[...]`; личный:
`PersonalRun`), до публикации: ответ записан → issue (если нужен) →
комментарий в PR → «закончен». Каждый шаг идемпотентен: повтор после
падения посреди публикации доделывает недостающее, не дублируя
(`find_issue` по маркеру, маркер комментария).

## 4. Режимы

Одинаково в `test` и `strict`; ослабления для test нет (подтверждено
владельцем 16.11). Пункт issue про «ослаблено N проверок» в test снят.

## 5. Решения по вопросам проверки дизайна (мои)

- **«Закончен» = PR проверен И все ручные проверки отвечены.** Пока есть
  неотвеченные, конвейер репо не закончен: `dfl run --subject <новая>` в
  том же репо отказывает так же, как при любой незаконченной цепочке.
- **Ветки «вмержен человеком без автоматической приёмки»**
  (`merged_unreviewed`, `code_merged`, `auto_tasks._finish_merged`) —
  вопрос задаётся и там: правило «перед словами „конвейер закончен“».
- **Личный путь — до мержа**, как enterprise: вопрос задаётся на шаге
  `code-pr`, пока PR открыт, до строки «смержите …»; ответив, владелец
  мержит. Отвеченные не переспрашиваются.
- **Issue без метки `inbox`.** `RealOps.create_issue` вешает `inbox`
  («запрос соседа», ADR-ECO-006), в чужом репо её может не быть. Нужен
  вызов без метки (параметр или отдельный метод `Ops`). Идемпотентность —
  номер issue в состоянии прогона, сохранённый сразу после создания;
  поиск по маркеру — только для восстановления, если номер не сохранился.

**Только новые прогоны** (решение владельца 16.11). Прогоны, чей конвейер
закончился до выхода функции (в т.ч. `sprc-runner-…-d52f5f`), вопросов не
получают: `dfl run` на них ведёт себя как сейчас. Признак — отметка в
состоянии прогона, которую новый код ставит при **создании** прогона;
прогон без неё — старый, шаг для него пропускается. (Отметка «по концу
прогона» не годится: незаконченный новый прогон тоже был бы без неё.) Старый случай владелец проверит заново
на новом репо с новой задачей.

## 6. Оставлено строителю

- Точное имя шага/опа и форма записи в состоянии.
- Где именно в цепочке enterprise (`auto_tasks` / `lite/dfl.py`
  `_next_hint`) и личного (`flow._step_code_pr`) встаёт шаг.
- Общий модуль для обоих путей (как `governance/run_resume.py` для #767)
  — желателен.
- Тексты, кроме зафиксированных выше форм.
