# DarkFactory из Claude Code Desktop: скил поверх пошагового `dfl` (devtools#766)

Статус: черновик дизайна, 2026-11-17. Решения владельца — из обсуждения 17.11.

## 1. Зачем

Многие коллеги работают в Claude Desktop и не работают в терминале. Им нужен
путь от идеи до старта реализации без терминала — разговором, в котором Claude
не просто задаёт вопросы по очереди, а **подсказывает ответы, предлагает
варианты, поясняет, отвечает на встречные вопросы по теме и по запросу
показывает, что уже отвечено, а что нет**. Попутно это лечит критику владельца
«процесс как экзамен» (демо 15.11).

Клиент — **Claude Code Desktop** (решение владельца): он работает на машине
пользователя, видит установленные `dfl`, `gh`, `uv`, понимает скилы.
Cowork не цель (изолированная машина без `dfl` и входа в GitHub).

## 2. Цели, не-цели, анти-цели

Цели:
- Скил `darkfactory` в Claude Code Desktop ведёт **оба пути** — личный и
  enterprise — от новой темы до старта реализации (личный: spec-PR вмержен;
  enterprise: W5 одобрена, задачи готовы).
- Скил заменяет **разговорную часть** `dfl`, не проверки: ответы записываются
  через discovery (enterprise) и через ту же проверку брифа (личный); бриф,
  этапы и спека задач проходят те же гейты и edge-check.
- В разговоре: подсказки, варианты, пояснения, ответы на вопросы по теме,
  список «отвечено / не отвечено» по запросу.
- Терминальный `dfl` для человека не меняется.

Не-цели (v1):
- Контроль долгой реализации из чата (п.3 #766): скил может запустить
  реализацию и показать `dfl status -v` по запросу, но живого прогресса,
  уведомлений и т. п. в v1 нет — отдельная работа после v1.
- MCP-сервер (вариант Б) — возможен позже поверх того же протокола.
- Cowork, Claude Desktop-чат без shell.
- Двуязычие (#769) — после этой работы.

Анти-цели (провал, даже если «работает»):
- Скил пишет артефакты в обход `dfl`/discovery (файлы узлов, бандл, журналы
  руками) — конвейер получит то, чему нельзя доверять.
- Скил мержит PR или выполняет другой акт человека за него. Мерж — человек,
  на GitHub, по ссылке.
- Ответ, придуманный Claude, записан как сказанный человеком без следа
  (см. §5.3).
- Обход песочницы/границы автора (`author_launch`) — скил только зовёт входы
  `dfl`.

## 3. Подходы

- **А. Скил + пошаговый режим `dfl` — выбран владельцем.** `dfl` без терминала
  не ждёт ввода: дойдя до места, где нужен человек, записывает вопрос и
  останавливается; скил читает вопрос, обсуждает с человеком, отдаёт ответ,
  снова зовёт `dfl run`. Работает в Claude Code Desktop и терминальном Claude
  Code; содержательная работа интервью — в сессии Claude.
- **Б. То же, вход — MCP-сервер** с типизированными инструментами. Строже
  формат, работает без shell, но лишний сервер и его подключение у каждого;
  Claude Code Desktop shell уже даёт. Отложен — можно надстроить над А.
- **В. Скил гоняет интерактивный `dfl` и пересказывает вопросы.** Отброшен:
  Claude Code не ведёт интерактивный ввод чужой программы; долгий `dfl run`
  обрывается по таймауту инструмента (~10 мин).

## 5. Дизайн

### 5.1. Протокол «вопрос наружу / ответ внутрь»

- **Ожидающий вопрос** — запись в каталоге прогона (`pending.json`): `id`
  (стабильный ключ места + содержимого вопроса), `kind` (`review`,
  `remarks-confirm`, `edge`, `manual`, `interview-enterprise`,
  `interview-personal`, …), `run_id`, текст вопроса, варианты (если есть),
  пути/ссылки на файлы для просмотра, что допустимо в ответе (номер варианта,
  «своё: …», «не согласен: …», «готово», …), время.
- **Без терминала** место, дойдя до вопроса без готового ответа, пишет
  `pending.json` и `dfl run` завершается **кодом 0** (ждёт человека, не сбой),
  строкой «ждёт ответа: <кратко> — dfl pending / dfl reply».
- **`dfl pending [--json]`** — ожидающий вопрос (или «нет»).
- **`dfl reply --id <id> (--text '…' | --file f)`** — проверяет ответ по `kind`
  сразу (номер в диапазоне, непустая причина у «не согласен» и т. п.; отказ —
  с причиной, как в терминале), записывает его к прогону. Прогон не двигает:
  дальше `dfl run`. Чужой/устаревший `id` — отказ.
- **Продолжение без повторных платных вызовов.** `dfl run` проходит место
  заново и берёт записанный ответ по `id`. Агентская работа ДО вопроса
  (сортировка замечаний, переписывание узла по замечаниям, варианты) не
  повторяется: её результат обязан быть сохранён к моменту записи вопроса.
  Где это уже так — оставить (журнал интервьюера личного пути; кэш `triage`
  edge-check в каталоге прогона; записи ручных проверок); где нет — сохранить
  (строитель проверяет каждое место; известный кандидат —
  `owner_review.revise_by_owner` → `confirm_removals`).
- **Агентская работа мест 3–6 остаётся в `dfl`** (решение владельца): скил
  только передаёт вопрос и ответ и поясняет. Платные вызовы и гейты не меняются.
- **Терминал побеждает.** `dfl run` в терминале при записанном вопросе задаёт
  его вживую, ответ из терминала снимает `pending.json`. Две стороны не пишут
  одновременно — прогон под замком (`run_lock`).

### 5.2. Интервью

**Enterprise (2e).** Скил ведёт разговор сам, по текущему вопросу discovery:
- `dfl pending --json` для `interview-enterprise` отдаёт id вопроса, тему, текст
  и **покрытие** (темы обязательные/необязательные, покрыты или нет; после конца
  интервью — находки гейта GC-08/13/05 по пунктам).
- Claude сессии раскладывает ответ в `text:` + `entries:` (то, что сегодня
  делает вложенный `claude -p` в `lite/structure.py`) и отдаёт через
  существующий `dfl answer --file` (`--question/--supersede` для добора и
  починки). Проверяет discovery; отказ — Claude исправляет и повторяет, человек
  видит простое сообщение.
- Правила раскладки (префиксы тем, traces FR→G/J, Priority, Acceptance,
  Target у NFR, M→G и т. п.) скил берёт из того же источника, что промпт
  `structure.py`, — без второй копии правил (строитель выбирает механизм:
  `dfl` отдаёт правила в `--json`, или скил ссылается на файл промпта).

**Личный путь (2p).** Интервьюер — Claude сессии:
- Вопросы и варианты Claude задаёт по смыслу `prompts/interviewer.md` (тот же
  источник), бриф собирает в форме `brief_from_json`.
- Новая команда **`dfl brief --file brief.json --transcript t.jsonl`**:
  прогоняет `brief_problems`/`demote_uncovered`, пишет журнал разговора в
  `interview.jsonl` того же формата и бриф — как `_write_brief`; проблемы брифа
  возвращает скилу (человек их не видит, как реплика `check` сегодня).
  Подтверждение «Верно?» — в разговоре, до вызова.
- Терминальный интервьюер (`interviewer.interview`) не меняется по поведению;
  внутренняя перестройка допустима, существующие тесты экрана и диалога
  проходят **без правок**.

**Список «отвечено / не отвечено»** — по запросу человека, из `dfl interview
--json`: enterprise — покрытие тем и находки гейта; личный — цели, функции
с/без критерия, «Уточнить».

### 5.3. Чьи слова

Правило то же, что в `dfl` сегодня: пункты формулирует агент (`entries:` /
бриф), рядом дословно хранится сказанное человеком (`text:` / реплики `human`
журнала). Если человек принял предложение Claude («да, так», «второй»), в
дословное поле пишется `принято предложение: <текст предложения>` — как
«2. <текст варианта>» в личном пути сегодня. Новых полей нет.

### 5.4. Скил

- Каталог `skills/darkfactory/` в devtools (`SKILL.md` + справка);
  `install.sh` ставит его в `~/.claude/skills/darkfactory` (обновление — тем же
  `install.sh`). Что Claude Code Desktop читает пользовательские скилы
  оттуда — проверить на первом шаге (живой факт, не допущение).
- Цикл: `dfl status --json` → (новая тема: пояснить и спросить тип проекта →
  `dfl run --subject … --track …`) → `dfl run` → есть `pending` — разговор →
  `dfl reply` / `dfl answer --file` / `dfl brief` → `dfl run` … → PR на мерж:
  ссылка человеку, ждать его слова «вмержил» → `dfl run`.
- Поведение в разговоре: подсказка ответа и варианты помечены как предложение;
  пояснение «зачем этот вопрос»; ответы на вопросы по теме — из памятки
  `docs/darkfactory-for-colleagues.md` и справки скила; список
  отвеченного — по запросу.
- Запреты скилу: не править файлы бандла/узлов и журналы руками; не мержить и
  не закрывать PR; не звать `make behaviour-run` и внутренние модули; на
  отказ `dfl` — показать причину человеку, не обходить.
- Старт реализации: скил говорит, что она долгая, и запускает `dfl run` в
  фоне; «как дела» — `dfl status -v`. Большего в v1 нет (§2).

### 5.5. Что меняется в терминале

Ничего в поведении. Видимое: команды `pending`, `reply`, `brief` в `--help`;
`dfl status` показывает ожидающий вопрос; без терминала вместо «запустите в
терминале» — «ждёт ответа: … dfl pending / dfl reply».

### 5.6. Уточнения после проверки строителем (решения агента, владелец проверяет при чтении)

Общий принцип: **правила и лимиты живут в `dfl` и тестируются; скил несёт
только содержание разговора** (подсказки, раскладку, пояснения).

1. **Чьи артефакты переписывает скил.** Артефакты интервью (бриф личного
   пути; ответы discovery) — пишет и переписывает Claude сессии; узлы этапов
   (design, decomposition, узлы волн) — агент внутри `dfl`, как сегодня.
   Следствие для паузы «бриф» личного пути: замечание владельца не уходит
   платному интервьюеру `dfl`; `dfl run` без терминала ставит pending
   `brief-remarks` (текст замечания), скил правит бриф с человеком,
   подтверждает «Верно?» и отдаёт `dfl brief --revise`: новый бриф заменяет
   прежний, запись одобрения брифа в `APPROVALS` снимается и ставится заново
   по обычному пути паузы. Терминальный путь не меняется.
2. **`dfl brief` и проверка.** Всегда возвращает проблемы (`brief_problems`),
   ничего не переносит сам. Принудительный перенос функций без критерия в
   «Уточнить» — только явным `dfl brief --accept-uncovered` (аналог
   терминального лимита 20 вопросов / 3 проверок); скил предлагает его
   человеку, когда исправить не выходит. **Любое изменение брифа после «Верно?»
   — новое «Верно?»**: в бандл не попадает текст, которого человек не видел.
   Pending `interview-personal` — сигнал «нужен бриф» с темой и, при
   продолжении, журналом.
3. **Журнал личного интервью пишется по ходу**, не одним куском: скил после
   каждого обмена зовёт `dfl note` (реплики `agent`/`human` формата
   `interview.jsonl`; встречные вопросы человека и пояснения — тоже, как
   реплики). Переход в терминал посреди интервью продолжает тот же журнал —
   терминальный интервьюер уже умеет продолжать с журнала (RF-1). `check`
   пишет `dfl brief`.
4. **Enterprise: управление интервью — в `dfl`.** Порядок вопросов, добор
   непокрытых тем (один проход, `--supersede` держателя) и починка по
   GC-08/13/05 (один проход; GC-05 — вердикт инженера) ведёт `dfl`: каждый
   шаг — pending своего вида (`interview-question`, `interview-topup`,
   `interview-repair`) с id вопроса/держателя, который скил отдаёт обратно в
   `dfl answer --file --question … [--supersede]`. Выход из
   `stopped_interview` — тот же `dfl run`. Лимит «≤2 уточнения» в скиле не
   нужен: уточнения — часть разговора до отправки, без платных вызовов.
5. **Лимиты кругов между вызовами.** Счётчики кругов разбора edge-check
   (`MAX_ROUNDS`, предложение «принять вопреки» на последнем круге) и повторов
   правки по замечаниям владельца хранятся в состоянии прогона на волну/этап,
   а не в локальной переменной вызова: цикл pending → reply → `dfl run` даёт
   ровно те же лимиты и ту же границу расходов, что терминал. Тест: N циклов
   без терминала = столько же платных вызовов и то же предложение, что один
   терминальный проход.

## 6. Порядок поставки (предложение)

1. Протокол (`pending.json`, `dfl pending`, `dfl reply`) + места 3 и 6 (без
   агентской работы до вопроса).
2. Места 4 и 5 (сохранение агентской работы до вопроса).
3. Enterprise-интервью: `pending --json` с покрытием и находками,
   `dfl interview --json`.
4. Личный путь: `dfl brief`.
5. Скил, установка, памятка; живой прогон обоих путей в Claude Code Desktop и
   один прогон в терминале (регрессия).

## 7. Проверка

- Тесты на каждое место: без терминала → `pending.json` и код 0; `reply` с
  верным/неверным ответом; продолжение берёт ответ и **не** делает повторных
  платных вызовов (счётчик фейка агента).
- Терминальные тесты экрана/диалога — без правок.
- Сквозной тест без терминала: личный и enterprise путь на фейках до старта
  реализации только через `run/pending/reply/answer/brief`.
- Живой прогон: оба пути в Claude Code Desktop коллегой-без-терминала (или
  владельцем в этой роли).

## 8. Оставлено строителю

Точная схема `pending.json` и `--json`-выводов; формат `id`; имена kind;
механизм передачи правил раскладки скилу без копии; структура справки скила;
как именно сохраняется агентская работа в местах 4–5.
