# dfl: личный путь — свободное интервью, облегчённый бриф, короткая цепочка — дизайн

Дата: 2026-11-15. Статус: на одобрение владельца (развилки решены 15.11, §8).
Связано: devtools#764 (гибкое интервью), #768 (пауза на ревью артефакта —
отдельный дизайн, ложится на точки этого), #762 (разбор замечаний edge-check),
живой прогон sdd-runer 12–15.11 (ai-prosto/ssd-runner#19).

## 1. Зачем

Живой прогон личного проекта sdd-runer прошёл через интервью заказчика
discovery и полную цепочку из семи документов (~3 600 строк). Слова владельца:

- «когда спросил про enterprise, хотя проект личный, — все последующие вопросы
  воспринимались как „мимо кассы“» (все — а не один);
- «для персонального проекта не вижу смысла в конкретных пунктах, скорее это
  должен быть скилл, который запускает брейншторм»; «интервьюер должен быть
  свободным в вопросах»;
- «помогли цели и функции с критериями приёмки, остальное — церемония».

Discovery задуман как интервью с заказчиком, а не как уточнение деталей
личного проекта (владелец). Поэтому личный путь — свой, в `dfl`; discovery
остаётся путём enterprise.

## 2. Цели, не-цели, анти-цели

Цели:
- Первый вопрос нового прогона — тип проекта: **личный** или **enterprise**.
- Личный проект: свободный разговор-брейншторм вместо банка вопросов;
  противоречие в ответах уточняется сразу новым вопросом.
- Облегчённый бриф: цели, функции с проверяемыми критериями приёмки, контекст.
- Короткая цепочка: бриф → дизайн → декомпозиция (задачи) → реализация
  spec-runner, edge-check только между соседними узлами.

Не-цели (этого дизайна):
- Enterprise-путь в devtools не меняется: полная цепочка из семи узлов и
  discovery. Опросник владельца (`docs/Опросник discovery для AI-продукта.md`)
  как основа фрейма заказчика и проверки брифа — issue в discovery-toolkit
  (соседний репо, его не правим).
- Уточнение противоречий в enterprise-интервью (`lite/interview_chat.py`) —
  отдельный шаг после этого дизайна.
- Пауза на ревью артефакта (#768) — отдельный дизайн; здесь только точки, где
  она встанет (бриф, дизайн, декомпозиция).
- Боевой режим (`strict`): `dfl` работает только в `test` (`lite/dfl.py:466`),
  личный путь — тоже.

Анти-цели (провал, даже если «работает»):
- Интервью ощущается экзаменом: вопросы по списку, не по ответам; вопрос про
  то, что из сказанного уже ясно; правка файлов руками.
- В личном проекте всплывают вопросы enterprise (спонсор, аппрув, compliance,
  стейкхолдеры, метрики «до»).
- Облегчение съело проверяемость: функция без критерия, по которому тест может
  сказать «да/нет»; задача без теста, который её проверяет.
- Enterprise-цепочка поломана или изменилось её поведение.

## 4. Решения

### 4.1 Тип проекта — первый вопрос

Новый прогон (`dfl run --subject …`) начинается вопросом с вариантами:
«1. Личный проект — для себя (возможно, с близким кругом) · 2. Enterprise —
заказчик, команда, регламенты». Ответ пишется в состояние прогона
(`RunState.track`: `personal` | `enterprise`) и не меняется до конца прогона
(сменить — новый прогон). Существующие прогоны без поля = `enterprise`
(обратная совместимость). Флаг `dfl run --subject … --track personal`
пропускает вопрос.

### 4.2 Свободный интервьюер (личный путь)

Поведение интервьюера — инструкция агенту (промпт-«скилл» в devtools), а не
список вопросов. Агент — тот же класс вызова, что раскладчик ответов сейчас
(`claude -p --safe-mode --tools ""`), без инструментов; вопрос/ответ идут через
терминал `dfl` (переиспользуется `stdin_read`, `read_answer`, ответ номером без
пустой строки).

Инструкция задаёт:
- Цель разговора — закрыть три блока брифа (4.3); каждый ход — один вопрос,
  выбранный по уже сказанному; варианты ответов — когда они помогают (человек
  может ответить своими словами).
- Контекст выясняется по ходу, а не анкетой: кто пользуется (только я / ещё
  люди), нужна ли авторизация, есть ли интернет, нужен ли доступ к локальной
  системе, платформа. Ответ на одно может сделать другое неактуальным
  (личный, только я → авторизация не нужна, не спрашивать).
- Противоречие с уже сказанным — следующий вопрос именно о нём, с вариантами
  разрешения; молча совмещать нельзя.
- Запрещено: вопросы enterprise (спонсор, аппрув, compliance, стейкхолдеры,
  метрики «до», бюджет), Q-NN-исследования, MoSCoW.
- Конец: агент показывает сводку брифа и спрашивает «верно?» (1. да ·
  2. поправить: …). «Да» — бриф готов.

Состояние разговора (реплики) хранится в каталоге прогона, чтобы `dfl run`
после Ctrl-C продолжал с того же места. Потолок — 20 вопросов; на потолке
агент обязан перейти к сводке с тем, что есть, а пробелы пометить «уточнить».
Платные вызовы считаются и видны (как в #762).

### 4.3 Облегчённый бриф

Файл `<bundle>/00-brief.md`, разделы:

```
## Цели
### G-01: <исход, а не фича>
<1–3 строки: зачем, как выглядит «стало хорошо»>

## Функции
### FR-01: <что умеет>
**Цели:** G-01
**Критерии приёмки:**
- <проверяемое утверждение: тест может сказать да/нет>
**Слова владельца:** <дословно, как сказано>

## Контекст
- Пользователи: <только я | я и …>
- Авторизация: <нет | …>
- Сеть: <есть | нет | только локально>
- Локальная система: <что читает/пишет | не трогает>
- Платформа: <macOS | Linux | …>
- Прочее: <важные факты из разговора>

## Уточнить
- <пробелы, если разговор упёрся в потолок; пусто — раздел опускается>
```

Проверка брифа (своя, в `lite/`, не discovery gate): ≥1 G; ≥1 FR; у каждого FR
есть ≥1 критерий приёмки и ссылка на существующую G; id уникальны и по
порядку; все пять строк контекста заполнены (допустимо «не важно»). Провал
проверки — не стоп человеку: агент интервью доспрашивает недостающее (тот же
разговор). Трассировки, приоритеты, персоны, NFR, метрики, риски — нет.

Одобрение брифа: подтверждение сводки в разговоре («верно? — да»)
записывается в журнал прогона как одобрение; отдельного PR брифа и мержа
человеком на личном пути нет (см. §8: весь личный путь — без волн, один PR
в конце). Точку для паузы-ревью добавит #768.

### 4.4 Короткая цепочка и edge-check

Узлы личного пути: `00-brief.md` → `20-design.md` → `30-decomposition.md` →
`tasks.md` (spec-runner). Номера файлов — как в полной цепочке, чтобы
инструменты, читающие по имени файла, не раздваивались.

- **Дизайн** пишется из брифа: модули, файлы, команды, вызовы, решения по
  контексту (платформа, сеть, хранение). Объём — сколько нужно проекту, без
  обязательных разделов полной цепочки.
- **Декомпозиция** пишется из дизайна и брифа. Каждая задача DT несёт свои
  проверки сама — вместо ссылок на BEH: строка `**Проверка:**` с `kind`
  (`pytest` | `manual` | …) и `target` (путь теста/узла), плюс `**Критерии:**`
  — ссылки на критерии приёмки FR брифа (`FR-01/1`). Каждый критерий каждого
  FR покрыт хотя бы одной задачей — инвариант графа.
- **Edge-check** — два ребра: `design-vs-brief`, `decomposition-vs-design-brief`
  (новые файлы правил в `contracts/edge-check/v1/rules/`). Разбор замечаний —
  как в #762 (агент правит сам, решения — вопросом с вариантами).

Реализация в коде:
- Вариант цепочки выбирается по `RunState.track`: новый вариант `PERSONAL_DAG`
  рядом с `BUNDLE_DAG` и профиль `profiles/personal.yaml`. Все захардкоженные
  копии цепочки (§3) читают вариант прогона, а не константу полной цепочки —
  один источник, остальные копии выводятся из него.
- `task_bridge` получает ветку для личного пути: цели проверок — из
  `**Проверка:**` задачи, без чтения `15-behaviour-spec.md`; инвариант
  покрытия критериев — в `decomposition_guard`.
- Промпты авторов узлов `design`/`decomposition` для личного пути — свои
  (короче, без BEH/AC), правила своего ребра автор получает, как сейчас
  (`rules_for(kind)`).

### 4.5 Enterprise

Без изменений в поведении: `track: enterprise` → текущий путь (discovery,
frame customer/engineer, семь узлов). Отдельно: issue в discovery-toolkit —
опросник владельца как основа фрейма заказчика, translation table и критерии
«Discovery завершён» — как проверка брифа.

## 5. Ограничения

- Authority-root (мерж — только человек): `governance/bundle_dag.py`,
  `profiles/`. Изменения в них — отдельным маленьким PR (вариант цепочки и
  профиль); остальное (`lite/`, `runner.py`, `spec_loop.py`, `task_bridge.py`,
  `decomposition_guard.py`, `edge_check/*`, `contracts/edge-check/`) — обычные
  PR с мержем агентом.
- Соседние репо (discovery, discovery-toolkit, spec-runner) не правим.
- Enterprise-регрессия: полный набор тестов devtools зелёный без изменений
  существующих тестов полной цепочки (кроме механических — чтение варианта
  вместо константы).

## 6. Решения за строителем

- Точная формулировка инструкции интервьюера и сводки (в рамках 4.2).
- Формат хранения реплик разговора и как он возобновляется.
- Как именно копии цепочки выводятся из одного источника.
- Разметка `**Проверка:**` (лишь бы `task_bridge` получил те же `kind`/`target`,
  что сейчас из `checked_by`).

## 7. Уточнения после чтения строителем

- **Кто пишет бриф.** Интервьюер в конце возвращает бриф структурой (JSON:
  цели, функции с критериями, контекст, «уточнить»); файл `00-brief.md`
  пишет `dfl` из этой структуры и проверяет (как сейчас `interview_chat`
  раскладывает ответ). Авторского вызова через `launch_author` для брифа нет.
- **Потолок и функция без критерия.** Потолок мягкий: на 20-м вопросе агент
  показывает сводку; функция, у которой так и нет критерия, уходит в
  «Уточнить» и в бриф (и дальше в дизайн) не попадает — честно, а не
  «реализовано без проверки». Человек может ответить в сводке («2. поправить»)
  и вернуть её.
- **Имена файлов и место бандла.** Бандл — там же, где сейчас
  (`workstreams/<ws>/spec/` в репо продукта); файлы `00-brief.md`,
  `20-design.md`, `30-decomposition.md`. Читатели, ключующие по имени
  (`_BUNDLE_FILENAMES`, `_AUTHOR_FILENAMES`), берут набор имён из варианта
  цепочки прогона, а не из констант полной цепочки.
- **`RunState.track`.** Поле с умолчанием `enterprise` при чтении старых
  леджеров, без смены версии схемы; места без `RunState` (`task_bridge`,
  `ops`) получают вариант цепочки параметром от вызывающего.
- **Узлы, которых нет (charter, requirements, behaviour-spec, acceptance).**
  Шаги, привязанные к ним (`acceptance_guard`, покрытие Must-FR/NFR, оракул
  закрытия `criteria_close` / `spec-runner verify --criteria`), на личном
  пути не выполняются. Проверяемость держат: инвариант «каждый критерий
  брифа покрыт задачей с проверкой» (декомпозиция) и зелёные тесты задач в
  integration-PR.

## 8. Решения владельца (15.11)

- **Без волн, один PR в конце.** На личном пути нет candidate-PR, заявок
  одобрения узлов (§I12), finalize и человеческих актов на узел. Бриф
  одобряется «да» на сводку в разговоре (запись в журнал прогона). Дизайн и
  декомпозиция пишутся по очереди, после каждого — edge-check своего ребра и
  разбор замечаний по #762 (агент правит сам; решения по существу — вопросом с
  вариантами); узлы коммитятся в ветку прогона. Затем spec-runner реализует
  задачи, и всё — бриф, дизайн, декомпозиция, `tasks.md`, код — уходит одним
  integration-PR, который мержит человек (как ssd-runner#19). Остановки на
  просмотр артефакта после брифа/дизайна/декомпозиции — настройка из #768.
- **Финальное закрытие по критериям не нужно** (оракул `criteria_close` на
  личном пути не выполняется, см. §7).

## 9. Мои решения (не обсуждались с владельцем — проверить)

- Выбор типа — вопрос с двумя вариантами + флаг `--track`; старые прогоны —
  enterprise.
- Потолок интервью — 20 вопросов, затем сводка с разделом «Уточнить».
- Одобрение брифа — «да» на сводку в разговоре, без PR брифа.
- Задача несёт свою проверку (`**Проверка:**`) вместо сценариев BEH.
- Имена файлов узлов сохраняют номера полной цепочки (`00`, `20`, `30`).
