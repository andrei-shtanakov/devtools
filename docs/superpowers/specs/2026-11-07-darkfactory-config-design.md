# DarkFactory для коллег: конфиг вместо зашитых учёток, тестовый режим, лёгкая установка

Дата: 2026-11-07. Статус: черновик дизайна (брейншторм с владельцем 07.11).
Владелец решений — andrei-shtanakov; всё, что помечено «решение исполнителя», выбрано не
владельцем и может быть пересмотрено.

## 1. Зачем

Коллеги владельца просят инструкцию, чтобы проверить работу агентов **на своём репо, на своём
Mac, со своей подпиской Claude**. Сегодня это невозможно ни инструкцией, ни установщиком
`darkfactory` (`df/`): конвейер «интервью → бриф → бандл → задачи → код → PR» зашит под
учётки и репо владельца в ~20 местах (разведка 07.11, §4), часть мест — authority-root, а
установщик `df/` до запуска конвейера ещё не дорос (этап 4, README «Запуск ролей»).

Слова владельца: «с этого и надо было начинать — отвязать от моих аккаунтов… это просто
НЕОБХОДИМО сделать».

**Успех для коллеги:** одна команда в своём репо → интервью → утверждение брифа → дальше
конвейер сам доходит до PR с кодом.

## 2. Цели, не-цели, анти-цели

**Цели**
1. Все учётки, репо, профили `gh`, пути и закрепления, зашитые под владельца, читаются из
   одного конфига пользователя.
2. Режим `test`: облегчённый конвейер для пробы — одна учётка GitHub, человеческий стоп только
   на брифе.
3. Лёгкая установка от обычного пользователя, без `sudo`, на macOS.
4. Инструкция для коллег (README).
5. Собственный конвейер владельца продолжает работать в режиме `strict` с теми же
   гарантиями, что сегодня, только значения приходят из его конфига.

**Не-цели**
- Установщик `df/` (этапы 3a/3b/4) — не трогаем; это отдельная линия, живой стенд 3a
  отложен до её завершения.
- Linux, Windows, организационные репо.
- Живые стенды, новые токены на каждый прогон, тщательная приёмка: проверка — коллега
  прогнал свой репо и получил PR.

**Анти-цели (провал, даже если «работает»)**
- Режим `test` молча включается или подставляет учётки владельца у владельца или коллеги.
- Нет конфига — и код тихо берёт значения владельца (`ai-prosto`, `andrei-shtanakov/…`).
- Режим `strict` владельца теряет гарантию: например, переменная окружения снова может
  подменить список утверждающих.
- Коллеге нужен второй аккаунт GitHub, App или ключ на этапе 1.

## 5. Дизайн

### 5.1. Конфиг

Файл: `$XDG_CONFIG_HOME/darkfactory/config.toml` (правило каталога — `act_settings.config_home`:
абсолютный `XDG_CONFIG_HOME`, иначе `~/.config`). Рядом уже живёт `act.toml` — его не
сливаем (решение исполнителя: разные назначения, меньше миграции).

Набросок (точные имена ключей — за строителем):

```toml
mode = "strict"            # strict | test — обязателен, умолчания нет

[accounts]
human = "andrei-shtanakov" # утверждает (бриф; в strict — и волны)
agent = "ai-prosto"        # ревью/мерж агента; в test может совпадать с human
human_gh_config_dir = "~/.config/gh"
agent_gh_config_dir = "~/.config/review"

[policy]                   # только strict
repo = "andrei-shtanakov/approval-policy"
ref = "main"
path = "policy/approvers.env"

[workspace]
root = "~/labs/all_ai_orchestrators"   # где лежат devtools, discovery, …

[harness]
author = "claude"
model = "claude-opus-5"

[app]                      # этап 2 (D4), необязательно
id = 0
key_file = "~/.config/darkfactory/apps/<id>.pem"
```

Правила:
- **Нет файла или нет обязательного ключа — отказ с названием файла и ключа.** Значения
  владельца в коде не остаются ни как умолчания, ни как fallback (анти-цель).
- Конфиг — данные человека вне любого репо; агент его не пишет. В `strict` это сохраняет
  смысл нынешнего authority-root: перенаправить источник политики может только тот, кто
  правит файл в домашнем каталоге человека.
- Переменные окружения, которые сегодня переопределяют профили (`REVIEW_GH_CONFIG_DIR` и т.п.),
  остаются с приоритетом над конфигом **только там, где они есть сейчас**; запрет env для
  списка утверждающих в `strict` сохраняется.
- Один загрузчик на devtools (`governance/df_config.py` или подобное) и тот же формат в
  discovery (своя копия загрузчика или вендоренный модуль — решает строитель, правило
  полирепо: вендорить, не ссылаться). Shell-скрипты читают значения через маленькую
  Python-утилиту загрузчика (один источник правды формата).

### 5.2. Режим `strict`

Поведение сегодняшнего конвейера без изменений, значения — из конфига:
- источник политики — `[policy]`; `source.env` в devtools и discovery либо уходят, либо
  становятся только документацией формата (решает строитель; главное — не два источника);
- учётки и профили — `[accounts]`;
- steward-копия акторов (`steward-actor-policy`) — актор берётся из конфига; сама копия и
  `PIN` остаются для release-гейта steward;
- песочница авторинга — как сейчас; `admitted.toml` перестаёт содержать путь владельца как
  единственную запись — допуск привязан к машине (см. 5.4).

### 5.3. Режим `test`

Включается **только** явным `mode = "test"`. Каждый запуск печатает строку «режим test:
защиты X, Y, Z выключены» (решение исполнителя — чтобы режим нельзя было не заметить).

Отличия от `strict`:
1. **Одна учётка** (D2): `accounts.agent` может равняться `accounts.human`, один профиль
   `gh`. Отказы «агентский профиль не может мержить как человек» (`human-merge.sh:87`) и
   «человек не может быть агентом» не применяются.
2. **Утверждающий — из конфига** (`accounts.human`), репо политики не нужен.
3. **Человеческий стоп только на брифе** (D3): candidate-PR волн W1–W5 и утверждение задач
   (`spec-runner spec approve tasks` + `--deliver-approve`) выполняются автоматически от
   учётки из конфига; запуск `spec-runner run` и приёмка PR с кодом (`accept-pr`) —
   тоже автоматически, конвейер доходит до PR с кодом. Мерж PR с кодом — за коллегой
   (решение исполнителя: финальный результат остаётся на виду у человека).
4. **Без песочницы авторинга**: `sandbox-exec`, `admitted.toml`, пробы связки ключей не
   требуются; claude запускается как обычный процесс пользователя.
5. **Без белого списка целей**: цель — текущий репо коллеги (`origin` текущего каталога).
   Механика (решение исполнителя, вопрос №6): ядро `spec_loop` не переписывается под
   «любой каталог»; `dfl run` регистрирует текущий репо в пользовательском списке целей
   (рядом с конфигом), который `spec_loop` читает в `test` после манифеста и
   `acceptance-targets`. Путь клона берётся из записи, а не из `WORKSPACE_ROOT/<repo>`.
6. Edge-check и терминальное ревью — остаются (это качество, не защита), харнесс `claude`.
7. **Ревью — комментариями, не approve** (решение исполнителя, вопрос проверяющего №1):
   GitHub не даёт учётке одобрить свой PR, а в `test` автор и ревьюер — одна учётка. Поэтому
   edge-check, `review-pr.sh`, `attest-vendor.sh` в `test` публикуют вердикт комментарием,
   а проверки `state == "APPROVED"` (`act_decision.py`, `act_premerge_core.py`, раннер)
   в `test` не применяются. Целевой репо не должен требовать ревью в ruleset/защите ветки:
   `dfl init-repo` это проверяет и отказывает с объяснением (не меняет чужую защиту сам).
8. **Классификация актора не применяется** (решение исполнителя, вопрос №2): одна учётка
   не может быть одновременно «человеком» и «агентом» в закрытом allowlist steward
   (`steward/src/steward/gatecheck/approval.py`). В `test` гейты, решающие по классу
   актора (кто мержил: человек/агент, `agent_merge_allowed`), не применяются; гейты
   содержания steward остаются. Steward получает понятие режима только если без этого
   нельзя — строитель сначала ищет путь без PR в steward.

Не меняется в `test`: интервью, бриф, авторинг узлов, steward-гейты содержания, spec-runner.

### 5.4. Песочница авторинга в `strict`

**Без изменений** (решение исполнителя после вопроса проверяющего №3: цель 5 — те же
гарантии `strict`). `admitted.toml` и `make sandbox-admit` с мержем записи допуска остаются
как есть; песочницы нет только в `test`. Попутно: у владельца claude обновился до 2.1.319 —
нужен обычный `make sandbox-admit` (не часть этой работы, но без него прогон владельца для
проверки этапа 2 встанет).

### 5.5. Лёгкая установка

`install.sh` в devtools (запуск: `curl … | sh` не нужен — клонировать devtools и выполнить
скрипт). Без sudo. Шаги:
1. Проверить: macOS, `git`, `gh` (залогинен), `uv`, `claude` (залогинен).
2. Клонировать в `~/darkfactory/` (или `--root`): devtools, discovery, spec-runner,
   disputatio и прочее, что нужно конвейеру по раскладке (§4), — все репо публичные.
3. `uv sync` в каждом; `spec-runner` — на `PATH` (через `uv tool install` или обёртку).
4. Спросить логин GitHub (подсказка — `gh api user`), написать `config.toml` с
   `mode = "test"`, `human = agent = <логин>`, `workspace.root`.
5. Поставить одну команду запуска (имя — за строителем, например `dfl`) в `~/.local/bin`.

Повторный запуск обновляет клоны (`git pull --ff-only`) и не перетирает конфиг.

### 5.6. Подготовка целевого репо

Команда (`dfl init-repo`) открывает в репо коллеги PR с тем, что нужно конвейеру (§4,
«Целевой репо»): `profiles/team-exp.yaml` и соседи по шаблону, кит ревью steward,
`spec-runner.config.yaml`; создаёт метки. В `test` этот PR мержится автоматически
(решение исполнителя; иначе первая же команда упирается в ручной шаг).

### 5.7. Запуск

`dfl run` в каталоге своего репо — обёртка над `make spec-loop … --need --frame customer`
→ интервью в терминале → `brief-propose` → **ожидание мержа брифа коллегой** (единственный
стоп) → `brief-approve` → engineer-прогон → волны → задачи → `spec-runner run` → PR с кодом.
`dfl status` — где прогон и чего ждёт. Возобновление после перерыва — `dfl run` снова
(идемпотентно по журналу прогона).

### 5.8. Обход гварда authority-root для этой работы (D7)

`merge-pr.sh` получает именованный флаг обхода гварда 4 (authority-root), например
`--authority-override '<причина>'`; причина пишется в журнал и в комментарий PR, как
`--budget-override`. Ограничения (решение исполнителя): только гвард 4; гварды candidate §I12,
`human-merge-required` и харнесс-пути не обходятся; флаг принимает только оператор вручную,
`Ops.merge` и раннер его не передают.

Первый PR, вводящий флаг, сам трогает authority-root (`merge-pr.sh`) и гвардом не
пропускается — **его мержит владелец одним кликом**; все последующие PR работы мержит агент
с флагом.

**Решения владельца по флагу (07.11, после проверки строителем):**
- флаг **только на эту работу**: последний PR работы его удаляет (D9);
- гвард харнесс-путей (`_HARNESS_PREFIXES`, в т.ч. сам `merge-pr.sh`, цепочка
  `human-merge.sh`) флаг **не обходит** — такие PR **мержит владелец** (D10). План
  группирует харнесс-правки так, чтобы таких PR было как можно меньше.

**Загрузчик конфига — под authority-root** (рекомендация исполнителя, владелец явно не
возражал — проверить при чтении): в `strict` он решает, откуда берётся список утверждающих;
без защиты агентский PR мог бы перенаправить источник политики. Следствие: будущие правки
загрузчика после снятия флага мержит владелец; в рамках этой работы — агент с флагом.

## 6. Ограничения

- Полирепо: правки в discovery, steward (копия акторов), spec-runner — PR в их репо (правило
  границ); devtools не правит соседей. Мерж — агент (D7).
- Правки authority-root путей devtools и `df/` не затрагиваются, кроме перечисленных в §4.
- Режим `strict` владельца — регрессия недопустима: существующие тесты зелёные; конфиг
  владельца пишется до переключения кода (иначе его конвейер встанет на «нет конфига»).
- Бюджет платного ревью — как в CLAUDE.md devtools (1 полный + 1 адресный на PR).

## 7. Этапы (предложение исполнителя)

1. PR-0 (мерж владельцем): флаг обхода в `merge-pr.sh` (§5.8).
2. Загрузчик конфига + конфиг владельца + `strict` читает значения из конфига (devtools),
   затем discovery. Проверка: прогон владельца на `spec-loop-sandbox` не изменился.
3. Режим `test` (5.3) + допуск песочницы в состоянии пользователя (5.4).
4. `install.sh`, `dfl init-repo`, `dfl run` (5.5–5.7).
5. README «DarkFactory для коллег»; пробный прогон владельцем на чистой учётке macOS
   (отдельный пользователь ОС, та же учётка GitHub) — без новых аккаунтов.

## 8. Оставлено строителю

Точные имена ключей и команд; где живёт загрузчик в discovery; судьба `source.env`;
механика автоматического мержа candidate-PR в `test` (через `human-merge.sh` с профилем из
конфига или напрямую из раннера); что именно кладёт `init-repo`; как обёртка находит
`workspace.root`.
