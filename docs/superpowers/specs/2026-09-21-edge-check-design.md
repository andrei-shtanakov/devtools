## 1. Цель и граница

### 1.1. Что наблюдается сегодня

Документы бандла не получают смыслового ревью на PR. После раскатки роутера
области ревью пути `workstreams/*/spec/*` объявлены прозой
(`contracts/review-scope/v1/prose-paths.env:18`), а prose-only PR получает
scope-аттестацию — «approve без единого взгляда модели»
(`review-pr.sh:959` и ниже). Шаг S6 прогона (`governance/runner.py:2235`,
`_step_review` → `Ops.review` → `review-pr.sh`) видит на таком PR код 0 и
продолжает. Механический гейт steward при этом работает и проверяет структуру:
ссылки существуют (`GC-TRACE`), пины свежие (`GC-STALE`), каждое Must/Should
требование покрыто сценарием, обязательством или waiver'ом
(`GC-BEH-COVERAGE`), у сценария объявлена проверка (`GC-CHECK-PLANNED`).

Итог: проверяется **структура связей**, не проверяется **соответствие по
существу**. «Сценарий ссылается на FR-03» доказано; «сценарий действительно
реализует FR-03 и не вводит необоснованных обязательств» — нет.

База сравнения для этой спеки — именно сегодняшняя scope-аттестация без
LLM-проверки. Восемь кругов терминального ревью на бандле
`durable-continuation-checkpoint-evidence-20260915` и ещё четырнадцать на
доработку — исторический пример связности документов
(`docs/evidence/2026-09-15-need-stage-live-run.md`), случившийся **до**
роутера; экономией относительно него эта работа не мотивируется.

### 1.2. Что вводится

Проверка «узел против его объявленных оснований по объявленным правилам»,
выполняемая перед человеческим гейтом решения 4, и публикуемый чек-лист,
применимость которого доказана для конкретного SHA головы PR.

### 1.3. Чем эта работа не является

- Не авторский цикл: инструмент не правит документы и не управляет сходимостью.
  Цикл остаётся у существующего пути авторинга и у disputatio.
- Не замена механического гейта: структурное остаётся гейту, повторять его
  вызовом модели — платить за доказанное вычислением.
- Не ревью диффов: предмет — документ и его основания целиком, не изменение.
- **`PASS` не означает `approved`.** Человеческий гейт остаётся актом человека;
  чек-лист и находки — то, что он читает перед решением.
- Каскад изменений не исчезает: пинование оснований не даёт им смениться
  незаметно, но пересмотр уже одобренного документа по-прежнему требует
  проверки актуальности зависимых результатов (§6.3).

| # | Решение |
|---|---|
| D1 | Единица проверки — узел со **всеми** его основаниями, а не пара документов: «дизайн покрывает поведение» и «дизайн не противоречит требованиям» — одно суждение |
| D2 | Набор рёбер выводится из профиля прогона (`upstream` артефакта), плюс объявленные привязки плоскости discovery и этапа реализации; числа рёбер в коде нет |

| D4 | Изоляция: содержимое подготовленных копий передаётся в запросе, инструментов ревьюеру не даётся, рабочий каталог — пустой временный каталог вне воркспейса; сетевых инструментов нет, допустим только транспорт вызова модели |
| D5 | Метаданные пишет инструмент, а не модель: `inputs`, хэши, `absence`, `rules`, `context`, `reviewer`. Модель возвращает результаты по пунктам и находки; инструмент проверяет схему ответа, ссылки на входные файлы и допустимость номеров строк |
| D6 | Четыре состояния результата: `PASS`, `FAIL`, `N/A`, `ERROR`, у последнего — машинный `error_code`. `PENDING` — состояние проверки у координатора, в запись результата не входит |
| D7 | `N/A` определяется правилом применимости **до** вызова модели и несёт `absence` (путь относительно корня бандла + id правила, разрешающего отсутствие). Отсутствие обязательного входа — `ERROR`, не `N/A`. Ошибка чтения отсутствием не считается |
| D8 | Две identity: `check_identity` (упорядоченные правила + инструкция ревьюеру + шаблон запроса + правила интерпретации ответа + политика серьёзности) и идентификатор с хэшем профиля, задающего состав рёбер |
| D9 | Ключ результата — subject (набор файлов с ролями), упорядоченный набор оснований с ролями и хэшами, решение о применимости, `check_identity`. Временные пути и время проверки в ключ не входят |
| D10 | У ключа может быть несколько попыток (`attempt_id`); действующий результат — **последняя завершённая попытка**, поиск исторического `PASS` запрещён |
| D11 | Инвалидация — следствие ключа, а не отдельный граф сбросов; готовность цепочки координатор вычисляет отдельно от актуальности результата |
| D12 | Доверие — к происхождению, не к расположению: действующие результаты читаются из леджера доверенного процесса проверки, недоступного авторскому агенту на запись. Evidence в ветке PR — переносимый отчёт, не основание approve и не вход проверки |
| D13 | Применимость к SHA доказывается чтением blob на выбранном коммите и пересчётом того же SHA-256, что считался при проверке, плюс проверкой типа и режима записи и подтверждением объявленных отсутствий |
| D14 | Публикация: сначала коммит evidence, затем фиксация итогового SHA, затем сверка, затем review. После отправки голова сверяется повторно |
| D15 | Коды возврата берутся из существующего словаря раннера; новых значений не вводится. Код 0 требует, в том числе, успешной доставки review |
| D16 | Перенос чек-листа в публикуемый вердикт разрешён, только если изменённые пути PR целиком лежат внутри объявленной поверхности (файлы бандла + разрешённый evidence) |
| D17 | Размер документа — предупреждение; невозможность передать полный объявленный вход — `ERROR` без усечения |
| D18 | Интеграция с disputatio (edge-check как проверяющий шаг его цикла) — вне объёма, отдельная заявка соседу |
| D19 | Проверка реализации («тесты и код ← задача с её критериями») — зависимый этап поставки: до появления адресуемых критериев приёмки (решение 5) не заявляется реализованной и догадками по тексту не подменяется |

## 3. Компоненты и границы

**`edge-check`.** Выполняет одну проверку: подготавливает объявленный вход,
зовёт одного ревьюера в изоляции (D4), валидирует ответ, записывает результат.
Не правит документы, не управляет сходимостью, не публикует, не решает за
политику серьёзности.

**Координатор бандла.** Владеет состоянием проверок: знает состав рёбер по
профилю, находит действующие результаты по ключу, вычисляет отсутствующие,
устаревшие и неготовые, запускает нужные проверки, собирает чек-лист. Сам
ничего не проверяет и документов не правит; возврат `FAIL` в авторинг —
обязанность вызывающего процесса или оператора.

**Публикующий адаптер.** Владеет подтверждением применимости к PR: сверяет
входы против дерева выбранного коммита, публикует один review и отдаёт
существующему контуру код возврата. Сам проверок не запускает — список
неприменимого возвращает координатору.

**Disputatio.** Остаётся авторским инструментом (вид `document`: цикл
«автор ↔ ревьюер» до сходимости, чек-лист контура объявляет оператор, лимиты
раундов и токенов объявлены). Подключение `edge-check` в качестве его
проверяющего шага требует работы на стороне соседа: адаптеры там — обёртки
агентских CLI с ролевыми правами (ревьюеру по умолчанию разрешены
`Read`/`Grep`/`Glob`/`git`/`pytest`/`ruff`), а пакет `verifier` даёт
статическую гарантию отсутствия агентских CLI. `edge-check` не попадает ни в
одну полосу, поэтому в v1 он самодостаточен (D18).

## 4. Одна проверка

### 4.1. Вход и изоляция

Вход **объявлен**, а не собирается обходом дерева: проверяемый объект (набор
файлов с ролями — для документа один, для реализации код и тесты), основания в
объявленном порядке, правила. Всё остальное входом не является; нехватка
объявленного основания — `ERROR`, а не догадка.

Изоляция обеспечивается конструкцией вызова: содержимое копий передаётся в
запросе, инструментов не даётся, рабочий каталог — пустой временный каталог вне
воркспейса (иначе CLI подхватит `CLAUDE.md` соседних деревьев). Копии —
обычные файлы, без ссылок наружу. Автоматическая загрузка пользовательских
настроек и MCP отключается флагами режима; фактическая конфигурация запуска
проверяется тестом (§9.1), а не принимается на слово.

Утверждение, которое из этого следует и которое спека делает: **зафиксированы
все явно переданные входы и конфигурация проверки**.

### 4.2. Разделение труда инструмента и модели

Модель возвращает: результат по каждому пункту правил, находки (класс,
место, утверждение). Инструмент: готовит вход, считает хэши, пишет метаданные,
валидирует схему ответа, проверяет, что ссылки ведут во входные файлы и что
номера строк допустимы, применяет политику серьёзности и выводит общий вердикт.
Отнесение находки к классу — суждение модели; допустимость класса и вычисление
итога — механика.

### 4.3. Схема результата

| Поле | Содержание |
|---|---|
| `schema_version` | версия схемы записи |
| `edge` | идентификатор проверки (тип узла + типы оснований) |
| `subject[]` | роль, путь относительно корня бандла, SHA-256 подготовленной копии, размер |
| `bases[]` | то же для каждого основания, в объявленном порядке |
| `absence[]` | путь и id правила применимости, разрешившего отсутствие |
| `check_identity` | хэш проверяющей конфигурации (D8) |
| `profile` | идентификатор и хэш профиля, из которого выведен состав рёбер |
| `rules` | идентификатор набора и упорядоченный список пунктов |
| `criteria[]` | `{id, status, reason}` по каждому пункту правил |
| `findings[]` | `{rule_id, class, location: {path, lines}, statement}` |
| `verdict` | `PASS` \| `FAIL` \| `N/A` \| `ERROR` |
| `error_code` | машинный код при `ERROR` |
| `reason` | обязательна при `N/A` и `ERROR` |
| `context` | измеренный объём запроса: единицы, метод подсчёта или оценки, резерв под ответ, объявленный потолок |
| `reviewer` | харнесс и его версия, фактически известный идентификатор модели, эффорт |
| `attempt_id`, `started_at`, `finished_at` | попытка и её границы |

Пустой `findings[]` сам по себе ничего не доказывает — полноту проверки
показывает `criteria[]`. Пропущенный обязательный пункт или невалидный ответ
модели — `ERROR`.

### 4.4. Состояния и их адресаты

| Состояние | Что означает | Кому |
|---|---|---|
| `PASS` | все обязательные пункты выполнены, блокирующих находок нет | человеку — как материал к гейту |
| `FAIL` | смысловое несоответствие с указанием мест | автору документа |
| `N/A` | проверка неприменима по объявленному правилу, отсутствие подтверждено | никому; учитывается как выполненная |
| `ERROR` | проверка не завершена | по `error_code`: таймаут — ограниченный повтор при неизменных входах; нехватка объявленного основания — исправление определения входа; превышенный потолок — решение оператора |

Ни `FAIL`, ни `ERROR`, ни `PENDING` не дают положительного итога и кода 0.

## 5. Каталог рёбер и правил

### 5.1. Состав рёбер

Профиль объявляет `upstream` у каждого артефакта — это и есть граф. Для
`team-exp` внутри бандла получается шесть проверок: требования ← charter;
поведение ← требования; дизайн ← требования + поведение; приёмка ←
требования + поведение; декомпозиция ← дизайн + приёмка; задачи ←
декомпозиция. Для `lite` (три узла) — две. Числа рёбер в коде нет.

Три связи профиль не знает, и они объявляются в каталоге наравне с
выведенными, без специальных веток в коде:

- бриф инженера ← бриф заказчика (плоскость discovery);
- charter ← бриф инженера + бриф заказчика (стык discovery и бандла);
- тесты и код ← задача с её критериями приёмки (единица — задача; §10).

### 5.2. Привязка правил

Для сочетания «тип узла + типы оснований» должен существовать совместимый
набор правил. Сочетание без набора — ошибка конфигурации с названным
сочетанием, а не молчаливый пропуск проверки.

### 5.3. Пример набора — «поведение ← требования»

```
R1  каждое Must/Should-требование получает реализацию по существу:
    сценарий, обоснованное обязательство или waiver с названной причиной
R2  поведение не вводит необоснованных обязательств и не противоречит
    требованиям; уточнение поведения само по себе допустимо
R3  сценарий наблюдаем снаружи: не описывает внутреннее устройство
R4  формулировка сценария допускает единственное прочтение
```

Правило «нет блокирующих находок» в смысловой чек-лист не входит: это
вычисляемое условие итогового вердикта, а не суждение модели. Порядок пунктов
входит в `check_identity`.

### 5.4. Политика серьёзности

Объявляется вместе с каталогом: какие классы находок дают `FAIL`, какие
остаются замечаниями при `PASS`. Инструмент применяет её механически.

## 6. Координатор

### 6.1. Ключ и попытки

Результат адресуется ключом D9. «Узел проверен» в отрыве от ключа не является
утверждением. У ключа может быть несколько попыток; действующая — последняя
завершённая (D10). `ERROR` допускает повтор при неизменных входах; политика
повторов пакетного режима объявляется вместе с каталогом.

### 6.2. Инвалидация

Отдельного механизма сброса нет. Правка требований меняет хэш основания у
поведения, дизайна и приёмки — их результаты перестают находиться по ключу и
показываются как `PENDING`. Транзитивность получается сама: переписанное
поведение меняет собственный хэш, и у дизайна с приёмкой не совпадает
основание. Сохранённый `PASS` при этом не удаляется: для своих входов он
остаётся действительным.

### 6.3. Актуальность против готовности

Это разные величины. После правки требований проверка декомпозиции может
оставаться актуальной (дизайн и приёмка не изменились), но цепочка не готова,
потому что выше `PENDING`. Координатор считает обе и показывает обе; пакетный
запуск соблюдает порядок зависимостей.

Смена профиля меняет **состав** проверок: координатор пересобирает список, а
уцелевшие узлы с теми же основаниями находят свои результаты по прежним ключам.
Чек-лист как целое при этом другой — он описывает другой граф.

### 6.4. Режимы

- **Поузловой** (основной): после авторинга узла запускается его проверка;
  `FAIL` возвращает узел в авторский путь.
- **Пакетный**: пересобрать состав по профилю, найти отсутствующее и
  `PENDING`, запустить только это. Авторинга не требует и документов не меняет.

### 6.5. Состояние

Во время авторинга действующие результаты живут в леджере доверенного процесса
проверки (D12). При доставке бандла результаты и собранный чек-лист едут внутри
того же PR, в `workstreams/<ws-id>/evidence/` — поверхность гейта это не
затрагивает (гейт работает по каталогу `spec/`), и прецедент задан вердиктами
S8 (E0.6b). Отдельного evidence-PR не заводится.

**Названный компромисс.** На другой машине доверенного леджера нет, поэтому
проверки перезапускаются. Evidence в PR остаётся переносимым отчётом и
основанием approve не становится ни при каких условиях.

## 7. Стыковка с прогоном и человеческими гейтами

Решение 4 переносит человеческий гейт внутрь авторинга: три гейта — после
`10-requirements`, после `15-behaviour-spec`, после пары `20-design` +
`25-acceptance`; `30-decomposition` закрывается вместе с бандлом. Проверка
ребра выполняется **перед** соответствующим гейтом, и человек получает к
решению чек-лист и находки.

Отношение состояний к акту: `PASS` — материал к решению, не решение. `FAIL`
до гейта не доводится — узел возвращается автору. Переоткрытие уже одобренного
узла остаётся явным актом (`stale` + переписывание), после которого зависимые
результаты проверяются на актуальность по §6.2–6.3.

## 8. Публикация

**Доверие.** Действующие результаты берутся из леджера доверенного процесса.
JSON, лежащий в ветке PR, адаптер не читает: он туда только пишет. Отсюда три
следствия — автор PR не может подсунуть себе `PASS`, evidence не попадает в
собственные входы проверки, и запись результата не меняет его ключ.

**Сверка применимости** (D13) идёт против дерева выбранного коммита, даже если
рабочий каталог уже отличается. Не совпало — галочка публикуется как `PENDING`,
сохранённый результат остаётся действительным для своих входов, причина
возвращается координатору. Адаптер сам проверок не перезапускает.

**Порядок:** коммит evidence → фиксация итогового SHA → сверка входов →
публикация review → повторная сверка головы. Собственный SHA внутрь коммита не
пишется. Если голова сдвинулась после отправки, review остаётся свидетельством
о прежнем коммите, возвращается код 4, и положительный результат к новой голове
не применяется. Последующий мерж пинуется на проверенный SHA (`merge-pr.sh
--expect-head`, уже так и вызывается раннером).

**Маркер** — собственный, не переиспользует маркер кита (у того своя
дедупликация, бюджет и правило остановки). Несёт идентификатор прогона, SHA и
identity итогового чек-листа. Доставленный `CHANGES_REQUESTED` человека
синтетическим approve не гасится и обойти действующую политику блокировки не
позволяет.

**Область замены аттестации** (D16): перенос чек-листа разрешён, только если
изменённые пути PR целиком лежат внутри объявленной поверхности. Посторонний
путь — отказ переноса и обычное ревью, тем же приёмом, каким аттестация
вендор-копий отказывает PR, везущему что-то помимо членов кита.

**Коды** (D15), из словаря раннера (`governance/runner.py:2235` и далее):

| Код | Условие | Что делает раннер |
|---|---|---|
| 0 | все обязательные проверки применимы к SHA и дали `PASS`/`N/A`, review доставлен | продолжает; мерж-гейт требует ровно `review_exit == 0` |
| 1 | есть `FAIL` или `PENDING` | стоп `stopped_review` |
| 3 | инструментальный класс: `ERROR`, невалидный ответ модели, превышенный потолок, сбой публикации | стоп «прибор не отработал» |
| 4 | голова уехала между сверкой и публикацией | сброс `gate-candidate`/`push`/`ready`, переигрывание S4 |

Незнакомых значений не вводится: неопознанный код раннер трактует как 4.

## 9. Приёмка

### 9.1. Детерминированные тесты механики

Проверяются обычными тестами, без участия модели: вычисление и сверка хэшей;
`check_identity` при переставленных пунктах правил; потолок входа (`ERROR`, не
усечение); игнорирование evidence из ветки PR; коды возврата и их приоритет при
сочетаниях состояний; гонки публикации (голова сдвинулась до отправки; после
отправки); фактическая конфигурация запуска ревьюера — отсутствие инструментов
и автоматической загрузки инструкций.

Границы, каждая с ожидаемым состоянием и точным кодом: отсутствие обязательного
входа; появление файла после `N/A`; недоступность леджера авторскому агенту;
выбор действующей попытки при наличии прежнего `PASS`; неготовый upstream при
актуальном downstream `PASS`; посторонний путь в PR; сбой публикации.

Тест с приманкой (необъявленный файл рядом с бандлом) входит в набор, но
доказательством изоляции не считается: модель может не прочитать файл, имея
такую возможность. Ссылка на необъявленный файл даёт `ERROR` только тогда,
когда его содержимое необходимо для проверки; обычная справочная ссылка ревью
не блокирует.

### 9.2. Качество суждения — на размеченном корпусе

Обнаружение смысловых несоответствий проверяется корпусом, содержащим и
дефектные, и корректные примеры; измеряются пропуски и ложные блокировки.
Один удачный ответ модели устойчивости не доказывает.

Пороги `blocking_recall` и доли ложных блокировок объявляются **до** прогона.
Review-eval harness steward переиспользуется как прибор, но пригодность его
корпуса подтверждается отдельно: кейсы ревью диффов не обязательно проверяют
соответствие документа основаниям, и для рёбер нужна своя разметка.

### 9.3. Эксплуатационная проверка

Первый живой бандл — дополнительная проверка, а не критерий готовности.
Снимаются три числа, каждое с объявленной интерпретацией:

1. **уникальные подтверждённые находки**, пойманные поузлово — найденные
   проблемы, а не доказанное число предотвращённых кругов;
2. **стоимость** проверок вместе с объёмом изменений, временем и повторами;
   прошлый бандл — ориентир, не контролируемый эксперимент;
3. **находки после публикации**, разобранные по причине: пропуск ревьюера,
   отсутствующее правило или основание, новое изменение, дефект реализации вне
   предмета проверки. Ненулевое число само по себе неполноту графа не
   доказывает.

**Критерий готовности инструмента** — пройденные проверки механики (§9.1) и
достигнутые объявленные пороги качества (§9.2).

## 10. Вне объёма и зависимости

- **Интеграция с disputatio** (D18): требует на стороне соседа либо адаптера с
  закрытым входом, либо третьей полосы между агентскими CLI и детерминированным
  `verifier`. Уходит заявкой по ADR-ECO-006 после приёмки v1.
- **Проверка реализации** (D19): зависит от адресуемых критериев приёмки
  (решение 5 от 2026-09-20 — `25-acceptance.md` сегодня документ, а не набор
  адресуемых критериев). Проверки документов ставятся раньше и её не ждут.
- **Исполняемая изоляция** с примонтированным staging: нужна, если вход
  перестанет помещаться в запрос; отдельное решение, а не молчаливое расширение.
- **Копии каталога правил в репо-целях**: в v1 не заводятся (D3).
- **Контур approval брифа**: принадлежит discovery (решение 8), здесь только
  читается как условие применимости — причём `approved` требуется лишь для
  engineer-апстрима, и его отсутствие в `N/A` не превращается.
