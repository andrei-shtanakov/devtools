## 0. Суть и явное изменение архитектуры

Сегодня человеческий акт на двух путях — утверждение брифа и одобрение узла бандла (§I12) —
это **мерж PR учёткой человека**; доказательство — `mergedBy`. Спека меняет акт на
**approve-ревью человека на конкретный head SHA и конкретную заявку**; мерж только **доставляет**
утверждённое содержимое и может выполняться агентом (GitHub App).

Это **изменение архитектуры**, а не замена поля:

1. **Появляется общий читатель фактов.** Сегодня все три пути (devtools узел, devtools бриф,
   discovery approve) читают `mergedBy`/`mergeCommit` из GitHub каждый своим кодом, а
   `approval-facts/v2` steward потребляет только сам steward. После спеки чтение и нормализацию
   фактов **ревью** и **доставки** выполняет одна реализация, принадлежащая steward; devtools и
   discovery её вызывают.
2. **steward становится владельцем общей реализации чтения GitHub** в рамках этой миграции.
3. **Акт отделён от доставки.** «Кто смержил» остаётся для аудита и проверки права мержить,
   но больше не является подписью.
4. **Конверт утверждения узла уходит из защищённых файлов** (§9.1, предложение) — иначе
   автоматическая финализация невозможна при CODEOWNERS-защите.

## 1. Основание

Spike 12.10 на стенде `andrei-shtanakov/df-roles-probe` (личный аккаунт):

- approve GitHub App засчитывается ruleset-ом как обязательное ревью; App мержит;
  `merged_by` = `<slug>[bot]` (REST) / `Bot` (GraphQL); автор не может одобрить свой PR;
- в проверенной конфигурации отказ агенту на человеческом пути получен через
  `require_code_owner_review` + CODEOWNERS на путях человеческого пути; CODEOWNERS обязан
  владеть `/.github/`;
- после человеческого approve App смержил PR человеческого пути — на личном аккаунте GitHub не
  ограничивает, кто нажимает merge. При акте «approve человека» это штатный сценарий.

## 2. Термины

| Термин | Значение |
|---|---|
| **Заявка** | Запрос на утверждение, **записанный внутри одобряемого коммита**: для брифа — `approval-request.yaml` в brief-PR; для узлов — манифест `workstreams/<ws-id>/approvals/requests/<request-id>.yaml` в candidate-PR. Фиксирует режим акта, идентификатор заявки, узлы, хеши содержимого, upstream-пины и пины обеих политик (§6). Читается **из head SHA**, который одобрил человек; запись в `run.json`, тело PR и конверт — только зеркала, при расхождении с манифестом — отказ |
| **Акт** | Действительное approve-ревью человека из `human_approvers` на head SHA заявки |
| **Доставка** | Мерж PR, при котором утверждённые байты оказались в merge-коммите, достижимом из базы |
| **Момент фиксации** | `merged_at` доставки — факт форджа (§8) |
| **Факты** | Установленные наблюдения GitHub, нормализованные общим читателем; решения не содержат |
| **Решение** | Вывод потребителя из фактов + заявки + политик |
| **Живая заявка** | Заявка без зафиксированного решения |
| **Историческое доказательство** | Зафиксированное решение, проверяемое задним числом |

## 3. Решения

**D1. Акт = approve человека на head SHA заявки.** На момент фиксации (§8) действителен, только
если: (а) у логина есть **эффективное** ревью (§5.3) в состоянии `APPROVED`;
(б) его `commit_id` = head SHA заявки = голова PR на момент мержа; (в) до момента фиксации оно не
было отозвано (§5.4, события `review_dismissed`); (г) логин ∈ `human_approvers` по пину политики
утверждающих (§6); (д) steward классифицирует логин как `human` по пину политики акторов (§6) и
`type_hint` ≠ `Bot` — бот не может быть утверждающим ни при каких списках.
Статус PR `reviewDecision: APPROVED` недостаточен.

**D2. Продолжение конвейера = действительный акт + доставка.** Approve на несмёрженный PR не
продвигает прогон (`waiting_delivery`). Доставка: PR смёржен, merge-коммит достижим из базы, и
выполняются **два раздельных инварианта** для каждого утверждённого пути (squash-безопасно):
- **I-bytes:** `git_blob(merge_commit, path) = git_blob(head, path)` — доставлены ровно
  одобренные байты;
- **I-content:** `self_hash_v(head, path) = request.content_hash[path]`, где `self_hash_v` —
  проекция версии акта (§7; узел — `node_approval.self_hash`, бриф — `sha256:`-проекция
  `discovery/approval.py`) — одобренные байты соответствуют заявке.
Подменять один инвариант другим нельзя: `self_hash` вырезает конверт и не доказывает
неизменность байтов, а git blob SHA не равен хешу заявки.

**D3. Мержер — отдельная проверка разрешения.** Доставка засчитывается, только если мержер —
(а) логин из `human_approvers` **и** `actor_class = human` по пину политики акторов **и**
`type_hint ≠ Bot`; или (б) актор с `actor_class = agent` **и** в allowlist роли `merger` (§6).
Актор с `actor_class = agent` проходит **только** через (б), даже если он ошибочно внесён в
`human_approvers`. Классификация и разрешение — разные проверки. Иначе доставка не засчитана,
прогон стоит, причина в evidence.

**D4. Общая реализация чтения — в steward; решения — у потребителей.** Библиотека steward
возвращает факты (§5). Привязку к заявке узлов, полномочия и леджер делает devtools; привязку к
заявке брифа, полномочия и штамп — discovery. Чтение GitHub выполняется **в процессе
потребителя**; файл evidence — запись результата, никогда не источник полномочий: любое решение
(в том числе историческое) переустанавливается из фактов форджа (§8).

**D5. Пины политик единые для всех путей**, с правилом устаревания (§6). Устраняет нынешнее
расхождение: devtools сверяет по пиненой версии (`brief_provenance.py:190`), discovery — по
текущей (`discovery/cli.py:466`).

**D6. Версионируется весь набор доказательств** (§7). Режим выбирается явно по маркеру; новый
код не угадывает версию и не превращает мерж в approve.

**D7. Требования к репо продукта** (поставляет установщик, спека B; обязательны для приёмки A):
ruleset на дефолтной ветке с `dismiss_stale_reviews_on_push: true`,
`require_last_push_approval: true`, `require_code_owner_review: true`; CODEOWNERS назначает
владельцами путей человеческого пути **только** логины из `human_approvers` и владеет
`/.github/`. Это первый рубеж; смысл заявки и байты проверяют devtools/discovery.
«Last push approval» сам не сбрасывает старые approve — D1(б) сверяет `commit_id` независимо.

## 4. Владение

| Часть | Владелец | Ответственность |
|---|---|---|
| Контракт фактов, GitHub-reader, нормализация ревью и доставки, fixtures и векторы сбора | **steward** | схема v3, библиотека, контрактные тесты; release-гейт steward мигрирует в том же изменении |
| Привязка к заявке узлов, полномочия, леджер, candidate, конверт | **devtools** | §I12, waves, `approve_node`, `node_approval`, `approval_ledger` |
| Привязка к заявке брифа, полномочия, штамп брифа | **discovery** | `discovery approve` |
| Сквозная спека, миграция, координация, приёмка | **devtools** | этот документ |

**Поставка библиотеки (Q2).** devtools — существующая пиненая git-зависимость на steward.
discovery — **такая же пиненая git-зависимость** на steward (транзитивно добавляет `typer`,
`jsonschema` — принято владельцем). Вендоренная копия не используется, пока не показано
конкретное препятствие. Транспорт GitHub внедряется параметром (для векторов §5.6). Вторая
самостоятельная реализация логики ревью не допускается.

## 5. Контракт фактов `approval-facts/v3`

### 5.1. Версия

Каталог `steward/contracts/approval-facts/v3/`; `v2/` заморожен (правило steward). Две записи —
`review` и `delivery`. Поля мержа v2 (`identity`, `type_hint`, `actor_class`) переходят в
`delivery.merged_by`.

### 5.2. Запись `review`

| Поле | Смысл |
|---|---|
| `repository`, `pr`, `observed_at` | адрес и время |
| `head_sha`, `base_ref`, `pr_state` | голова, база, состояние |
| `reviews[]` | все ревью: `review_id`, `login`, `type_hint`, `state`, `commit_id`, `submitted_at`. У `PENDING` `submitted_at` штатно отсутствует/`null` (GitHub); у отправленных ревью оно обязательно |
| `dismissals[]` | события отзыва из таймлайна: `review_id`, `actor`, `created_at`, **`previous_state`** (состояние ревью до отзыва; GraphQL `ReviewDismissedEvent.previousReviewState`) |
| `effective[]` | нормализация §5.3 по логину |
| `complete` | `true` только при выполнении протокола §5.5 |

### 5.3. Нормализация эффективного ревью (факт, не решение)

Нормализация вычисляется **на момент T** в два шага.

0. **Отбросить неотправленные.** Ревью в состоянии `PENDING` (без `submitted_at`) исключаются
   **до** любых сравнений с T. Отправленное ревью без `submitted_at` → `unavailable`.
1. **Восстановить состояние каждого ревью на T.** Сравнения с T — по правилу §8.2 (равенство
   меток с точностью до секунды не упорядочивает события). Ревью с `submitted_at > T`
   отбрасывается. Для остальных: если есть отзыв с `created_at < T` — состояние `DISMISSED`;
   если отзыв `> T` — состояние `previous_state` из события отзыва (GitHub после отзыва отдаёт
   `state = DISMISSED`, исходное берётся только из события); иначе — `state` ревью. Отзыв без
   `previous_state` или ревью в `DISMISSED` без события отзыва → `unavailable`.
2. **Выбрать эффективное.** Для логина: последнее по `submitted_at` (при равенстве — по
   `review_id`) ревью, восстановленное состояние которого ∈ {`APPROVED`, `CHANGES_REQUESTED`,
   `DISMISSED`}. `COMMENTED`, `PENDING` эффективного состояния не меняют. Отозванное последнее
   ревью делает эффективным `DISMISSED` — более раннее `APPROVED` **не** восстанавливается.

Контрпримеры, обязательные в §5.6: `APPROVED → CHANGES_REQUESTED → отзыв второго` ⇒ эффективное
`DISMISSED`, не `APPROVED`; `APPROVED` отозвано после T ⇒ на T эффективное `APPROVED`;
`APPROVED` + `PENDING` без `submitted_at` ⇒ эффективное `APPROVED`; отзыв или approve с меткой,
равной T ⇒ по §8.2.

### 5.4. Запись `delivery`

| Поле | Смысл |
|---|---|
| `merged`, `merge_commit`, `merged_at` | факт мержа |
| `merged_by` | `{identity, type_hint, actor_class}` (классификация по пину политики акторов) |
| `head_at_merge` | голова смёрженного PR: REST `pulls/{n}.head.sha` = GraphQL `PullRequest.headRefOid` (обязаны совпасть; читаются в обоих проходах). **Не** из события мержа: `MergedEvent.commit` = `merge_commit` (для squash — результат squash). Проверено на стенде: PR #1, #4 |
| `in_base` | merge-коммит достижим из базы |
| `paths[]` | путь → blob в merge-коммите и blob на заданном head SHA |
| `complete` | все чтения выполнены по §5.5 |

### 5.5. Протокол чтения и отказы

**Окончательное решение** читается в фиксированном порядке:
(1) **доставка**: смёржен ли PR, `merge_commit`, `merged_at`, `head_at_merge` — если не
смёржен, результат `waiting_delivery`, и **никакой предварительный результат ревью не
переиспользуется для допуска**; (2) первый полный проход: все страницы ревью и все страницы
событий таймлайна (`reviewed`, `review_dismissed`, `merged`); (3) второй полный проход того же
и повторное чтение доставки. `complete = true` только если два прохода дали **идентичные**
множества (`review_id`, `state`, `commit_id`, события отзыва с `previous_state`) и доставка не
изменилась. Иначе `unavailable: unstable`. Решение вычисляется на срезе `T = merged_at` (§8),
поэтому изменения ревью после мержа на него не влияют, а изменения до мержа обязаны быть видны
в обоих проходах — после доставки ревью до `T` уже неизменны (кроме появления событий отзыва с
`created_at > T`, которые срез отбрасывает).

`unavailable` с причиной (никогда «пустой список»): неполная пагинация; HTTP 401/403/404/5xx;
таймаут; **GraphQL-ответ с `errors` при любом HTTP-статусе**, в том числе `200` с частичными
`data`; отсутствие обязательных полей; неизвестное значение `state`; отсутствие `commit_id`;
несогласованность форм логина бота (`<slug>[bot]`/`<slug>`) после нормализации по правилу
политики акторов. Потребитель трактует `unavailable` как отказ продвижения (fail-closed).
Требование сохраняет гарантию нынешнего producer steward (`approvalfacts/producer.py:78,103`).

### 5.6. Общие проверки (steward, обязательны)

Векторы **сбора** с подменённым транспортом, не только схема: неполная пагинация; ошибка доступа;
смена головы во время чтения; **отзыв ревью и новое `CHANGES_REQUESTED` между страницами при
неизменной голове**; **отзыв после второго прохода, но до доставки** (решение не должно
опираться на чтения до мержа); `200 + partial data + errors` с видимым `APPROVED`;
восстановление на T (оба контрпримера §5.3); отзыв без `previous_state`; несколько ревью одного
логина (`APPROVED→CHANGES_REQUESTED`, `CHANGES_REQUESTED→APPROVED`,
`APPROVED(old)→APPROVED(new)`, `APPROVED→COMMENTED`); отзыв до и после `merged_at`; две формы
логина бота; squash и merge-коммит для `paths[]`. Векторы вендорятся потребителями и гоняются в их
CI.

## 6. Политики: источник, пин и устаревание

**Один доверенный источник для обеих политик** (предложение rev 4). Сегодня политика
утверждающих живёт в репо `approval-policy` (`policy/approvers.env`), а политика акторов — в
вендоренной копии devtools (`contracts/steward-actor-policy/v1`, `policy_sources.py:33`) и в
`steward/profiles/approval-policy.yaml`. Для акта утверждения нормативной становится только
версия в доверенном источнике:

| Файл в `approval-policy` | Что даёт |
|---|---|
| `policy/approvers.env` | `AUTHORIZED_APPROVER_ACCOUNTS` (= `human_approvers`), `AUTHORIZED_MERGER_ACCOUNTS` (Q3) |
| `policy/modes.yaml` | `ACT_MODE` **по продукту**: `<owner>/<repo>: merge \| review` (§10, Q8). Продукт без записи — режим не определён |
| `policy/actors.yaml` | `human_identities`, `agent_identities` для `classify_actor` (`steward/gatecheck/approval.py:96`) |

**Локальные копии не участвуют в акте.** Копии политики акторов в devtools
(`contracts/steward-actor-policy/v1`) и steward (`profiles/approval-policy.yaml`) сохраняются
**только для release-гейта steward** (`gate-check --stage release`) — это отдельная область
применения. Проверка акта утверждения их не читает ни при каких условиях, в том числе как fallback
при недоступности источника (недоступность = `unavailable`). Обновление локальной установки ничего
не активирует (§6.1). Загрузчик
отвергает пересечение `human_identities ∩ agent_identities` (сейчас не запрещено). Совпадение с
`AUTHORIZED_MERGER_ACCOUNTS` проверяется отдельно от классификации (D3).

**Следствие единого пина (Q9).** Любая активация набора — включая смену `ACT_MODE` другого
продукта или правку списка утверждающих — меняет действующую активацию, и **все живые заявки
нового контракта** (`review/v1`, пин `activation_commit`) всех продуктов этого источника получают
`policy_changed` (нужны новая заявка и approve). Изоляции по продуктам в v1 нет: это осознанная
цена атомарного пина. **Legacy-заявки** (без маркера) сохраняют прежнее правило устаревания —
версия меняется только при изменении `approvers.env` (`discovery/policy.py:108`,
`devtools/governance/approval_facts.py:309`), поэтому смена чужого `ACT_MODE` их не трогает;
границе переключения **собственного** продукта (барьер §10) они подчиняются всё равно.
Завершённые законные акты (доставки, допущенные на свой T) ретроактивно не отменяются (Q1).

Последствие принято владельцем явно: добавление продукта или переключение его режима может
потребовать новых заявок и человеческих approve в **других** продуктах. Инструмент изменения
политики (спека B) обязан до активации показать этот эффект — список затрагиваемых живых
заявок; если список неполон (недоступный продукт, частичное чтение), это показывается как
неполнота, а не как отсутствие последствий.

Заявка фиксирует **один пин** — единую схему во всех носителях (манифест узла,
`approval-request.yaml` v2, `run.json`, конверт, evidence):
`policy{repo, branch, activation_commit, files_sha256}`, где `activation_commit` — `merge_commit`
активации §6.1 (нейтральный коммит ветки активацией не является и пином быть не может).
Утверждающие, мержеры, классификация акторов и `ACT_MODE` читаются **из этого одного коммита**;
ветка между чтениями заново не разрешается; чтение любого файла политики из другого коммита
(смешивание версий) — отказ. `files_sha256` — только контроль целостности прочитанного набора,
не идентичность версии. Формулировки «пины обеих политик» в прежних ревизиях означают этот один пин.

**Живая заявка.** На каждой проверке пин обязан совпадать с текущей активацией; иначе
`invalidated: policy_changed` (существующее правило devtools `approve_node.py:1890-1903`
распространяется на discovery и на политику акторов). Продолжение — **только новой заявкой и
новым approve** (`--repropose`). Комментарий `policy-reconfirm` **не** оживляет живую заявку:
он остаётся отдельным механизмом допуска уже утверждённого upstream с сохранением различия
P/W/C (`brief_provenance.py:250,285`).

**Историческое доказательство.** Пин заявки обязан совпадать с активацией, **действовавшей в
момент мержа** (§6.1); текущая активация на вердикт не влияет. Иначе историческое правило обходило
бы смену политики до доставки (§8.1, строки 4–5).

### 6.1. История активации (Q6; модель доверия — Q7)

Время коммита (`committer date`, `author date`) **не используется**: это время создания коммита,
а не появления версии в доверенной ветке, и оно задаётся произвольно (`GIT_COMMITTER_DATE`).

**Модель доверия — человеческий периметр (Q7, решено).**

> **Гарантия v1.** При непрерывном сохранении человеческого периметра с момента bootstrap агент не
> может самостоятельно изменить политику или её историю. Читатель проверяет доступные факты и
> структуру истории, но **не доказывает** отсутствие прежней компрометации полномочий или скрытого
> отката администратором.

| | Содержание | Кто обеспечивает |
|---|---|---|
| **Доверенные предпосылки** (не проверяются в рантайме) | периметр сохранялся непрерывно с bootstrap (текущий снимок прав не доказывает, что агенту вчера не выдавали запись); у агента нет человеческих credentials, deploy keys и иной автоматизации с записью в источник; администратор не менял защиту скрыто | владелец политики; при установке — проверка человеком (§6.2) |
| **Проверяемые факты** (каждое чтение) | форма истории (п. 2–5 ниже); самоотчёт прав каждого credential, который держит процесс (§6.2 б); доступные настройки источника | библиотека steward + потребитель; нарушение или ошибка обязательного чтения → `unavailable` |

Читатель проверяет **форму** истории (каждое звено first-parent — `merge_commit` смёрженного PR;
прямой push и многокоммитный rebase-merge дают звенья без PR; отсутствие rebase-merge форма не
доказывает — п. 2),
но не обнаруживает переписывание истории тем, у кого есть права администратора (force-push на
предка с сохранённым bootstrap неотличим от честной истории — R4-3). Такой откат
**предотвращается действующим ruleset-ом при отсутствии подходящего bypass**; скрытое
административное изменение защиты читатель обнаружить не гарантирует.

1. **Корень доверия — репо установки `df-trust`** (rev 16). В нём `source.env` (`repo`, `branch`
   источника политики, `bootstrap_activation`, `POLICY_ADMINS`) и журнал `epochs.yaml` (§6.3).
   Bootstrap закрепляется при установке человеком и задаёт исходное доверие вне проверяемой
   политики (новая политика не легитимирует своё появление).
   - **Привязка** к `df-trust` — защищённая локальная конфигурация установки (спека B §3.7,
     `trust.toml`, владелец root): GitHub-host, числовой `repository_id`, ветка; транспорт чтения
     в v1 — только публичный (оба репо доверия публичны; приватные — неподдерживаемый профиль).
     Читатель не доверяет произвольному `origin` рабочего чекаута и **не следует** за сменой
     default branch; агент не может переопределить привязку через CLI, env или конфигурацию
     продукта. Смена корня — отдельная человеческая операция с новой полной проверкой (§6.2 а).
   - **Чтение по снимку.** Читатель получает доверенную ветку `df-trust`, фиксирует её SHA и
     читает `source.env` и все версии `epochs.yaml` (история файла по first-parent этой ветки) из
     этого снимка; проверку перехода журнала (§6.3) выполняет относительно него же. SHA корня
     доверия записывается в evidence решения **отдельно** от пина набора политик
     (`activation_commit`). Недоступность обязательных данных → `unavailable`; **запасного чтения
     из devtools или рабочего дерева нет**.
   - **`df-trust` — отдельный периметр** (§6.2): ни machine user, ни App продукта, ни App
     издателя не имеют туда записи или bypass. Повреждение источника политики не даёт права
     переписать журнал восстановления. Запрет незаметного отката человеком остаётся предпосылкой
     человеческого периметра — новый репо эту проблему не устраняет.
2. **Активация = PR-мерж в доверенную ветку**, меняющий файлы политики, методом **merge-commit или
   squash**. Rebase-merge в источнике политики **запрещён** (настройка репо `allow_rebase_merge =
   false`): при rebase first-parent получает несколько коммитов на один PR, и правило п. 4
   объявило бы законный PR прямым push (R4-2). Запрет — **предпосылка человеческого периметра**:
   обязательная проверка — человеком при установке (§6.2 а); рантайм видит настройку не всегда
   (§6.2 б, четыре состояния). **Предел обнаружения:** форма истории (п. 4) ловит многокоммитный
   rebase-merge — его промежуточные коммиты не являются `merge_commit_sha` никакого PR. Однокоммитный
   rebase-merge следа не оставляет: `merge_commit_sha` такого PR — коммит, на который обновилась
   базовая ветка (документированная семантика API GitHub; живым тестом не проверено), сверка
   коммит ↔ PR проходит, и по форме он неотличим от squash. Проверка формы обнаруживает
   определённые нарушения, но **не доказывает отсутствие rebase-merge**. Факты активации: номер PR,
   `merge_commit`, `merged_at`, `files_sha256` в `merge_commit`. Версия идентифицируется
   **активацией**, а не байтами: возврат к прежним байтам — новая активация и **не оживляет**
   прежние заявки.
3. **Начальная версия** — событие `bootstrap_activation`. История до него не восстанавливается.
4. **Форма истории.** Цепочка first-parent **диапазона эпохи** проверяемой активации (§6.4: открытая —
   `anchor…HEAD`, закрытая — `anchor…last_confirmed`; для эпохи 1 якорь — `bootstrap_activation`):
   каждый коммит цепочки — `merge_commit` смёрженного PR в эту ветку (связь коммит → PR через API и
   обратная сверка `PR.merge_commit_sha`). Коммит first-parent без PR, чей `merge_commit_sha`
   равен этому коммиту, отсутствие якоря проверяемой эпохи в её диапазоне (§6.4), неполная пагинация → `unavailable`.
   **Предел обнаружения:** косвенный мерж (indirect merge — коммиты PR попали в ветку прямым push)
   может дать коммит на first-parent, формально связанный с PR; положение в графе способ доставки
   не доказывает. Читатель обнаруживает только несоответствие связи коммит ↔ PR; прямой push
   внутри периметра исключается предпосылкой (ruleset «только PR» без подходящего bypass, §6.1
   модель доверия), а не проверкой.
   Коммиты, не меняющие файлы политики, — нейтральные звенья (тоже обязаны быть PR-мержами).
5. **Порядок активаций — по first-parent, не по времени.** Активация на момент T — **последняя по
   first-parent** активация с `merged_at < T`. Если `merged_at` активаций противоречат их порядку на
   first-parent (более поздняя по цепочке имеет меньшее время) → `unavailable`. Если активация имеет
   `merged_at = T` (метки форджа — с точностью до секунды) — по §8.2: если исходы решения при
   версии до и после неё различаются → `ambiguous_event_order`, иначе исход принимается. Несколько активаций в одну секунду `< T` разрешаются порядком first-parent (R4-5).
   Совпавшие метки событий в разных репозиториях порядок не доказывают.
6. **Где живёт.** Читатель истории — часть общей библиотеки steward (§5), факты — запись
   `policy_history` контракта v3 с правилами `unavailable` §5.5.

*Альтернатива для Q7 (не рекомендуется для v1):* без периметра — каждая активация обязана нести
человеческий акт (approve + мерж по правилам D1–D3) **по предыдущей** доверенной активации,
плюс внешний монотонный контрольный журнал активаций для обнаружения усечения истории. Даёт
защиту и от агента с правами записи в источник, но вводит рекурсивную проверку и новый
доверенный журнал.

### 6.2. Периметр: проверка при установке и при каждом чтении

**Охват периметра.** Любой способ записи в источник, доступный агенту: machine user, App ролей и
их токены установки, человеческие credentials на машине исполнения, deploy keys, CI/автоматизация
с правом записи, ruleset bypass. **Набор проверяемых личностей не берётся из проверяемой версии
политики:** проверка формулируется как allowlist — каждый принципал с правом записи, admin или
bypass в источнике обязан входить в список **администраторов политики**, закреплённый человеком
при bootstrap (`df-trust/source.env`, ключ `POLICY_ADMINS` — он же `policy_admins` этой спеки).
Периметр охватывает **оба** репо доверия — `approval-policy` и `df-trust`; их периметры
независимы. Удаление
агентом себя из `agent_identities` поэтому ничего не меняет.

**(а) При установке — человек, полная проверка** (`df setup-trust`, спека B §6.2, в человеческом
контексте): коллабораторы и их права, команды, deploy keys, установленные App, ruleset-ы
доверенной ветки **вместе с `bypass_actors`** (их GitHub отдаёт только вызывающему с правом записи в
ruleset), запрет force-push и удаления, только PR, `allow_rebase_merge = false`. Результат —
evidence установки; это запись проверки, а не источник полномочий.

**(б) При каждом чтении — потребитель, доступные проверки.** Агенту **не выдаются**
административные credentials ради диагностики. Проверяется то, что видно без них:
- самоотчёт: **каждый процесс проверяет credentials, которые держит** (rev 16), и обязателен
  только для своего решения. Токен (PAT machine user и иные токены процесса):
  `GET /repos/{approval-policy}` и `GET /repos/{df-trust}` **этим токеном** — `permissions.push`,
  `maintain`, `admin` обязаны быть `false`; отсутствующее поле, 404 или ошибка → `unavailable`
  (не `false`); поддерживаемость типа токена (поле `permissions` на публичном репо без доступа)
  подтверждается спайком спеки B §6.3. Ключ App (держит только издатель спеки B): JWT и полномочия
  **установки** — установка App на `approval-policy` или `df-trust` → нарушение; проверяется
  установка, а не выпущенный токен (суженный токен не делает безопасным ключ, которым можно
  выпустить токен с записью). Производный токен установки, выданный другому процессу, покрыт
  проверкой установок у держателя ключа; самоотчётом на источниках этим токеном не проверяется.
  Распределение по контекстам установки — спека B §6.1;
- форма истории §6.1 п. 2–5;
- ruleset доверенной ветки, читаемый с `Metadata: read`: наличие запрета force-push/удаления и
  требования PR;
- `allow_rebase_merge` из `GET /repos/{policy}` — четыре состояния: `false` — настройка
  проверена; `true` — нарушение периметра; `null` или поле отсутствует **в корректном ответе**
  (GitHub показывает настройки мержа только вызывающему с правом записи, которого у агента нет)
  — непроверенная предпосылка: решение не блокирует, фиксируется в evidence решения, проверка —
  человеком при установке (а); ошибка запроса или некорректный ответ → `unavailable`, в
  допустимый `null` не превращается.

**Чтение содержимого источников** (v1): оба репо доверия публичны и читаются **без credentials**;
транспорт задаёт защищённая конфигурация установки (спека B §6.1), а не запрос или окружение
исполнителя. Чтение содержимого и самоотчёт — разные операции: анонимное чтение не доказывает
отсутствия прав у проверяемого credential. Расширять установку App продукта на источники доверия
нельзя. **Приватные источники доверия не поддерживаются** в v1 (предлагавшийся App-читатель
отменён решением владельца 13.10).

**Недоступное ≠ подтверждённое.** Поле, которое API не вернуло вызывающему (например,
`bypass_actors` без права записи в ruleset), — **не пустой список** и не подтверждение отсутствия
bypass. Непроверяемое в (б) сохранение периметра остаётся доверенной предпосылкой (§6.1), а не
результатом рантайм-проверки. Обнаруженное нарушение или ошибка **обязательного доступного**
чтения → `unavailable`.

### 6.3. Журнал эпох доверия

**Журнал** — `epochs.yaml` в репо `df-trust` (rev 16; правка только PR-ом с мержем человеком,
ruleset — только PR, без force-push и удаления; агент его изменить не может). Это упорядоченный список эпох;
порядок — **позиция в списке**. **Допустима ровно одна мутация** — атомарный переход в одном PR:
заполнить отсутствующие `last_confirmed`, `valid_until`, `closed_reason` у **последней открытой**
эпохи и добавить следующую эпоху. Изменение `epoch`/`anchor`, правка закрытых записей, удаление и
перестановка запрещены; валидатор журнала (каждый потребитель при чтении — по всей истории файла
в зафиксированном снимке §6.1 п. 1; CI `df-trust` — при PR) сверяет
новую версию с предыдущей и отвергает любой иной переход (`unavailable`).

| Поле эпохи | Смысл |
|---|---|
| `epoch` | монотонный номер (1, 2, …) — равен позиции |
| `anchor` | активация-якорь эпохи: для эпохи 1 — `bootstrap_activation`; для следующих — `trusted_point`, выбранный человеком (потомок прежней истории или новый bootstrap после разрыва) |
| `last_confirmed` | только у **закрытой** эпохи: последняя активация, до которой периметр в этой эпохе подтверждён человеком |
| `valid_until` | только у закрытой эпохи: момент форджа, после которого политика эпохи не действует — `merged_at` первой неподтверждённой активации после `last_confirmed`, а если её нет — время обнаружения нарушения. Задаёт человек, копируя факт форджа |
| `closed_reason` | только у закрытой эпохи: описание нарушения (свободный текст, ссылки на расследование) |

Текущая эпоха — последняя в списке; она открыта (без `last_confirmed`). Закрытие и открытие — только
описанным атомарным переходом; откатить якорь назад нельзя, новая эпоха всегда в конце.

**Обнаружение нарушения потребителем.** Потребитель, обнаруживший нарушение (самоотчёт §6.2 б,
признак в форме истории), регистрирует **событие периметра** в долговечном транзакционном журнале
событий установки (rev 16, механизм заменил маркер-файл; хранилище, писатель, операции и машина
состояний — спека B §6.1). Пространство журнала событий — **идентичность корня доверия** (host,
`repository_id` и ветка `df-trust`); номера эпох сравниваются только внутри него. Номер эпохи
события — номер последней эпохи этого корня **на момент регистрации** (консервативно; время
обнаружения хранится отдельно); если журнал эпох в этот момент недоступен, событие
регистрируется незавершённым (`pending`) и блокирует, пока его не завершат с номером на момент
завершения. Решения корня запрещены, пока есть незавершённое событие или событие с номером ≥
номера последней эпохи. Потребитель уведомляет человека любым каналом; канал уведомления —
**не часть протокола**. В режиме разработки журнал событий лежит в
`$XDG_STATE_HOME/darkfactory/perimeter/` без гарантии защиты от агента, но в том же формате.

**Гарантия распространения.** **Внутри установки** зарегистрированное событие обязательно
учитывается всеми её потребителями (общий журнал событий). **Между установками** (другие машины,
не читающие этот журнал) — останавливаются, когда (а) сами обнаружили нарушение или (б) человек
закрыл эпоху в журнале эпох; до записи человека они **не обязаны** останавливаться — это
ограничение v1, а не обещание. Журнал эпох читается с forge (закреплённая ветка `df-trust`,
снимок §6.1 п. 1) перед каждым решением; недоступность → `unavailable`.

### 6.4. Решение с учётом эпох

**Диапазон эпохи.** Открытая эпоха: first-parent от `anchor` до текущей головы ветки. Закрытая
эпоха: first-parent от `anchor` до `last_confirmed` — **собственный зафиксированный диапазон**;
его достижимость из нынешней головы не требуется, а коммиты после `last_confirmed` в нём не
проверяются. Форма истории (§6.1 п. 4) проверяется на диапазоне эпохи. Если объекты диапазона
закрытой эпохи недоступны на форже (например, удалены после переписывания истории) →
`unavailable`: это ограничение, а не отказ по существу.

Для доставки в момент T:
1. **Эпоха доставки** — эпоха E с наибольшим номером, у которой `merged_at(anchor(E)) < T`
   (для открытой — без верхней границы; для закрытой — при условии `T < valid_until(E)`).
2. **Активация на T** определяется по §6.1 п. 5 **только внутри диапазона E**.
3. Если T попадает **строго внутрь** интервала между `valid_until(E)` и `merged_at(anchor(E+1))`
   → отказ (политика не определена; восстановление не легитимирует). Совпадение T с любой из
   границ — по §8.2 (оба порядка; разные исходы → `ambiguous_event_order`).

| # | Случай | Итог |
|---|---|---|
| e1 | T в открытой эпохе, активация на T в её диапазоне | обычная проверка §6, §8 |
| e2 | T в закрытой E, `T < valid_until(E)`, активация ≤ `last_confirmed` | действителен; проверка в диапазоне E (законный старый акт) |
| e3 | T в закрытой E, **строго** `valid_until(E) < T < merged_at(anchor(E+1))` | отказ (межэпохальный интервал); равенство с границей — e6 |
| e4 | Законный старый акт E1; после него прямой push X, восстановление якорем H (потомок) | действителен: X вне диапазона E1 (`anchor…last_confirmed`) |
| e5 | Законный старый акт E1; восстановление новым bootstrap H в несвязанной истории | действителен, если объекты диапазона E1 доступны; иначе `unavailable` |
| e6 | T равно `valid_until(E)` или `merged_at(anchor(E+1))` с точностью до секунды | по §8.2: если исходы по разные стороны границы различаются → `ambiguous_event_order`; если совпадают (например, акт отвергнут или допущен в обоих) — этот исход |
| e7 | Акт в открытой E2 с якорем — новый bootstrap | проверка от H; старый bootstrap не требуется |

Правила одинаковы для всех потребителей и установок: журнал читается с forge перед каждым
решением.

## 8. Момент фиксации и отзыв ревью

**Момент фиксации решения = `merged_at` доставки** — неизменяемый факт форджа, а не локальная
запись. Решение (в том числе историческое, после перезапуска) переустанавливается так:
нормализация §5.3 **на момент `merged_at`** по полным ревью и событиям таймлайна; D1 проверяется
на этом срезе; голова на момент мержа (`head_at_merge`) = head заявки; затем D2–D3.

Следствия:
- **отзыв до `merged_at`** — акт на момент фиксации недействителен → доставка не засчитана,
  прогон стоит (новая заявка/approve; смёрженное содержимое без акта — отказ с причиной);
- **отзыв в ту же секунду, что `merged_at`** — по §8.2: если от этого отзыва зависит наличие
  действительного акта → `ambiguous_event_order` (а не «отзыв до мержа»); если не зависит
  (например, отозвано ревью другого, неавторизованного логина) — исход принимается;
- **отзыв после `merged_at`** — решение не отменяется ретроактивно (на срезе он отсутствует);
  событие записывается как аудит `review_dismissed_after_delivery` и всплывает в наблюдении.
  **Остановка дальнейшего использования** утверждённого содержимого — отдельное явное действие
  человека (для узла — существующее переоткрытие узла, ветка `-r<n>`; для брифа — новая заявка),
  а не следствие отзыва (Q1);
- локальный снимок не нужен и не доверяется: подложенный снимок ничего не меняет, потому что
  решение всегда выводится из таймлайна.

*Требует проверки на стенде (вектор M3):* полнота событий `review_dismissed` в таймлайне,
наличие `previousReviewState`, временные метки относительно `merged_at`.

### 8.2. Общее правило временной неоднозначности

Метки форджа имеют точность до секунды; события с равной меткой **не упорядочены**. Правило
действует для **всех** сравнений с моментом T (доставка) и между границами: ревью (`submitted_at`),
отзывы (`created_at`), активации политики (`merged_at`), границы эпох (`valid_until`,
`merged_at(anchor)`), активация режима продукта.

1. **Группа.** G — все события с меткой, равной T (ревью, отзывы, активации, границы эпох,
   активация режима), вместе с самой доставкой. Событие, относящееся к решению, но с другой
   меткой, упорядочено своей меткой.
2. **Допустимые порядки.** Перебираются **все линейные порядки G**, совместимые с известными
   зависимостями: отправка ревью предшествует его отзыву; активации одной ветки — в порядке
   first-parent; события одного объекта — в их собственном порядке. Других допущений о порядке
   нет. Проверять события по одному, считая остальные «после T», **нельзя** — это пропускает
   совместные варианты.
3. **Решение.** Для каждого допустимого порядка вычисляется полный исход решения (§5.3, §6, §6.4,
   §10). Единственный общий исход принимается; разные исходы → `unavailable:
   ambiguous_event_order`. Утверждать, что событие доказанно предшествовало или следовало
   доставке, нельзя.
4. **Предел перебора.** Если в G больше 8 событий, перебор не выполняется →
   `ambiguous_event_order` (консервативно). Независимый поштучный перебор допустим только как
   оптимизация с доказанной эквивалентностью полному.
5. **Это единственный нормативный алгоритм для равных меток.** Все частные упоминания (§5.3,
   §6.1 п. 5, §6.4 п. 3, e6, §8, legacy-граница и п. 5 admission в §10, приёмка) — его применения
   с тем же условием «если исходы различаются»; безусловных отказов из-за одной лишь равной
   секунды в спеке нет.

**Практическое следствие для мержера.** Агентский мерж выполняется не раньше, чем через 2 с после
`submitted_at` действительного approve и после последнего события, способного повлиять на решение
(`merge-pr.sh` ждёт границы секунды), — иначе штатная доставка рискует получить
`ambiguous_event_order`.

### 8.1. Время и политики — таблица сочетаний (R1-1, R1-2, R2-2 — один класс)

Обозначения: A — approve человека, M — мерж (`merged_at`), C — смена политики (любой из двух),
D — отзыв ревью, R — первое чтение потребителем. Требование: результат определяется **только**
фактами, неподделываемыми агентом, и не зависит от того, когда потребитель впервые запустился.

| # | Порядок | Должно быть | Rev 2 давала | Чем обеспечивается (rev 4) |
|---|---|---|---|---|
| 1 | A → M → R | принято | принято | срез на M |
| 2 | A → D → M → R | отказ | отказ | срез на M (§5.3) |
| 3 | A → M → D → R | принято + аудит | **отказ** (approve пропадал) | `previous_state` (§5.3) |
| 4 | A → C → M → R | `policy_changed` | **принято** (историческое правило) | история активации §6.1 |
| 5 | A → M → C → R | принято | неопределено | история активации §6.1 |
| 6 | A → C → R → M | `policy_changed` | `policy_changed` | живое правило §6 |
| 7 | A → R(до M) → D → M → R | отказ | зависело от реализации | порядок §5.5: доставка первой |
| 8 | A(H) → смена пинов в `run.json`/теле PR → M | пины из H | **принято с чужими пинами** | манифест в H (§2) |

| # | Ситуация | Должно быть |
|---|---|---|
| 9 | Коммит политики создан до A, смёржен в доверенную ветку после M | активация после M → строка 5 (принято) |

## 9. Изменения по путям

### 9.1. Узел бандла (§I12, devtools)

- Метка candidate-PR `human-merge-required` → `human-approval-required`; тело несёт
  `act: review/v1` и строку пина `policy{…activation_commit…}` (зеркало манифеста).
- `_reconcile_candidate`: вместо `merge_event` — факты `review` + `delivery`; решение по D1–D3, §8.
- candidate-PR мержит агент (`merge-pr.sh`) после действительного акта.
- Ожидания: `waiting_human_approval` / `waiting_delivery`.

**Конверт утверждения (Q5 — решено: вариант (а)).** Сегодня finalize-PR дописывает
`status/approved_by/approved_at` во frontmatter узлов (`approve_node.py:2279`) и мержится агентом
после scope-аттестации (`approve_node.py:2404`). При D7 эти файлы под CODEOWNERS-человеком, и
агентский finalize заблокирован: approve candidate-PR не переносится на другой PR. Варианты:

- **(а) Конверт — отдельный файл вне защищённых путей** (принято): finalize пишет
  `workstreams/<ws-id>/approvals/<node>.yaml`, а не frontmatter узла. Файл не является
  источником полномочий (D4). Агентская запись безопасна **только при условиях**:
  0. *Конверт — проверяемая производная запись.* Он не выбирает собственный режим проверки и
     не несёт привязку сам по себе: продукт, воркстрим, узел и поколение устанавливаются через
     **манифест заявки в одобренном коммите**; конверт лишь обязан с ним совпасть.
  0a. *Действующее поколение — по истории доставок, не по конверту.* Действующее одобрение узла —
     **последний по first-parent базовой ветки** доставленный candidate-коммит, чей манифест
     включает узел (с учётом доставленных переоткрытий `-r<n>` и supersede). Манифест несёт
     монотонный `generation` узла; поколение в конверте обязано совпасть с поколением этого
     последнего манифеста. Совпадение `self_hash` и upstream-пинов **не** различает поколения с
     одинаковым содержимым (`version`/`status` вне self-hash, `node_approval.py:84`) — поэтому
     поколение выбирается по истории, а не по содержимому.
  1. *Идентичность конверта:* `request_id`, `generation`, путь манифеста заявки, head SHA, `self_hash` узла,
     upstream-пины, `merge_commit` candidate, `review_id`. Каждый читатель статуса проверяет,
     что конверт относится к **текущему** узлу и текущему поколению (сверка `self_hash` узла и
     upstream-пинов, как сейчас делает `node_debt`, `node_approval.py:207`), и переустанавливает
     акт из фактов форджа по §8 через манифест заявки.
  2. *Отказы:* отсутствующий конверт = не одобрен; конверт не прошёл переустановку или
     относится к другому узлу/поколению (в т.ч. **исторически действительный конверт другого
     узла или прежнего поколения**, подставленный агентом) = отказ.
  3. *Смешанный DAG и отсутствие fallback:* режим узла определяется **только** заявкой его
     действующего одобрения в истории форджа: candidate-коммит с манифестом → `review/v1`
     (статус только из конверта); candidate-коммит без манифеста, смёрженный **до активации
     `ACT_MODE=review`** (§6.1) → `merge` (старый код, frontmatter). Отсутствующий или
     подменённый конверт у узла режима `review/v1` → «не одобрен»; **fallback на старый
     frontmatter запрещён**. Заявка без манифеста, смёрженная после активации `ACT_MODE=review`,
     — отказ.
  4. *Статус в хеше DAG сохраняется:* канонический хеш DAG в `task_bridge` намеренно учитывает
     `status` (`task_bridge.py:1167`); для `review/v1` в каноническую проекцию входит
     производный статус из проверенного конверта, чтобы изменение допуска не скрывалось за no-op.
  Читатели статуса узла (`node_approval`, гейты steward, task_bridge) переходят на конверт для
  `review/v1`.
- Отклонённые альтернативы: второй человеческий approve на finalize-PR (6 → 12 актов на бандл);
  узлы вне CODEOWNERS (снимает первый рубеж).

## 10. Режим и миграция

**Режим разрешает политика, фиксирует заявка.** `ACT_MODE` в доверенном источнике — источник
**разрешённого** режима. Маркер в заявке (`act: review/v1` в манифесте узла и в
`approval-request.yaml` v2 брифа) фиксирует, **что именно одобрил человек**. Режим заявки обязан
соответствовать `ACT_MODE`, действовавшему **на момент доставки** (§6.1, T = `merged_at`).

**Режим — по продукту (Q8, решение владельца).** `ACT_MODE` задаётся для каждого репо продукта в
`policy/modes.yaml` единого набора. Это делает **область переключения равной области draining**
(NEW-4): переключается один продукт, и барьер проверяет живые заявки именно этого продукта.
Отсутствующая запись не даёт режима по умолчанию (шаг 2 admission ниже).

**Legacy-эпоха (NEW-2).** Для продукта P граница — активация, впервые вводящая запись
`ACT_MODE[P]` («активация режима P»). Доставки с `T` **строго до** неё и заявкой без маркера —
legacy: проверяются старым кодом с прежними пинами (`approval-policy-source/v1`) и прежними
проверками, без требования `ACT_MODE` и без истории до bootstrap. Доставка в ту же секунду, что
активация режима P, — по §8.2: если legacy-допуск до границы и admission после неё дают разный
исход → `ambiguous_event_order`, иначе исход принимается. Для уже существующих продуктов первая запись — `merge` (легализует
незавершённые старые заявки до барьера), для новых продуктов — сразу `review`.

**Единый admission режима — до выбора читателя, для обоих путей** (R4-4):
1. Найти доставку; если T до активации режима P — legacy (выше); иначе определить
   `ACT_MODE[P]` на T по §6.1.
2. `ACT_MODE[P]` отсутствует или неизвестен после активации режима P → отказ (старый режим не
   подразумевается).
3. `ACT_MODE = merge` на T → допустима только заявка без маркера (узел без манифеста,
   `approval-request.yaml` v1), проверяется старым кодом.
4. `ACT_MODE = review` на T → допустима только заявка с маркером `review/v1`; заявка без маркера
   (в том числе **новый или ранее открытый brief-PR с v1**) → отказ без утверждения, нужна новая
   заявка.
5. Активация `ACT_MODE` имеет `merged_at = T` → по §8.2: admission вычисляется для режима до и
   после неё; разные исходы → `ambiguous_event_order`, одинаковые — исход принимается.
6. Только после admission выбирается читатель (legacy или v3). Читатель режим не выбирает.

**Правила перехода.**
- Старый акт, завершённый (доставленный) до переключения, проверяется по старому контракту.
- Старый кандидат или brief-PR, смёрженный после переключения, утверждения не получает; нужна
  новая заявка.
- **Обратное переключение не поддерживается в v1:** активация `ACT_MODE = merge` после
  `ACT_MODE = review` делает политику недействительной для акта (`unavailable`) до исправления
  новой активацией `review`. Возврат старых байтов политики не оживляет прежние заявки (§6.1 п. 2).

**Единый барьер миграции** (R1-6), строго по порядку:
1. **Остановка создания** заявок `merge`: devtools и discovery отказываются создавать новые заявки
   без маркера (флаг установки `act_migration: draining`; это локальная настройка, поэтому она
   только останавливает создание и ничего не разрешает).
2. **Разбор всех живых заявок `merge` на всех стадиях** — candidate OPEN, merged-but-unrecorded,
   pending-finalize, brief-PR OPEN, brief merged-but-unapproved: довести старым путём или явно
   инвалидировать (`invalidated: act_migrated`, `--repropose`).
3. **Только затем** — активация `ACT_MODE[P] = review` в источнике и включение D7 в репо P.
   `df setup-repo apply` (спека B) отказывает в включении D7 и в предложении активации, пока в
   **репо P** есть любая живая заявка без маркера. Другие продукты того же источника переключение
   P не затрагивает — их режим остаётся своим.

| Шаг | Репо | Содержание | Выход |
|---|---|---|---|
| M0 | steward | v3, библиотека (stdlib), векторы, запрет пересечения, миграция release-гейта | PR steward |

## 11. Приёмка

### 11.1. Живая матрица (стенд `df-roles-probe`, затем реальный продукт)

Сценарии 1–4 — **на обоих путях** (бриф и узел бандла).

**Разрушительные сценарии — только на стенде** (решение владельца 13.10). Сценарии, требующие
нарушить периметр источника (выдать агенту запись, force-push/прямой push или rebase-merge в
источник, скрытый bypass, порча журнала) — №21, 28, 29, 33–37, 39, 45, — на реальном продукте

же пины зависимостей, та же схема контракта, отличаются только данные; иначе — повторный
стендовый прогон); (3) в итоговой матрице строка помечена «проверено на
стенде» со ссылкой на evidence; (4) безопасные проверки реального периметра (самоотчёт прав,

## 12. Вне объёма

Установщик и роли (спека B); организационный аккаунт (отдельная проверка на стенде);
независимость полномочий (отдельный OS-контекст); dispatcher как потребитель фактов.
**Требование к спеке B** (из Q9): предпросмотр изменения политики показывает затрагиваемые живые
заявки `review/v1` всех продуктов источника; неполный список помечается как неполный.
