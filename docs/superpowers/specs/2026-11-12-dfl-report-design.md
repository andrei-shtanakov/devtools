# `dfl report`: доставка ошибок коллег в devtools — дизайн

Дата: 2026-11-12. Статус: черновик, ждёт одобрения владельца.

## 1. Зачем

Коллеги ставят DarkFactory (`install.sh`, `dfl`) на свои машины и пробные репо.
Когда `dfl` останавливается, всё, что нужно для разбора, лежит только на машине
коллеги: вывод в терминале, `out/governance-runs/<прогон>/`, версии. Сейчас
владелец получает это вручную — вставкой в чат или по ssh (живой Linux-прогон
11–12.11, `dfl init-repo` без `origin/HEAD` → devtools#744).

Цель — одна команда у коллеги, после которой у владельца есть **информация,
достаточная, чтобы начать разбираться с ошибкой** (формулировка владельца), без
переписки с коллегой.

## 2. Решения владельца

- Отчёт — не весь журнал прогона, а достаточный для начала разбора.
- Коллеги пока гоняют DarkFactory на **пробных** репо.
- Отчёты уходят **публичными issue в `andrei-shtanakov/devtools`** — публичность
  принята. Зонтик `atp` приватный, коллегам туда доступа нет.

## 3. Цели, не-цели, анти-цели

**Цели**

1. `dfl report` собирает отчёт о последнем сбое `dfl` в текущем репо,
   показывает его целиком и после подтверждения открывает issue в devtools
   от учётки коллеги (тот `gh`, что уже залогинен).
2. Повтор той же ошибки не плодит issue: отчёт уходит комментарием в уже
   открытое issue с тем же отпечатком.
3. Отказ `dfl` и стоп прогона подсказывают команду: «отчёт разработчикам:
   `dfl report`».

**Не-цели (v1)**

- Автоматическая отправка без участия коллеги, фоновые отправки, телеметрия.
- Транскрипты агентов, бандл, код репо коллеги в отчёте.
- Автоматическое исправление по отчёту. Разбор делает владелец или агент по
  просьбе владельца (§8).
- Рабочие (закрытые) репо: для них нужен другой канал (§10).
- Отчёты не-`dfl` путей (`make behaviour-run`, strict).

**Анти-цели** (провал, даже если «работает»)

- В публичное issue утёк токен, содержимое файлов репо или транскрипт.
- Коллега отправил отчёт, не увидев его.
- Отчёт есть, но по нему нельзя понять, на каком шаге и почему остановилось.
- Каждый повтор одной ошибки — новое issue.

## 4. Поток коллеги

```
$ dfl run
…
dfl run: отказ (код 2)
  причина:     …
  что сделать: …
  отчёт разработчикам: dfl report

$ dfl report
<отчёт целиком, как он уйдёт>
Отправить в andrei-shtanakov/devtools как публичное issue? [y/N] y
issue: https://github.com/andrei-shtanakov/devtools/issues/NNN
```

- `dfl report` без терминала (stdin не tty) — не спрашивает и **не отправляет**:
  печатает отчёт и отказ «подтвердите отправку в терминале или используйте
  `--print`». Флага «отправить без подтверждения» нет (анти-цель 2).
- `dfl report --print` — только напечатать (например, чтобы вставить в чат).
- `dfl report` не требует режима test и рабочего конфига: в `main` он
  обрабатывается до `_require_test_mode` — сломанный конфиг тоже надо уметь
  отправить.
- Отправка — от профиля `gh` человека: `accounts.human_gh_config_dir` конфига,
  если конфиг читается, иначе `gh` по умолчанию. `gh` не залогинен или нет
  сети — отказ (код 2) с подсказкой `dfl report --print`.
- Нет записанного сбоя для этого репо — «записанного сбоя нет», код 0, ничего
  не отправляется.
- Повтор: если найдено открытое issue с тем же отпечатком (§7), вопрос звучит
  «Добавить комментарий к …/issues/NNN?», ответ — ссылка на комментарий.

## 5. Что записывается при сбое

`dfl` при каждом вызове **любой подкоманды** (кроме самого `report`) с
ненулевым кодом записывает **запись сбоя** для репо:
`$XDG_STATE_HOME/darkfactory/failures/<repo-key>/last.json` (по умолчанию
`~/.local/state/darkfactory/…`). Перезаписывается последним сбоем; успешный
вызов её не трогает (отчёт о вчерашнем сбое остаётся доступен).

`<repo-key>` — первые 16 hex `sha256` от realpath корня git-репо
(`git rev-parse --show-toplevel` из `--cwd`), а если `--cwd` не git-репо — от
realpath самого `--cwd`. Ключ `user_targets` (имя каталога) не годится: его
регистрирует только `run` (`lite/dfl.py`), и сбой до регистрации (нет
`origin`, конфиг, `init-repo`) остался бы без записи. Запись делает обёртка
вокруг всего тела `main`, включая `_require_test_mode`.

Поля записи:

| Поле | Источник |
|---|---|
| `command`, `argv` | вызов `dfl` (аргументы как есть; `--file` — только имя файла) |
| `exit_code`, `time` (UTC) | вызов |
| `output_tail` | последние 200 строк того, что коллега видел в терминале (stdout+stderr вызова), см. ниже |
| `run_ids` | прогоны репо, которые вызов создал или изменил: снимок `(run_id, mtime run.json)` прогонов репо до и после вызова; не изменился ни один — самый свежий прогон репо с пометкой «вызов его не менял»; прогонов нет — пусто |
| `cause` | причина (ниже) |
| `cwd_repo` | slug `origin` репо |

**Причина** (для заголовка и отпечатка), первое найденное:

1. отказ `dfl` (`DflError`, `ConfigError`, `TargetsError`, `InitError`) —
   часть «причина» блока `refusal`;
2. `stop-reason.txt` прогона из `run_ids`, изменённого вызовом, — первая строка;
3. неперехваченное исключение — `<Тип>: <первая строка сообщения>`
   (traceback целиком — в `output_tail`); обёртка его перехватывает, пишет
   запись и пробрасывает дальше, код и вывод для коллеги прежние;
4. иначе — последняя непустая строка вывода вызова.

**Подсказка.** Строку «отчёт разработчикам: `dfl report`» печатает обёртка
`main` в stderr последней при любом ненулевом коде (не `refusal`), кроме
вызова самого `report`.

**Вывод вызова.** Главный источник — то, что коллега видел: отказ `dfl`,
сообщения раннера, стоп. Не все стопы пишут `stop-reason.txt`
(`runner.py`, комментарий у записи стопа), поэтому записи раннера недостаточно.
`dfl` дублирует **свой** вывод (`sys.stdout`/`sys.stderr` процесса — отказы,
раннер, который исполняется в процессе, перепечатанные ошибки `git`/`gh`) в
кольцевой буфер; дескрипторы 1 и 2 не трогаются.

Вывод дочерних процессов (`spec-runner`, `claude`), пишущих прямо в терминал,
в буфер **не попадает** — поправка 2026-11-12 по финальному ревью реализации.
Первый вариант (подмена fd 1/2 на pipe и потоки-читатели) давал: зависание
`dfl`, когда экран закрыт (`dfl … | head`); запись потомка, пережившего
`dfl`, в переиспользованный дескриптор; блочную буферизацию и сдвиг порядка
stdout/stderr у дочерних процессов. Цена поправки: при сбое внутри
`spec-runner` его собственный текст в отчёт не попадёт — остаются стоп
раннера, его причина и журналы прогона на машине коллеги. Запись сбоя
делается после выхода из перехвата.

## 6. Состав отчёта

Отчёт собирается в момент `dfl report` из записи сбоя и состояния машины:

1. **Заголовок:** команда, код, время, slug репо.
2. **Где остановилось:** для каждого `run_id` из записи — `status`, `wave`,
   последняя операция в `ops` (порядок вставки JSON — это порядок записи
   операций) и её статус, `pr`; текст `stop-reason.txt`, если есть.
3. **Вывод:** `output_tail` (200 строк, блок кода).
4. **Версии:** коммит devtools (`git rev-parse HEAD` установленного), пины
   `lite/components.toml` и фактические HEAD клонов компонентов, `claude --version`,
   `gh --version`, `uv --version`, `git --version`, ОС и архитектура, Python.
5. **Конфиг:** `mode` и логины `[accounts]` — без путей профилей и ключей.
   Конфиг не читается — строка «конфиг не читается: <причина>» (частый сбой
   сам по себе), отчёт всё равно собирается.
6. **Отпечаток** (§7) последней строкой.

Не входит: транскрипты (`author-transcripts/`), файлы бандла, `brief`, ответы
интервью, содержимое `answer.yaml`, переменные окружения.

**Очистка перед показом** (применяется ко всему тексту отчёта):

- домашний каталог → `~`;
- токены по образцам (`gh[pousr]_…`, `github_pat_…`, `sk-ant-…`, `Bearer …`,
  `xox[abp]-…`, строки вида `token = …`/`TOKEN=…`) → `<скрыто>`;
- обрезка до лимита тела issue GitHub (65 536 символов) с пометкой; хвост
  вывода режется первым.

Очистка — страховка, не гарантия; гарантия — показ отчёта коллеге до отправки.

## 7. Отпечаток и повторы

Отпечаток — `sha256` от (`command`, имя последней операции прогона или
`"dfl"`, первая строка «причины» отказа/стопа после нормализации: SHA,
числа, пути, URL, номера PR и кавычки с содержимым заменены плейсхолдерами),
первые 12 hex.

- Заголовок issue: `[dfl-report] <command>: <причина, до 80 символов> (fp <12hex>)`.
- Перед созданием `dfl report` ищет открытое issue в devtools с `fp <12hex>` в
  заголовке (`gh search issues` / `gh issue list --search`). Найдено —
  комментарий с отчётом; нет — новое issue.
- Метки: у коллеги нет прав в devtools, метку он поставить не может. Отчёты
  опознаются по префиксу `[dfl-report]`; метку `dfl-report` при разборе ставит
  владелец или агент (§8).

## 8. Обработка у владельца

v1 — без автомата на стороне devtools:

- Найти новые: `gh issue list --search "[dfl-report] in:title" --state open`.
- Разбор — владелец или агент по просьбе («разбери отчёты»): прочитать отчёт,
  воспроизвести, завести исправление обычным путём (issue → PR), закрыть отчёт
  ссылкой на PR, поставить метку `dfl-report`.
- Дальнейшее (вне v1, по решению владельца): плановый агент разбора на VPS,
  связка с conductor. Условие возврата — поток отчётов, который неудобно
  разбирать руками.

## 9. Оставлено исполнителю

- Точный набор образцов токенов и правил нормализации отпечатка — в коде с
  тестами на каждый образец.
- Формат тела issue (Markdown), если в нём есть всё из §6.
- Имена модулей: ожидается `lite/report.py` (сбор, очистка, отправка),
  `lite/failure_log.py` или часть `report.py` (запись сбоя и дублирование
  вывода) и правка `lite/dfl.py`, памятки
  `docs/darkfactory-for-colleagues.md` (раздел «Если что-то сломалось»).

## 10. Ограничения и что дальше

- Отчёт публичный. Для рабочих репо этот канал не годится: нужен приватный
  (приватный репо отчётов с доступом коллег или отправка файлом). Решать, когда
  появится первый коллега с рабочим репо.
- Учётка коллеги видна в issue как автор — это и есть обратная связь с ним.
- Лимиты API GitHub на создание issue у коллеги не учитываются (ручной запуск).
- Пути `make`/strict отчётов не получают.

## 11. Проверка

- Тесты: запись сбоя на ненулевом коде и её отсутствие на нулевом; дублирование
  вывода включая дочерний процесс; очистка на каждом образце токена и на
  домашнем каталоге; отпечаток стабилен при разных SHA/путях/номерах и различен
  при разной причине; поиск дубля → комментарий вместо issue; без tty — не
  отправляет; `--print` — не ходит в сеть; нет записи — код 0.
- Живая проверка: на сервере (`betta-tester`) вызвать известный отказ
  (`dfl run` без `--subject` в репо без прогонов), `dfl report` → issue в devtools,
  повтор → комментарий; закрыть оба вручную.
