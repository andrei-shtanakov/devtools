# dfl run: продолжение прогона и сиротские тест-файлы (#767)

Статус: дизайн, одобрен владельцем в обсуждении 16.11 (текст — на ревью).
Issue: devtools#767. Источник — живой прогон sdd-runer 14–15.11.

## 1. Зачем

В живом прогоне spec-runner сделал TASK-001…014 на ветке
`spec-runner/run-20261114-173445`. На TASK-015/016 он остановился: у
verify-задач в `**Verifies:**` стояли тест-файлы, которые ни одна задача
реализации не создаёт. Повторный `dfl run` создал новую ветку от `main`,
работы 001–014 в ней не было, и spec-runner отказал
(`_refuse_rerun_of_success`). Выйти удалось только тем, что человек вручную
влил ветку прогона в `main`.

Это два разных дефекта:

1. **Продолжение.** Повторный запуск не продолжает начатую ветку.
2. **Сиротские тест-файлы.** Гейт декомпозиции видит такой файл, но выдаёт
   только предупреждение. Ошибка обнаруживается лишь на исполнении, после
   трёх оплаченных попыток.

## 2. Цели, не-цели, анти-цели

**Цели**
- Повторный `dfl run` после остановки посреди реализации продолжает ту же
  ветку прогона без ручного мержа. Оба пути: личный и enterprise.
- Перед продолжением владелец видит, какой проект и какая ветка
  продолжаются и сколько задач уже сделано.
- Декомпозиция с тест-файлом, который никто не создаёт, не доходит до
  исполнения: её исправляет автор.

**Не-цели**
- Новая команда `dfl` для продолжения. Владелец решил, что продолжает
  обычный повтор `dfl run`.
- Выбор ветки из нескольких кандидатов в интерактиве.
- Правка spec-runner из этого репо (соседний репо, только issue).

**Анти-цели** (провал, даже если «работает»)
- Повтор молча создаёт новую ветку и выбрасывает сделанную работу.
- Частичный integration-PR принимается как готовый результат.
- Продолжение ветки, о которой dfl не знает наверняка, что это ветка этого
  прогона.

## 3. Дефект 1: продолжение ветки прогона

### 3.1 Что известно сейчас

- spec-runner при `--integration-pr` всегда создаёт новую
  `spec-runner/run-<время>` от main (`create_integration_branch`). Режима
  продолжения существующей ветки нет.
- При ненулевом коде spec-runner непустую ветку всё равно пушит и
  открывает по ней PR (`finalize_integration_branch`). Поэтому после
  остановки на фордже есть открытый частичный PR, и его head — это ветка
  прогона.
- dfl уже записывает этот PR как новый относительно `before`:
  enterprise — `state.ops["spec-run"]["failed_prs"]`
  (`governance/auto_tasks.py::_record_run_failure`); личный путь —
  `run.before_prs` и `run.run_exit != 0` (`lite/personal/flow.py::_step_code_run`).
  Сейчас этот PR просто добавляется в `before` и игнорируется.

### 3.2 spec-runner (issue, не правка)

Issue заведён: spec-runner#678 (ai-prosto). Просьба: способ запустить
`run --all --integration-pr` на **существующей** ветке прогона, например
флаг `--integration-branch=<ветка>`. Ожидаемое поведение:
- ветка берётся как есть (локально или с remote), новая не создаётся;
- задачи, отмеченные done в tasks.md этой ветки, не выполняются заново;
  отказ `_refuse_rerun_of_success` при этом не срабатывает, потому что
  tasks.md читается с этой ветки;
- в конце ветка пушится и используется **уже открытый** PR по ней, а не
  открывается второй;
- ветка, которой нет, — отказ с понятной причиной, без форка.

Точный интерфейс решает spec-runner. dfl потребляет его, когда он выйдет.

### 3.3 dfl: обнаружение и плашка

На повторе шага запуска spec-runner (оба пути) dfl ищет незавершённую
ветку прогона:
- кандидат — открытый `spec-runner/run-*` PR, которого нет в записанном
  `before` прошлой попытки, при записанном ненулевом коде этой попытки.
  Одно правило для обоих путей (общий помощник): на личном пути это
  `run.before_prs` + `run.run_exit`, на enterprise — `before` + `exit` записи
  `ops["spec-run"]`. На `failed_prs` не опираемся: между записью `exit` и
  `failed_prs` возможен обрыв. Запись прошлой попытки не перетирается,
  потому что при найденном кандидате раннер не запускается (`op_start` не
  зовётся);
- ветка прогона = head этого PR; принимается, только если начинается с
  `spec-runner/run-`;
- кандидатов больше одного — стоп с перечнем, без выбора за владельца
  (из одной попытки новый PR один, так что это аномалия, а не штатный
  случай);
- PR закрыт — это решение человека начать заново (так велят и нынешние
  тексты остановок: «закройте его и повторите»): продолжения нет, обычный
  запуск, как сейчас;
- код прошлой попытки не наблюдён (`exit` не записан) — прежнее поведение
  без изменений: стоп «PR может быть частичным, закройте и повторите».

Чтение tasks.md для счётчика — через `Ops.show_file` по ref ветки PR
(remote-tracking, после `fetch` этой ветки). Путь tasks.md — тот же, по
которому его находит остальной код прогона. Не прочитан по любой причине,
включая сбой `fetch`, — плашка без счётчика.

Найдя ветку, dfl печатает плашку (форма — решение владельца):

```
▶ продолжаю проект «<subject>» · <repo_slug>
  ветка <ветка> · сделано N из M задач
```

- `subject` и `repo_slug` берутся из состояния прогона (они есть в обоих:
  `RunState`, `PersonalRun`).
- N из M считается по tasks.md на этой ветке: M — все задачи, N —
  отмеченные done. Если tasks.md не прочитан, строка выходит без счётчика
  («ветка … · счётчик задач не прочитан»), прогон из-за этого не стоит.

### 3.4 dfl: что делает после плашки

- **spec-runner умеет продолжать** (вышел интерфейс из 3.2): dfl передаёт
  ему ветку. Результатом считается тот же PR: при коде 0 он принимается
  как integration-PR прогона, при ненулевом коде — запись и стоп, как
  сейчас.
- **Пока не умеет** (сейчас): dfl после плашки останавливается и объясняет:
  продолжить ветку пока нельзя, новую ветку он не создаёт, чтобы не
  потерять сделанное. В тексте — что сделать вручную (влить ветку прогона
  в main и повторить `dfl run`; либо закрыть PR, чтобы начать заново) и
  ссылка на spec-runner#678. Механизм и код выхода — существующие
  остановки путей (`ctx.stop` на личном, `_stop` на enterprise), нового
  кода нет.

Как dfl узнаёт, что spec-runner умеет продолжать (проверка версии, флага в
`--help` или пин), — решает исполнитель, когда интерфейс будет известен.
Пока его нет, сделана только ветка «не умеет».

## 4. Дефект 2: сиротские тест-файлы

### 4.1 Что сейчас

`decomposition_guard._orphan_verifies_findings` находит элемент `verifies`,
который не является целью `checked_by` ни одной задачи. Сейчас это
non-fatal находка: `non_fatal_findings` → `warning GC-DT-GRAPH` в
gate-findings.txt (`governance/runner.py` ~4235), прогон не останавливается.
Фатальная проверка замыкания (`graph_findings`) покрывает только файлы, у
которых владелец есть. Сирота останавливает гейт только косвенно — когда у
задачи не остаётся ни одной исполнимой цели («группа наблюдения не
выводится»). Если рядом есть другие цели, как у DT-15/DT-16, сирота
проходит.

Предупреждением это сделали ради старых бандлов, где у файла есть цель
`checked_by`, но нет `verifies`. К сироте этот довод не относится: такой
файл не появится никогда.

### 4.2 Решение (владелец 16.11)

- Сиротский путь в `verifies` — **ошибка гейта** в `graph_findings`. Так
  он ловится на обоих путях: enterprise (`_step_gate`, `task_bridge.deliver`)
  и личном (`lite/personal/check.py` → круг `_fix_invariants`).
- Текст ошибки называет задачу, файл и оба исправления: дать файл задаче
  реализации через `checked_by` её сценария или убрать его из `verifies`.
- **Исправляет автор сразу**, как другие ошибки графа, без вопроса
  владельцу: enterprise-прогон стоит на гейте и переписывает узел, личный
  путь — тем же кругом `_fix_invariants`.
- Срез `::`-селектора перед сверкой сохраняется.
- Второй вызывающий `graph_findings` — `task_bridge.deliver`: повторная
  доставка старого бандла с сиротой теперь тоже откажет. Это верно: такой
  бандл всё равно упал бы на исполнении. Довод «старые бандлы» в
  комментариях относился к `checked_by` без `verifies` — его не трогаем,
  комментарии про предупреждение о сироте поправить.
- Личный путь зовёт `graph_findings(checks, whole)` с разделом «## Проверки»
  в роли текста поведения. Привязки `checked_by` должны разбираться из него
  так же; это проверяет тест личного пути из 4.3, а не предположение.
- `non_fatal_findings` и вывод `warning GC-DT-GRAPH` после этого не нужны;
  убрать их или оставить пустыми — решает исполнитель (меньше кода лучше).

### 4.3 Тесты

- Регрессия на форме sdd-runer: verify-задача (как DT-15/DT-16) с файлами в
  `verifies`, которых нет ни в одном `checked_by` → `graph_findings` не
  пуст, текст содержит задачу и путь.
- Файл с `::test`-селектором, владелец которого в бандле есть, —
  находки нет.
- Личный путь: сирота уходит в `_fix_invariants`, а не в исполнение.

## 6. Решения, принятые мной (проверьте)

- Кандидат на продолжение — только PR, который dfl сам записал как
  частичный в этом прогоне; ветки, найденные иначе (по префиксу на
  фордже), не продолжаются. Причина — анти-цель «не продолжать чужую
  ветку».
- Если tasks.md на ветке не прочитан, плашка выходит без счётчика, а не
  останавливает прогон.
- Несколько кандидатов — стоп, а не выбор последнего.
- Кандидат — по записанному `before` и коду прошлой попытки, не по
  `failed_prs`.
- Закрытый частичный PR = решение человека начать заново.
- Старый бандл с сиротой при повторной доставке тоже откажет.

## 7. Решения владельца (16.11)

- Продолжает обычный повтор `dfl run`, отдельной команды нет.
- Плашка — и тема, и репо, в форме из 3.3.
- Сирота в `verifies` — ошибка гейта; исправляет автор сразу, без вопроса.
- Остановка при открытом частичном PR — **всегда**, без порога «сделана
  хотя бы одна задача». Начать заново — закрыть PR. Это заменяет нынешнее
  «повтор перезапустит раннер» для случая ненулевого кода с частичным PR;
  тексты и тесты, которые это утверждают, меняются.
