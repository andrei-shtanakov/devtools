## 0. Цель и границы

R16 — еженедельная проверка утверждений KB о коде, на который они ссылаются
(claim-level freshness). Сейчас она крутится на ноутбуке: launchd запускает
её догоняющим способом из `_cowork_output/`. Если ноутбук выключен, вторник
пропускается. Цель — выпустить раннер в devtools как код репо и исполнять
его на VPS, который включён всегда.

Критерии успеха:
1. runtime-код раннера живёт в devtools и не читает и не импортирует
   `_cowork_output/`;
2. схема квитанции — контракт devtools, который Robin может вендорить
   закреплённой копией;
3. раннер исполняется на VPS со своими клонами, доступными на запись;
   квитанции лежат в собственном каталоге состояния, Robin его только читает;
4. в каждый момент активен ровно один исполнитель; право создавать и
   обновлять issue передаётся Mac → VPS в названной точке (§2.2);
5. логика циклов, попыток, пропусков и доставки переносится без изменения
   поведения, кроме перечисленного в §1.2.

Вне объёма:
- **публикация квитанций исполнителей не с VPS** (acceptance 5 заявки,
  машинная ветка devtools). Решение владельца 2026-09-25: отложить.
  Квитанции пишет только VPS. Заводится отдельным пунктом с триггером
  «появился исполнитель не с VPS»;
- проверка ожидаемого цикла и Telegram в Robin — отдельная заявка в
  robin-runtime;
- само развёртывание на VPS делает владелец (доступ). Здесь — артефакты и
  чек-лист к нему.

### 1.2. Отличия `r16_runner.py` от `run.py`

Всё прочее переносится без изменения поведения.

1. **Корни — из конфигурации, не из `__file__`.** Три обязательных значения:

   | аргумент CLI | переменная окружения | на VPS |
   |---|---|---|
   | `--workspace` | `R16_WORKSPACE` | `/srv/r16/workspace` |
   | `--state-dir` | `R16_STATE_DIR` | `/srv/r16/state` |
   | `--gh-config-dir` | `R16_GH_CONFIG_DIR` | `/srv/r16/gh` |

   И одно обязательное значение-метка: `--host-label` / `R16_HOST_LABEL`.
   CLI побеждает окружение. Все четыре проверяются ДО любого действия
   (до блокировки, pull, аудита): отсутствие значения, отсутствие
   каталога, отсутствие `prograph-vault/scripts/kb_freshness.py` под
   workspace, отсутствие в каталоге профиля gh файла `hosts.yml`,
   читаемого текущим пользователем, дают exit 2 без квитанции. Это
   проверка **наличия конфигурации** — локальная, без сети. Авторизацию
   (действует ли токен ai-prosto) раннер при старте не проверяет: её
   сбой — сеть и GitHub, он проявляется при доставке как
   `delivery: failed`. Перед включением сервиса авторизацию проверяет
   владелец отдельной командой (`gh auth status`, §2.2 шаг 1).
   Производные пути: квитанции — `<state-dir>/receipts/`, блокировка —
   `<state-dir>/r16.lock`. Блокировка лежит вне `receipts/`, чтобы у
   группы читателей не было к ней доступа.
2. **Зона цикла закреплена в коде.** Константа `CYCLE_TZ = "Asia/Tbilisi"`,
   через `zoneinfo`. Это не настройка окружения. Цикл — от вторника 09:30
   по этой зоне до следующего вторника 09:30, при любой системной зоне
   машины. Если `ZoneInfo` не находит зону, exit 2 до любых действий
   с указанием, что поставить (`tzdata`). Все метки времени, которые
   пишет раннер, — ISO 8601 со смещением.
3. **Перед аудитом — клон vault приводится к опубликованной ветке и это
   проверяется.** Аудит читает заметки из своего клона vault
   (`kb_freshness.py` сам fetch'ит только репо-опоры), поэтому клон должен
   совпадать с origin. Успешный `pull --ff-only` этого не гарантирует:
   локальные коммиты впереди upstream и незакоммиченные изменения
   переживают его. Поэтому:
   1. ветка по умолчанию берётся у origin (`git ls-remote --symref origin
      HEAD`, как у самого аудитора, а не из возможно устаревшего
      локального `origin/HEAD`);
   2. `git pull --ff-only origin <ветка>`;
   3. проверка: текущая ветка — `<ветка>`; `HEAD` равен
      `refs/remotes/origin/<ветка>` после fetch; `git status --porcelain
      --untracked-files=all` пуст. Неотслеживаемые файлы тоже в счёт:
      аудит сканирует `authored/` на диске, и лишняя заметка попала бы в
      проверку.

   Любой сбой шагов 1–3 (сеть, расхождение истории, не та ветка, HEAD
   впереди, грязное дерево) даёт попытке `execution: failed`, причину в
   `audit_tail`, доставку `skipped`. Аудит не запускается: читать
   заметки не опубликованного дерева — ровно то, от чего защищает
   `--target published`. Грязное дерево раннер не чистит сам: это
   чьё-то изменение, и решать о нём владельцу.

   `--dry-run` выполняет и pull, и проверку: он меняет только клон, а не
   квитанции и не issue. Без этого пробный прогон проверял бы не то дерево,
   которое прочтёт боевой.
4. **`producer.host`.** Квитанция называет исполнителя (`--host-label`).
   Это единственный способ задним числом увидеть, что квитанции писали
   двое.
5. **Указатель в issue.** Последняя строка тела issue:
   `Квитанции прогонов: <host-label>:<state-dir>/receipts/<cycle_id>.json`.
   Это указатель для оператора, не общедоступная ссылка; путь абсолютный.
6. **Блокировка — требование, а не деталь.** `flock` берётся на
   `<state-dir>/r16.lock` и держится весь запуск: pull, аудит, доставку в
   GitHub, запись квитанции. Второй одновременный запуск выходит сразу
   (exit 0, «another run holds the lock») и ничего не пишет. `decide()`
   защищает от последовательных повторов, блокировка — от одновременных.
   Пересечение Mac и VPS (у них разные файлы блокировки) закрывается не
   блокировкой, а порядком передачи (§2.2).

### 1.3. На VPS

Хост тот же, что у Robin (решение владельца 2026-09-25), пользователь свой —
`r16`. Раскладка:

```
/srv/r16/           r16:r16-readers 0710  ← группе только проход
├── devtools/       r16:r16         0700  ← код раннера; обновляется руками
│                                           (pull --ff-only), сам себя не обновляет
├── workspace/      r16:r16         0700  ← клоны с правом записи: prograph-vault +
│                                           все репо из workspace-manifest.toml
│                                           по каноническим именам; аудит ищет
│                                           репо-опоры как соседей vault
├── state/          r16:r16-readers 0710  ← группе только проход
│   ├── r16.lock    r16:r16         0600
│   └── receipts/   r16:r16-readers 2750  ← setgid; файлы 0640, подкаталоги 2750
├── gh/             r16:r16         0700  ← GH_CONFIG_DIR профиля ai-prosto;
│                                           файлы 0600
└── r16.env         r16:r16         0600  ← EnvironmentFile
```

Права:
- `robin` входит в группу `r16-readers`. Через `/srv/r16` и `state/` у
  группы есть только проход (`x`), без листинга. Читать можно только
  `receipts/`. К `devtools/`, `workspace/`, `gh/`, `r16.env`, `r16.lock`
  у группы доступа нет;
- `setup.sh` выставляет всю таблицу явно и создаёт `r16.lock` сам с
  режимом 0600. Раннер открывает уже существующий файл и режим не меняет;
- новые квитанции наследуют группу через setgid каталога. `UMask=0027` в
  юните даёт им режим 640. Запись идёт через `tmp` + `replace` в том же
  каталоге, так что права и группа у заменённого файла те же;
- `setup.sh` клонирует репо по каноническим именам из
  `workspace-manifest.toml` (урок переименований 2026-07-16: каталог по
  старому имени Robin не видел молча). Репо, которого нет в workspace, аудит
  отметит `unverified` («no checkout»), и это станет находкой в issue.

Таймер: `OnCalendar=hourly`, `Persistent=true`. `decide()` делает
повторный запуск безопасным: успех → `done`, три провала → `gave-up` до
следующего цикла. Так сохраняются попытки по часу, как было на Mac.

## 2. Перенос и миграция

### 2.1. Что переносится и почему это и есть состояние

Переносится каталог `_cowork_output/cadence/r16/receipts/` целиком,
включая `legacy/`. Раннер видит только файлы верхнего уровня
`????-??-??.json`, остальное — история. От квитанций зависит всё
состояние раннера:
- `decide()` читает квитанцию текущего цикла. Если на Mac была попытка 2
  из 3, VPS продолжает с попытки 3, а не начинает заново;
- `last_issue()` берёт номер issue из самой свежей квитанции, где он
  указан. Так VPS обновит существующее issue, а не заведёт дубль (индекс
  `gh issue list` отстаёт в обе стороны — prograph-vault#157–#161);
- `latest_cycle()` задаёт нижнюю границу для пометки `missed`.

Отсюда условие: снимок квитанций делается **после** того, как Mac
остановлен. Иначе Mac успеет записать попытку, которой на VPS не будет.

### 2.2. Передача права на issue

Оба исполнителя пишут от одного аккаунта ai-prosto, и GitHub их не
различает. Поэтому передача — это последовательность, в которой в каждый
момент активен не больше чем один исполнитель:

1. **VPS готов, но не запущен.** `setup.sh` поставил пользователя,
   группу, клоны, профиль gh, `r16.env` и юниты. Таймер установлен, но
   **не включён**. Проверки от `r16`:
   - `r16_runner.py --dry-run` — pull vault и полный аудит, без квитанции и
     без issue. Доказывает, что есть клоны, fetch и зона;
   - `GH_CONFIG_DIR=/srv/r16/gh gh auth status` и
     `gh issue list -R andrei-shtanakov/prograph-vault --label kb-freshness`
     — профиль ai-prosto читается. Пробный прогон gh не вызывает: доставки
     в нём нет.
2. **Mac остановлен.**
   `launchctl bootout gui/$UID/dev.atp.r16-kb-freshness`, plist удаляется
   из `~/Library/LaunchAgents`. Прогон не идёт, если блокировка
   `_cowork_output/cadence/r16/receipts/.lock` захватывается без ожидания
   (`flock -n`). Тем же шагом в `_cowork_output/ops/r2-liveness-check.sh`
   выключается блок R16 (§2.4). С этого момента ни один исполнитель не
   активен.
3. **Снимок.** Каталог квитанций копируется в `/srv/r16/state/receipts/`
   **без переноса прав с Mac**: `rsync -rt --no-perms --no-owner
   --no-group` (переносятся только содержимое и время). Затем права
   восстанавливаются явно, `legacy/` включительно:
   `chown -R r16:r16-readers receipts`, каталоги `2750`, файлы `0640`.
   Сверяются список файлов и sha256 на обеих сторонах, после чего
   `sudo -u robin cat` одного файла верхнего уровня и одного из
   `legacy/` проходит.
4. **VPS включён.** `systemctl enable --now r16-kb-freshness.timer`.
   Право создавать и обновлять issue переходит к VPS **ровно здесь**.
   Первый прогон делает то, что решит `decide()` по перенесённой
   квитанции текущего цикла.
5. **Приёмка:** первая квитанция, записанная на VPS, несёт
   `producer.host = <VPS>`, группу `r16-readers` и режим 640 (§4.4).

Пропуск между шагами 2 и 4 безопасен: догоняющая логика запустит
текущий цикл при первом срабатывании таймера.

### 2.3. Откат

Шаги в обратном порядке с тем же условием — активен не больше чем один:
1. `systemctl disable --now r16-kb-freshness.timer`. Это запрещает только
   **новые** запуски: уже идущий прогон продолжает писать;
2. дождаться, пока `systemctl is-active r16-kb-freshness.service`
   вернёт `inactive`, и проверить, что блокировка свободна:
   `sudo -u r16 flock -n /srv/r16/state/r16.lock true` проходит. Пока
   любое из двух не выполнено, состояние не переносится;
3. квитанции скопировать обратно на Mac (они новее) тем же способом, что
   на шаге 3 передачи: без переноса прав, со сверкой sha256;
4. только затем вернуть plist и `launchctl bootstrap`.

### 2.4. Сторож на Mac и названная дыра

`_cowork_output/ops/r2-liveness-check.sh` читает квитанции R16 с Mac-пути.
После шага 4 он каждый вторник поднимал бы ложную тревогу. Решение
владельца 2026-09-25: блок R16 сторожа выключается на шаге 2, **без
замены**. Дыра названа: до появления проверки ожидаемого цикла в Robin
(отдельная заявка в robin-runtime) живость R16 автоматически не
проверяет никто. Пропущенный цикл всё равно станет виден: следующий
прогон пометит его `missed`, и квитанция это сохранит.

Правка сторожа — в `_cowork_output/` (dev-only), её делает владелец на шаге
2; этот репо её не несёт.

## 3. Контракт квитанции и отказы

### 3.1. `contracts/r16-receipt/v1/schema.json`

JSON Schema draft 2020-12, `additionalProperties: false` на всех уровнях.
Две формы через `oneOf` по `execution`: выполненная попытка
(`completed`/`failed`) и `missed`.

| поле | форма | где |
|---|---|---|
| `schema_version` | `1` | обе |
| `check_id` | `"r16-kb-freshness"` | обе |
| `cycle_id` | `YYYY-MM-DD` (вторник) | обе |
| `attempt` | `0` у missed; `1..3` у выполненной | обе |
| `started_at`, `finished_at` | ISO 8601 | выполненная |
| `noted_at` | ISO 8601 | missed |
| `target` | `"published"` | выполненная |
| `producer.runner`, `producer.auditor` | SHA коммита (возможно с суффиксом `+dirty`) или null | выполненная |
| `producer.host` | метка исполнителя из `--host-label` (не SHA): непустая строка | выполненная |
| `revisions` | `{repo: SHA или текст ошибки}`; у missed — `{}` | обе |
| `coverage` | `{notes, with_evidence, unparsed_frontmatter}` — целые, каждый необязателен | выполненная |
| `statuses` | `{статус: целое}` | выполненная |
| `problems` | `{claims, revisions, coverage}` — целые | выполненная |
| `execution` | `completed` \| `failed` \| `missed` | обе |
| `delivery.action` | `created` \| `updated` \| `closed` \| `not-needed` \| `skipped` \| `failed` \| `not-run` \| `dry-run` | обе |
| `delivery.issue` | целое или null | обе |
| `delivery.issue_url`, `delivery.error` | строка или null | обе |
| `audit_tail` | строка у `failed`, null у `completed` | выполненная |
| `ok` | true только при `execution: completed` и доставке не `failed`/`skipped`; у missed — false | обе |

Метка времени без смещения (перенесённые квитанции Mac) означает
`Asia/Tbilisi`. Раннер devtools пишет только метки со смещением.

Квитанции с `delivery.action: dry-run` раннер не записывает (пробный
прогон только печатает запись); значение в схеме есть, потому что
напечатанная запись тоже должна быть валидна.

### 3.2. Правила чтения (`README.md`, их вендорит Robin)

- «Цикл закрыт» = файл `<cycle_id>.json` с `ok: true`.
- `missed` означает «цикл никто не запускал», а не «прошёл без находок».
- `ok: false` при `attempt < 3` — цикл ещё может закрыться; при
  `attempt = 3` — раннер сдался до следующего цикла.
- `problems` > 0 при `ok: true` — нормальный исход: находки доставлены в
  issue.

Эволюция. Схема закрыта (`additionalProperties: false`), и Robin
держит закреплённую копию. Поэтому **любое** изменение формы, даже новое
необязательное поле, — это новая версия: закреплённый валидатор v1
отвергнет незнакомое поле. Порядок:
1. в devtools рядом с `v1/` появляется `v2/`; `v1/` не меняется;
2. потребитель (Robin) вендорит `v2/` и принимает обе версии;
3. только после подтверждения потребителя раннер начинает писать
   `schema_version: 2`.

`schema_version` в квитанции всегда равен номеру каталога, по которому
она валидна.

### 3.3. Отказы

Все fail-closed; ни один не даёт молчаливого успеха.

| ситуация | исход |
|---|---|
| не задан обязательный путь или метка, нет каталога, нет аудитора, нет читаемого `hosts.yml` в профиле gh, нет зоны | exit 2 до блокировки; квитанции нет — это конфигурация, не попытка |
| блокировка занята | exit 0, «another run holds the lock», ничего не пишется |
| vault не приведён к опубликованной ветке (сбой pull, не та ветка, HEAD впереди origin, грязное дерево) | `execution: failed`, причина в `audit_tail`, доставка `skipped`, аудит не запускается, попытка засчитана |
| токен gh недействителен | прогон `completed`, `delivery: failed` (как любой сбой gh при доставке) |
| аудит не дошёл до summary | `execution: failed`, доставка `skipped` (как в `run.py`) |
| сбой отдельного репо в аудите | прогон `completed`, ошибка в `revisions`, находка в issue |
| сбой gh при доставке | `completed` + `delivery: failed`, `ok: false`; повтор через час, счётчик растёт |
| три неудачи в цикле | `gave-up` до следующего цикла; видно по `attempt: 3, ok: false` |

Почему сбой pull — попытка, а ошибка конфигурации — нет: сеть проходит
сама, и повтор через час имеет смысл. Конфигурацию повтор не лечит, и
засчитанные попытки только сожгли бы цикл.

## 4. Проверки

### 4.1. Перенос без ослабления

27 тестов `test_run.py` переезжают в `tests/test_r16_runner.py`. Сначала —
отдельным коммитом — они адаптируются только по импорту и путям и
прогоняются на дословной копии `run.py`. Так видно, что перенос тесты не
ослабил. Затем тот же набор идёт на `r16_runner.py`, и правки §1.2
появляются вместе со своими новыми тестами.

### 4.2. Новые тесты

- зона: цикл считается по `Asia/Tbilisi` при системной зоне `UTC`
  (граница вторника 09:30 со стороны обеих зон); отказ exit 2, если
  `ZoneInfo` не находит зону;
- конфигурация: CLI побеждает окружение; отсутствие каждого из четырёх
  значений даёт exit 2 **до** блокировки (файла `r16.lock` не появляется);
- vault: каждый из случаев — сбой pull, не та ветка, локальный коммит
  впереди origin, изменённый отслеживаемый файл, неотслеживаемый файл —
  даёт `failed` + `skipped`, и аудит не вызывается. Проверяется на
  настоящих git-репо во временном каталоге (bare origin + клон), а не на
  заглушке git;
- конфигурация профиля gh: нет `hosts.yml` → exit 2 до блокировки;
  действительность токена раннер не проверяет, и тест это фиксирует:
  без сети старт не падает;
- `producer.host` берётся из метки;
- одновременный запуск: при удерживаемой блокировке второй запуск
  выходит 0 и не создаёт и не меняет ни одного файла в `receipts/`;
- указатель в issue: `<host-label>:<state-dir>/receipts/<cycle_id>.json`;
- схема: каждая квитанция, которую пишут тесты раннера, проходит
  `schema.json`; три примера из `examples/` проходят; мусорное поле и
  чужое значение `execution` отвергаются.

Валидатор схемы в тестах — зависимость только тестовой группы; раннер
остаётся stdlib-only.

### 4.3. Мутации

Каждая краснит свой тест: зона взята системная; pull после аудита или
без проверки результата; снята проверка HEAD = origin; снята проверка
чистого дерева (отдельно отслеживаемые и неотслеживаемые); блокировка
отпущена до доставки; `attempt` не переносится из существующей
квитанции; `producer.host` не пишется.

### 4.4. Приёмка развёртывания (чек-лист `deploy/r16/README.md`, владелец)

1. `sudo -u r16 … r16_runner.py --dry-run` на VPS — completed, квитанций и
   issue нет; `gh auth status` из профиля — ai-prosto (§2.2 шаг 1).
2. Права — по таблице §1.3, проверка `stat` каждой строки. От `robin`:
   `cat` квитанции верхнего уровня и квитанции из `legacy/` проходит;
   `ls /srv/r16`, `ls /srv/r16/gh`, `cat /srv/r16/r16.env`,
   `cat /srv/r16/state/r16.lock`, `ls /srv/r16/workspace` отказывают.
3. Шаги 2–4 передачи (§2.2), со сверкой sha256 на шаге 3.
4. Первая квитанция, записанная на VPS: `producer.host`, группа
