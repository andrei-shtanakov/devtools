## 0. Зачем

Одобренные и запиненные по байтам узлы `15-behaviour-spec` и `25-acceptance` —
оракул, зафиксированный ДО кода (§I12, волны `sequential-node-approval`).
Прецедент честного оракула — disputatio D1/D6: инварианты `INV-NN` зафиксированы
до диффа, поэтому вердикт по диффу честен.

Сверху вниз адресуемые ID уже есть и частично проверяются: бриф `G-NN/FR-NN` →
требования `FR/NFR-NN` (+ `Priority`) → `BEH-NN` (`traces`, `checked_by`;
steward GC-BEH-TRACE/COVERAGE/CHECK-PLANNED) → `AC-NN` (`verification`,
`traces`, `scenarios`; `acceptance_guard`) → `DT-NN` (`scenarios`,
`delivers[].sources`; `decomposition_guard`). Ниже декомпозиции цепочка рвётся:

1. мост (`task_bridge.py`) сворачивает BEH в `**Traces to:** [FR-..]`, BEH
   остаётся прозой чек-листа;
2. evidence исполнения ключуется TASK-ID/селектором — критерий не назван;
3. `checked_by: planned → materialized` не продвигает никто;
4. ID не квалифицированы: чужой `BEH-09` удовлетворяет `scenarios.py`;
5. парсеры расходятся: steward — виды `atp|contract|integration|e2e|manual`
   без `[a-z]`, реальные бандлы пишут `kind: unit`; `acceptance_guard`
   понимает только `Must`/`Should`, реальный бандл объявляет `Could`
   (`executable-negative-control…/10-requirements.md` FR-12).

Живой прогон волн 22.09 (`docs/evidence/2026-09-22-waves-live-run.md`) показал
цену: критерий, проверяемый чтением исходника, не краснеет.

**Цель.** После исполнения задач отдельный акт приёмки отвечает на вопрос «какие
критерии подтверждены чем» на продуктовом SHA; неподтверждённый Must — приёмки
нет.

**Жизненный цикл (Р1).** Раннер документов (`governance/runner.py`, `_STEPS`:
интервью → авторинг → гейт → edge-check → candidate → finalize) одобряет
**документы**; к его finalize кода продукта ещё нет. Мост в задачи — отдельная
команда после `completed`, tasks-спека рождается `draft` и исполняется
spec-runner после одобрения человеком. Закрытие — **третья, отдельная**
команда после исполнения (§3). Жизненный цикл раннера документов не меняется.

**Вне объёма.** Смысловая проверка реализации против текста критерия (edge-check
«тесты и код ← задача») — отдельный этап; эта спека даёт ему адресуемость.
Машинная грамматика `metric` — следующий этап (стенд замеров). Не-Python тесты —
отдельное решение. Связь патча со смыслом BEH не проверяется (§4.1, граница).

## 1. Грамматика и токен

### 1.1 Код воркстрима и схема charter

`00-charter.md` получает frontmatter `schema: 2` и `code: <CODE>`,
`CODE` = `^[A-Z]{2,6}$`; в схеме 2 `code:` обязателен. Мост и шаблоны генерируют
charter схемы 2. Код неизменяем: гейт отвергает правку `code:` в любом PR,
включая `--reopen` charter.

### 1.2 Реестр кодов

`workstreams/codes.toml` репо-владельца бандла — только растёт:

```toml
[ENC]
workstream = "executable-negative-control-under-standard-20260921"
approved = 2026-09-21
```

Гейт реестра (devtools, новый `charter_guard`):

- каждый ключ реестра базы присутствует в голове с тем же `workstream` —
  удаление и переназначение запрещены;
- код charter схемы 2 есть в реестре и указывает на свой воркстрим;
- уникальность нового кода — по всему реестру, не по живым каталогам (иначе код
  закрытого воркстрима достался бы новому вместе с его тестами); историю git не
  берём — CI делает checkout `fetch-depth: 1`;
- два одновременных PR с одним новым кодом ловят парсер TOML (повторный ключ —
  ошибка разбора) и гейт, который гоняется и на push в default ветку.

### 1.3 Квалифицированный ID и токен

Вне бандла ID пишется `<CODE>:<ID>` (`ENC:BEH-03`, `ENC:AC-07`); внутри
документов бандла — коротким. Совпадение —
`(?<![A-Za-z0-9_])ENC:BEH-03(?![A-Za-z0-9_])`: `XENC:BEH-03`, `ENC:BEH-030`,
`ENC:BEH-03a` не совпадают.

### 1.4 Владение токеном (Python)

Токен принадлежит **наиболее вложенному** определению теста, в чьей области он
стоит. Область определения считается по строкам исходника (комментарии в AST не
видны), `ast` даёт границы:

- область функции/метода: от первого декоратора (`decorator_list[0].lineno`,
  иначе `lineno`) до `end_lineno`, **минус** диапазоны вложенных `def`/`class`;
- область класса: его декораторы, заголовок, docstring и тело **вне** диапазонов
  вложенных функций и классов. Токен области класса засчитывается всем его
  тест-методам; токен метода в класс не поднимается и соседям не достаётся;
- шапка модуля и соседние определения — не засчитываются;
- параметризация: токен функции относится ко всем её собранным селекторам;
- один тест может нести несколько токенов, у BEH — несколько тестов.

Токен в не-Python файле или язык тестов репо не Python — бандл
`not-applicable: language` (§3.6), не молчаливый ноль.

### 1.5 Приоритет

Словарь один на все парсеры: `Must | Should | Could | Won't` (steward уже
распознаёт все четыре; devtools `acceptance_guard` сводится к нему, §5).
Приоритет BEH и AC выводится по их `traces` в `FR/NFR`: максимум по
трассируемым пунктам (`Must > Should > Could > Won't`). Пустой или
неразрешимый `traces` — `error` (блокирует). Исход по приоритету — §3.3.

### 1.6 Исполняемость критерия

| критерий | вид | статус закрытия |
|---|---|---|
| BEH | `checked_by` исполняемого вида (`unit`, `integration`, `contract`, `e2e`, `atp`) | test-критерий (§4) |
| BEH | `kind: manual` | `human`: Given/When/Then как наблюдаемый знак (Р2) |
| BEH | `status: waived` | `waived`: основание waiver дословно из бандла (Р2) |
| AC | `verification: test` | выводится devtools из статусов его `scenarios` (§5.2); пустой `scenarios` — `error` |
| AC | `verification: manual \| metric` | `human`: наблюдаемый знак, источник порога |

Выход «сценарий не проверяется тестом» — `--reopen` 15-behaviour-spec со сменой
`kind` на `manual` и повторным одобрением; критерий уходит в человеческий
чек-лист, а не пропадает.

## 2. Исполнение

### 2.1 Мост в задачи (devtools, `task_bridge.py`)

- Для задачи с `scenarios` в DT — строка `**Scenarios:** ENC:BEH-03, ENC:BEH-04`.
  `**Traces to:**` — как есть.
- Для каждого контроля задачи — отдельная строка с **собственным маркером**
  `**Criterion-control:** ENC:BEH-03 :: <patch-path> :: <selector>` (провод
  DT→tasks v3). Маркер v2 `**Negative-control:**` (две части, только при
  `tdd_waiver`) не меняется — разбор не угадывает версию по числу частей.
  Строки v3 повторяемы, spec-runner копит их списком.
- Обе строки выдаются только при запиненной версии spec-runner ≥ минимальной из
  `contracts/criteria-closure/v1/min-spec-runner.env`; иначе закрытие даёт
  `not-applicable: spec-runner-version` (§3.6).
- Пункты чек-листа исполнителю (токен внутри определения теста, патч только в
  продуктовом коде) — **подсказка**: правило держат гейт задачи и закрытие.

### 2.2 Negative control на каждый test-BEH (Р4) — DT v3

Доказательство способности упасть — только negative-control патч, заново
исполняемый при закрытии на продуктовом SHA с гарантиями §4.1. Красный чекпоинт
TDD — практика исполнения, не доказательство для оракула.

Грамматика DT (devtools `decomposition_guard`, DT → v3): у задачи любого типа
(`implement`, `verify`) — список `negative_controls: [{scenario: BEH-03,
selector: <sel>}]` **без** `tdd_waiver`; пара v2 `tdd_waiver` ⇔
`negative_control` сохраняется. Правила guard:

- каждый test-BEH (§1.6), на который ссылается хотя бы один не-Won't AC, покрыт
  ровно одной записью (§3.3: такие BEH измеряются независимо от своего
  приоритета);
- запись стоит в задаче, в чьих `scenarios` есть этот BEH — владелец патча
  однозначен;
- `selector` — информационная подсказка исполнителю; множество селекторов BEH
  при закрытии задаётся токенами (§1.4), подсказка его не ограничивает и на
  статус не влияет.

Путь патча — `spec/negative-controls/<ws-id>/<CODE>-<BEH>.patch`, выводит мост;
патч коммитится задачей-владельцем.

### 2.3 spec-runner во время исполнения (заявка, §6)

`scenarios.py` — квалифицированный токен и владение по §1.3–1.4. Гейт задачи
для не-waived `implement`/`verify` (отдельная проводка, не через
`waiver_applied`): объявленный BEH несёт хотя бы один тест группы; файл патча
есть на коммите задачи; измерение с гарантиями §4.1 на коммите задачи даёт
`confirmed`. Ранний сигнал исполнителю — оракул мерит заново при закрытии.

## 3. Закрытие — контракт A: автомат попыток (Р1)

### 3.1 Команда, попытки, идентичность

`make criteria-close ARGS='--run <id прогона бандла> [--new-attempt]
[--product-sha <sha>]'` (devtools, `governance/criteria_close.py`). Состояние —
`out/criteria-close/<run-id>/`, список **попыток**; у попытки неизменяемая
идентичность `(run_id, attempt, bundle_pin, product_sha)`:

- `bundle_pin` — пин одобрения последней волны прогона бандла (`completed`);
  замыкание узлов (charter, requirements, 15, 25, 30) читается по нему из
  git-объектов, недоступный байт — отказ шага;
- `product_sha` — `--product-sha` или голова default-ветки в момент создания
  попытки; обязан быть предком живой верхушки default-ветки
  (`git merge-base --is-ancestor`), иначе создание отказывает; после записи не
  меняется;
- `--new-attempt` — единственный путь к новому SHA; на уже измеренной паре
  `(bundle_pin, product_sha)` **запрещён** (переброс до удачи); прежняя
  незавершённая попытка → `superseded`; после `accepted` запрещён;
- resume продолжает текущую попытку: первый **валидный** ответ измерения и
  отчёт неизменяемы; невалидный ответ в попытку не пишется — только в журнал
  отказов шага, повтор его перезапрашивает;
- `--reopen` бандла даёт новый прогон бандла и новый пин; закрытие по нему —
  новый `run_id`.

**Эксклюзивность на воркстрим, между машинами.** Держит форджа: попытка до
первого внешнего действия создаёт ref `refs/heads/criteria-close/<CODE>` в
репо-владельце (создание атомарно; существующий ref — отказ с именем владельца
ref'а из его коммита). Ref снимается переходом попытки в терминальное состояние.
Исполнитель на VPS и на Mac видит одну форджу. Локально — `fcntl.flock` на
каталог прогона как оптимизация, не гарантия.

### 3.2 Состояния и переходы

Живые: `verifying`, `proposing`, `awaiting-merge`. Терминальные: `blocked`,
`not-applicable`, `accepted`, `rejected`, `invalidated`, `abandoned`,
`superseded`.

| из | событие | в | действие |
|---|---|---|---|
| — | devtools решил `not-applicable` до запроса (схема 1, версия spec-runner) | `not-applicable` | попытка создаётся ради отчёта; ref не берётся |
| — | создание попытки | `verifying` | ref воркстрима, запись идентичности (write-ahead) |
| `verifying` | ответ невалиден / код 2 | `verifying` | журнал отказа, повтор resume |
| `verifying` | ошибка уровня ответа (код 3: сбор, `foreign-import`, `product-roots-unknown`) | `blocked` | продукт на этом SHA не измеряется |
| `verifying` | ответ `not-applicable: language` | `not-applicable` | отчёт |
| `verifying` | Must `unconfirmed`/любой `error` (§3.3) | `blocked` | отчёт + комментарий в PR tasks-спеки (номер из записи моста) |
| `verifying` | стопа нет; снимок политики получен | `proposing` | запись предложения (§3.4) до push |
| `verifying` | снимок политики: `FORBIDDEN env` | `verifying` | отказ команды |
| `verifying` | снимок политики: `UNAVAILABLE`/`absent`/`empty` | `verifying` | отказ шага, повтор |
| `proposing` | push/создание PR/лейбл упали | `proposing` | повтор resume: сверка форджи, усыновление по идентичности |
| `proposing` | PR создан или усыновлён, лейбл по составу стоит | `awaiting-merge` | сверка PR ↔ предложение |
| `awaiting-merge` | test-only: команда вызывает `merge-pr.sh --expect-head <голова> --expect-base <живая верхушка, записанная write-ahead>` | — | исход по коду ниже |
| `awaiting-merge` | мерж выполнен (кем угодно) | `accepted` / `rejected` | предикат §3.5 |
| `awaiting-merge` | `merge-pr.sh` код 2 / 5 | `awaiting-merge` | повтор; при 5 — новый пин базы, без перемера |
| `awaiting-merge` | `merge-pr.sh` код 3 / 4 | `rejected` | причина |
| `awaiting-merge` | сужение политики увидено до мержа (§3.5) | `invalidated` | закрыть PR, `superseded_by`; перевыпуск новой попыткой |
| `awaiting-merge` | PR закрыт без мержа | `abandoned` | — |
| `awaiting-merge` | появился более новый прогон бандла воркстрима | `superseded` | закрыть PR |
| незавершённое | `--new-attempt` | `superseded` | сперва сверка форджи и усыновление PR незавершённого намерения, затем закрыть его |
| терминальное ≠ `accepted` | его PR всё же смержен | то же | **void-PR**: агентский PR помечает файл приёмки `status: void` с причиной (§3.4) |

Внешние действия (ref, push, создание/закрытие PR, мерж) — write-ahead:
намерение записано до вызова; resume сверяет форджу и усыновляет результат по
идентичности (ветка `criteria-close/<CODE>-<run>-a<attempt>`, голова, хэши), а
не по имени.

### 3.3 Исход по приоритету

Измеряются все test-BEH, на которые ссылается хотя бы один не-Won't AC, —
независимо от собственного приоритета. Приоритет решает только исход:

| приоритет | `unconfirmed` | `error` |
|---|---|---|
| Must | стоп (`blocked`) | стоп |
| Should | строка отчёта | стоп |
| Could | строка отчёта | стоп |
| Won't (не упомянут не-Won't AC) | не измеряется, перечисляется | — |

`error` здесь — ошибки графа и per-BEH `io`/`runner`; ошибки уровня ответа —
§3.2. Выход из `blocked` — доработка и `--new-attempt` на новом SHA или
`--reopen` бандла. **Флага обхода нет и быть не должно** (`--skip-criteria` и
аналоги запрещены спекой).

### 3.4 Предложение приёмки

До push записывается неизменяемое **предложение**: идентичность попытки, default
ветка (имя), байты и sha256 ответа измерения, sha256 блоба
`workstreams/<ws>/spec/90-acceptance-closure.md`, имя ветки, ожидаемая голова,
полный снимок политики (§3.5). Файл приёмки: frontmatter `status: proposed`,
шапка «подтверждено N из M test-критериев (Must a/b, Should c/d, Could e/f);
ждут человека K», таблица по критериям, человеческий чек-лист (`human` —
наблюдаемый знак, `waived` — основание), пин бандла, продуктовый SHA, sha256
ответа. Читатели ветки (консоль, дайджесты) считают приёмку состоявшейся только
по записи `accepted` в состоянии закрытия либо по отсутствию последующего
`status: void`. PR с `human`/`waived` **создаётся** с лейблом
`human-merge-required` в том же вызове создания.

### 3.5 Предикат `accepted` и подпись

`accepted` ставит одна функция сверки на всех путях (первый проход, resume,
усыновление уже смерженного PR):

1. **Идентичность предмета:** смержена ровно голова предложения; `baseRefName`
   равен default-ветке предложения; блоб файла приёмки в смерженном дереве
   совпадает с записанным хэшем; дифф PR — только этот файл.
2. **Актуальность оракула:** `bundle_pin` — пин последнего `completed` прогона
   воркстрима, и более нового прогона воркстрима нет в любом статусе;
   `product_sha` — предок верхушки default-ветки.
3. **Акт** (наблюдаемые факты форджи):
   - есть `human`/`waived` — `mergedBy.login` в снимке предложения и не
     `ai-prosto`;
   - только test-критерии — `mergedBy.login` ∈ {`ai-prosto`} ∪ снимок
     (человеческий мерж test-only PR допустим);
   - переменная окружения `AUTHORIZED_APPROVER_ACCOUNTS` — отказ команды, как в
     §I12.

Иначе `rejected` (1, 3) или `superseded` (2).

Снимок политики (Р3′): при создании предложения сохраняется **полный**
проверенный снимок — версия `approval-policy`, отпечаток, список учёток
(отдельная форма закрытия; `PolicySnapshot.as_record()` список не пишет и не
используется). При resume до мержа — `policy_snapshot(pinned_sha=None)` и
сравнение со снимком. **Сужение** — `snapshot.accounts ⊄ current.accounts`.

| текущая политика относительно снимка | увидено | исход |
|---|---|---|
| сужение | до мержа (PR открыт) | `invalidated`, перевыпуск |
| `FORBIDDEN absent`/`empty` | до мержа | `invalidated` |
| расширение / иная смена | до мержа | предупреждение при каждом resume |
| `UNAVAILABLE` | до мержа | отказ шага без перехода |
| `FORBIDDEN env` | когда угодно | отказ команды |
| любая | после мержа | подпись по снимку |

Обещание: «подпись действительна по снимку предложения; сужение, замеченное до
мержа, инвалидирует». Названная граница: сужение (и недоступность политики), в
окне которого до мержа не было ни одного resume, не поймано.

### 3.6 Не применимо

`not-applicable` с причиной `schema-1` · `language` · `spec-runner-version`. В
шапке любого отчёта — счётчик «оракул не применим: N (схема 1: …, язык: …,
spec-runner: …)».

## 4. Контракт B: гарантии измерения (владелец механизма — spec-runner)

Спека фиксирует, **что** обязан гарантировать `confirmed` в `criteria-closure/v1`,
и что devtools видит в ответе. **Как** — механизм spec-runner; предлагаемая
реализация — приложение
`2026-09-28-bundle-criteria-oracle-spec-runner-annex.md`, уходит заявкой (§6).
devtools проверяет только контракт.

### 4.1 Гарантии `confirmed` для BEH

- **G1 Продуктовый SHA и окружение:** измерено на `product_sha` в окружении из
  его lock; импортируемый продукт — из продуктовых корней этого дерева.
- **G2 Защищённый измеритель:** патч не касается ничего, что pytest загрузил
  как часть тестовой инфраструктуры (тестовые файлы, conftest, плагины, их
  пакеты) — множество выводится измерением, не шаблонами имён; только продуктовые
  корни.
- **G3 Полнота:** множество селекторов BEH — все собранные на `product_sha`
  элементы с его токеном (§1.4), без фильтров; каждый `passed` в фазе `call`
  без патча.
- **G4 Причинность:** каждый прогон на свежем дереве; для доказательства
  падения — чередование чистый/с патчем K ≥ 2 раз с единогласием; падение только
  в фазе `call`; патч, не меняющий AST продукта, — не доказательство.
- **G5 Без переброса:** на паре `(bundle_pin, product_sha)` одно измерение
  (§3.1).

**Граница (вне объёма).** Связь патча со смыслом BEH не проверяется: общий тест
с токенами многих BEH и один патч, ломающий общую функцию, дадут `confirmed`
всем. Это граница смысловой проверки, а не дыра механизма.

### 4.2 Наблюдаемые поля ответа

Ответ по BEH: `status` (`confirmed` · `unconfirmed` · `error`), `reason`
(`no-test` · `not-passed` · `no-control` · `control-stale` ·
`control-out-of-roots` · `control-no-op` · `control-not-failing` ·
`nondeterministic` · `io` · `runner`), `k_runs`, по каждому селектору — node ID,
определение (файл + qualname), исходы всех прогонов с фазой; по контролю — путь
и blob-хэш патча. Уровень ответа: `protected_set_sha256`, `environment`
(lock-хэш, Python, плагины pytest), эхо запроса; ошибки уровня ответа —
`error` верхнего уровня без `beh` (код 3).

## 5. Контракт C: граф критериев и сверка у devtools

### 5.1 Запрос и ответ `criteria-closure/v1`

Владелец схемы — spec-runner. Запрос: `protocol: 1`, `owner_repo`, `workstream`,
`code`, `bundle_pin` (SHA одобрения + пути узлов замыкания), `product_sha`,
`test_criteria: [{id: CODE:BEH-NN}]` (§3.3). Ответ — §4.2. Коды: `0` — ответ
выдан; `2` — ошибка запроса/окружения (повтор); `3` — ошибка уровня ответа
(`blocked`); иные — отказ шага.

### 5.2 Граф и вывод (devtools)

devtools строит типизированный граф из байтов бандла по пину: BEH (вид по §1.6,
приоритет; неизвестный `kind` — `error`), AC (`verification`, непустой
`scenarios` для `test`), рёбра AC → BEH. `waived` у BEH приоритетнее
исполняемого `kind`. Статусы AC выводятся **только** здесь:

| AC | статусы его BEH | статус AC |
|---|---|---|
| `test` | все `confirmed` | `confirmed` |
| `test` | есть `error` | `error` |
| `test` | есть `unconfirmed` (без `error`) | `unconfirmed` |
| `test` | есть `human`/`waived`, остальные `confirmed` | `human` (в чек-лист со ссылкой на BEH) |
| `manual`/`metric` | — | `human` |

### 5.3 Сверка ответа

JSON Schema; эхо совпадает с запросом; множество `beh[].id` **точно** равно
`test_criteria`. У `confirmed`:

- непустые селекторы; каждый отображается на определение, несущее токен этого
  BEH на `product_sha` (devtools проверяет по своим байтам, §1.4);
- все чистые прогоны `call: passed`; `k_runs ≥ 2`; все прогоны с патчем хотя бы
  одного селектора `call: failed`;
- путь патча = `spec/negative-controls/<ws-id>/<CODE>-<BEH>.patch`, blob-хэш =
  блоб в `product_sha`; пути в патче — только внутри продуктовых корней по
  `environment` (devtools сверяет пути патча с тестовыми файлами селекторов и
  `conftest.py` — грубая независимая проверка G2).

Итоги производителя и статусы AC от производителя не принимаются.

| отрицательный ответ | исход |
|---|---|
| пустой stdout / не JSON / не по схеме / код иной | отказ шага |
| чужой `product_sha`/`bundle_pin`/`code` | отказ шага |
| пропущен/лишний/дубль BEH | отказ шага |
| нет `k_runs`, `protected_set_sha256` или `environment` | отказ шага |
| `confirmed` с `k_runs < 2` / без `call: failed` под патчем / со `skipped`/`xfailed` без патча | отказ шага |
| селектор `confirmed` без токена BEH на `product_sha` | отказ шага |
| путь патча не канонический / blob ≠ блоб в `product_sha` / патч задевает файл селектора или conftest | отказ шага |
| `error` верхнего уровня вместе с `beh` | отказ шага |

### 5.4 Вендоринг

`contracts/criteria-closure/v1/` в devtools: схемы, `min-spec-runner.env`,
`PIN` (upstream SHA), `manifest.json` (sha256). Целостность — локально в CI без
соседа; дрейф — по ref из `PIN`: в CI отсутствие входа — ошибка, локально —
`not-checked`. `check-contract-drift.sh` как есть не используется.

## 8. Тестирование и приёмка

### 8.1 devtools, фикстуры

- Токен (§1.4): граница; класс; красный сосед без токена + токен только в зелёном
  методе; вложенная функция; комментарий; шапка модуля; параметризация.
- Реестр: удаление, переназначение, дубль ключа, код вне реестра, смена `code:`.
- Приоритет: `Could` (реальный FR-12), максимум трасс, пустая трасса; Won't-BEH,
  упомянутый Must-AC, — измеряется.
- DT v3: контроль у `verify` без waiver; test-BEH без контроля; контроль в чужой
  задаче; два контроля на BEH; провод — несколько строк `**Criterion-control:**`
  рядом с v2.
- Автомат A: каждая строка таблицы §3.2; crash между намерением и вызовом для ref,
  push, создания PR, мержа; ref воркстрима занят другой машиной → отказ;
  `--new-attempt` на измеренной паре → отказ; `--new-attempt` после `accepted` →
  отказ; мерж PR терминальной попытки → void-PR; `product_sha` не предок
  default → отказ.
- Подпись и предикат: каждая строка таблицы политики §3.5; `ai-prosto` при
  `human`; человек из снимка мержит test-only → `accepted`; голова ≠
  предложению; блоб изменён; лишний файл; перенацеленная база; более новый
  прогон бандла → `superseded`.
- Граф C: каждая строка §5.2; каждая строка отрицательной таблицы §5.3; чужое
  evidence для Must-AC → вывод по графу, стоп.
- Вендоринг: подменённый байт; нет соседа в CI.

### 8.2 Живая приёмка

Бандл схемы 2 на крошечном предмете, исполнение задач, затем `criteria-close`:

1. Must без теста с токеном → `blocked`, `no-test`;
2. тест с токеном заменён на `assert True` после исполнения → `control-not-failing`;
3. контроль правит хелпер теста в пакете продукта или conftest → `control-out-of-roots`;
4. флейки-тест с патчем-комментарием → `control-no-op`; флейки-тест с реальным
   патчем → `nondeterministic`;
5. BEH с пустой трассой → `error`;
6. `human`-критерий, приёмочный PR смержен не человеком из снимка → не `accepted`;
7. сужение политики при открытом PR, затем resume → `invalidated`;
8. честный прогон → приёмочный PR с чек-листом, мерж человеком → `accepted`.

## 10. Условие остановки и следующий механизм

Если локальный круг по контракту B снова найдёт находку класса «патч доказывает
не то», это четвёртый заход одного класса: механизм не латаем, а меняем
**источник патча** — исполнитель больше не выбирает свой контроль:

- **TDD-задачи:** доказательство — красный на продуктовом коде до задачи (дифф
  продукта задачи откатан, тесты задачи оставлены);
- **`verify_first`:** инструментальная мутация функций, реально покрытых
  селектором (по coverage), а не патч исполнителя.

Сейчас не реализуется; записано, чтобы при несходимости не изобретать заново.
