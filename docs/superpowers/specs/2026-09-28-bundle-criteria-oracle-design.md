## 0. Зачем

Одобренные и запиненные по байтам узлы `15-behaviour-spec` и `25-acceptance` —
оракул, зафиксированный ДО кода (§I12, волны `sequential-node-approval`).
Прецедент честного оракула — disputatio D1/D6: инварианты `INV-NN` зафиксированы
до диффа, поэтому вердикт по диффу честен.

Сверху вниз адресуемые ID уже есть и частично проверяются: бриф `G-NN/FR-NN` →
требования `FR/NFR-NN` (+ `Priority`) → `BEH-NN` (`traces`, `checked_by`;
steward GC-BEH-TRACE/COVERAGE/CHECK-PLANNED) → `AC-NN` (`verification`,
`traces`, `scenarios`; `acceptance_guard`) → `DT-NN` (`scenarios`,
`delivers[].sources`; `decomposition_guard`). Ниже декомпозиции цепочка рвётся:

1. мост (`task_bridge.py`) сворачивает BEH в `**Traces to:** [FR-..]`, BEH
   остаётся прозой чек-листа;
2. evidence исполнения ключуется TASK-ID/селектором — критерий не назван;
3. `checked_by: planned → materialized` не продвигает никто;
4. ID не квалифицированы: чужой `BEH-09` удовлетворяет `scenarios.py`;
5. парсеры расходятся: steward — виды `atp|contract|integration|e2e|manual`
   без `[a-z]`, реальные бандлы пишут `kind: unit`; `acceptance_guard`
   понимает только `Must`/`Should`, реальный бандл объявляет `Could`
   (`executable-negative-control…/10-requirements.md` FR-12).

Живой прогон волн 22.09 (`docs/evidence/2026-09-22-waves-live-run.md`) показал
цену: критерий, проверяемый чтением исходника, не краснеет.

**Цель.** После исполнения задач отдельный акт приёмки отвечает на вопрос «какие
критерии подтверждены чем» на продуктовом SHA; неподтверждённый Must — приёмки
нет.

**Жизненный цикл (Р1).** Раннер документов (`governance/runner.py`, `_STEPS`:
интервью → авторинг → гейт → edge-check → candidate → finalize) одобряет
**документы**; к его finalize кода продукта ещё нет. Мост в задачи — отдельная
команда после `completed`, tasks-спека рождается `draft` и исполняется
spec-runner после одобрения человеком. Закрытие — **третья, отдельная**
команда после исполнения (§3). Жизненный цикл раннера документов не меняется.

**Вне объёма.** Смысловая проверка реализации против текста критерия (edge-check
«тесты и код ← задача») — отдельный этап; эта спека даёт ему адресуемость.
Машинная грамматика `metric` — следующий этап (стенд замеров). Не-Python тесты —
отдельное решение. Связь доказательства со смыслом BEH проверяется не полностью —
граница названа в §4.1.

## 1. Грамматика и токен

### 1.1 Код воркстрима и схема charter

`00-charter.md` получает frontmatter `schema: 2` и `code: <CODE>`,
`CODE` = `^[A-Z]{2,6}$`; в схеме 2 `code:` обязателен. Мост и шаблоны генерируют
charter схемы 2. Код неизменяем: гейт отвергает правку `code:` в любом PR,
включая `--reopen` charter.

### 1.2 Реестр кодов

`workstreams/codes.toml` репо-владельца бандла — только растёт:

```toml
[ENC]
workstream = "executable-negative-control-under-standard-20260921"
approved = 2026-09-21
```

Гейт реестра (devtools, новый `charter_guard`):

- каждый ключ реестра базы присутствует в голове с тем же `workstream` —
  удаление и переназначение запрещены;
- код charter схемы 2 есть в реестре и указывает на свой воркстрим;
- уникальность нового кода — по всему реестру, не по живым каталогам (иначе код
  закрытого воркстрима достался бы новому вместе с его тестами); историю git не
  берём — CI делает checkout `fetch-depth: 1`;
- два одновременных PR с одним новым кодом ловят парсер TOML (повторный ключ —
  ошибка разбора) и гейт, который гоняется и на push в default ветку.

### 1.3 Квалифицированный ID и токен

Вне бандла ID пишется `<CODE>:<ID>` (`ENC:BEH-03`, `ENC:AC-07`); внутри
документов бандла — коротким. Совпадение —
`(?<![A-Za-z0-9_])ENC:BEH-03(?![A-Za-z0-9_])`: `XENC:BEH-03`, `ENC:BEH-030`,
`ENC:BEH-03a` не совпадают.

### 1.4 Владение токеном (Python)

Токен принадлежит **наиболее вложенному** определению теста, в чьей области он
стоит. Область определения считается по строкам исходника (комментарии в AST не
видны), `ast` даёт границы:

- область функции/метода: от первого декоратора (`decorator_list[0].lineno`,
  иначе `lineno`) до `end_lineno`, **минус** диапазоны вложенных `def`/`class`;
- область класса: его декораторы, заголовок, docstring и тело **вне** диапазонов
  вложенных функций и классов. Токен области класса засчитывается всем его
  тест-методам; токен метода в класс не поднимается и соседям не достаётся;
- шапка модуля и соседние определения — не засчитываются;
- параметризация: токен функции относится ко всем её собранным селекторам;
- один тест может нести несколько токенов, у BEH — несколько тестов.

Токен в не-Python файле или язык тестов репо не Python — бандл
`not-applicable: language` (§3.6), не молчаливый ноль.

### 1.5 Приоритет

Словарь один на все парсеры: `Must | Should | Could | Won't` (steward уже
распознаёт все четыре; devtools `acceptance_guard` сводится к нему, §5).
Приоритет BEH и AC выводится по их `traces` в `FR/NFR`: максимум по
трассируемым пунктам (`Must > Should > Could > Won't`). Пустой или
неразрешимый `traces` — `error` (блокирует). Исход по приоритету — §3.3.

### 1.6 Исполняемость критерия

| критерий | вид | статус закрытия |
|---|---|---|
| BEH | `checked_by` исполняемого вида (`unit`, `integration`, `contract`, `e2e`, `atp`) | test-критерий (§4) |
| BEH | `kind: manual` | `human`: Given/When/Then как наблюдаемый знак (Р2) |
| BEH | `status: waived` | `waived`: основание waiver дословно из бандла (Р2) |
| AC | `verification: test` | выводится devtools из статусов его `scenarios` (§5.2); пустой `scenarios` — `error` |
| AC | `verification: manual \| metric` | `human`: наблюдаемый знак, источник порога |

Выход «сценарий не проверяется тестом» — `--reopen` 15-behaviour-spec со сменой
`kind` на `manual` и повторным одобрением; критерий уходит в человеческий
чек-лист, а не пропадает. Указание автору бандла: BEH, чьё поведение — свойство
**текста** продукта (докстринг, формулировка в исходнике), размечается
`kind: manual`, а не тестом; правило уходит в шаблоны узла и в steward (§6), не
только в эту спеку.

### 1.7 Полнота приёмки: нет сирот

Каждый BEH, кроме Won't, входит в `scenarios` хотя бы одного **не-Won't** AC.
Сирота — и BEH вне всех AC, и BEH, на который ссылаются только Won't-AC.
Проверяет `acceptance_guard` при одобрении 15-behaviour-spec, при одобрении
25-acceptance и при любом `--reopen`, меняющем множество BEH или AC (сирота иначе
появилась бы переоткрытием 15 без правки 25). Закрытие перепроверяет то же по
запиненному бандлу и при нарушении даёт `error` уровня ответа — fail-closed, не
полагаясь на предусловие. Замер 2026-09-28: во всех 9 реальных бандлах сирот 0
(236 BEH).

## 2. Исполнение

### 2.1 Мост в задачи (devtools, `task_bridge.py`)

- Для задачи с `scenarios` в DT — строка `**Scenarios:** ENC:BEH-03, ENC:BEH-04`.
  `**Traces to:**` — как есть. Грамматика DT и провод контролей **не меняются**:
  исполнитель доказательство падения не пишет (§4).
- Строка выдаётся только при запиненной версии spec-runner ≥ минимальной из
  `contracts/criteria-closure/v1/min-spec-runner.env`; иначе закрытие даёт
  `not-applicable: spec-runner-version` (§3.6).
- Пункт чек-листа исполнителю (токен внутри определения теста, §1.4) —
  **подсказка**: правило держат гейт задачи и закрытие.

### 2.2 spec-runner во время исполнения (заявка, §6)

`scenarios.py` — квалифицированный токен и владение по §1.3–1.4. Гейт задачи:
объявленный BEH несёт хотя бы один тест группы на коммите задачи. Измерение §4 на
коммите задачи допустимо как ранний сигнал исполнителю; доказательством для
оракула не служит — оракул мерит заново при закрытии.

## 3. Закрытие — контракт A: автомат попыток (Р1)

### 3.1 Команда, попытки, идентичность

`make criteria-close ARGS='--run <id прогона бандла> [--new-attempt]
[--product-sha <sha>]'` (devtools, `governance/criteria_close.py`). Состояние —
`out/criteria-close/<run-id>/`, список **попыток**; у попытки неизменяемая
идентичность `(run_id, attempt, bundle_pin, product_sha, task_commits)`:

- `bundle_pin` — пин одобрения последней волны прогона бандла (`completed`);
  замыкание узлов (charter, requirements, 15, 25, 30) читается по нему из
  git-объектов, недоступный байт — отказ шага;
- `product_sha` — `--product-sha` или голова default-ветки в момент создания
  попытки; предок живой верхушки default-ветки (`git merge-base --is-ancestor`),
  иначе создание отказывает; после записи не меняется;
- `task_commits` — список коммитов задач tasks-спеки этого бандла из леджера
  исполнения spec-runner (все они — предки `product_sha`); база измерения
  изменения (§4.2) строится только из их диффов против первого родителя —
  посторонние PR в базу не попадают по построению;
- ключ измерения — `(bundle_pin, content_sha256)`, где `content_sha256` — хэш
  содержимого продуктовых корней и тестовых файлов на `product_sha`. На
  измеренном ключе `--new-attempt` **запрещён**: коммит только документации даёт
  новый SHA, но не новое содержимое, и переброса флейки-теста не открывает;
- `--new-attempt` — единственный путь к новому содержимому (после доработки):
  прежняя незавершённая попытка → `superseded`; после `accepted` запрещён;
- resume продолжает текущую попытку: первый **валидный** ответ измерения и отчёт
  неизменяемы; невалидный ответ в попытку не пишется — только в журнал отказов
  шага, повтор его перезапрашивает;
- `--reopen` бандла даёт новый прогон бандла и новый пин — закрытие по нему —
  новый `run_id`.

**Эксклюзивность на воркстрим, между машинами.** Держит форджа: попытка до
первого внешнего действия создаёт ref `refs/heads/criteria-close/<CODE>` в
репо-владельце (создание атомарно; существующий ref — отказ с указанием попытки
из его коммита). Ref снимается переходом попытки в терминальное состояние.
Локально — `fcntl.flock` на каталог прогона как оптимизация, не гарантия.

### 3.2 Состояния и переходы

Живые: `verifying`, `proposing`, `awaiting-merge`, `stamping`. Терминальные:
`blocked`, `not-applicable`, `accepted`, `rejected`, `abandoned`, `superseded`.
Предложение имеет **ревизии** внутри попытки (перевыпуск при сужении политики или
отставании ветки не меряет заново).

| из | событие | в | действие |
|---|---|---|---|
| — | devtools решил `not-applicable` до запроса (схема 1, версия spec-runner) | `not-applicable` | попытка ради отчёта; ref не берётся |
| — | создание попытки | `verifying` | ref воркстрима, идентичность (write-ahead) |
| `verifying` | ответ невалиден / код 2 | `verifying` | журнал отказа, повтор resume |
| `verifying` | код 3 или `error` уровня ответа (сбор, `foreign-import`, `product-roots-unknown`, сирота §1.7) | `blocked` | продукт на этом содержимом не измеряется |
| `verifying` | ответ `not_applicable` (язык) | `not-applicable` | отчёт |
| `verifying` | Must `unconfirmed`/`budget-exhausted` или любой `error` (§3.3) | `blocked` | отчёт + комментарий в PR tasks-спеки (номер из записи моста) |
| `verifying` | стопа нет; снимок политики получен | `proposing` | предложение r1 (§3.4) до push |
| `verifying` | снимок: `FORBIDDEN env`/`source` | `verifying` | отказ команды |
| `verifying` | снимок: `UNAVAILABLE`/`absent`/`empty` | `verifying` | отказ шага, повтор |
| `proposing` | push/создание PR/лейбл/аттестация упали | `proposing` | повтор resume: сверка форджи, усыновление по идентичности |
| `proposing` | PR создан или усыновлён, лейбл по составу стоит, scope-аттестация опубликована | `awaiting-merge` | сверка PR ↔ предложение |
| `awaiting-merge` | test-only: команда вызывает `merge-pr.sh --expect-head <голова> --expect-base <живая верхушка, записанная write-ahead>` | — | исход по коду ниже |
| `awaiting-merge` | мерж выполнен (кем угодно) | `stamping` / `rejected` | предикат §3.5 |
| `awaiting-merge` | `merge-pr.sh` код 2 / 5 | `awaiting-merge` | повтор; при 5 — новый пин базы без перемера |
| `awaiting-merge` | `merge-pr.sh` код 3 из-за `BEHIND` | `proposing` | ревизия r+1: ветка приёмки пересобирается на живой верхушке (добавляет один файл), без перемера |
| `awaiting-merge` | `merge-pr.sh` код 3 иной / код 4 | `rejected` | причина |
| `awaiting-merge` | сужение политики увидено до мержа (§3.5) | `proposing` | закрыть PR ревизии, ревизия r+1 с новым снимком, без перемера |
| `awaiting-merge` | PR закрыт без мержа | `abandoned` | — |
| `awaiting-merge` | оракул устарел (§3.5 п.2) | `superseded` | закрыть PR |
| `stamping` | stamp-PR (§3.4) смержен агентом | `accepted` | снять ref воркстрима |
| `stamping` | stamp-PR упал | `stamping` | повтор resume |
| незавершённое | `--new-attempt` | `superseded` | сперва сверка форджи и усыновление PR незавершённого намерения, затем закрыть его |
| терминальное ≠ `accepted` | его PR всё же смержен | то же | **void-PR**: агентский PR ставит файлу приёмки `status: void` с причиной |

Внешние действия (ref, push, создание/закрытие PR, аттестация, мерж) —
write-ahead: намерение записано до вызова; resume сверяет форджу и усыновляет
результат по идентичности (ветка `criteria-close/<CODE>-<run>-a<attempt>-r<rev>`,
голова, хэши), а не по имени.

### 3.3 Исход по приоритету

Измеряются все test-BEH (по §1.7 каждый из них — в каком-то не-Won't AC).
Приоритет решает только исход:

| приоритет | `unconfirmed` / `budget-exhausted` | `error` |
|---|---|---|
| Must | стоп (`blocked`) | стоп |
| Should | строка отчёта | стоп |
| Could | строка отчёта | стоп |

`budget-exhausted` («не мерили») отличается от `unconfirmed` («не убил»): для Must
это стоп с названной причиной, а не вердикт о тесте. `error` здесь — ошибки графа
и per-BEH `io`/`runner`; ошибки уровня ответа — §3.2. Выход из `blocked` —
доработка и `--new-attempt` на новом содержимом или `--reopen` бандла. **Флага
обхода нет и быть не должно** (`--skip-criteria` и аналоги запрещены спекой).

### 3.4 Предложение приёмки и штамп

До push ревизии записывается неизменяемое **предложение**: идентичность попытки,
номер ревизии, default-ветка, байты и sha256 ответа измерения, sha256 блоба
`workstreams/<ws>/spec/90-acceptance-closure.md`, имя ветки, ожидаемая голова,
полный снимок политики (§3.5). Файл приёмки: frontmatter `status: proposed`,
шапка «подтверждено N из M test-критериев (Must a/b, Should c/d, Could e/f);
ждут человека K, из них по границе измерителя (`verify`-BEH) V», таблица по
критериям с родом BEH и доказательством, человеческий чек-лист (`human` —
наблюдаемый знак, `waived` — основание, `verify-human` — отметка «граница
измерителя»), пин бандла, продуктовый SHA, sha256 ответа.

PR приёмки создаёт учётка оператора; `ai-prosto` публикует на нём
scope-аттестацию (`review-pr.sh`, prose-only — файл лежит в прозаическом пути),
закрывающую требование одобряющего ревью. PR с `human`/`waived`/`verify-human`
**создаётся** с лейблом `human-merge-required` в том же вызове создания.

**Штамп.** После предиката §3.5 команда открывает агентский stamp-PR, меняющий в
файле только `status: proposed → accepted` (+ ссылка на мерж), с той же
аттестацией, и мержит его `merge-pr.sh`. Читатели ветки (консоль, дайджесты)
считают приёмку состоявшейся **только** по `status: accepted` в файле; `proposed`
и `void` — не приёмка.

### 3.5 Предикат перехода в `stamping` и подпись

Одна функция сверки на всех путях (первый проход, resume, усыновление уже
смерженного PR):

1. **Идентичность предмета:** смержена ровно голова текущей ревизии;
   `baseRefName` равен default-ветке предложения; блоб файла приёмки в смерженном
   дереве совпадает с записанным хэшем; дифф PR — только этот файл.
2. **Актуальность оракула** (по фордже, не по локальному `out/`): байты узлов
   замыкания на верхушке default-ветки равны байтам `bundle_pin`, и нет открытых
   PR веток одобрения этого воркстрима (формы веток — SSOT
   `contracts/approval-branches/v1/patterns.env`); `product_sha` — предок
   верхушки default-ветки.
3. **Акт** (наблюдаемые факты форджи):
   - есть `human`/`waived`/`verify-human` — `mergedBy.login` в снимке ревизии и
     не `ai-prosto`;
   - только test-критерии — `mergedBy.login` ∈ {`ai-prosto`} ∪ снимок;
   - переменная окружения `AUTHORIZED_APPROVER_ACCOUNTS` или источник политики
     вне закреплённого — отказ команды, как в §I12.

Иначе `rejected` (1, 3) или `superseded` (2). `human-merge.sh` сверяет логин с
**текущей** политикой — строже снимка; предикат судит по снимку. Расхождение
возможно только при расширении политики и безопасно.

Снимок политики (Р3′): при создании ревизии сохраняется **полный** проверенный
снимок — версия `approval-policy`, отпечаток, список учёток (отдельная форма
закрытия; `PolicySnapshot.as_record()` список не пишет и не используется). При
resume до мержа — `policy_snapshot(pinned_sha=None)` и сравнение со снимком.
**Сужение** — `snapshot.accounts ⊄ current.accounts`.

| текущая политика относительно снимка | увидено | исход |
|---|---|---|
| сужение | до мержа (PR открыт) | новая ревизия с новым снимком |
| `FORBIDDEN absent`/`empty` | до мержа | закрыть PR; ревизия невозможна → `blocked` до восстановления политики, resume |
| расширение / иная смена | до мержа | предупреждение при каждом resume |
| `UNAVAILABLE` | до мержа | отказ шага без перехода |
| `FORBIDDEN env`/`source` | когда угодно | отказ команды |
| любая | после мержа | подпись по снимку ревизии |

Обещание: «подпись действительна по снимку ревизии; сужение, замеченное до
мержа, требует новой ревизии». Названная граница: сужение (и недоступность
политики), в окне которого до мержа не было ни одного resume, не поймано.

### 3.6 Не применимо

`not-applicable` с причиной `schema-1` · `language` · `spec-runner-version`. В
шапке любого отчёта — счётчик «оракул не применим: N (схема 1: …, язык: …,
spec-runner: …)».

## 4. Контракт B: измерение (владелец механизма — spec-runner)

Спека фиксирует, **что** обязан гарантировать ответ `criteria-closure/v1` и что
devtools видит; **как** — механизм spec-runner; предлагаемая реализация —
приложение `2026-09-28-bundle-criteria-oracle-spec-runner-annex.md` (заявка §6).

**Решение круга 4.** Источник доказательства падения — **не** патч исполнителя
(Р4 в редакции rev 1–4 отменён): история продукта и инструментальная мутация.
Род BEH (изменение/сохранение) — новое решение относительно «мутация для всех
задач» (выбор (а) владельца после круга 4): дешевле, и у BEH изменения
естественный TDD-смысл «тест краснеет без кода воркстрима». Проверено замерами
§4.4.

### 4.1 Гарантии для test-BEH

- **G0 Исполнение продукта:** селекторы BEH в фазе `call` исполняют продуктовый
  код (непустое покрытие продуктовых корней в `call`). Иначе
  `unconfirmed: no-product-execution`. Предусловие несущее: тест, читающий
  исходник как данные (докстринг), без него прошёл бы как BEH изменения.
- **G1 Продуктовый SHA и окружение:** измерено на `product_sha` в окружении из
  его lock; импортируемый продукт — из продуктовых корней клона.
- **G2 Обнаружил тест:** падение засчитывается, только если тип исключения —
  `AssertionError`, `pytest.fail` (`Failed`) или «DID NOT RAISE» **и** кадр, где
  оно брошено, лежит в защищённом множестве (собранные тестовые файлы,
  `conftest.py`, модули плагинов pytest и тестовых хелперов). Исключение из кадра
  продукта (`RuntimeError`, `TypeError`, `NameError`, `assert` внутри продукта) —
  не обнаружение: иначе продукт подтверждал бы свой критерий.
- **G3 Полнота:** множество селекторов BEH — все собранные на `product_sha`
  элементы с его токеном (§1.4), без фильтров; каждый `passed` в фазе `call`.
- **G4 Род и доказательство** (§4.2).
- **G5 Детерминизм:** каждый прогон на свежем дереве; доказательство
  подтверждается чередованием K ≥ 2 с единогласием; отбор мутантов — фиксированный
  порядок (оператор, узел, позиция), без случайного seed; бюджет исчерпан раньше,
  чем проверены все кандидаты, — `budget-exhausted`, не вердикт.
- **G6 Без переброса:** одно измерение на ключ `(bundle_pin, content_sha256)`
  (§3.1).

**Граница (вне объёма).** Для BEH сохранения убийство мутанта общего кода,
который тест охраняет своей проверкой, засчитывается — это законная мера
сохранения; связь с **конкретным** смыслом BEH не проверяется (тест с токенами
многих BEH подтвердит их одним убийством). Для BEH изменения граница —
реальная правка общего кода задачей, исполненная селектором: она видна в PR.

### 4.2 Род BEH и доказательство

**База изменения** для BEH: HEAD (`product_sha`), в которой откатаны **только**
куски (hunks) диффа `task_commits` (каждый коммит против первого родителя), хотя
бы одна изменённая или добавленная строка которых исполнена селекторами BEH в
фазе `call` на `product_sha`. Докстринги, мёртвый код, неиспользуемые константы
coverage исполняемыми не считает — они не откатываются, поэтому тест-читатель
(чистый или смешанный) на базе не краснеет.

| исход селекторов BEH на базе изменения | род | доказательство | статус |
|---|---|---|---|
| ≥1 селектор падает (G2), все зелёные на `product_sha` | **изменение** | переход «красный на базе → зелёный на HEAD», K ≥ 2 | `confirmed` |
| все зелёные | **сохранение** | мутация (ниже) | `confirmed` / `unconfirmed: not-killed` / `budget-exhausted` |
| база не разбирается/не импортируется | — | — | `unconfirmed: base-unbuildable` |
| падение только не-G2 (исключение продукта) | **сохранение** | мутация | как выше |

Частичный откат может дать несогласованный, но импортируемый код; это безопасно:
падение на нём засчитывается только по G2, остальное уводит к правилу сохранения.

**Мутация для сохранения:** кандидаты — узлы продуктовых функций, исполненные
селекторами BEH в фазе `call`, в порядке «сначала функции, покрытые наименьшим
числом тестов»; детерминированные операторы (сравнения, булевы, `not`, возврат,
арифметика, константы `True/False`, строковые литералы исполненных строк включая
константные части f-строк; не докстринги); потолок на функцию; первое убийство
по G2 с подтверждением K ≥ 2 — `confirmed`.

**`verify`-задачи.** BEH из `scenarios` задач `type: verify` измеряются тем же
правилом; если он получает не `confirmed` — статус **`verify-human`**: уходит в
человеческий чек-лист с отметкой «граница измерителя» и отдельным счётчиком в
шапке (§3.4), а не в стоп. Основание — замер: 4 из 5 `verify`-BEH devtools не
имеют специфичной цели.

### 4.3 Наблюдаемые поля ответа

По BEH: `status` (`confirmed` · `unconfirmed` · `budget-exhausted` · `error`),
`class` (`change` · `preservation`), `reason` (`no-test` ·
`no-product-execution` · `not-passed` · `not-killed` · `base-unbuildable` · `io` ·
`runner`), по каждому селектору — node ID, определение (файл + qualname), все
прогоны с фазой, типом исключения и файлом кадра; для `change` — откатанные куски
(коммит, файл, диапазон строк) и прогоны на базе; для `preservation` — убивший
мутант (оператор, файл:строка) и прогоны. Уровень ответа: `product_roots`,
`protected_set_sha256`, `environment` (sha256 lock, Python, плагины pytest),
`content_sha256`, `not_applicable?`, `error?` (без `beh`), эхо запроса.

### 4.4 Замеры, на которых стоит правило (2026-09-28, i5/#171, 17 BEH с тестами)

| замер | правило | итог |
|---|---|---|
| 1 | мутация покрытых функций (импорт+call) | 470 функций вместо 120; половина подтверждений — поломкой общего кода |
| 2 | узлы диффа ∩ call | 6/17: честные BEH сохранения не имеют кандидатов |
| 3 | + строковые литералы, убийство по G2 | 6/16 — FAIL |
| 4 | род BEH (база — полный откат файлов) | 15/16, BEH-12 — слабый тест (проверено) — PASS по критерию владельца |

## 5. Контракт C: граф критериев и сверка у devtools

### 5.1 Запрос и ответ `criteria-closure/v1`

Владелец схемы — spec-runner. Запрос: `protocol: 1`, `owner_repo`, `workstream`,
`code`, `bundle_pin` (SHA одобрения + пути узлов замыкания), `product_sha`,
`task_commits`, `test_criteria: [{id: CODE:BEH-NN, verify_task: bool}]`. Ответ —
§4.3. Коды: `0` — ответ выдан; `2` — ошибка запроса/окружения (повтор); `3` —
ошибка уровня ответа (`blocked`); иные — отказ шага.

### 5.2 Граф и вывод (devtools)

devtools строит типизированный граф из байтов бандла по пину: BEH (вид по §1.6,
приоритет; неизвестный `kind` — `error`), AC (`verification`, непустой
`scenarios` для `test`), рёбра AC → BEH; сироты §1.7 — `error` уровня ответа.
`waived` у BEH приоритетнее исполняемого `kind`. Статусы AC — **только** здесь:

| AC | статусы его BEH | статус AC |
|---|---|---|
| `test` | все `confirmed` | `confirmed` |
| `test` | есть `error` | `error` |
| `test` | есть `unconfirmed`/`budget-exhausted` (без `error`) | `unconfirmed` |
| `test` | есть `human`/`waived`/`verify-human`, остальные `confirmed` | `human` (в чек-лист со ссылкой на BEH) |
| `manual`/`metric` | — | `human` |

### 5.3 Сверка ответа

JSON Schema; эхо совпадает с запросом; множество `beh[].id` **точно** равно
`test_criteria`. devtools пересчитывает сам по своим байтам на `product_sha`:

- **полнота:** множество определений с токеном BEH (§1.4, парсер devtools) равно
  множеству определений селекторов ответа;
- **`confirmed`:** все селекторы `call: passed` на `product_sha`; число прогонов
  доказательства (devtools считает по записям прогонов, не по полю итога) ≥ 2 с
  единогласием; каждое засчитанное падение — тип и файл кадра по G2 (файл кадра —
  в тестовых путях или conftest по собственному разбору devtools);
- **`change`:** откатанные куски — подмножество кусков диффа `task_commits`
  (devtools строит дифф сам); каждый откатанный кусок содержит строку,
  исполненную селектором (по покрытию из ответа);
- **`preservation`:** убивший мутант — на строке исполняемого узла продуктовой
  функции внутри `product_roots`, не в докстринге;
- **окружение:** sha256 lock из ответа равен sha256 lock на `product_sha`;
  `content_sha256` равен пересчитанному devtools.

Итоги производителя и статусы AC от производителя не принимаются.

| отрицательный ответ | исход |
|---|---|
| пустой stdout / не JSON / не по схеме / код иной | отказ шага |
| чужой `product_sha`/`bundle_pin`/`code`/`task_commits` | отказ шага |
| пропущен/лишний/дубль BEH; неполное множество определений | отказ шага |
| нет `product_roots`, `protected_set_sha256`, `environment` или `content_sha256` | отказ шага |
| `confirmed` с <2 прогонами доказательства / без единогласия / с падением не по G2 / со `skipped`/`xfailed` на `product_sha` | отказ шага |
| селектор `confirmed` без токена BEH на `product_sha` | отказ шага |
| `change` с куском вне диффа `task_commits` или без исполненной строки | отказ шага |
| `preservation` с мутантом в докстринге/вне корней | отказ шага |
| `not_applicable` или `error` уровня ответа вместе с `beh` | отказ шага |
| lock/`content_sha256` не совпали | отказ шага |

### 5.4 Вендоринг

`contracts/criteria-closure/v1/` в devtools: схемы, `min-spec-runner.env`,
`PIN` (upstream SHA), `manifest.json` (sha256). Целостность — локально в CI без
соседа; дрейф — по ref из `PIN`: в CI отсутствие входа — ошибка, локально —
`not-checked`. `check-contract-drift.sh` как есть не используется.

### 8.2 Отрицательные двойники измерения (эталоны)

| двойник | ожидаемо |
|---|---|
| тест читает докстринг, продукт в `call` не исполняет | `unconfirmed: no-product-execution` |
| смешанный: исполняет продукт, проверяет `__doc__` (строка добавлена задачей) | не `change` (кусок докстринга не откатывается), `unconfirmed: not-killed` |
| слабый тест (эталон — BEH-12 i5: проверяет результат заглушки) | `unconfirmed: not-killed` |
| мутант роняет продукт `RuntimeError`/`TypeError`, тест не проверял | не убийство (G2) |
| флейки-тест | нет единогласия K ≥ 2 → не `confirmed` |
| тест заменён на `assert True` | `unconfirmed` (ни база, ни мутанты его не роняют) |
| коммит только документации после `blocked` | `--new-attempt` отказ (тот же `content_sha256`) |

### 8.3 Живая приёмка

Бандл схемы 2 на крошечном предмете, исполнение задач, затем `criteria-close`:

1. Must без теста с токеном → `blocked`, `no-test`;
2. Must-BEH с тестом-читателем докстринга → `blocked`, `no-product-execution`;
3. BEH изменения → `confirmed` по базе; BEH сохранения → `confirmed` мутацией;
4. BEH с пустой трассой / сирота → `error`;
5. `human`-критерий, PR смержен не человеком из снимка → не `accepted`;
6. сужение политики при открытом PR → новая ревизия;
7. честный прогон → PR приёмки, мерж человеком, stamp-PR → `status: accepted`.
