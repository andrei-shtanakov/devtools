# Документы бандла как оракул проверки продукта

Дата: 2026-09-28. Статус: **draft, rev 2** — дизайн согласован с владельцем по
секциям в сессии 2026-09-28 (вопросы 1–7, секции 1–3 с поправками). rev 2
закрывает круг 1 локального ревью (2 blocker, 7 major, 2 minor) и четыре решения
владельца по нему (Р1–Р4, §8). Пункт плана: `TODO.md` `@id:bundle-docs-as-oracle`
(эпик `eco.dark-factory`).

## 0. Зачем

Одобренные и запиненные по байтам узлы `15-behaviour-spec` и `25-acceptance` —
оракул, зафиксированный ДО кода (§I12, волны `sequential-node-approval`).
Прецедент честного оракула — disputatio D1/D6: инварианты `INV-NN` зафиксированы
до диффа, поэтому вердикт по диффу честен.

Сверху вниз адресуемые ID уже есть и частично проверяются: бриф `G-NN/FR-NN` →
требования `FR/NFR-NN` (+ `Priority`) → `BEH-NN` (`traces`, `checked_by`;
steward GC-BEH-TRACE/COVERAGE/CHECK-PLANNED) → `AC-NN` (`verification`,
`traces`, `scenarios`; `acceptance_guard`) → `DT-NN` (`scenarios`,
`delivers[].sources`; `decomposition_guard`). Ниже декомпозиции цепочка рвётся:

1. мост (`task_bridge.py`) сворачивает BEH в `**Traces to:** [FR-..]`, BEH
   остаётся прозой чек-листа;
2. evidence исполнения ключуется TASK-ID/селектором — критерий не назван;
3. `checked_by: planned → materialized` не продвигает никто;
4. ID не квалифицированы: чужой `BEH-09` удовлетворяет `scenarios.py`;
5. парсеры расходятся: steward — виды `atp|contract|integration|e2e|manual`
   без `[a-z]`, реальные бандлы пишут `kind: unit`; `acceptance_guard`
   понимает только `Must`/`Should`, реальный бандл объявляет `Could`
   (`executable-negative-control…/10-requirements.md` FR-12).

Живой прогон волн 22.09 (`docs/evidence/2026-09-22-waves-live-run.md`) показал
цену: критерий, проверяемый чтением исходника, не краснеет.

**Цель.** После исполнения задач отдельный акт приёмки отвечает на вопрос «какие
критерии подтверждены чем» на продуктовом SHA; неподтверждённый Must — приёмки
нет.

**Жизненный цикл (Р1).** Раннер документов (`governance/runner.py`, `_STEPS`:
интервью → авторинг → гейт → edge-check → candidate → finalize) одобряет
**документы**; к его finalize кода продукта ещё нет. Мост в задачи — отдельная
команда после `completed`, tasks-спека рождается `draft` и исполняется
spec-runner после одобрения человеком. Закрытие — **третья, отдельная**
команда после исполнения (§3). Жизненный цикл раннера документов не меняется.

**Вне объёма.** Смысловая проверка реализации против текста критерия (edge-check
«тесты и код ← задача») — отдельный этап; эта спека даёт ему адресуемость.
Машинная грамматика `metric` — следующий этап (стенд замеров). Не-Python тесты —
отдельное решение.

## 1. Грамматика и токен

### 1.1 Код воркстрима и схема charter

`00-charter.md` получает frontmatter `schema: 2` и `code: <CODE>`,
`CODE` = `^[A-Z]{2,6}$`; в схеме 2 `code:` обязателен. Мост и шаблоны генерируют
charter схемы 2. Код неизменяем: гейт отвергает правку `code:` в любом PR,
включая `--reopen` charter.

### 1.2 Реестр кодов

`workstreams/codes.toml` репо-владельца бандла — только растёт:

```toml
[ENC]
workstream = "executable-negative-control-under-standard-20260921"
approved = 2026-09-21
```

Гейт реестра (devtools, новый `charter_guard`):

- каждый ключ реестра базы присутствует в голове с тем же `workstream` —
  удаление и переназначение запрещены;
- код charter схемы 2 есть в реестре и указывает на свой воркстрим;
- уникальность нового кода — по всему реестру, не по живым каталогам (иначе код
  закрытого воркстрима достался бы новому вместе с его тестами); историю git не
  берём — CI делает checkout `fetch-depth: 1`;
- два одновременных PR с одним новым кодом ловят парсер TOML (повторный ключ —
  ошибка разбора) и гейт, который гоняется и на push в default ветку.

### 1.3 Квалифицированный ID и токен

Вне бандла ID пишется `<CODE>:<ID>` (`ENC:BEH-03`, `ENC:AC-07`); внутри
документов бандла — коротким. Совпадение —
`(?<![A-Za-z0-9_])ENC:BEH-03(?![A-Za-z0-9_])`: `XENC:BEH-03`, `ENC:BEH-030`,
`ENC:BEH-03a` не совпадают.

### 1.4 Владение токеном (Python)

Токен принадлежит **наиболее вложенному** определению теста, в чьей области он
стоит. Область определения считается по строкам исходника (комментарии в AST не
видны), `ast` даёт границы:

- область функции/метода: от первого декоратора (`decorator_list[0].lineno`,
  иначе `lineno`) до `end_lineno`, **минус** диапазоны вложенных `def`/`class`;
- область класса: его декораторы, заголовок, docstring и тело **вне** диапазонов
  вложенных функций и классов. Токен области класса засчитывается всем его
  тест-методам; токен метода в класс не поднимается и соседям не достаётся;
- шапка модуля и соседние определения — не засчитываются;
- параметризация: токен функции относится ко всем её собранным селекторам;
- один тест может нести несколько токенов, у BEH — несколько тестов.

Токен в не-Python файле или язык тестов репо не Python — бандл
`not-applicable: language` (§3.4), не молчаливый ноль.

### 1.5 Приоритет

Словарь один на все парсеры: `Must | Should | Could | Won't` (steward уже
распознаёт все четыре; devtools `acceptance_guard` сводится к нему, §5).
Приоритет BEH и AC выводится по их `traces` в `FR/NFR`: максимум по
трассируемым пунктам (`Must > Should > Could > Won't`). Пустой или
неразрешимый `traces` — `error` (блокирует). Исход по приоритету — §3.3.

### 1.6 Исполняемость критерия

| критерий | вид | статус закрытия |
|---|---|---|
| BEH | `checked_by` исполняемого вида (`unit`, `integration`, `contract`, `e2e`, `atp`) | test-критерий (§3.2) |
| BEH | `kind: manual` | `human`: Given/When/Then как наблюдаемый знак (Р2) |
| BEH | `status: waived` | `waived`: основание waiver дословно из бандла (Р2) |
| AC | `verification: test` | подтверждён ⇔ подтверждены все его `scenarios`; пустой `scenarios` — `error` |
| AC | `verification: manual \| metric` | `human`: наблюдаемый знак, источник порога |

Выход «сценарий не проверяется тестом» — `--reopen` 15-behaviour-spec со сменой
`kind` на `manual` и повторным одобрением; критерий уходит в человеческий
чек-лист, а не пропадает.

## 2. Исполнение

### 2.1 Мост в задачи (devtools, `task_bridge.py`)

- Для задачи с `scenarios` в DT — строка `**Scenarios:** ENC:BEH-03, ENC:BEH-04`.
  `**Traces to:**` — как есть.
- Строка выдаётся только при запиненной версии spec-runner ≥ минимальной из
  `contracts/criteria-closure/v1/min-spec-runner.env`; иначе закрытие даёт
  `not-applicable: spec-runner-version` (§3.4). Молчаливое игнорирование строки
  старым spec-runner = «зелёный без оракула».
- Пункты чек-листа исполнителю: токен внутри определения теста (§1.4) и
  negative-control патч на каждый test-BEH задачи (§2.2). Это **подсказка**:
  правило держат гейт задачи и закрытие, пункт чек-листа проверкой не считается.

### 2.2 Negative control на каждый test-BEH (Р4)

Доказательство способности упасть — только negative-control патч, заново
исполняемый при закрытии на продуктовом SHA (§3.2). Красный чекпоинт TDD
остаётся практикой исполнения, но доказательством для оракула не служит.

Грамматика DT (devtools `decomposition_guard`, контракт DT → v3): у задачи
любого типа (`implement` и `verify`) допускается список
`negative_controls: [{scenario: BEH-03, selector: <sel>}]` **без** `tdd_waiver`;
действующая пара `tdd_waiver` ⇔ `negative_control` v2 сохраняется. Патч —
`spec/negative-controls/<ws-id>/<CODE>-<BEH>.patch`, путь выводит мост (DT не
знает номер задачи). Каждый test-BEH из `scenarios` задачи обязан быть покрыт
записью `negative_controls` этой или другой задачи бандла — проверка
`decomposition_guard`.

### 2.3 spec-runner во время исполнения (заявка, §5)

- `scenarios.py` ищет квалифицированный токен по §1.3–1.4.
- Гейт задачи отказывает, если объявленный BEH не несёт ни один тест группы или
  для него нет файла патча на коммите задачи; патч обязан применяться к коммиту
  задачи и ронять селекторы с токеном (та же проверка, что при закрытии, — ранний
  сигнал исполнителю, не доказательство для оракула).

## 3. Закрытие — отдельная команда после исполнения (Р1)

### 3.1 Команда и состояние

`make criteria-close ARGS='--run <id прогона бандла> [--product-sha <sha>]'`
(devtools, `governance/criteria_close.py`). Своё состояние
`out/criteria-close/<id>/state.json` со ссылкой на прогон бандла; resume по
тому же id. Шаги:

1. **Вход.** Из состояния прогона бандла (`completed`) — репо-владелец,
   воркстрим, код, пин одобрения последней волны. Бандл читается из **байтов
   одобренных узлов** (замыкание по пину: charter, requirements, 15, 25, 30),
   не из рабочего дерева. `--product-sha` — явно, иначе голова default-ветки на
   момент вызова, записанная в состояние и дальше неизменная.
2. **Ожидаемое множество.** devtools сам разбирает пиненый бандл (свои guards) и
   выводит полное множество `CODE:ID` критериев с их видом (§1.6) и приоритетом
   (§1.5).
3. **Вычисление** — `spec-runner verify --criteria` (§3.2) с запросом §4.
4. **Сверка ответа** (§4.3). Любое расхождение — `unknown`, отказ шага.
5. **Исход** (§3.3): стоп или приёмочный PR.
6. **Подпись** (§3.5) — если есть `human`/`waived`.

### 3.2 Что делает `verify --criteria` на продуктовом SHA

В отдельном worktree на продуктовом SHA (не рабочее дерево):

1. **Сбор.** Полная коллекция тестов (`pytest --collect-only`, весь набор репо,
   без фильтров) — авторитетное множество селекторов; node ID нормализуются
   (путь относительно корня, `::` квалификация, параметры). Каждый собранный
   селектор отображается на определение в исходнике (файл + qualname) и получает
   токены по §1.4. Пустая коллекция или ошибка сбора — `error` на весь ответ.
2. **Прогон без патча.** Все селекторы с токенами test-BEH исполняются явным
   списком node ID. Требуется `passed` у каждого; `skipped`, `xfailed`,
   `xpassed`, не исполненный (deselected/отсутствующий в отчёте) — не
   `confirmed`.
3. **Прогон с патчем.** Для каждого test-BEH: `git apply --check` патча к
   продуктовому SHA, применение, прогон тех же селекторов BEH. Требуется хотя бы
   один `failed` среди них; все зелёные — патч не доказывает падения. Патч не
   применяется — `control-stale`. Откат патча после прогона.
4. Результат по BEH:

| статус | когда |
|---|---|
| `confirmed` | есть ≥1 селектор с токеном; все `passed` без патча; ≥1 `failed` с патчем |
| `unconfirmed` | причина: `no-test` · `not-passed` (с исходом каждого селектора) · `no-control` · `control-stale` · `control-not-failing` |
| `error` | `traces` пуст/не разрешается; коллекция пуста/упала |
| `human` / `waived` | по §1.6 |

Исторические красные/зелёные evidence задач закрытием не принимаются: только
прогоны этого вызова на продуктовом SHA.

### 3.3 Исход по приоритету

| приоритет | `unconfirmed` | `error` |
|---|---|---|
| Must | **стоп** | стоп |
| Should | строка отчёта | стоп |
| Could | строка отчёта | стоп |
| Won't | вне закрытия, перечисляется в отчёте | стоп |

Стоп = приёмочный PR не открывается; отчёт с поимённым списком `CODE:ID` и
причин — в `out/criteria-close/<id>/report.md` и в комментарий PR tasks-спеки.
Выход — доработка (новые задачи, повторный вызов) или `--reopen` бандла.
**Флага обхода у команды нет и быть не должно** (`--skip-criteria` и аналоги
запрещены спекой) — он пробил бы оракул изнутри.

### 3.4 Не применимо

Бандл целиком получает `not-applicable` с причиной `schema-1` · `language` ·
`spec-runner-version`: приёмочного PR нет, отчёт говорит почему. В шапке любого
отчёта закрытия — счётчик «оракул не применим: N (схема 1: …, язык: …,
spec-runner: …)».

### 3.5 Приёмочный PR и подпись

Если стопа нет — PR в репо-владельце с файлом
`workstreams/<ws>/spec/90-acceptance-closure.md`: шапка «подтверждено N из M
test-критериев (Must a/b, Should c/d, Could e/f); ждут человека K», таблица по
критериям, человеческий чек-лист (`human` — наблюдаемый знак; `waived` —
основание), пин бандла, продуктовый SHA, sha256 отчёта `verify`.

- Есть хотя бы один `human`/`waived` — PR **создаётся** с лейблом
  `human-merge-required` (в том же вызове создания, до любой попытки мержа);
  `merge-pr.sh` на нём отказывает. Иначе PR мержит агент по ADR-ECO-011.
- Снимок политики (Р3): при создании PR проверенный снимок
  (`approval_facts.policy_snapshot`: SHA версии `approval-policy` и список
  `AUTHORIZED_APPROVER_ACCOUNTS` из `policy/approvers.env`) сохраняется в
  состоянии закрытия, SHA версии — в тело PR. Смена политики **до мержа** —
  PR `invalidated` (`policy_changed`), команда перевыпускает его с новым
  снимком. **После мержа** подпись судится по сохранённому снимку
  (`approval_facts.authorized_signature(event, snapshot)`) и при resume не
  пересматривается. Переменная окружения того же имени — отказ, как в §I12.
- Засчитывается акт конкретной учётки: полное событие мержа (`mergedBy.login`,
  `mergedAt`, merge SHA) сохраняется в состоянии; логин в сохранённом снимке и
  не `ai-prosto`. Иначе приёмка не состоялась.
- Состояние закрытия не становится `accepted` ни на каком пути (resume,
  повторный вызов, уже смерженный PR), пока проверка подписи не пройдена;
  недоступность факта мержа — ожидание (`awaiting-merge`), не завершение и не
  необратимая инвалидация.

## 4. Контракт `criteria-closure/v1`

Владелец — spec-runner как производитель. Схема запроса и ответа — JSON Schema в
`contracts/criteria-closure/v1/` spec-runner.

### 4.1 Запрос (CLI)

`spec-runner verify --criteria --request <file.json> --json`, запрос:
`protocol: 1`, `owner_repo`, `workstream`, `code`, `bundle_pin` (SHA одобрения
+ пути узлов), `product_sha`, `negative_controls_dir`, `expected` — список
`{id, kind: test|human|waived, priority}` из §3.1 шаг 2.

### 4.2 Ответ и коды выхода

Ответ повторяет `protocol`, `owner_repo`, `workstream`, `code`, `bundle_pin`,
`product_sha` и даёт `criteria: [{id, status, reason?, selectors: [{node_id,
outcome_plain, outcome_patched}]}]`, `not_applicable?`. Коды: `0` — ответ
выдан (статусы внутри); `2` — ошибка запроса/окружения; `3` — сбор тестов
упал. Иные коды — `unknown` у потребителя.

### 4.3 Сверка у потребителя (devtools)

JSON Schema; совпадение всех эхо-полей с запросом; множество `id` ответа
**точно равно** ожидаемому (отсутствующий, лишний, дублированный — `unknown`);
статус допустим для вида критерия; `confirmed` требует непустых `selectors` с
`outcome_plain: passed` у всех и `failed` хотя бы у одного `outcome_patched`.
Итоги производителя не принимаются — devtools пересчитывает сам.

### 4.4 Вендоринг

devtools вендорит схему и `min-spec-runner.env` пиненой копией:
`contracts/criteria-closure/v1/PIN` (upstream SHA) + `manifest.json` (sha256
обоих файлов).

- **Целостность копии** — локально, без соседа, в CI devtools: хэши манифеста
  против файлов.
- **Дрейф от апстрима** — отдельная проверка против upstream ref из `PIN`; в CI
  отсутствие любого входа — ошибка; локально без соседнего чекаута —
  `not-checked`, а не «в синхроне». Существующий `check-contract-drift.sh`
  пропускает отсутствующие пары молча — для этого контракта не используется
  как есть (§6).

## 5. Заявки соседям

- **spec-runner** (ADR-ECO-006, основание — эта спека): §1.3–1.4 в
  `scenarios.py`; гейт задачи §2.3; разбор `negative_controls` DT v3;
  `verify --criteria` §3.2; контракт §4 и минимальная версия.
- **steward**: парсер BEH — `kind: unit`, суффикс `[a-z]`; гейт charter
  `schema: 2`/`code:` и реестра (или вендоринг `charter_guard` — на усмотрение
  владельца steward).
- **devtools сам**: `acceptance_guard` — словарь приоритетов `Must|Should|Could|Won't`
  (§1.5); `decomposition_guard` — DT v3 (§2.2).

## 6. Раскатка

1. devtools: charter схемы 2, реестр, `charter_guard` (PR и push); словарь
   приоритетов; DT v3 в `decomposition_guard` и мосте.
2. Заявки spec-runner и steward.
3. devtools: вендоринг контракта с целостностью и дрейфом в CI; `criteria-close`
   под пином минимальной версии — до spec-runner ≥ X команда честно отвечает
   `not-applicable: spec-runner-version`.
4. Живая приёмка (§7.2).

## 7. Тестирование и приёмка

### 7.1 devtools, фикстуры

- Владение токеном: граница (`XENC:`, `-030`, `03a`); класс (токен в docstring
  класса → всем методам); **красный сосед без токена + токен только в зелёном
  методе → токен не у соседа**; вложенная функция; комментарий в теле; шапка
  модуля; параметризация.
- Реестр: удаление, переназначение, дубль ключа, код вне реестра, смена `code:`
  при `--reopen`.
- Приоритет: `Could` из реального FR-12; смешанные трассы → максимум; пустая
  трасса → `error`.
- DT v3: `negative_controls` у `verify` без waiver; test-BEH без контроля —
  отказ guard.
- `criteria-close` на подменённом ответе `verify`: каждый статус; пропущенный,
  лишний, дублированный ID; чужой `product_sha`/`bundle_pin`; `confirmed` без
  `failed` под патчем; пустой вывод, невалидный JSON, код 2/3/иной.
- Подпись: лейбл при создании ⇔ есть `human`/`waived`; `ai-prosto` или логин вне
  снимка — не `accepted`; смена политики до мержа → `invalidated`; смена между
  мержем и resume → подпись по сохранённому снимку; resume уже смерженного PR не
  проскакивает проверку.
- Вендоринг: подменённый байт схемы → целостность красная; отсутствующий сосед в
  CI → ошибка.

### 7.2 Живая приёмка

Бандл схемы 2 на крошечном предмете, исполнение задач, затем `criteria-close`:

1. Must без теста с токеном → стоп, `no-test`;
2. тест с токеном заменён на `assert True` после исполнения → `control-not-failing`, стоп;
3. BEH с пустой трассой → `error`, стоп;
4. `human`-критерий, приёмочный PR смержен не человеком из политики → не
   `accepted`;
5. честный прогон → приёмочный PR с чек-листом, мерж человеком из политики →
   `accepted`.

## 8. Решения владельца

- Вопросы 1–7 (2026-09-28): ядро — механическое закрытие; связь — токен в тесте;
  квалификация — код воркстрима; `manual`/`metric` — человек; Must блокирует,
  Should — отчёт; вычисление — у spec-runner.
- Поправки к секциям 1–3: реестр только растёт, код неизменяем, граница токена,
  владение по AST-диапазону, отказ на пустой трассе, `schema: 2`, счётчик
  «не применим», двойное правило способности упасть, пин минимальной версии,
  чек-лист — подсказка, человеческий мерж проверяется по учётке, запрет флага
  обхода.
- **Р1**: закрытие — отдельная команда после исполнения с приёмочным PR, не шаг
  раннера документов.
- **Р2**: BEH `manual` → `human`, `waived` → `waived`, оба в человеческий чек-лист.
- **Р3**: смена политики — семантика §I12 (D3): до мержа `invalidated`, после —
  по сохранённому снимку.
- **Р4**: доказательство падения — negative-control патч на каждый test-BEH,
  заново на продуктовом SHA; `verify` пересчитывает, историю не принимает.
