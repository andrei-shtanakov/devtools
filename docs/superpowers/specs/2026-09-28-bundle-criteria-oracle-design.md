## 0. Зачем

Одобренные и запиненные по байтам узлы `15-behaviour-spec` и `25-acceptance` —
оракул, зафиксированный ДО кода (§I12, волны `sequential-node-approval`).
Прецедент честного оракула — disputatio D1/D6: инварианты `INV-NN` зафиксированы
до диффа, поэтому вердикт по диффу честен.

Сверху вниз адресуемые ID уже есть и частично проверяются: бриф `G-NN/FR-NN` →
требования `FR/NFR-NN` (+ `Priority`) → `BEH-NN` (`traces`, `checked_by`;
steward GC-BEH-TRACE/COVERAGE/CHECK-PLANNED) → `AC-NN` (`verification`,
`traces`, `scenarios`; `acceptance_guard`) → `DT-NN` (`scenarios`,
`delivers[].sources`; `decomposition_guard`). Ниже декомпозиции цепочка рвётся:

1. мост (`task_bridge.py`) сворачивает BEH в `**Traces to:** [FR-..]`, BEH
   остаётся прозой чек-листа;
2. evidence исполнения ключуется TASK-ID/селектором — критерий не назван;
3. `checked_by: planned → materialized` не продвигает никто;
4. ID не квалифицированы: чужой `BEH-09` удовлетворяет `scenarios.py`;
5. парсеры расходятся: steward — виды `atp|contract|integration|e2e|manual`
   без `[a-z]`, реальные бандлы пишут `kind: unit`; `acceptance_guard`
   понимает только `Must`/`Should`, реальный бандл объявляет `Could`
   (`executable-negative-control…/10-requirements.md` FR-12).

Живой прогон волн 22.09 (`docs/evidence/2026-09-22-waves-live-run.md`) показал
цену: критерий, проверяемый чтением исходника, не краснеет.

**Что из цены 22.09 закрыто, а что нет (rev 8).** Закрыто:

- тест-читатель, не исполняющий продукт (ни в фазе `call`, ни ленивым импортом
  внутри теста), — `unconfirmed`, для Must — стоп (§4.1 G0);
- голый ID где угодно в файле заменён квалифицированным токеном `CODE:BEH-NN`,
  засчитанным только внутри определения теста (§1.3–1.4);
- флейкость, наблюдённая в двух прогонах, — не `traced` (G3);
- сироты — BEH вне всех AC — запрещены (§1.7);
- Must без прослеженного теста блокирует приёмку (§3.3).

**Не закрыто** (граница, §4.1): смешанный читатель (исполняет продукт, но
проверяет текст/`__doc__`/`co_names`) и тест, вызывающий продукт с `assert True`,
получают `traced`. Способность теста упасть и его связь со смыслом BEH — объём
смыслового edge-check следующего этапа. Проблема 22.09 этой спекой решена
**частично**.

**Цель.** После исполнения задач отдельный акт приёмки отвечает на вопрос «какие
критерии прослежены до каких тестов» на продуктовом SHA; Must без зелёного
теста, исполняющего продукт, — приёмки нет.

**Жизненный цикл (Р1).** Раннер документов (`governance/runner.py`, `_STEPS`:
интервью → авторинг → гейт → edge-check → candidate → finalize) одобряет
**документы**; к его finalize кода продукта ещё нет. Мост в задачи — отдельная
команда после `completed`, tasks-спека рождается `draft` и исполняется
spec-runner после одобрения человеком. Закрытие — **третья, отдельная**
команда после исполнения (§3). Жизненный цикл раннера документов не меняется.

**Вне объёма.** Смысловая проверка реализации против текста критерия (edge-check
«тесты и код ← задача») — отдельный этап; эта спека даёт ему адресуемость.
Машинная грамматика `metric` — следующий этап (стенд замеров). Не-Python тесты —
отдельное решение; сегодня это kapelle (Elixir): 2 бандла, 50 BEH — все получат
`not-applicable: language`. Способность теста упасть и его связь со смыслом BEH не
проверяются (§4.1) — это и есть объём смыслового edge-check.

## 1. Грамматика и токен

### 1.1 Код воркстрима и схема charter

`00-charter.md` получает frontmatter `schema: 2`, `code: <CODE>` и
`plan_item: todo://<repo>/<id>`, `CODE` = `^[A-Z]{2,6}$`; в схеме 2 оба поля
обязательны. `plan_item` — пункт `TODO.md` репо-владельца (`@id:<id>`), ради
которого бандл существует; `charter_guard` проверяет, что пункт существует.
Связь «пункт плана ↔ воркстрим» — данные charter, а не тег на пункте TODO:
забыть поставить тег нельзя, charter без `plan_item` не проходит гейт. Мост и шаблоны генерируют
charter схемы 2. Код неизменяем: гейт отвергает правку `code:` в любом PR,
включая `--reopen` charter.

### 1.2 Реестр кодов — сами charter'ы схемы 2 (rev 10)

Отдельного файла-реестра нет (решение владельца 2026-09-29 после ревью
реализации: `workstreams/codes.toml` не доезжал до default-ветки — candidate-PR
переносит только узлы, и прогон с кодом падал на второй волне). Цель прежнего
реестра — код закрытого воркстрима не переиспользуется — держат данные, которые
и так попадают в base вместе с одобрением:

- **Надгробие.** Charter схемы 2 нельзя удалить или перенести: переименование
  или перенос каталога воркстрима — то же удаление, гейт отказывает так же.
  Каталог закрытого воркстрима может остаться с одним charter'ом.
- **Уникальность** кода — среди всех charter'ов схемы 2 на голове.
- **Профилактика одновременных W1.** Раннер до штампа charter'а сверяет код с
  charter'ами на живой верхушке default-ветки и в открытых candidate-PR W1
  других воркстримов; занят — стоп до штампа. Факт недоступен — стоп
  (fail-closed), не пропуск.
- **Правило разрешения оставшегося окна.** Если на default всё же два charter'а
  с одним кодом, нарушитель — тот, что влит позже по first-parent истории
  default-ветки (не влитый — всегда нарушитель). Воркстрим нарушителя
  блокирован гейтом, и **только в этом случае** разрешена смена кода через
  `--reopen` charter: гейт пропускает её, лишь предъявив коллизию с более ранним
  charter'ом в base. Это единственное исключение из неизменяемости кода (§1.1).

Гейт (devtools `charter_guard`, на PR и на push в default): грамматика §1.1,
уникальность и порядок влития по `git rev-list --first-parent` (CI делает
checkout с полной историей), запрет удаления/переноса против base, смена кода
только нарушителем. Битый frontmatter charter'а — находка, а не «схема 1».

### 1.3 Квалифицированный ID и токен

Вне бандла ID пишется `<CODE>:<ID>` (`ENC:BEH-03`, `ENC:AC-07`); внутри
документов бандла — коротким. Совпадение —
`(?<![A-Za-z0-9_])ENC:BEH-03(?![A-Za-z0-9_])`: `XENC:BEH-03`, `ENC:BEH-030`,
`ENC:BEH-03a` не совпадают.

### 1.4 Владение токеном (Python)

Токен принадлежит **наиболее вложенному** определению теста, в чьей области он
стоит. Область определения считается по строкам исходника (комментарии в AST не
видны), `ast` даёт границы:

- область функции/метода: от первого декоратора (`decorator_list[0].lineno`,
  иначе `lineno`) до `end_lineno`, **минус** диапазоны вложенных `def`/`class`;
- область класса: его декораторы, заголовок, docstring и тело **вне** диапазонов
  вложенных функций и классов. Токен области класса засчитывается всем его
  тест-методам, **включая методы вложенных классов** (метод получает области
  всех объемлющих классов); токен метода в класс не поднимается и соседям не
  достаётся;
- индекс определений — модуль и классы; составные операторы (`if`, `try`,
  `with`, циклы, `match`) просматриваются насквозь, их собственные строки на
  уровне модуля ничем не владеют; `def`, вложенный в функцию, определением не
  является; повторное имя — выживает последнее в порядке исходника вместе с
  потомками (как в Python);
- строки режутся только по `\r\n|\r|\n` (нумерация `ast`), ведущий BOM
  срезается;
- что из индекса — тест, решает сбор pytest, а не имя (паритет со spec-runner —
  devtools#491, D.1–D.7);
- шапка модуля и соседние определения — не засчитываются;
- параметризация: токен функции относится ко всем её собранным селекторам;
- один тест может нести несколько токенов, у BEH — несколько тестов.

Паритет с парсером spec-runner закреплён общими фикстурами
`contracts/criteria-closure/v1/fixtures/ownership/` (вендорены под своим `PIN`,
devtools#491): оба парсера обязаны дать их `owned`.

Токен в не-Python файле или язык тестов репо не Python — бандл
`not-applicable: language` (§3.6), не молчаливый ноль.

### 1.5 Приоритет

Словарь один на все парсеры: `Must | Should | Could | Won't` (steward уже
распознаёт все четыре; devtools `acceptance_guard` сводится к нему, §5).
Приоритет BEH и AC выводится по их `traces` в `FR/NFR`: максимум по
трассируемым пунктам (`Must > Should > Could > Won't`). Пустой или
неразрешимый `traces` — `error` (блокирует). Исход по приоритету — §3.3.

### 1.6 Исполняемость критерия

| критерий | вид | статус закрытия |
|---|---|---|
| BEH | `checked_by` исполняемого вида (`unit`, `integration`, `contract`, `e2e`, `atp`) | test-критерий: `traced`/`unconfirmed` (§4) |
| BEH | `kind: manual` | `human`: Given/When/Then как наблюдаемый знак (Р2) |
| BEH | `status: waived` | `waived`: основание waiver дословно из бандла (Р2) |
| AC | `verification: test` | выводится devtools из статусов его `scenarios` (§5.2); пустой `scenarios` — `error` |
| AC | `verification: manual \| metric` | `human`: наблюдаемый знак, источник порога |

Выход «сценарий не проверяется тестом» — `--reopen` 15-behaviour-spec со сменой
`kind` на `manual` и повторным одобрением; критерий уходит в человеческий
чек-лист, а не пропадает. Указание автору бандла: BEH, чьё поведение — свойство
**текста** продукта (докстринг, формулировка в исходнике), размечается
`kind: manual`, а не тестом; правило уходит в шаблоны узла и в steward (§6), не
только в эту спеку.

### 1.7 Полнота приёмки: нет сирот

Каждый BEH, кроме Won't, входит в `scenarios` хотя бы одного **не-Won't** AC.
Сирота — и BEH вне всех AC, и BEH, на который ссылаются только Won't-AC.
Проверяет `acceptance_guard` при одобрении 15-behaviour-spec, при одобрении
25-acceptance и при любом `--reopen`, меняющем множество BEH или AC (сирота иначе
появилась бы переоткрытием 15 без правки 25). Закрытие перепроверяет то же по
запиненному бандлу и при нарушении даёт `error` уровня ответа — fail-closed, не
полагаясь на предусловие. Замер 2026-09-28: во всех 9 реальных бандлах сирот 0
(236 BEH).

## 2. Исполнение

### 2.1 Мост в задачи (devtools, `task_bridge.py`)

- Для задачи с `scenarios` в DT — строка `**Scenarios:** ENC:BEH-03, ENC:BEH-04`.
  `**Traces to:**` — как есть. Грамматика DT и провод контролей **не меняются**:
  исполнитель доказательство падения не пишет (§4).
- Строка выдаётся только при **доступном оракуле**: контракт вендорен (в
  `contracts/criteria-closure/v1/` есть `PIN` и манифест сходится — отдельного
  флага «выпущено» нет, рассогласоваться нечему) и установленный spec-runner
  (`spec-runner --version` — свойство машины) не ниже `min-spec-runner.env`;
  иначе закрытие даёт
  `not-applicable: spec-runner-version` (§3.6).
- Пункт чек-листа исполнителю (токен внутри определения теста, §1.4) —
  **подсказка**: правило держат гейт задачи и закрытие.

### 2.2 spec-runner во время исполнения (заявка, §6)

`scenarios.py` — квалифицированный токен и владение по §1.3–1.4. Гейт задачи:
объявленный BEH несёт хотя бы один тест группы на коммите задачи. Измерение §4 на
коммите задачи допустимо как ранний сигнал исполнителю; доказательством для
оракула не служит — оракул мерит заново при закрытии.

## 3. Закрытие — контракт A: автомат попыток (Р1)

**Срез 2 (§7.2).** В срезе 1 закрытие — измерение и файл закрытия агентским PR
без ревизий, подписи и штампа (§7.1); автомат ниже — целевое состояние.

### 3.1 Команда, попытки, идентичность

`make criteria-close ARGS='--run <id прогона бандла> [--new-attempt |
--repropose] [--product-sha <sha>]'` (devtools, `governance/criteria_close.py`).
Состояние — `out/criteria-close/<run-id>/`, список **попыток**; у попытки
неизменяемая идентичность `(run_id, attempt, bundle_pin, product_sha)`:

- `bundle_pin` — пин одобрения последней волны прогона бандла (`completed`);
  замыкание узлов (charter, requirements, 15, 25, 30) читается по нему из
  git-объектов, недоступный байт — отказ шага;
- `product_sha` — `--product-sha` или голова default-ветки в момент создания
  попытки; предок живой верхушки default-ветки (`git merge-base --is-ancestor`),
  иначе создание отказывает; после записи не меняется;
- ключ измерения — `(bundle_pin, content_sha256)`, где `content_sha256` — хэш
  содержимого продуктовых корней и тестовых файлов на `product_sha`. На
  измеренном ключе `--new-attempt` **запрещён**: коммит только документации не
  даёт флейки-тесту второго шанса стать зелёным;
- `--new-attempt` — единственный путь к новому содержимому; прежняя незавершённая
  попытка → `superseded`; в `stamping` и после `accepted` — отказ;
- `--repropose` — явная команда для терминального `rejected` по причине вне
  измерения (§3.2); обычный resume закрытие PR человеком не отменяет;
- resume продолжает текущую попытку: первый **валидный** ответ измерения и отчёт
  неизменяемы; невалидный ответ в попытку не пишется — только в журнал отказов
  шага, повтор его перезапрашивает;
- `--reopen` бандла даёт новый прогон бандла и новый пин — закрытие по нему —
  новый `run_id`.

**Эксклюзивность на воркстрим, между машинами.** Держит форджа: создание попытки
и `--repropose` атомарно создают ref `refs/heads/criteria-close/<CODE>` в
репо-владельце (существующий ref — отказ с указанием попытки из его коммита;
измерение не повторяется). Ref снимается переходом попытки в терминальное
состояние. Локально — `fcntl.flock` как оптимизация, не гарантия.

### 3.2 Состояния и переходы

Фазы: `verifying` → `proposal` → `stamping` → терминальный исход (`blocked`,
`not-applicable`, `accepted`, `rejected`, `superseded`). `proposal` хранит
опубликованную ревизию предложения **или** причину ожидания `wait: policy` (тогда
открытого PR ревизии нет). Перевыпуск ревизии измерение не повторяет.
«Терминальный» — не продолжается обычным resume; явные команды (`--repropose`,
`--new-attempt`) — исходящие переходы.

| из | событие | в | действие |
|---|---|---|---|
| — | `not-applicable` решено до запроса (схема 1, версия spec-runner) или ответом (язык) | `not-applicable` | отчёт; ref снимается/не берётся |
| — | создание попытки | `verifying` | ref воркстрима (атомарно), идентичность (write-ahead) |
| `verifying` | ответ невалиден / код 2 | `verifying` | журнал отказа, повтор resume |
| `verifying` | код 3 / `error` уровня ответа (сбор, `foreign-import`, `product-roots-unknown`, сирота §1.7) | `blocked` | продукт на этом содержимом не измеряется |
| `verifying` | исход §3.3 — стоп | `blocked` | отчёт + комментарий в PR задач (номер из записи моста) |
| `verifying` | стопа нет | `proposal` | обработчик политики; при снимке — ревизия r1 (§3.4) до push |
| любая фаза | снимок `FORBIDDEN env`/`source` | та же | отказ команды (проверяется раньше всех прочих правил политики, в т.ч. после мержа) |
| `verifying`/`proposal` | снимок `UNAVAILABLE` | та же | отказ шага, повтор |
| `verifying`/`proposal` (PR не смержен) | снимок `FORBIDDEN absent`/`empty` | `proposal` + `wait: policy` | закрыть открытый PR ревизии |
| `proposal` + `wait: policy` | политика восстановлена (resume) | `proposal` | новая ревизия, без перемера |
| `proposal` | сужение политики до мержа (§3.5) | `proposal` | закрыть PR ревизии; новая ревизия с новым снимком |
| `proposal` | публикация ревизии не завершена (push/создание/лейбл/аттестация) | `proposal` | resume: сверка форджи, усыновление по идентичности, дозавершение |
| `proposal` (опубликована) | test-only: `merge-pr.sh --expect-head <голова ревизии> --expect-base <живая верхушка, write-ahead>` | по коду | 0 → предикат §3.5; 2 → повтор; 3 `BEHIND` → новая ревизия на живой верхушке; 3 иной / 4 → `rejected`; 5 → перечитать факты: голова PR ≠ голове ревизии → `rejected` (`head-moved`); иначе (дрейф базы) → повтор с новой записанной верхушкой |
| `proposal` | PR смержен (кем угодно) | `stamping` / `rejected` / `superseded` | предикат §3.5 |
| `proposal` | PR закрыт без мержа | `rejected` (`closed`) | — |
| `rejected` (причина `closed`, `head-moved`, код 3/4, предикат п.1/3) | `--repropose` | `proposal` | атомарно вернуть ref (занят — отказ); проверить актуальность оракула (§3.5 п.2; иначе `superseded`); новая ревизия, измерение переиспользуется |
| `stamping` | проверка штампа (ниже) → `valid` | `accepted` | снять ref |
| `stamping` | → `invalid` | `stamping` | агентский stamp-PR, возвращающий файл ровно к ожидаемому штампу (блоб ревизии + `status: accepted`); проверка штампа заново |
| `stamping` | → `unavailable` | `stamping` | повтор resume |
| `stamping` | stamp-PR закрыт без мержа / не создан | `stamping` | новый stamp-PR |
| незавершённое (кроме `stamping`) | `--new-attempt` | `superseded` | сперва сверка форджи и усыновление PR незавершённого намерения, затем закрыть его |
| терминальное ≠ `accepted` | его PR ревизии всё же смержен | то же | void-PR, если файл приёмки в default-ветке — ровно блоб этой ревизии (не трогать файл более новой попытки) |

**Проверка штампа** — одна функция на всех путях (агентский мерж, resume,
усыновление чужого мержа): в default-ветке файл приёмки — ровно записанный блоб
ревизии, у которой прошёл предикат §3.5, с единственным отличием
`status: proposed → accepted` и ссылкой на мерж; дифф stamp-PR — только этот
файл. Кто смержил штамп — не важно: акт приёмки уже проверен на PR ревизии.
Исходы: `valid` · `invalid` (иное содержимое) · `unavailable` (факт форджи не
получен).

Внешние действия — write-ahead: намерение записано до вызова; resume сверяет
форджу и усыновляет результат по идентичности (ветка
`criteria-close/<CODE>-<run>-a<attempt>-r<rev>`, голова, хэши), а не по имени.

### 3.3 Исход по статусу и приоритету

Обещание оракула (rev 7, сужение §10): **каждый test-критерий прослежен до
зелёного теста (флейкость в 2 прогонах не наблюдалась), исполняющего продукт в
процессе** (`traced`).
Способность теста упасть и его связь со смыслом BEH оракул **не** утверждает —
это зона смыслового edge-check (§0, вне объёма).

| статус test-BEH | Must | Should / Could |
|---|---|---|
| `traced` | — | — |
| `unconfirmed` (нет теста, нет исполнения продукта в процессе, только подпроцесс, не зелёный, флейки) | **стоп** | строка отчёта |
| `error` (per-BEH `io`/`runner`, ошибка графа) | стоп | стоп |

**Must-AC.** Производный (§5.2) статус AC с приоритетом Must `unconfirmed` или
`error` — тоже стоп, даже если его BEH не Must (Must-AC может ссылаться на
Should-BEH — без этого правила он прошёл бы без стопа; найдено кругом по плану).

Выход из `blocked` — доработка и `--new-attempt` на новом содержимом или
`--reopen` бандла. **Флага обхода нет и быть не должно** (`--skip-criteria` и
аналоги запрещены спекой).

### 3.4 Предложение приёмки и штамп

До push ревизии записывается неизменяемое **предложение**: идентичность попытки,
номер ревизии, default-ветка, байты и sha256 ответа измерения, sha256 блоба
`workstreams/<ws>/spec/90-acceptance-closure.md`, имя ветки, ожидаемая голова,
полный снимок политики (§3.5). Файл приёмки: frontmatter `status: proposed`,
шапка «прослежено T из M test-критериев (Must a/b, Should c/d, Could e/f); ждут
человека K; оракул не применим:
…», таблица по критериям с селекторами, человеческий чек-лист (`human` —
наблюдаемый знак, `waived` — основание), пин бандла, продуктовый SHA, sha256 ответа. В шапке прямо
написано, что `traced` не утверждает способность теста упасть.

PR ревизии создаёт учётка оператора; `ai-prosto` публикует на нём
scope-аттестацию (`review-pr.sh`, prose-only). PR с `human`/`waived`
**создаётся** с лейблом `human-merge-required` в том же вызове
создания.

**Штамп** (оставлен после круга 5: читатели — консоль, дайджесты, зеркала vault,
другие машины — видят только git; предикат зависит от `mergedBy` и свежести
оракула, которые им недоступны). После предиката §3.5 команда открывает агентский
stamp-PR (`status: proposed → accepted` + ссылка на мерж), с той же аттестацией,
и мержит его `merge-pr.sh`. Читатели считают приёмку состоявшейся **только** по
`status: accepted`; `proposed` и `void` — не приёмка.

### 3.5 Предикат перехода в `stamping` и подпись

Одна функция сверки на всех путях (первый проход, resume, усыновление уже
смерженного PR):

1. **Идентичность предмета:** смержена ровно голова текущей ревизии;
   `baseRefName` равен default-ветке предложения; блоб файла приёмки в смерженном
   дереве совпадает с записанным хэшем; дифф PR — только этот файл.
2. **Актуальность оракула** (по фордже): байты узлов замыкания на верхушке
   default-ветки равны байтам `bundle_pin`, и нет открытых PR веток одобрения
   этого воркстрима — обе формы SSOT `contracts/approval-branches/v1/patterns.env`
   (`spec/<ws>-approve-<wave>-<step>-<attempt>` и `-final`); `product_sha` —
   предок верхушки default-ветки.
3. **Акт** (факты форджи):
   - есть `human`/`waived` — `mergedBy.login` в снимке ревизии и
     не `ai-prosto`;
   - только test-критерии — `mergedBy.login` ∈ {`ai-prosto`} ∪ снимок.

Иначе `rejected` (1, 3) или `superseded` (2). `human-merge.sh` сверяет логин с
**текущей** политикой — строже снимка; расхождение возможно только при
расширении политики и безопасно.

Снимок политики (Р3′): при создании ревизии сохраняется **полный** проверенный
снимок — версия `approval-policy`, отпечаток, список учёток (отдельная форма
закрытия; `PolicySnapshot.as_record()` список не пишет и не используется). При
resume до мержа — `policy_snapshot(pinned_sha=None)` и сравнение со снимком.
**Сужение** — `snapshot.accounts ⊄ current.accounts`.

| текущая политика (порядок проверки сверху вниз) | увидено | исход |
|---|---|---|
| `FORBIDDEN env`/`source` | когда угодно | отказ команды |
| сужение | до мержа (PR открыт) | новая ревизия с новым снимком |
| `FORBIDDEN absent`/`empty` | до мержа | `wait: policy` |
| `UNAVAILABLE` | до мержа | отказ шага без перехода |
| любая иная | после мержа | подпись по снимку ревизии |

Расширение или иная смена до мержа — только диагностическое предупреждение при
resume, переходов не меняет. Обещание: «подпись действительна по снимку
ревизии; сужение, замеченное до мержа, требует новой ревизии». Названная
граница: сужение (и недоступность политики), в окне которого до мержа не было ни
одного resume, не поймано.

### 3.6 Не применимо

`not-applicable` с причиной `schema-1` · `language` · `spec-runner-version`. В
шапке любого отчёта — счётчик «оракул не применим: N (схема 1: …, язык: …,
spec-runner: …)».

## 4. Контракт B: измерение прослеживаемости (владелец механизма — spec-runner)

Спека фиксирует, **что** обязан гарантировать ответ `criteria-closure/v1` и что
devtools видит; **как** — механизм spec-runner; предлагаемая реализация —
приложение `2026-09-28-bundle-criteria-oracle-spec-runner-annex.md` (заявка §6).

**Решение (§10, круг 6).** Причинное подтверждение (`confirmed`) **снято**
целиком. Пять заходов показали, что любой синтетический «красный» — патч
исполнителя (круг 4), изменение на диске (круг 5), изменение в памяти (круг 6:
тест читает `f.__code__.co_names`) — тест может обнаружить, читая продукт как
данные, а частичная база может сломаться от самого измерителя (круг 6: откат
вызывает удалённый хелпер). Оракул обещает только то, что проверяется без
синтетического продукта: **прослеживаемость**.

### 4.1 Гарантии `traced`

- **G0 Исполнение продукта в процессе:** селекторы BEH в фазе `call` исполняют
  продуктовый код в процессе pytest. Засчитываются **только строки внутри тел
  функций и методов** продуктовых корней в контексте `call`; модульный уровень и
  тела классов (исполняются при импорте — в том числе ленивом импорте или
  `importlib.reload` внутри теста) не считаются. Нет — `unconfirmed: no-product-execution`. Селектор,
  исполняющий продукт только в дочернем процессе (subprocess, `make`, CLI), —
  `unconfirmed: subprocess-only`, не тихий `traced` (замер 6: у i5 таких 0).
- **G1 Продуктовый SHA и окружение:** измерено на `product_sha` в окружении из
  его lock; импортируемый продукт — из продуктовых корней клона.
- **G3 Полнота и зелёный без наблюдённой флейкости:** множество селекторов BEH — все собранные
  на `product_sha` элементы с его токеном (§1.4), без фильтров; каждый `passed`
  в фазе `call` в **двух** прогонах подряд. Иначе `unconfirmed: not-passed` /
  `nondeterministic`. Формулировка отчёта — «флейкость не наблюдалась в 2
  прогонах», не «стабилен»: флейки-тест с вероятностью падения 0,1 проходит
  оба прогона в 81 % случаев.
- **G6 Без переброса:** одно измерение на ключ `(bundle_pin, content_sha256)`
  (§3.1).

Синтетического продукта нет, поэтому защищённое множество, классификация кадров
и база не нужны и из контракта удалены.

**Граница (вне объёма).** `traced` не утверждает, что тест способен упасть, и не
связывает его со смыслом BEH: тест, вызывающий продукт и проверяющий `assert
True`, — `traced`. Это видно в отчёте (§3.4) и закрывается смысловым edge-check
следующего этапа.

### 4.2 Статусы

| исход | статус |
|---|---|
| G0, G3 выполнены | `traced` |
| нет селекторов с токеном | `unconfirmed: no-test` |
| G0 не выполнен | `unconfirmed: no-product-execution` / `subprocess-only` |
| G3 не выполнен | `unconfirmed: not-passed` / `nondeterministic` |
| сбой чтения/раннера per-BEH | `error: io` / `runner` |

**`verify`-задачи** подчиняются общему правилу и общей таблице §3.3: особого
пути нет (исключение `verify-human` существовало только при причинном
подтверждении, где у `verify`-задач не было цели мутаций; снято в rev 8).

### 4.3 Наблюдаемые поля ответа

По BEH: `status` (`traced` · `unconfirmed` · `error`); `reason` — обязателен при
`unconfirmed`/`error`, отсутствует при `traced`; по каждому селектору — node ID,
определение (файл + qualname), исходы двух прогонов в фазе `call`, число строк
тел функций/методов продуктовых корней, исполненных в `call` в процессе, признак запуска дочернего
процесса. Уровень ответа: `product_roots`, `environment` (sha256 lock, Python,
плагины pytest), `content_sha256`, `not_applicable?`, `error?` (без `beh`), эхо
запроса.

### 4.4 Замеры и круги, на которых стоит решение (2026-09-28, i5/#171)

| замер / круг | правило | итог |
|---|---|---|
| 1 | мутация покрытых функций | половина подтверждений — поломкой общего кода |

## 5. Контракт C: граф критериев и сверка у devtools

### 5.1 Запрос и ответ `criteria-closure/v1`

Владелец схемы — spec-runner. Запрос: `protocol: 1`, `owner_repo`, `workstream`,
`code`, `bundle_pin` (SHA одобрения + пути узлов замыкания), `product_sha`,
`test_criteria: [{id: CODE:BEH-NN, verify_task: bool}]`. Ответ — §4.3. Коды: `0`
— ответ выдан; `2` — ошибка запроса/окружения (повтор); `3` — ошибка уровня
ответа (`blocked`); иные — отказ шага.

### 5.2 Граф и вывод (devtools)

devtools строит типизированный граф из байтов бандла по пину: BEH (вид по §1.6,
приоритет; неизвестный `kind` — `error`), AC (`verification`, непустой
`scenarios` для `test`), рёбра AC → BEH; сироты §1.7 — `error` уровня ответа.
`waived` у BEH приоритетнее исполняемого `kind`. Статусы AC — **только** здесь:

| AC | статусы его BEH | статус AC |
|---|---|---|
| `test` | все `traced` | `traced` |
| `test` | есть `error` | `error` |
| `test` | есть `unconfirmed` (без `error`) | `unconfirmed` |
| `test` | есть `human`/`waived`, остальные `traced` | `human` (в чек-лист со ссылкой на BEH) |
| `manual`/`metric` | — | `human` |

### 5.3 Сверка ответа

JSON Schema; эхо совпадает с запросом; множество `beh[].id` **точно** равно
`test_criteria`. devtools пересчитывает сам по своим байтам на `product_sha`:

- **полнота:** множество определений с токеном BEH (§1.4, парсер devtools) равно
  множеству определений селекторов ответа;
- **`traced`:** каждый селектор `call: passed` в обоих прогонах (devtools считает
  по записям прогонов); число исполненных строк тел функций продукта > 0
  (devtools сверяет, что строки ответа лежат в телах функций, по своему AST); признака
  «только дочерний процесс» нет;
- **окружение:** sha256 lock из ответа равен sha256 lock на `product_sha`;
  `content_sha256` равен пересчитанному devtools.

Итоги производителя и статусы AC от производителя не принимаются.

| отрицательный ответ | исход |
|---|---|
| пустой stdout / не JSON / не по схеме / код иной | отказ шага |
| чужой `product_sha`/`bundle_pin`/`code` | отказ шага |
| пропущен/лишний/дубль BEH; неполное множество определений | отказ шага |
| нет `product_roots`, `environment` или `content_sha256` | отказ шага |
| `traced` с не-`passed`, одним прогоном, нулём исполненных строк или признаком только-подпроцесса | отказ шага |
| `traced` с `reason`; `unconfirmed`/`error` без `reason` | отказ шага |
| селектор `traced` без токена BEH на `product_sha` | отказ шага |
| `not_applicable` или `error` уровня ответа вместе с `beh` | отказ шага |
| lock/`content_sha256` не совпали | отказ шага |

### 5.4 Вендоринг

`contracts/criteria-closure/v1/` в devtools: схемы, `min-spec-runner.env`
(только версия),
`PIN` (upstream SHA), `manifest.json` (sha256). Целостность — локально в CI без
соседа; дрейф — по ref из `PIN`: в CI отсутствие входа — ошибка, локально —

   `check-plan-fields.py` (сенсор уровня воркспейса, не в CI) может показывать
   то же правило по флоту только как **предупреждение**; спека не называет его
   блокирующим.

**Приёмка среза 1** — не «код devtools влит», а живой прогон на spec-runner ≥ X
