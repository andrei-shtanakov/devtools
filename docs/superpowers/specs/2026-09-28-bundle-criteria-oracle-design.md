## 0. Зачем

Одобренные и запиненные по байтам узлы `15-behaviour-spec` и `25-acceptance` —
оракул, зафиксированный ДО кода (§I12, волны `sequential-node-approval`).
Прецедент честного оракула — disputatio D1/D6: инварианты `INV-NN` зафиксированы
до диффа, поэтому вердикт по диффу честен.

Сверху вниз адресуемые ID уже есть и частично проверяются: бриф `G-NN/FR-NN` →
требования `FR/NFR-NN` (+ `Priority`) → `BEH-NN` (`traces`, `checked_by`;
steward GC-BEH-TRACE/COVERAGE/CHECK-PLANNED) → `AC-NN` (`verification`,
`traces`, `scenarios`; `acceptance_guard`) → `DT-NN` (`scenarios`,
`delivers[].sources`; `decomposition_guard`). Ниже декомпозиции цепочка рвётся:

1. мост (`task_bridge.py`) сворачивает BEH в `**Traces to:** [FR-..]`, BEH
   остаётся прозой чек-листа;
2. evidence исполнения ключуется TASK-ID/селектором — критерий не назван;
3. `checked_by: planned → materialized` не продвигает никто;
4. ID не квалифицированы: чужой `BEH-09` удовлетворяет `scenarios.py`;
5. парсеры расходятся: steward — виды `atp|contract|integration|e2e|manual`
   без `[a-z]`, реальные бандлы пишут `kind: unit`; `acceptance_guard`
   понимает только `Must`/`Should`, реальный бандл объявляет `Could`
   (`executable-negative-control…/10-requirements.md` FR-12).

Живой прогон волн 22.09 (`docs/evidence/2026-09-22-waves-live-run.md`) показал
цену: критерий, проверяемый чтением исходника, не краснеет.

**Цель.** После исполнения задач отдельный акт приёмки отвечает на вопрос «какие
критерии подтверждены чем» на продуктовом SHA; неподтверждённый Must — приёмки
нет.

**Жизненный цикл (Р1).** Раннер документов (`governance/runner.py`, `_STEPS`:
интервью → авторинг → гейт → edge-check → candidate → finalize) одобряет
**документы**; к его finalize кода продукта ещё нет. Мост в задачи — отдельная
команда после `completed`, tasks-спека рождается `draft` и исполняется
spec-runner после одобрения человеком. Закрытие — **третья, отдельная**
команда после исполнения (§3). Жизненный цикл раннера документов не меняется.

**Вне объёма.** Смысловая проверка реализации против текста критерия (edge-check
«тесты и код ← задача») — отдельный этап; эта спека даёт ему адресуемость.
Машинная грамматика `metric` — следующий этап (стенд замеров). Не-Python тесты —
отдельное решение.

## 1. Грамматика и токен

### 1.1 Код воркстрима и схема charter

`00-charter.md` получает frontmatter `schema: 2` и `code: <CODE>`,
`CODE` = `^[A-Z]{2,6}$`; в схеме 2 `code:` обязателен. Мост и шаблоны генерируют
charter схемы 2. Код неизменяем: гейт отвергает правку `code:` в любом PR,
включая `--reopen` charter.

### 1.2 Реестр кодов

`workstreams/codes.toml` репо-владельца бандла — только растёт:

```toml
[ENC]
workstream = "executable-negative-control-under-standard-20260921"
approved = 2026-09-21
```

Гейт реестра (devtools, новый `charter_guard`):

- каждый ключ реестра базы присутствует в голове с тем же `workstream` —
  удаление и переназначение запрещены;
- код charter схемы 2 есть в реестре и указывает на свой воркстрим;
- уникальность нового кода — по всему реестру, не по живым каталогам (иначе код
  закрытого воркстрима достался бы новому вместе с его тестами); историю git не
  берём — CI делает checkout `fetch-depth: 1`;
- два одновременных PR с одним новым кодом ловят парсер TOML (повторный ключ —
  ошибка разбора) и гейт, который гоняется и на push в default ветку.

### 1.3 Квалифицированный ID и токен

Вне бандла ID пишется `<CODE>:<ID>` (`ENC:BEH-03`, `ENC:AC-07`); внутри
документов бандла — коротким. Совпадение —
`(?<![A-Za-z0-9_])ENC:BEH-03(?![A-Za-z0-9_])`: `XENC:BEH-03`, `ENC:BEH-030`,
`ENC:BEH-03a` не совпадают.

### 1.4 Владение токеном (Python)

Токен принадлежит **наиболее вложенному** определению теста, в чьей области он
стоит. Область определения считается по строкам исходника (комментарии в AST не
видны), `ast` даёт границы:

- область функции/метода: от первого декоратора (`decorator_list[0].lineno`,
  иначе `lineno`) до `end_lineno`, **минус** диапазоны вложенных `def`/`class`;
- область класса: его декораторы, заголовок, docstring и тело **вне** диапазонов
  вложенных функций и классов. Токен области класса засчитывается всем его
  тест-методам; токен метода в класс не поднимается и соседям не достаётся;
- шапка модуля и соседние определения — не засчитываются;
- параметризация: токен функции относится ко всем её собранным селекторам;
- один тест может нести несколько токенов, у BEH — несколько тестов.

Токен в не-Python файле или язык тестов репо не Python — бандл
`not-applicable: language` (§3.6), не молчаливый ноль.

### 1.5 Приоритет

Словарь один на все парсеры: `Must | Should | Could | Won't` (steward уже
распознаёт все четыре; devtools `acceptance_guard` сводится к нему, §5).
Приоритет BEH и AC выводится по их `traces` в `FR/NFR`: максимум по
трассируемым пунктам (`Must > Should > Could > Won't`). Пустой или
неразрешимый `traces` — `error` (блокирует). Исход по приоритету — §3.3.

### 1.6 Исполняемость критерия

| критерий | вид | статус закрытия |
|---|---|---|
| BEH | `checked_by` исполняемого вида (`unit`, `integration`, `contract`, `e2e`, `atp`) | test-критерий (§4) |
| BEH | `kind: manual` | `human`: Given/When/Then как наблюдаемый знак (Р2) |
| BEH | `status: waived` | `waived`: основание waiver дословно из бандла (Р2) |
| AC | `verification: test` | выводится devtools из статусов его `scenarios` (§5.2); пустой `scenarios` — `error` |
| AC | `verification: manual \| metric` | `human`: наблюдаемый знак, источник порога |

Выход «сценарий не проверяется тестом» — `--reopen` 15-behaviour-spec со сменой
`kind` на `manual` и повторным одобрением; критерий уходит в человеческий
чек-лист, а не пропадает.

## 2. Исполнение

### 2.1 Мост в задачи (devtools, `task_bridge.py`)

- Для задачи с `scenarios` в DT — строка `**Scenarios:** ENC:BEH-03, ENC:BEH-04`.
  `**Traces to:**` — как есть.
- Для каждого контроля задачи — отдельная строка
  `**Negative-control:** ENC:BEH-03 :: <patch-path> :: <selector>` (формат
  провода DT→tasks v3, §2.2). Строки повторяемы; разбор spec-runner копит их
  списком, а не перезаписывает (сегодня `task.py` хранит один контроль и
  повтор заменяет предыдущий — это меняется заявкой §5).
- Обе строки выдаются только при запиненной версии spec-runner ≥ минимальной из
  `contracts/criteria-closure/v1/min-spec-runner.env`; иначе закрытие даёт
  `not-applicable: spec-runner-version` (§3.6). Молчаливое игнорирование строки
  старым spec-runner = «зелёный без оракула».
- Пункты чек-листа исполнителю (токен внутри определения теста, патч в продуктовых
  корнях) — **подсказка**: правило держат гейт задачи и закрытие.

### 2.2 Negative control на каждый test-BEH (Р4) — DT v3

Доказательство способности упасть — только negative-control патч, заново
исполняемый при закрытии на продуктовом SHA (контракт B, §4). Красный чекпоинт
TDD — практика исполнения, не доказательство для оракула.

Грамматика DT (devtools `decomposition_guard`, DT → v3): у задачи любого типа
(`implement`, `verify`) — список `negative_controls: [{scenario: BEH-03,
selector: <sel>}]` **без** `tdd_waiver`; пара v2 `tdd_waiver` ⇔
`negative_control` сохраняется и сосуществует. Правила guard:

- каждый test-BEH (§1.6) из `scenarios` бандла покрыт ровно одной записью;
- запись стоит в задаче, в чьих `scenarios` есть этот BEH — владелец патча
  однозначен, чужой задаче контроль не поручается (снимает зависимость гейта
  задачи от будущей задачи в DAG);
- `selector` — node ID или функция; он обязан принадлежать множеству
  селекторов BEH при закрытии (§4, B2), но множество не ограничивает.

Путь патча — `spec/negative-controls/<ws-id>/<CODE>-<BEH>.patch` в
репо-владельце, выводит мост; патч коммитится задачей-владельцем.

### 2.3 spec-runner во время исполнения (заявка, §6)

- `scenarios.py` — квалифицированный токен и владение по §1.3–1.4.
- Гейт задачи для не-waived `implement`/`verify` (отдельная проводка, не через
  предикат `waiver_applied`): объявленный BEH несёт хотя бы один тест группы;
  файл патча есть на коммите задачи; патч проходит правило путей (§4, B1) и по
  измерению B роняет селекторы BEH на коммите задачи. Это ранний сигнал
  исполнителю, доказательством для оракула не служит — оракул мерит заново при
  закрытии.

## 3. Закрытие — контракт A: автомат попыток (Р1)

### 3.1 Команда, попытки, идентичность

`make criteria-close ARGS='--run <id прогона бандла> [--new-attempt]
[--product-sha <sha>]'` (devtools, `governance/criteria_close.py`). Состояние —
`out/criteria-close/<run-id>/` со списком **попыток**; у попытки неизменяемая
идентичность `(run_id, attempt, bundle_pin, product_sha)`:

- `bundle_pin` — пин одобрения последней волны прогона бандла (`completed`);
  замыкание узлов (charter, requirements, 15, 25, 30) читается по нему из
  git-объектов, недоступный байт — `unknown`, отказ;
- `product_sha` — `--product-sha` или голова default-ветки в момент **создания
  попытки**; после записи не меняется;
- `--new-attempt` — единственный путь к новому SHA (после доработки): прежняя
  незавершённая попытка → `superseded`; без флага команда продолжает текущую
  (resume) и не пересчитывает её запрос, ответ и отчёт;
- `--reopen` бандла даёт новый прогон бандла и новый пин — закрытие по нему —
  новый `run_id`; попытки старого прогона → `superseded` при первой попытке
  нового прогона того же воркстрима.

Сериализация: эксклюзивная блокировка каталога прогона закрытия (как
резервирование `run_id` в `runner.py`), состояние — CAS по версии записи. На
воркстрим — не больше одной попытки в `proposed`/`awaiting-merge` по всем
прогонам.

### 3.2 Состояния и переходы

| из | событие | в | действие |
|---|---|---|---|
| — | создание попытки | `verifying` | запись идентичности (write-ahead) |
| `verifying` | ответ B+C: есть Must `unconfirmed`/любой `error` | `blocked` | отчёт + комментарий в PR tasks-спеки |
| `verifying` | ответ `not-applicable` | `not-applicable` | отчёт с причиной |
| `verifying` | ответ невалиден (§4.3, C) | `verifying` (`unknown`) | отказ шага, повтор resume |
| `verifying` | стопа нет | `proposing` | запись предложения (§3.4) до push |
| `proposing` | PR создан/усыновлён по идентичности | `awaiting-merge` | сверка PR ↔ предложение |
| `awaiting-merge` | смержен, подпись и идентичность сошлись (§3.5) | `accepted` | запись события мержа |
| `awaiting-merge` | смержено иное содержимое / подпись не прошла | `rejected` | причина; выход — новая попытка |
| `awaiting-merge` | сужение политики, увиденное до мержа (§3.5) | `invalidated` | закрыть PR, связь `superseded_by`; команда перевыпускает новую попытку |
| `awaiting-merge` | PR закрыт без мержа | `abandoned` | — |
| любое незавершённое | `--new-attempt` / новый прогон бандла | `superseded` | закрыть открытый PR с причиной |

`blocked`, `not-applicable`, `accepted`, `rejected`, `invalidated`, `abandoned`,
`superseded` — терминальные; поздний мерж PR терминальной попытки её не
оживляет и принятия не даёт. Внешние действия (push ветки, создание/закрытие PR,
мерж) идут write-ahead: намерение записано до вызова; resume сверяет форджу и
усыновляет результат по идентичности (ветка `criteria-close/<run>-a<attempt>`,
голова, хэши), а не по имени.

### 3.3 Исход по приоритету

| приоритет | `unconfirmed` | `error` |
|---|---|---|
| Must | стоп (`blocked`) | стоп |
| Should | строка отчёта | стоп |
| Could | строка отчёта | стоп |
| Won't | вне закрытия, перечисляется | стоп |

Выход из `blocked` — доработка и `--new-attempt` или `--reopen` бандла.
**Флага обхода нет и быть не должно** (`--skip-criteria` и аналоги запрещены
спекой).

### 3.4 Предложение приёмки

До push записывается неизменяемое **предложение**: идентичность попытки, байты и
sha256 отчёта B, sha256 блоба `workstreams/<ws>/spec/90-acceptance-closure.md`,
имя ветки, ожидаемая голова, полный снимок политики (§3.5). Файл приёмки:
шапка «подтверждено N из M test-критериев (Must a/b, Should c/d, Could e/f);
ждут человека K», таблица по критериям, человеческий чек-лист (`human` —
наблюдаемый знак, `waived` — основание), пин бандла, продуктовый SHA, sha256
отчёта. PR с `human`/`waived` **создаётся** с лейблом `human-merge-required` в
том же вызове создания.

### 3.5 Два терминальных предиката и подпись

`accepted` ставит одна функция сверки на всех путях (первый проход, resume,
усыновление уже смерженного PR):

1. **Идентичность предмета** (оба случая): смержена ровно голова предложения;
   блоб файла приёмки в смерженном дереве совпадает с записанным хэшем; дифф PR —
   только этот файл. Иначе `rejected`.
2. **Акт**:
   - есть `human`/`waived` — мерж человеком: `mergedBy.login` в **снимке
     предложения** и не `ai-prosto`; переменная окружения
     `AUTHORIZED_APPROVER_ACCOUNTS` — отказ, как в §I12;
   - только test-критерии — агентский мерж `merge-pr.sh --expect-head <голова
     предложения> --expect-base <sha>` от `ai-prosto`.

Снимок политики (Р3′): при создании предложения сохраняется **полный**
проверенный снимок — версия `approval-policy`, отпечаток и список учёток
(отдельной формой закрытия: `PolicySnapshot.as_record()` список не пишет и не
используется). Правило смены:

| смена политики относительно снимка | впервые увидена | исход |
|---|---|---|
| сужение: подписант снимка исчез | до мержа (PR открыт) | `invalidated`, перевыпуск |
| расширение/иная | до мержа | предупреждение при каждом resume, не блок |
| сужение | после мержа | подпись по снимку |
| расширение/иная | после мержа | подпись по снимку |

Обещание: «подпись действительна по снимку предложения; сужение, замеченное до
мержа, инвалидирует». Названная граница: сужение, между которым и мержем не было
ни одного resume, не поймано.

### 3.6 Не применимо

`not-applicable` с причиной `schema-1` · `language` · `spec-runner-version`
(§3.2, терминально). В шапке любого отчёта — счётчик «оракул не применим: N
(схема 1: …, язык: …, spec-runner: …)».

## 4. Контракт B: измерение per-BEH на продуктовом SHA

Исполняет `spec-runner verify --criteria` (заявка §6); devtools сверяет ответ
(контракт C).

**B0. Окружение.** Свежий клон репо-владельца на `product_sha`; `uv sync
--frozen` из этого клона. Общий кэш uv — **намеренно**: `--frozen` фиксирует
lock, кэш лишь ускоряет, гарантия не слабеет. `PYTEST_ADDOPTS` и прочие
`PYTEST_*` из окружения вызова очищаются; конфигурация pytest самого репо
(`pyproject`/`pytest.ini`/`tox.ini`/`setup.cfg`) — часть продукта и
применяется как есть. Происхождение продукта проверяется: каждый пакет из
продуктовых корней (B1) импортируется из клона (путь модуля внутри клона), иначе
`error: foreign-import`. Отпечаток окружения (lock-хэш, версия Python, список
плагинов pytest) — в ответ и эхом в сверку.

**B1. Продуктовые корни и правило путей патча.** Корни — исходные каталоги
пакетов верхнего уровня дистрибутива проекта, определённые сборкой колеса на
`product_sha` (backend-агностично; не удалось — `error: product-roots-unknown`).
Патч вправе менять только файлы внутри корней, кроме: `test_*.py`, `*_test.py`,
`conftest.py` и модулей, объявленных точками входа `pytest11` дистрибутива. Всё
остальное (включая `pytest.ini`, `tox.ini`, `setup.cfg`, `pyproject.toml`,
`sitecustomize.py`, `*.pth`, тесты рядом с кодом вне корней) — отказ до
применения, `unconfirmed: control-out-of-roots`. Список — разрешающий, не
запрещающий.

**B2. Сбор.** `pytest --collect-only` всего набора в профиле B0, без фильтров
от закрытия. Пустая коллекция/ошибка — `error: collection`. Каждый селектор
отображается на определение (файл + qualname) и получает токены по §1.4;
множество селекторов BEH — все собранные node ID с его токеном.

**B3. Прогон без патча.** Каждый node ID множества — отдельным прогоном на
свежем дереве. Требуется фаза `call` = `passed` у каждого; `skipped`,
`xfailed`, `xpassed`, отсутствие в отчёте — `unconfirmed: not-passed` с исходом
по каждому.

**B4. Прогон с патчем.** `git apply --check`, затем применение к свежему дереву;
не применился — `control-stale`; файла нет — `no-control`; ошибка чтения —
`error: io`. Каждый node ID множества — отдельным прогоном. Требуется хотя бы
один `failed` **в фазе `call`**; падение в `setup`/`teardown`, ошибка сбора,
раннера или таймаут доказательством не являются
(`control-not-failing`/`error: runner`). После каждого BEH — сброс tracked,
index и untracked до чистого `product_sha`.

**B5. Ответ по BEH** (только BEH — статусы AC выводит devtools, контракт C):

| статус | условие |
|---|---|
| `confirmed` | множество непусто; B3 все `call: passed`; B4 ≥1 `call: failed` |
| `unconfirmed` | `no-test` · `not-passed` · `no-control` · `control-stale` · `control-out-of-roots` · `control-not-failing` |
| `error` | `collection` · `foreign-import` · `product-roots-unknown` · `io` · `runner` |

Для каждого селектора — исходы B3/B4 с фазой; для контроля — путь и blob-хэш
патча из `product_sha` (патч берётся только из дерева продукта, не с машины).

## 5. Контракт C: граф критериев и сверка у devtools

### 5.1 Запрос и ответ `criteria-closure/v1`

Владелец схемы — spec-runner. Запрос: `protocol: 1`, `owner_repo`, `workstream`,
`code`, `bundle_pin` (SHA одобрения + пути узлов замыкания), `product_sha`,
`test_criteria: [{id: CODE:BEH-NN, selector_hint}]`. Ответ эхом повторяет
запрос и даёт `environment`, `beh: [...]` по B5, `not_applicable?`. Коды:
`0` — ответ выдан; `2` — ошибка запроса/окружения; `3` — сбор упал; иные —
`unknown`.

### 5.2 Граф и вывод (devtools)

devtools строит типизированный граф из байтов бандла по пину (свои guards):
BEH (вид по §1.6, приоритет), AC (`verification`, непустой `scenarios` для
`test`), рёбра AC → BEH. Статусы AC выводятся **только** здесь:

| AC | статусы его BEH | статус AC |
|---|---|---|
| `test` | все `confirmed` | `confirmed` |
| `test` | есть `error` | `error` |
| `test` | есть `unconfirmed` (без `error`) | `unconfirmed` |
| `test` | есть `human`/`waived`, остальные `confirmed` | `human` (в чек-лист со ссылкой на BEH) |
| `manual`/`metric` | — | `human` |

`waived` у BEH имеет приоритет над исполняемым `kind`.

### 5.3 Сверка ответа

JSON Schema; эхо-поля совпадают с запросом; множество `beh[].id` **точно**
равно `test_criteria` (отсутствующий, лишний, дубль — `unknown`); у
`confirmed` непустые селекторы, все B3 `call: passed`, ≥1 B4 `call: failed`;
blob-хэш патча совпадает с блобом в `product_sha`. Итоги производителя и любые
статусы AC от производителя не принимаются.

| отрицательный ответ | исход |
|---|---|
| пустой stdout / не JSON / не по схеме | `unknown`, отказ шага |
| код 2 / 3 / иной | `unknown`, отказ шага |
| чужой `product_sha`/`bundle_pin`/`code` | `unknown` |
| пропущен/лишний/дубль BEH | `unknown` |
| `confirmed` без `call: failed` под патчем | `unknown` (ложь производителя) |
| `confirmed` с `skipped`/`xfailed` без патча | `unknown` |
| blob патча ≠ блоб в `product_sha` | `unknown` |
| `not_applicable` вместе с `beh` | `unknown` |

### 5.4 Вендоринг

`contracts/criteria-closure/v1/` в devtools: схемы запроса/ответа,
`min-spec-runner.env`, `PIN` (upstream SHA), `manifest.json` (sha256).
Целостность — локально в CI devtools без соседа; дрейф — отдельная проверка по
ref из `PIN`: в CI отсутствие входа — ошибка, локально — `not-checked`.
`check-contract-drift.sh` как есть не используется (молча пропускает
отсутствующие пары).

## 8. Тестирование и приёмка

### 8.1 devtools, фикстуры

- Токен (§1.4): граница; класс; красный сосед без токена + токен только в зелёном
  методе; вложенная функция; комментарий; шапка модуля; параметризация.
- Реестр: удаление, переназначение, дубль ключа, код вне реестра, смена `code:`.
- Приоритет: `Could` (реальный FR-12), максимум смешанных трасс, пустая трасса.
- DT v3: контроль у `verify` без waiver; test-BEH без контроля; контроль в чужой
  задаче; два контроля на BEH — отказ guard; провод — несколько строк.
- Автомат A: каждая строка таблицы §3.2; crash между намерением и вызовом для
  push/создания PR/мержа → resume усыновляет по идентичности; два процесса на
  один прогон → второй отказ по блокировке; поздний мерж терминальной попытки не
  даёт `accepted`; `--new-attempt` закрывает открытый PR.
- Подпись: четыре строки таблицы §3.5; `ai-prosto` при `human`; логин вне
  снимка; смерженная голова ≠ предложению; блоб файла приёмки изменён в той же
  ветке; лишний файл в диффе PR.
- Граф C: каждая строка §5.2; каждая строка отрицательной таблицы §5.3; AC
  ссылается на unconfirmed Should-BEH, а производитель подсовывает confirmed
  чужого BEH → вывод по графу, стоп по Must-AC.
- Вендоринг: подменённый байт → целостность красная; нет соседа в CI → ошибка.

### 8.2 Живая приёмка

Бандл схемы 2 на крошечном предмете, исполнение задач, затем `criteria-close`:

1. Must без теста с токеном → `blocked`, `no-test`;
2. тест с токеном заменён на `assert True` после исполнения → `control-not-failing`;
3. контроль правит тест или `conftest.py` → `control-out-of-roots`;
4. BEH с пустой трассой → `error`;
5. `human`-критерий, приёмочный PR смержен не человеком из снимка → не `accepted`;
6. сужение политики при открытом PR, затем resume → `invalidated`;
7. честный прогон → приёмочный PR с чек-листом, мерж человеком → `accepted`.

## 9. Решения владельца

- Вопросы 1–7 (2026-09-28): ядро — механическое закрытие; связь — токен в тесте;
  квалификация — код воркстрима; `manual`/`metric` — человек; Must блокирует,
  Should — отчёт; вычисление — у spec-runner.
- Поправки к секциям 1–3: реестр только растёт, код неизменяем, граница токена,
  владение по AST-диапазону, отказ на пустой трассе, `schema: 2`, счётчик «не
  применим», пин минимальной версии, чек-лист — подсказка, человеческий мерж
  проверяется по учётке, запрет флага обхода.
- **Р1**: закрытие — отдельная команда после исполнения с приёмочным PR.
- **Р2**: BEH `manual` → `human`, `waived` → `waived`.
- **Р3′** (сужение Р3 после круга 2): подпись по снимку предложения; сужение
  политики, замеченное до мержа, инвалидирует; остальное — предупреждение;
  граница названа (§3.5).
- **Р4**: доказательство падения — negative-control патч на каждый test-BEH,
  заново на продуктовом SHA; история не принимается.
- **Круг 2**: пути патча — разрешающий список продуктовых корней (B1); общий кэш
  uv намеренно (B0); статусы AC выводит только devtools (C); провод контролей —
  повторяемые строки, патч пишет задача-владелец BEH.
