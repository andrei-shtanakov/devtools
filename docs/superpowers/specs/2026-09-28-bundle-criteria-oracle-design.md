# Документы бандла как оракул проверки продукта

Дата: 2026-09-28. Статус: **draft, rev 1** — дизайн согласован с владельцем по
секциям в сессии 2026-09-28 (вопросы 1–7, секции 1–3 с поправками). Пункт плана:
`TODO.md` `@id:bundle-docs-as-oracle` (эпик `eco.dark-factory`).

## 0. Зачем

Одобренные и запиненные по байтам узлы `15-behaviour-spec` и `25-acceptance` —
оракул, зафиксированный ДО кода (§I12, волны `sequential-node-approval`).
Прецедент честного оракула — disputatio D1/D6: инварианты `INV-NN` зафиксированы
до диффа, поэтому вердикт по диффу честен.

Сверху вниз цепочка адресуемых ID уже проверяется механически: бриф
`G-NN/FR-NN` → требования `FR/NFR-NN` (+ `Priority`) → `BEH-NN` (`traces`,
`checked_by`; steward GC-BEH-TRACE/COVERAGE/CHECK-PLANNED) → `AC-NN`
(`verification`, `traces`, `scenarios`; `acceptance_guard`) → `DT-NN`
(`scenarios`, `delivers[].sources`; `decomposition_guard`). Ниже декомпозиции
она рвётся:

1. мост (`task_bridge.py`) сворачивает BEH в `**Traces to:** [FR-..]`, BEH
   остаётся прозой чек-листа; машинной строки `**Scenarios:**` нет;
2. evidence прогона (красные чекпоинты, TDD-заявки, negative control) ключуется
   TASK-ID/селектором — критерий не назван нигде;
3. `checked_by: planned → materialized` не продвигает никто;
4. ID не квалифицированы: чужой `BEH-09` удовлетворяет `scenarios.py`;
5. два парсера BEH расходятся (steward: виды `atp|contract|integration|e2e|manual`
   без `[a-z]`; реальные бандлы пишут `kind: unit`).

Живой прогон волн 22.09 (`docs/evidence/2026-09-22-waves-live-run.md`) показал
цену: критерий, проверяемый чтением исходника, не краснеет.

**Цель.** Итог прогона отвечает на вопрос «какие критерии подтверждены чем», а не
«какие задачи зелёные»; неподтверждённый Must-критерий останавливает прогон.

**Вне объёма.** Смысловая проверка реализации против текста критерия (edge-check
«тесты и код ← задача») — отдельный этап; эта спека даёт ему только
адресуемость (квалифицированный ID и текст критерия по ID). Машинная грамматика
`metric` — следующий этап (нужен стенд замеров). Не-Python тесты — отдельное
решение.

## 1. Грамматика и токен

### 1.1 Код воркстрима и схема charter

`00-charter.md` получает frontmatter-поля `schema: 2` и `code: <CODE>`, где
`CODE` — `^[A-Z]{2,6}$`. В схеме 2 `code:` обязателен. Мост и шаблоны
генерируют charter сразу схемы 2. Код неизменяем: гейт отвергает правку `code:`
в любом PR, в том числе при `--reopen` charter (ошибка в коде косметическая,
смена осиротила бы токены в тестах).

### 1.2 Реестр кодов

`workstreams/codes.toml` репо-владельца бандла — реестр, который только растёт:

```toml
[ENC]
workstream = "executable-negative-control-under-standard-20260921"
approved = 2026-09-21
```

Гейт реестра (devtools, `charter_guard`):

- каждый ключ реестра базовой ветки присутствует в реестре головы с тем же
  `workstream` — удаление и переназначение запрещены;
- код charter схемы 2 обязан быть в реестре и указывать на свой воркстрим;
- уникальность нового кода — по всему реестру, а не по живым каталогам
  `workstreams/*/spec/` (иначе код закрытого воркстрима достался бы новому, и его
  старые тесты засчитались бы чужому бандлу). Историю git вместо реестра не
  берём: CI делает checkout `fetch-depth: 1`;
- два одновременных PR с одним новым кодом: дубль ловят парсер TOML (повторный
  ключ — ошибка разбора) и гейт реестра, который гоняется и на push в default
  ветку, не только на PR.

### 1.3 Квалифицированный ID и токен

Вне бандла ID пишется квалифицированно: `<CODE>:<ID>` (`ENC:BEH-03`,
`ENC:AC-07`). Внутри документов бандла ID остаются короткими (код подразумевается
charter'ом).

Совпадение токена — регэксп с границами:
`(?<![A-Za-z0-9_])ENC:BEH-03(?![A-Za-z0-9_])` — `XENC:BEH-03`, `ENC:BEH-030`,
`ENC:BEH-03a` не совпадают (суффикс — другой ID).

### 1.4 Определение теста (Python)

Токен засчитывается тесту, только если стоит внутри его определения: диапазон
строк исходника от первого декоратора узла (`decorator_list[0].lineno`, иначе
`lineno`) до `end_lineno` функции или класса теста по `ast`. Диапазон, а не обход
AST, — комментарии в AST не видны. Шапка модуля и соседние определения не
считаются.

- Токен на классе засчитывается всем его тест-методам.
- Параметризация: токен относится ко всем селекторам функции (`test[a]`,
  `test[b]`). BEH подтверждён, если на финальной голове зелёные ВСЕ селекторы с
  его токеном и способность упасть доказана хотя бы для одного из них (§2.3).
- Один тест может нести несколько токенов; у BEH может быть несколько тестов.
- Токен в файле не на Python или язык тестов репо не Python — бандл получает
  «оракул не применим: язык» (§3.2), а не молчаливый ноль.

### 1.5 Приоритет критерия

Приоритет BEH и AC (`verification: test`) выводится по их `traces` в
`FR/NFR` требований: Must, если хоть один трассируемый пункт Must. Новой разметки
нет. Пустой или неразрешимый `traces` — статус `error` (§3.1), блокирующий: снятая
трасса не должна тихо понижать критерий.

## 2. Исполнение и evidence

### 2.1 Мост в задачи spec-runner (devtools, `task_bridge.py`)

- Для задачи с `scenarios` в DT — машинная строка
  `**Scenarios:** ENC:BEH-03, ENC:BEH-04` (квалифицированные ID).
  `**Traces to:**` — как есть.
- Строка выдаётся только если запиненная версия spec-runner ≥ минимальной из
  `contracts/criteria-closure/v1/min-spec-runner.env` (вендорится, не
  угадывается); иначе отчёт — «оракул не применим: spec-runner < X» (§3.2).
  Молчаливое игнорирование строки старым spec-runner = «зелёный без оракула».
- Пункт чек-листа исполнителю: «каждый тест, проверяющий сценарий, несёт токен
  `ENC:BEH-NN` внутри своего определения». Это **подсказка**, не проверка:
  правило держит гейт (§2.2), пункт чек-листа проверкой не считается.

### 2.2 spec-runner во время исполнения (заявка, §4)

- `scenarios.py` ищет квалифицированный токен по §1.3–1.4, а не голый ID в любом
  месте тестовых файлов группы.
- Гейт задачи отказывает, если объявленный в `**Scenarios:**` BEH не несёт ни
  один тест группы на коммите задачи.
- Evidence хранит отображение «селектор → токены в его определении» — выведенное
  разбором кода, не со слов исполнителя — на двух коммитах: коммите
  доказательства падения и финальной голове (§2.3).

### 2.3 Способность упасть — одно правило для всех задач

Доказательство падения засчитывается BEH, только если получено на селекторе,
который несёт токен этого BEH, — красный чекпоинт TDD или пройденный negative
control. Для `verify_first` (тест поверх готового кода) — только negative control
(контракт DT v2 уже требует его при `tdd_waiver`).

Подмена закрыта двойным снимком: BEH подтверждён, только если на коммите
доказательства падения и на финальной голове его токен несёт один и тот же
селектор. Перенос токена с красного теста A на всегда-зелёный тест B —
`unconfirmed`. Существующий тест группы засчитывается по тому же правилу —
присутствия токена мало.

## 3. Закрытие, блокировка, человеческие критерии

### 3.1 Вычисление — `spec-runner verify --criteria --json`

Бандл читается из байтов одобренных узлов по пину одобрения, не из рабочего
дерева: оракул зафиксирован до кода, правка 15/25 после одобрения закрытию не
видна. Вход — пин бандла и финальная голова прогона. Выход (контракт
`criteria-closure/v1`, §4):

| статус | когда | что несёт |
|---|---|---|
| `confirmed` | §2.3 выполнено, все селекторы с токеном зелёные на голове | селекторы, коммит и вид доказательства (`red-checkpoint`/`negative-control`) |
| `unconfirmed` | иначе | причина: `no-test` · `no-fail-proof` · `selector-moved` · `red-at-head` |
| `error` | `traces` пуст или не разрешается | ID и неразрешённая ссылка |
| `human` | AC `verification: manual\|metric` | наблюдаемый знак, источник порога |

AC `verification: test` подтверждён ⇔ подтверждены все его `scenarios`.
Бандл целиком получает `not-applicable` с причиной: `schema-1` · `language` ·
`spec-runner-version`.

### 3.2 Шаг раннера devtools — перед finalize

1. Вызывает `verify --criteria`. Пустой вывод, неразбираемый JSON или код,
   отличный от договорённых, — отказ шага (`unknown`), не «пустой список
   находок».
2. Must со статусом `unconfirmed` или любой `error` — стоп до finalize;
   комментарий в PR с поимённым списком `CODE:ID` и причин. Выход — доработка
   (resume) или `--reopen` бандла (например, смена `verification` на `manual` с
   повторным одобрением). **Флага обхода стопа у раннера нет и быть не должно**:
   `--skip-criteria` и аналоги запрещены спекой — они пробили бы оракул изнутри.
3. Should `unconfirmed` — строка отчёта, не стоп.
4. Отчёт закрытия — в evidence прогона и в тело finalize-PR. Шапка:
   «подтверждено N из M test-критериев (Must a/b, Should c/d); ждут человека K;
   оракул не применим: P бандлов (схема 1: …, язык: …, spec-runner: …)».
   Счётчик «не применим» виден всегда, а не только построчно.

### 3.3 Человеческие критерии

Мерж finalize сегодня — не человеческий акт: по ADR-ECO-011 finalize-PR мержит
`ai-prosto` при одобряющем ревью, а на прозаическом PR `review-pr.sh`
публикует бесплатную scope-аттестацию (S7: все шесть узлов так). Поэтому:

- бандл с хотя бы одним `human`-критерием — раннер вешает на finalize-PR лейбл
  `human-merge-required`; `merge-pr.sh` на нём отказывает (существующий отказ);
- засчитывается акт **конкретной учётки**: после мержа шаг раннера сверяет
  `mergedBy.login` PR со списком `AUTHORIZED_APPROVER_ACCOUNTS` из
  `policy/approvers.env` репозитория `approval-policy` (по пину заявки;
  `approval_facts.policy_snapshot`; переменная окружения того же имени — отказ,
  как и в §I12) и требует, чтобы это был не `ai-prosto`. Тот же факт «создаёт ли
  этот мерж подпись» уже вычисляет `approval_facts` для §I12 — переиспользуется,
  а не пишется заново. Иначе `human`-критерии не подтверждены и прогон не закрыт;
- чек-лист `human`-критериев (наблюдаемый знак, источник порога) — в теле
  finalize-PR; мерж человеком из списка = подпись под ним.

## 4. Контракты и заявки соседям

- **`criteria-closure/v1`** — JSON-схема вывода `verify --criteria` (§3.1);
  владелец — spec-runner как производитель. devtools вендорит пиненую копию +
  `min-spec-runner.env` и держит обе гарантии: целостность копии и дрейф от
  апстрима (`check-contract-drift.sh`).
- **Заявка spec-runner** (ADR-ECO-006, основание — эта спека): §1.3–1.4 в
  `scenarios.py`, двойной снимок §2.2–2.3, `verify --criteria`, контракт.
- **Заявка steward**: свести парсер BEH с devtools (`kind: unit`, суффикс
  `[a-z]`), гейт charter `schema: 2`/`code:` и реестра (или вендоринг
  `charter_guard` — на усмотрение владельца steward).

## 5. Раскатка

1. devtools: charter схемы 2, реестр кодов, `charter_guard` (PR и push) — без
   зависимостей.
2. Заявки spec-runner и steward.
3. devtools: мост и шаг раннера под пином минимальной версии; до spec-runner ≥ X
   отчёт честно говорит «не применимо».
4. Живая приёмка (§6.2).

## 6. Тестирование и приёмка

### 6.1 devtools, фикстуры

- Таблица форм токена: граница (`XENC:`, `-030`, `03a`), класс, параметризация,
  комментарий в теле, шапка модуля (не засчитан), соседнее определение.
- Реестр: удаление, переназначение, дубль ключа, код charter вне реестра, смена
  `code:` при `--reopen`.
- Шаг раннера на подменённом выводе `verify` для каждого статуса §3.1 и
  `not-applicable`; отказ на пустом выводе/неразбираемом JSON/чужом коде.
- `human`: лейбл вешается ⇔ есть `human`-критерий; `merged_by = ai-prosto` или
  логин вне политики — не подтверждено.
- Мост: `**Scenarios:**` при версии ≥ X и её отсутствие ниже.

### 6.2 Живая приёмка

Бандл схемы 2 на крошечном предмете, пять случаев:

1. Must без теста с токеном → стоп до finalize с `ENC:BEH-NN` и `no-test`;
2. перенос токена на другой селектор после красного → `selector-moved`, стоп;
3. BEH с пустой трассой → `error`, стоп;
4. `human`-критерий, finalize смержен не человеком из политики → прогон не
   закрыт;
5. честный прогон → закрытие, чек-лист `human` в finalize-PR, мерж человеком из
   политики.
