# CLAUDE.md — devtools (дом fleet-агента)

## Роль

`devtools/` — дом **fleet-агента**: единой точки управления polyrepo-workspace
(экосистема ATP). Агент наблюдает состояние флота репозиториев и **действует
только косвенно** — PR-ами в другие репо и `tasks.md`-спеками для spec-runner.

Границы ролей (не дублировать):

- **dispatcher** — read-only дашборд runtime-артефактов; *смотрит*.
- **Robin (robin-runtime)** — отвечает на вопросы по KB; *объясняет*.
- **steward** — гейтит спеки; *проверяет*.
- **fleet-агент (здесь)** — сводит состояние флота и планирует действия; *управляет*.

## Инварианты (конституция)

1. **READ-ONLY к соседним репо.** Никаких прямых записей/коммитов в другие
   репозитории workspace. Изменения уходят только через PR (ветка → PR → ревью).
2. **Сенсоров два — намеренно, не дублирование.** Текущее состояние флота
   (ветки, ahead/behind, dirty, PRs/issues/alerts) — `github-checker snapshot`
   (см. `../github-checker/README.md`, headless-режим). Дельта за период
   («что изменилось с X») — `recent_changes.py` (stdlib-only: пригоден как
   tool для Robin без pydantic-зависимости). Не сливать и не «дедуплицировать».
   repos.sh — интерактивная обёртка для человека, не источник данных для отчётов.
3. **Память — prograph-vault.** Отчёты fleet-check предназначены для
   `../prograph-vault/derived/fleet/` и доставляются PR-ом. Регистрация
   писателя в конституции vault — отдельным ADR (до его принятия PR-ы
   помечать maintainer-у).
4. **Планирование — спеками.** Задачи развития экосистемы агент оформляет как
   `tasks.md`-спеки для spec-runner в репо-владельце изменений, не исполняет сам.
   Шаблон — `templates/tasks-spec-template.md`, процесс — скилл
   `skills/spec-bridge/` (managed-спека, status: draft; approve — человек).
5. Отчёт всегда содержит `host` — чьи локальные клоны он описывает
   (ahead/behind/dirty — состояние конкретной машины).

Диапазон PR (`base`..head) обязан целиком лежать внутри состава кита — посторонний путь отказывает кодом 3. Доставленный `CHANGES_REQUESTED` от `ai-prosto` не гасится синтетическим approve; повтор на той же голове идемпотентен (дедуп по собственному маркеру). Тело называет честное число — N присутствующих из M членов апстрима (M — из `required_kit_default` апстримного `checksum.sh`), легально отсутствующий переходный член (`?path`, двухшаговый ре-вендор состава кита) называется поимённо, а не растворяется в «все совпали»; в тело идёт ТОЛЬКО собственный вычисленный текст (вывод чужого, даже апстримного, кода — только в stderr), страж перед публикацией отказывает при лишней `<!--`-последовательности. Маркер — собственный (`ai-prosto-vendor-attestation`), без подстроки `<!-- codex-terminal-review `. **Аттестуется только PR, состоящий РОВНО из членов кита и его PIN**: PR, везущий что-то ещё (например `.github/codex/review-prompt.md` — репо-данные, намеренно вне инвентаря), получает отказ кодом 3 и остаётся предметом обычного ревью. Коды выхода: 0 — чисто (или `--dry-run`, или дедуп), 2 — конфигурация/аргументы/состояние PR/публикация/неустановленный факт, 3 — сверка не прошла (апстрим не предок доверенной ветки, PR трогает пути вне кита, расхождение с текущим апстримом, красный `checksum.sh`), 4 — голова уехала между сверкой и публикацией |

## Входящие запросы (inbox)

В начале работы проверь входящие: `gh issue list --label inbox --state open`.
Issue с лейблом `inbox` — запрос от соседнего репо, ещё **не** пункт плана.
Принять = завести пункт в `TODO.md` с указанным `slug:`; принял под другим
именем — поправь `slug:` в теле issue.
Отказать = `gh issue close --reason "not planned"`.
Нужна работа в соседнем репо — не редактируй его: заведи там issue
(`slug:` + `from:` + проза). Правило: ADR-ECO-006 — канон в `ecosystem-kb`
(каталог `prograph-vault/` в корне воркспейса),
`authored/decisions/2026-07-28-adr-eco-006-cross-repo-issue-inbox.md`.

Исходящее ожидание — вторая половина того же ритуала: «ждём соседа» существует
**только** как чекбокс `TODO.md` с `@blocked_by:todo://<repo>/<id>` (переходно —
`<repo>#<номер>`); память сессий, заметки и handoff-доки — лишь зеркало. Находка
PF-BLOCKER-STALE по этому репо = «ожидание доставлено — действуй или переставь тег».
Правило (SSOT): `../prograph-vault/authored/rules/cross-repo-waits.md`.

## Git workflow (у репо есть remote)

- Ветка `<type>/<slug>` → push → `gh pr create`. **Прямые коммиты в `master`
  запрещены**, как и локальный мерж ветки в `master` в обход PR.
- **Ревью PR — терминальный прогон от ai-prosto** (дефолт с 2026-08-28).
  Штатный флоу — **один** платный вызов на круг:
  `sh review-pr.sh <repo> <pr> --dry-run --write-verdict <file>`, затем
  `sh review-pr.sh <repo> <pr> --use-verdict <file>` — публикация переносит
  уже полученный вердикт и модель не зовёт. Прежняя пара «`--dry-run`, затем
  без `--dry-run`» больше не штатная: она платит дважды за один круг и
  съедает весь бюджет (ниже) на первом же ревью. `--use-verdict` переносит
  результат только при точных `head` + `fp`. Находки отрабатывать как обычно: валидное — фикс-коммитом,
  невалидное — ответить с обоснованием, не применять вслепую. CI-гейт
  codex-review СНЯТ по флоту (решение владельца 2026-08-31: платный API
  поверх Actions-лимита); лейбл `codex-review` больше не вешать — ревью
  только терминальным прогоном. **Copilot по умолчанию не запрашивать** —
  только по явной просьбе владельца. SSOT: `../prograph-vault/authored/rules/git-workflow.md`.
  **Что проверяет терминальное ревью** (решение владельца 2026-09-15, devtools#223,
  спека `docs/superpowers/specs/2026-09-15-merge-base-live-tip-design.md` §2):
  патч от merge-base — диф `merge-base(base, head)..head` и контекст из merge-base;
  с верхушки базы читаются только `linguist-generated`-декларации. Оно **не
  гарантирует** семантическую корректность результата слияния с базой, ушедшей
  вперёд после ответвления: этот класс — зона CI и тестов, ревью merge-результата
  (D4) не вводится до первого наблюдённого дефекта такого класса.
- **Бюджет платных прогонов: 1 полный review + 1 адресный recheck**
  (решение владельца 2026-09-18). Круг — фактический вызов модели; отпечаток
  и `--use-verdict` не платят и бюджетом не ограничены — потому штатный флоу
  выше и стоит один круг, а не два. Списывается состоявшийся вердикт: отказ
  прибора (кит 2/3) бюджет не тратит. Новый круг открывает
  ТОЛЬКО блокирующая находка (`blocker`/`major` + `confidence: high` +
  evidence) или падение детерминированной проверки. `minor`, `nit`,
  `confidence: medium/low` и редактура нового круга **не открывают**: чинить
  без повторного ревью либо записывать в debt. Это **проверяется механически,
  а не доверием**: классифицировать находки самому не нужно — порог уже
  посчитал `apply-threshold.sh`, и его решение доставлено на PR как состояние
  последнего ревью ai-prosto. Круг после **опубликованного** approve
  `review-pr.sh` не открывает; источник — сам PR, а не локальный журнал:
  журнал списывает круг и там, где вердикт до PR не дошёл (dry-run без
  публикации, «голова уехала»), и на другой машине он пуст. Следствие, которое
  надо знать: новая голова после approve сама по себе круга не даёт — лимит
  на PR, и решение «ревьюить ли новый код ещё раз» принимает владелец.
  Адресный recheck — `review-pr.sh … --targeted` (devtools#260): база дифа не
  `origin/<base>`, а прошлая отревьюированная голова из строгого маркера
  последнего вердикта ai-prosto, то есть ревьюируются только фикс-коммиты.
  **Граница доверия при этом НЕ сужается**: киту уходит
  `--trusted-base origin/<base>`, потому что из своей базы он берёт не только
  диф, но и `.gitattributes`-декларацию `linguist-generated` и курируемый
  контекст — прошлая голова лежит на ветке PR, и объявленный там generated
  прятал бы фикс-коммиты от модели (steward#181). Кит без `--trusted-base` —
  отказ, а не сужение: обвязка определяет поддержку греп-приёмом, как у
  `--fingerprint-only`.
  Отпечаток считается по тому же суженному диапазону, поэтому адресный
  вердикт не унаследуется как полный, а тело вердикта сужение называет:
  полного ревью текущей головы он НЕ заменяет.
  Fail-closed отказы до вызова кита: нет маркера · диапазон пуст по
  СОДЕРЖИМОМУ (головы могут различаться при тождественном дереве —
  `--allow-empty`, коммит с его же revert) · прошлая голова недоступна
  локально или не предок текущей — у последних двух разные сообщения.
  Область ревью классифицируется по тому же суженному диапазону; если в нём
  нет кода, прогон отказывает, а НЕ публикует scope-аттестацию: та утверждала
  бы про весь PR то, что верно про его хвост.
  Барьер бюджета и stop rule в адресном режиме выполняются и в ветке прозы —
  она выходит нулём, и без этого `--targeted` после approve проходил бы без
  `--budget-override`. Но НЕ раньше: выше по течению лежат отпечаток и
  `--use-verdict`, которые модель не зовут и бюджетом не ограничены, и барьер
  перед ними ломал бы штатный двухфазный флоу — вердикт оплачен, а публикация
  упирается в код 6. У обычного прогона место прежнее, после fp-блока: ветка
  прозы срабатывает там, лишь когда прозаический весь PR.
  Канон правила (SSOT): `../prograph-vault/authored/rules/git-workflow.md`,
  раздел «Stop rule»; исполнение — здесь (devtools#256). «Чистый от любых замечаний
  вердикт» условием мержа не является — условие приёмки — зелёные
  обязательные гейты и отсутствие блокирующих находок. Бюджет исчерпан →
  `review-pr.sh` отказывает (fail-closed) **кодом 6** — отдельным от 2
  (конфигурация/прибор) и общим со stop rule: оба барьерных отказа лечатся
  одним и тем же решением владельца, и контур обязан называть такой стоп
  своим именем, а не «прибор не отработал» (devtools#258; под кодом 2 S6
  постил в PR ложную причину). Но и называть одну из двух причин фактом
  контур не вправе: stop rule срабатывает ДО обращения к журналу, то есть
  код 6 приходит и при неисчерпанном бюджете, а `Ops.review` возвращает
  только код. Поэтому комментарий в PR перечисляет обе причины и отсылает
  за точной к stderr ручного прогона. Автоматический контур бюджет **не обходит**:
  `Ops.review`/`review_fresh` флагов не принимают — решение владельца
  принимает человек, вручную. Превышение — с названной причиной
  (`--budget-override '<причина>'`), она уходит в журнал
  и в шапку опубликованного вердикта. Барьер — правило и defense-in-depth,
  не security boundary: прямой вызов кита он не предотвращает, но делает
  перерасход осознанным и видимым. Почему барьером, а не прозой: на
  spec-runner#526 порог не нарушался ни разу — каждый из девяти кругов
  открывала настоящая блокирующая находка, — а прозаическое правило в той же
  сессии агент дважды обошёл разумно звучащим доводом.
- **Проза модельному ревьюеру не отдаётся** (решение владельца 2026-09-18):
  PR, все пути которого классифицированы как проза
  (`contracts/review-scope/v1/prose-paths.env` — SSOT; код сильнее прозы для
  `.github/`, `contracts/`, `eval/`, `fixtures/`, `schemas/`), получает
  **scope-аттестацию** от ai-prosto вместо вердикта: модель не вызывается,
  бюджет не списывается. Аттестация — отдельная governance-сущность с
  собственным маркером `ai-prosto-scope-review`; шаг 3 она закрывает **только
  вместе с независимо зелёными required checks**. Прозаический PR с
  доставленным `CHANGES_REQUESTED` остаётся человеку: аттестация не
  публикуется. Спека: `docs/superpowers/specs/2026-09-18-review-scope-router-design.md`.
  Тот же фильтр применяет и сам кит (срез B): диф непустой, но после фильтра
  области ревьюировать нечего — кит возвращает код **5**, обвязка публикует
  scope-аттестацию через общую `publish_scope_attestation()`, бюджет не
  списывается — модель не звалась. Аттестация честно называет происхождение:
  `kind=prose-only` — ранняя классификация обвязки (кит не вызывался, все
  пути — проза по её контракту); `kind=kit-filtered` — обвязка сама сочла PR
  кодовым, но кит (его слово последнее) после СВОЕГО фильтра не нашёл, что
  ревьюировать; тела и маркеры двух kind не совпадают, дедуп по head узнаёт
  оба вида — второй прогон не кладёт вторую аттестацию, даже другого kind,
  чем первая. Оператору нужен полный прогон вопреки фильтру (ранней
  классификации или кита) — `--include-prose`: обходит и раннюю ветку прозы,
  и фильтр кита (флаг уходит в оба его вызова, отпечаток и полный прогон).
  Repo-конфиг области ревью у кита (читается из base, только расширяет
  список — может добавить пути под платное ревью, не может исключить)
  приезжает вместе с китом отдельной волной ре-вендора (Task 2) — в этом
  репо на момент правки обвязки (devtools) его ещё нет; имя файла и точный
  контракт — за китом, здесь не канон.
- **Мерж — агент по умолчанию** (ADR-ECO-011 «DarkFactory», 2026-08-30): при
  approve от ревью-контура и зелёных обязательных проверках агент мержит сам и
  выполняет хвост чистки. Агентский мерж выполняется **только через
  `sh merge-pr.sh <repo> <pr>`**; любой прямой вызов мержа (`gh pr merge`,
  `gh api -X PUT …/merge`) для агента запрещён — это правило и
  defense-in-depth, не security boundary: намеренный обход прямым API
  обвязка не предотвращает, нарушение правила наблюдаемо в аудите
  `merged_by`; настоящая граница — только защита ветки на стороне форджи
  (devtools#184). Живых путей ровно три, и все
  три ведут сюда: руки оператора, `make accept-pr` и S7 раннера — последние
  два через `Ops.merge`, который вызывает эту же обвязку. Она сверяет логин
  профиля (`~/.config/review` → `ai-prosto`), отказывает на PR, которые обязан
  мержить человек (candidate-ветки §I12, лейбл `human-merge-required`; finalize-PR с ADR-ECO-011 D5 мержит агент по умолчанию),
  мержит с пином проверенной головы (`sha=`) и, если вызывающий передал
  `--expect-base`, с пином базы вердикта. Мерж от основного аккаунта записал бы
  агентский мерж человеческим, обнулив `merged_by` — наблюдаемый различитель
  agent/human (аудит `gh pr list --json mergedBy`), а гварды обошёл бы целиком.
  Request-changes или неприбывшее ревью = `unknown` ⇒
  мерж не выполняется, PR остаётся человеку. Человеческий мерж — opt-in: строка
  `Мерж: человек` в этой секции (здесь НЕ объявлена) либо `merge_policy`
  экосистемного конфига. Объявление прогона (`merge_authority: human`,
  ADR-ECO-008 D5) — третий, самый узкий уровень: прогон может ужесточить политику
  до человеческого мержа, ослабить репо-оверрайд — нет.
  Всегда человеку: authority-root пути (ADR-ECO-004 I2)
  и PR без предъявленного evidence.
- После мержа (кем бы то ни было): `git switch master && git pull --ff-only`, затем удалить
  влитую ветку в **обеих половинах**: локально `git branch -d <ветка>` (после squash-мержа
  `-d` откажется — сверить, что `git diff master <ветка>` пуст, и удалить
  `git branch -D <ветка>`) и на origin
  `git push origin --delete <ветка>`, если GitHub не удалил сам; затем `git fetch --prune`.
- Никогда не делать force-push в общие ветки; не трогать другие репо (см. scope выше).
- Полное правило (SSOT): `../prograph-vault/authored/rules/git-workflow.md`.

## `../_cowork_output/` — dev-only

Координационный dev-scratch воркспейса; у пользователей и клонов проекта его НЕТ.
Shipped/runtime-код никогда не читает и не резолвит пути под ним; кросс-репные
контракты вендорятся пиненой копией внутрь, не ссылкой наружу. Ссылаться на него
могут только dev-тулинг самого воркспейса и документация. Канонические факты живут
в репо-владельце (пример: SSOT agents-catalog — `atp-platform/method/agents-catalog.toml`,
ADR-ECO-003). Полное правило (SSOT): `../prograph-vault/authored/rules/cowork-output.md`.
